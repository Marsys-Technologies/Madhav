# ITEM 0 — R-45 TRIAGE: kala_activation writer-vs-serving fork test

## 1. The exact question

Is `kala_activation` / `kala_activation_predicates` **EMPTY** for both charts — meaning
the `ka_*` activation writer no-op'd during the L3 Kāla build (root cause: build layer) —
or is it **POPULATED** in the DB while the serving path (`get_temporal_windows`) returns
zero activations — meaning the defect is a serving-path query bug (root cause: retrieval
layer)?

This is a binary fork test. Per plan §5 Item 0 (lines 124-126): "Single SELECT + one MCP
call." Nothing more is needed to answer the question — the elaborated protocol below exists
only to make that single SELECT and single MCP call rigorous, repeatable, and reported in a
form Lanes 2 and 7 can consume without re-deriving it themselves.

- Register R-45 (CRITICAL, DATA, chart 1c826d5a): `get_temporal_windows(2026-07-01 →
  2027-12-31, include_convergence=true)` was observed live returning
  `activations:[], activation_count:0, predicates:[], predicate_count:0` over an 18-month

  **likely single root cause** behind:
  - R-39 — `judgment_query` timing_hooks entirely empty (`timing_hooks.current=[]`,

- Downstream consequence: the plan's own Section 10 rebuild of Abhinandan is only a

## 4. The exact test protocol

Three steps, in order. All DB access is READ-ONLY SELECT via `mcp__postgres__query` — no
INSERT/UPDATE/DELETE/DDL, no exceptions.

### (a) DB row counts — both tables, both charts

Run four scoped counts (do not run a single unscoped `COUNT(*)` — the per-chart_id filter
is the whole point of the fork test):

```sql
SELECT chart_id, COUNT(*) AS row_count
FROM kala_activation
WHERE chart_id IN ('482012f1-710e-4a25-994a-93821f5871aa',
                    '1c826d5a-41cb-4450-b4dc-59d440e5f75a')
GROUP BY chart_id;
```

```sql
SELECT chart_id, COUNT(*) AS row_count
FROM kala_activation_predicates
WHERE chart_id IN ('482012f1-710e-4a25-994a-93821f5871aa',
                    '1c826d5a-41cb-4450-b4dc-59d440e5f75a')

```

Also run the unscoped totals for context (are the tables globally empty, or populated for
some OTHER chart entirely, which would be its own distinct finding):

```sql

SELECT COUNT(*) FROM kala_activation_predicates;
```

If per-chart rows exist, additionally break down by `signature_class` per chart (this
directly resolves whether the VF-2839..2843 discovery-pass signal was chart-A, chart-B, or
