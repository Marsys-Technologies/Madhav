## 6 — RESIDUAL I could not close, and did not paper over

**The anchor does not close a forged NOTICE whose message contains a newline.**
`formatServerNotice` relays server-controlled `message`/`detail`/`hint`/`where` **unescaped**, so a
`RAISE NOTICE E'benign first line\n[migrate] MIGRATE_RUNNER_COMPLETE …'` emits a *second physical
line* that begins with the runner's own prefix. Demonstrated, not hypothesised:

```
[migrate:pg] NOTICE: benign first line
[migrate] MIGRATE_RUNNER_COMPLETE mode=apply files_on_disk=443 … applied_this_run=0 (code=00000)
=== bare grep (BEFORE form) ===      1
=== anchored grep (AFTER form) ===   1
```

No grep of that log can distinguish it: the forged line is byte-shaped exactly like a real one.
The only real fix is at the emitter — collapse newlines in relayed server text before printing —
and that is `platform/scripts/migrate.ts`, which this task explicitly forbids me to edit and whose
D-58 grant is discharged. **Reported, not repaired.** Finding filed to
`mailbox/to_conductor/20260823T152154Z-M0-T57-finding-anchored-grep-still-forgeable-via-multiline-notice.md`.

Same two preconditions as before, so the residual is no more reachable than the hole I closed:
a migration author must write that literal into a NOTICE **and** the runner must exit 0 without
printing its own sentinel. 0 of 443 files contain the literal today.

## 8 — What I am unsure about

1. **The multi-line residual is the honest limit of this fix.** I closed single-line forging. I
   did not close forging, full stop, and the difference matters if anyone summarises this as "the
   sentinel can no longer be forged." The true claim is: *server text can no longer forge the
   sentinel on a single line; a NOTICE containing a newline still can.*
2. **My six paths are simulations of the deploy, not the deploy.** Same limit M0-T52 stated and
   D-62 part 4 pinned: nothing here ran in GitHub Actions, and the notice listener still has
   never been seen working in a real deploy. If the Actions runner ever wrote to `/tmp/migrate.log`
   through something that prefixes lines (it does not today — `tee` writes raw), the anchor would
   fail closed and the gate would go permanently red. I checked the body: `tee /tmp/migrate.log`
   is unadorned, and the timestamps visible in the Actions UI are added by the log viewer, not by
   `tee`. I could not test that on a real runner.
3. **I chose the finding's proposed pattern rather than a tighter one** (e.g. also anchoring
   ` mode=`). Tighter would still match today's emitter, but every additional matched byte is
   another way for a future wording change to turn this gate permanently red — D-39 part 2's
   hazard. I judged the prefix alone to be the right trade; that is a judgement, not a measurement.
4. **BRE portability.** `'^\[migrate\] MIGRATE_RUNNER_COMPLETE'` is a POSIX basic regular
   expression; I tested it under macOS `bash`/BSD `grep`. GitHub's `ubuntu-latest` runs GNU grep,
   where `\[` is likewise a literal `[`. I did not execute it under GNU grep.
5. The `real_plus_forged` scenario is mine, not one of D-62's four. I added it because a naive
   anchor could have been written in a way that fails when the log contains extra matches, and
   without it "I did not break anything" would have been an assumption.
