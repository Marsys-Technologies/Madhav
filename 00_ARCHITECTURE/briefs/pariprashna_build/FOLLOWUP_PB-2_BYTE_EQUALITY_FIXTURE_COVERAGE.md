# FOLLOW-UP — the golden byte-equality gate is a false-confidence gate

## §0 — Framing (read this first)

This is **not** "partial fixture coverage" and must never be filed, tracked, or
talked about as such. Partial coverage implies the gate is honest about a
smaller scope than ideal. That is not what is happening here.

**What is actually happening:** `canonical_serialization_golden.test.ts` names
itself, in its own header, "the wave's [integrity] centerpiece" and BRIEF_PB-2
§G-1 requires it run "across the full fixture corpus AND against one real
deployed reading." It does neither. It runs against exactly **one** hand-authored
inline fixture, via a **test-owned reimplementation** of the client reducer
(explicitly not the shipped `s1LiveAdapter.ts`), and has never once been run
against a real reading's persisted DB rows. The gate reports PASS on every run.
Every one of those PASSes is real — the code paths it does exercise genuinely
agree — but the assertion it is standing in for ("the reducer and the writer
cannot silently diverge, across the shapes this system actually produces") is
not what a green run demonstrates. This is structurally identical to two
anti-patterns this same campaign has explicitly named and rejected elsewhere:
a test suite that mocks the one thing it's supposed to prove works, and a
"deploy is green" signal that was never run against real traffic. A gate that
always reports the same color regardless of whether the underlying claim holds
is worse than no gate — it actively launders false confidence, and BRIEF_PB-2's
own anti-gaming charge predicted exactly this failure mode almost verbatim
("find the byte-equality run only against fixtures, never the deployed
reading's DB rows").

## §1 — What was found (full evidence in REPORT_PB-2.md §3, gate item 1)

An independent gate-runner agent (opus, fresh context, dispatched specifically
to try to break this claim) confirmed:

1. The byte-equality assertion runs against **one** fixture (`FIXTURE_EVENTS`,
   ~19 events, inline in the test file) — not the 12-fixture corpus at
   `platform/tests/pariprashna/fixtures/*.json` generated by
   `platform/scripts/replay/build_fixtures.ts`.
2. Its "reducer path" is a from-scratch function
   (`applyToReducerState`/`reducerStateToCanonicalParts`) written inside the
   test file, not the real shipped client reducer
   (`src/components/pariprashna/state/s1LiveAdapter.ts` /
   `state/reducer.ts`). It proves the TEST's idea of the mapping agrees with
   itself, not that the shipped reducer agrees with the shipped writer.
3. Its "writer path" calls the real production mapping functions
   (`route_writer_adapter.ts`) but feeds them the same in-memory fixture
   events directly — never a persisted DB row.
4. No script or test anywhere diffs a real deployed reading's actual
   `message_parts` rows against a replay of that reading's actual SSE stream,
   because **no mechanism persists a real reading's raw event stream at all**
   (`route.ts` accumulates state server-side and writes only the terminal
   `message_parts` via `writeTurn` — the stream itself is emitted to the
   client and discarded, never logged).

## §2 — Why this isn't a quick wiring fix (investigated 2026-07-28)

The obvious-looking fix — "just point the existing byte-equality loop at the
12 fixture files instead of the one inline fixture" — does not work, because
the 12-fixture corpus is in a **different, older event shape** than the real
wire protocol the byte-equality gate needs:

- The 12 fixtures (`tests/pariprashna/fixtures/*.json`) are C-2's PRE-LOCK
  harness format from before S-1 drafted the real merged wire: `final_text`
  instead of `text`, `block_count`/`citation_count` on `turn.commit` instead of
  `assistant_chars`, `kind`/`index` on `block.open` instead of `role`, a
  `citation_anchor.open`/`citation_anchor.set` PAIR for inline citation
  placement that **has no equivalent event in the real protocol at all**, and
  `flag{flag_key: 'honest_gap.*'}` where the real protocol has no
  corresponding flag code.
- There IS an existing adapter for the 12-fixture shape —
  `src/components/pariprashna/state/c2ProtocolAdapter.ts` — but it converts
  into a **third**, UI-renderer-internal shape (`ScheduledEvent`/`WireEvent`
  for driving the React component tree), not into the real, Zod-validated
  `PariprashnaEvent` the canonical store's byte-equality gate is defined
  against. It solves a different, already-closed problem (letting the
  renderer play back C-2's recordings) and cannot be reused here as-is.
- Building a real bridge (12-fixture-shape → real `PariprashnaEvent[]`)
  requires a genuine semantic-mapping decision per event type, not a
  mechanical rename, and at least two event types have no honest 1:1 target
  in the real protocol (`citation_anchor.*`, `honest_gap.*` flags) — meaning
  some of the 12 fixtures may need to be either reinterpreted, dropped, or
  regenerated from scratch in the real shape, which is itself an authored
  decision, not a mapping.

Given that, the two real options are:

- **(A) Write a new, real bridge** (12-fixture-shape → validated
  `PariprashnaEvent[]`), handling the no-equivalent event types explicitly
  (documented decision per type: drop / reinterpret / synthesize), then loop
  the existing byte-equality assertion (reducer path vs. writer path) over
  all 12 converted fixtures instead of the one inline fixture. This does
  **not** by itself fix the "against a real deployed reading" half of the
  claim (§3 below covers that separately) — it only fixes the "full fixture
  corpus" half.
- **(B) Regenerate `build_fixtures.ts`** to emit the real `PariprashnaEvent`
  shape directly (a rewrite of a lane-C-2-owned generator + all 12 golden
  fixture files it produces) — undoing the M-2 lane's own prior, explicit
  decision to leave that generator as a retained historical artifact and
  author one new fixture directly in the real shape instead. That decision
  was made once already, for a reason stated in the test file's own header
  (`canonical_serialization_golden.test.ts` lines 5–13); reopening it is an
  architecture-adjacent call this follow-up deliberately does NOT make
  unilaterally.

Either path is a real, multi-hour engineering task with its own review/
verification cycle — not something to rush inside a wave-close session
without the same rigor (fresh-context Verifier, real re-run against
production) every other fix in this campaign has gotten. That is why this is
being filed rather than attempted live.

## §3 — The second, separate half: "against one real deployed reading"

Even with (A) or (B) done, the gate still would not satisfy BRIEF_PB-2 §G-1's
second clause, because **there is currently no way to capture a real reading's
raw SSE stream to replay it against**. Closing this half requires its own
design decision (a bounded, sampled, non-production-impacting capture
mechanism — e.g. temporarily mirroring N sampled real turns' event streams to
a debug log or table, gated behind a flag, with a retention/privacy story) and
is a genuinely separate piece of work from (A)/(B) above. Do not consider (A)
or (B) alone sufficient to close this follow-up — both halves of the original
§G-1 claim need to be true before this gate can honestly report PASS as
originally specified.

## §4 — Recommended disposition

- Do not attempt a partial/quick version of (A) or (B) under time pressure —
  a half-built bridge that silently drops the two no-equivalent event types
  without a documented decision would itself become a new instance of the
  exact problem this follow-up exists to fix.
- When scheduled: assign a dedicated lane/session with its own fresh-context
  Verifier, exactly as PB-2's own M-1..M-6 lanes were run. Scope it as TWO
  deliverables (fixture-corpus bridge; real-reading stream capture), not one,
  since §3 shows they are independent.
- Until this closes, `canonical_serialization_golden.test.ts` passing should
  **never** be cited, in any future report, as evidence that the reducer and
  writer paths agree in general — only that the one authored fixture's
  specific event sequence round-trips through the two independently-coded
  functions in the test file. Any future session citing this gate as broader
  proof than that is repeating the same overstatement this follow-up exists
  to correct.
