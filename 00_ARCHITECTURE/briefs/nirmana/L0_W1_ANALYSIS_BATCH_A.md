## bg_ephemeris

1. **Pillars.** D-TIME (P6) primarily — this is the raw astronomical substrate every temporal engine ultimately derives from. Still the right instrument: Swiss Ephemeris DE441 daily positions is the correct deterministic base; no computation should route around it.
2. **Dependencies.** Registry declares `depends_on: []`. Writer (`bg_ephemeris.py`, `@register("bg_ephemeris")`) confirms this — it computes positions via `pyswisseph` directly against `brahmagyan.l0_ephemeris` constants (`BUILD_START`/`BUILD_END`/`AYANAMSHA_ID`), with no reads of any other bg_* table. Declared and real dependencies match. Note: the writer has a documented graceful-degradation path — if `pyswisseph` is unavailable it returns `rows_inserted=0` with a "pre-populated" note rather than crashing; this is a deliberate fallback (not a defect) but means a build-log showing `bg_ephemeris` "complete" with 0 rows inserted does not by itself prove the table was rebuilt — it may mean the table was already populated AND may mean swisseph silently wasn't available. Worth a W2 look at whether that ambiguity should be split into two distinct WriterResult notes.
3. **Leverage.** Extensive real consumers confirmed: `platform/src/lib/tools/structured/query_planet_position.ts`, `platform/src/lib/retrieval/registry/layers/L1_ganita/get_positions.ts`, `get_graha_yuddha.ts`, `get_av_transit_gating.ts`, `L0_brahmagyan/query_planet_position.ts`, `query_aspects_at_time.ts`, `query_planet_transit.ts`, `query_retrograde_periods.ts`, and MCP tools `l0_ephemeris.ts`, `kala_timeline.ts`, `muhurta_finder.ts`. Not built-but-unplugged — this is one of the most heavily consumed L0 tables.
4. **Grounding.** Not interpretive — raw astronomical position data (pratyaksa-class if anything ever needed to label it, but as a fact table it doesn't carry a grounding_tier; it's the ground truth other layers ground *against*).
5. **Temporal identity (L3).** Yes — this is the direct feed for multiple L3 (Kāla) writers: confirmed reads of `ephemeris_daily` in `ka_moorti_nirnaya.py`, `ka_vedha_gochara.py`, `services/ka_graha_sancara/{__init__,engine}.py`, `services/ka_kota_chakra/writer.py`, `services/ka_kshetra/stage0_kinematics.py` (the 8.6M-row monster named in plan §5 L3). It answers "where is each graha, on which date, tropically" — the arbiter for disagreements about raw position is inherently this table itself (nothing downstream should compute a competing raw position); L1 chart-fact writers do not read `ephemeris_daily` directly (they go through the panchanga/positions service layer instead), which is consistent with L1 owning the natal-chart-specific computation.
6. **Service.** Real consumer (point 3). `target_floor=825084` (825,075 days × 9 bodies + rounding, per the writer's own docstring "~825,075 rows × 9 bodies") is a very specific number backed by a strong `integrity_check_sql`: exact count, date range bounds, 9-body coverage, per-date completeness (`GROUP BY date HAVING COUNT(*) <> 9`), and longitude-range sanity. `integrity_check_sql` present and unusually thorough.
7. **Cost.** Unmeasured — would need runtime instrumentation. No documented wall-clock/token cost found. (The writer batches 100 days × 9 bodies per round-trip, which is a design choice visible in code, not a measured cost.)
8. **Findings → W2.**
   - NOW candidate: distinguish "0 rows inserted because pre-populated" from "0 rows inserted because swisseph unavailable" in `WriterResult.notes` (currently both produce similar-looking near-zero notes) — cheap, improves O-wave WP-1 receipt/staleness signal quality (D-TIME feed integrity). Cite: CLAUDE.md §N.8 (a signal needs a real detector, not an inferred proxy).
   - NEVER/LATER: no correctness defect found; the table, its consumers, and its integrity check are all solid.

## bg_texts

1. **Pillars.** D-GROUNDING (P3) centrally — this IS the sruti substrate (verse chunks from BPHS, Jaimini Sutram, KP Reader, Tajaka, Phaladeepika, etc.) that every downstream `sruti`-tier citation ultimately resolves to. Also D-SERVICE (retrieval/search consumers). Still the right instrument, and named in plan §5 as a `verified_reuse` candidate requiring full lineage proof — the writer and its integrity check are unusually rigorous for exactly this reason (content-hash-per-chunk, a dedicated `nirmana_bg_texts_integrity_baselines` lineage table, and an explicit 88/10,651 accepted-mismatch accounting for one supervised machine-translation pass).
2. **Dependencies.** Registry declares `depends_on: []`. Writer (`bg_texts.py`, `@register("bg_texts")`) confirms this: it reads only GCS PDFs (`_download_gcs`), an archive.org DjVu OCR fallback (sarvartha_chintamani), and its own tables (`classical_texts`, `classical_text_chunks`) — no reads of other bg_* tables. Declared and real dependencies match (both empty). Note: the writer calls out to an external embedding service (Vertex AI `text-multilingual-embedding-002`) that is not a DB dependency but is a real external dependency not captured in `depends_on` (expected — `depends_on` models data-plane lineage, not infra dependencies — but worth naming since it is the one non-deterministic-input surface in an otherwise ZERO-LLM writer).
3. **Leverage.** Extensive real consumers confirmed: `platform/src/lib/tools/classical_text_tools.ts`, `classical_text_search.ts`, `L0_brahmagyan/query_classical_texts.ts`, `query_compendium_index.ts`, and MCP tools `read_classical_text.ts`, plus the higher-level `find_verses_about`/`search_classical_texts`/`read_classical_text`/`list_classical_texts`/`ref_vector_search` surface. Not built-but-unplugged.
4. **Grounding — chunk citation keys.** Per the special instruction, I checked whether `classical_text_chunks` rows are addressable for verse-level refs. They are, structurally: `integrity_check_sql` enforces a strict `chunk_id` format invariant (`chunk_id = text_id || '_pg' || lpad(chapter,4,'0') || '_c' || zero-padded verse_start`), non-empty `verse_ref`, non-null `chapter`/`verse_start`/`verse_end` with `verse_end >= verse_start`, non-empty `source_citation`, and a `content_sha256` matching `sha256(text_id::content_en)` for 10,563/10,651 rows (the 88 mismatches are an accepted, documented supervised-machine-translation exception for `muhurta_chintamani`, not silent drift). So **text_id + source_citation + chunk_id integrity is verified and addressable at the row level** — the "chunk citation keys" baseline the plan asks to extend exists and is enforced here.
   - **Concordance bridge linkage (noted, not verified here per instructions):** `bg_concordance.py`'s own docstring documents a real schema mismatch downstream of this table: `classical_attributions.source_chunk_ids` is typed `BIGINT[]` (migration 177) but `classical_text_chunks.chunk_id` is `TEXT` with no bigint PK, so `bg_concordance` can only ever store `source_chunk_ids` as an **empty array** — chunk-level citation pointers from the concordance back to specific `bg_texts` rows are structurally broken, even though `source_text_ids` (TEXT[], text-level only) does carry information. `bg_texts` itself is not at fault (its own chunk_id integrity is verified, per above); the break is in `bg_concordance`'s output typing. This is exactly the linkage the plan's "Concordance bridge" work item names (verify `bg_concordance` pointer freshness against this 10,651-chunk corpus; 721 rows must resolve) — the actual verification of `bg_concordance`'s 721 rows belongs to that asset's own W1 packet in a different batch, not duplicated here.
5. **Temporal identity.** N/A — text corpus, not a temporal engine.
6. **Service.** Real consumer (point 3), `target_floor=10651` matches the exact chunk count. `count_sql` is exact and sane. `integrity_check_sql` is the strongest in this batch — full lineage baseline comparison (`nirmana_bg_texts_integrity_baselines`), per-text row-count map, identity+content sha256 digests, and the documented accepted-mismatch carve-out. `data_disposition: RETAINED_AS_CAPITAL` is explicitly set (unique in this batch), consistent with plan §5 naming it a `verified_reuse` candidate.
7. **Cost.** Unmeasured — would need runtime instrumentation. The writer's own design (batched embedding calls of 20, `EMBED_BATCH_SIZE`) is a code-level choice, not a measured cost figure; no documented wall-clock/token cost was found in the repo.
8. **Findings → W2.**
   - MUST: none found — chunk-level citation integrity is verified and the 88/10,651 mismatches are an accepted, documented exception, not an undetected defect.
   - NOW candidate (in a *different* asset's scope, flagged here only as a linkage note per instructions): the `bg_concordance.source_chunk_ids` BIGINT[]-vs-TEXT chunk_id schema mismatch is a real, currently-broken chunk-level pointer — belongs to `bg_concordance`'s own W2 decision, cites D-GROUNDING (concordance bridge work item) and D-SERVICE.
   - NEVER/LATER: none identified for `bg_texts` itself beyond the above; routing to `verified_reuse` (plan §5) looks well-supported by the evidence already in the integrity check.

## bg_text_index

Still the right instrument for its narrow purpose, though its role is explicitly "coverage metric," not a served retrieval index itself — worth confirming at W2 that this framing (measurement vs. index) is still accurate given how thin the actual tag coverage is (see point 6).

Declared and real dependencies match exactly, and the writer's own error message is unusually explicit about the dependency ("vocabulary must be seeded first (bg_reference dependency)").
3. **Leverage.** Real consumers of `classical_text_chunks.topic_tag` confirmed via the same registry/MCP surface as bg_texts (`query_classical_texts.ts`, `read_classical_text.ts`, etc., which filter/facet on topic_tag). Not built-but-unplugged.
4. **Grounding.** Not interpretive in itself (it's a coverage metric), but it is the mechanism that makes chunk-level grounding *findable* by topic — the classifier is a deterministic keyword/regex matcher against `reference_topic_tags` vocabulary (ZERO LLM, per its docstring), which is the correct grounding-adjacent discipline (no invented tags — `classify_chunk()` only returns a tag if it is in `valid_tags`).
5. **Temporal identity.** N/A — text-classification asset, not a temporal engine. (It does classify some dasha/gochara/transit *topic* tags, but that's a subject-matter label, not a timing computation.)
6. **Service — notable coverage gap.** Real consumer exists (point 3), and `count_sql`/`integrity_check_sql` are both present and exact: `target_floor=361` matches `count(DISTINCT topic_tag) ... = 361` exactly, and the integrity check additionally pins `topic_tag IS NOT NULL` count = 7,010 out of 10,651 total chunks — i.e., **only 66% of chunks carry any topic_tag** (3,641 chunks, 34%, are unclassified by design/keyword-miss). This is disclosed honestly in the integrity check (not hidden), consistent with §N.8, but it is a real coverage ceiling on the deterministic keyword classifier worth naming for W2: any downstream grounding-matcher (plan §5 L2 "signal configuration → sutravali antecedent_jsonb match → verse refs; concordance topic → chunk pointers") built on this classifier inherits a ~34% blind spot.
7. **Cost.** Unmeasured — would need runtime instrumentation. The writer documents a two-stage classification design (stage-1 token scan, stage-2 regex) explicitly as a performance optimization in its own docstring, but no measured wall-clock figure is recorded anywhere in the repo.
8. **Findings → W2.**
   - NOW candidate: the 34% unclassified-chunk gap (3,641/10,651) is a real, disclosed limitation of the deterministic keyword classifier; whether to extend the keyword/domain vocabulary (bounded cost — Python dict additions) is a legitimate W2 NOW candidate, cites D-GROUNDING (this is the substrate the L2 grounding matcher will consume — plan §5).
   - NEVER/LATER: no correctness defect — the classifier's ZERO-LLM discipline and the honest disclosure of coverage numbers in the integrity check are both sound.
