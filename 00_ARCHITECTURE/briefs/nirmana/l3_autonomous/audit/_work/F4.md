## 1. Re-measured privilege coverage by table-name prefix

Query:

```sql
WITH rels AS (
  SELECT c.relname AS table_name,
    CASE
      WHEN c.relname LIKE 'kala\_%' THEN 'kala_'
      WHEN c.relname LIKE 'bodha\_%' THEN 'bodha_'
      WHEN c.relname LIKE 'mimamsa\_%' THEN 'mimamsa_'
      WHEN c.relname LIKE 'phala\_%' THEN 'phala_'
      WHEN c.relname LIKE 'chart\_%' THEN 'chart_'
      WHEN c.relname LIKE 'ganita\_%' THEN 'ganita_'
      ELSE 'other'
    END AS prefix
  FROM pg_class c
  JOIN pg_namespace n ON n.oid = c.relnamespace
  WHERE n.nspname = 'public' AND c.relkind IN ('r','p','v','m')
)
SELECT prefix, count(*) AS total,
  count(*) FILTER (WHERE has_table_privilege('data_plane_builder', 'public.'||table_name, 'SELECT')) AS sel,
  count(*) FILTER (WHERE has_table_privilege('data_plane_builder', 'public.'||table_name, 'INSERT')) AS ins,
  count(*) FILTER (WHERE has_table_privilege('data_plane_builder', 'public.'||table_name, 'UPDATE')) AS upd,
  count(*) FILTER (WHERE has_table_privilege('data_plane_builder', 'public.'||table_name, 'DELETE')) AS del
FROM rels GROUP BY prefix ORDER BY prefix;
```

Result (tables + partitioned tables + views + materialized views; relkind IN `r,p,v,m`):

|---|---|---|---|---|---|
| bodha_ | 36 | 28 | 28 | 28 | 28 |
| chart_ | 15 | 4 | 4 | 4 | 4 |
| ganita_ | 2 | 0 | 0 | 0 | 0 |
| kala_ | 41 | 39 | 39 | 39 | 39 |
| mimamsa_ | 37 | 0 | 0 | 0 | 0 |
| phala_ | 20 | 0 | 0 | 0 | 0 |
| other | 280 | 107 | 69 | 69 | 68 |
| **TOTAL** | **431** | **178** | — | — | — |

**Re-verification of the F4 charter numbers:** `kala_* 39/41`, `bodha_* 28/36`, `chart_* 4/15`,
`mimamsa_* 0/37`, `phala_* 0/20` all match the cited figures **exactly**. The one figure that

Sequences (needed for `INSERT`-driven serial/identity columns): 90 total in `public`, 56 with

## 6. Confirmed build-blocking gaps (would fail an L3 build TODAY)

### 6.1 `ka_moorti_nirnaya` ← `bg_transit_moorti` — **CONFIRMED HARD FAIL**

`services/ka_moorti_nirnaya/writer.py`:

```python
_FETCH_MOORTI_TABLE_SQL = """
SELECT nakshatra_offset, moorti_name, quality_tier, phala_brief, classical_citation
FROM bg_transit_moorti
"""
...
def _fetch_moorti_table(conn: Any) -> dict[int, dict[str, Any]]:
    with conn.cursor(row_factory=psycopg.rows.dict_row) as cur:
        cur.execute(_FETCH_MOORTI_TABLE_SQL)
        rows = cur.fetchall()
    return {int(r["nakshatra_offset"]): dict(r) for r in rows}

class KaMoortiNirnayaWriter(WriterBase):
    def run(self, ctx) -> WriterResult:
        ...
        moorti_table = _fetch_moorti_table(conn)   # <-- unconditional, unguarded
```

No `try`/`except` anywhere in the file around this call. `data_plane_builder` has no SELECT on
`bg_transit_moorti` (confirmed §5). A build of the `ka_moorti_nirnaya` asset today raises an
unhandled `psycopg.errors.InsufficientPrivilege` on its first substantive DB call, in a LIGHT
writer with no substep boundary to isolate the failure. **This asset cannot build today.**

### 6.2 `ka_kshetra` ← `phala_rectification` — **CONFIRMED HARD FAIL**

`services/ka_kshetra/uncertainty.py`:

```python
def fetch_sigma_t_days(chart_id: str, conn: Any) -> tuple[float, str]:
    rows = conn.execute(
        """
        SELECT offset_minutes, lel_fit_score, lagna_stable
        FROM phala_rectification
        WHERE chart_id = %s
        """,
        [chart_id],
    ).fetchall()
```

called unconditionally from `services/ka_kshetra/stage3_clocks.py:1012`
(`sigma_t_birth_days, sigma_t_source = U.fetch_sigma_t_days(chart_id, conn)`). No try/except
anywhere in either file. `ka_kshetra` is a HEAVY, substep-based writer (stage0…stage8); stage3
(clocks) is on the mandatory substep path. **This asset cannot complete its stage3 substep
today.**

### 6.3 `ka_kshetra` ← `bg_synthetic_cohort` / `bg_synthetic_cohort_md` — **looks handled, isn't (transaction poisoning)**

`services/ka_kshetra/writer.py:1754-1770` wraps `cohort_client.cohort_base_rate(...)` in a
`try/except Exception` with an explicit comment: *"NOT swallowed: recorded once, with the
reason, and surfaced as a NULL Informativeness factor."* That is the *intended* graceful
degradation this codebase already uses correctly elsewhere (see `bg_transit_av_gates`,
§6.4 below, and `bg_combustion_orbs` in §5's table). But neither `cohort_client.py` nor the
call site in `writer.py` issues a `SAVEPOINT` before the risky query. Grepped both files for
`SAVEPOINT` — zero hits in either.

Per the FROZEN orchestrator contract (`ORCHESTRATOR_CONVERGENCE_CLOSE_v1_0.md §2` /
CLAUDE.md §N.2), the writer runs on `ctx.db_conn` and the orchestrator owns the
transaction/savepoint *per substep*, not per internal call. When a query raises
`InsufficientPrivilege` inside a Postgres transaction with no savepoint wrapping it, the whole
transaction enters the aborted state (`current transaction is aborted, commands ignored until
end of transaction block`) — catching the Python exception does **not** undo that. The very next
SQL statement issued on the same connection within the same substep (e.g. the
`kala_field_salience` row inserts stage6 goes on to do) will itself fail, with a confusing
downstream error that doesn't obviously point back to `bg_synthetic_cohort`.

`gochara_grammar/primitives.py` lines 95–131 document this *exact* failure mode in prose and
fix it with a uniquely-named per-query `SAVEPOINT` for `bg_transit_av_gates` — proving the
codebase knows the pattern. `cohort_client.py` / `ka_kshetra/writer.py` just didn't apply it
here. **Net effect: the same hard-fail-on-privilege-gap outcome as §6.1/§6.2, one step removed
and harder to diagnose from the error message alone.**

### 6.4 `ka_bhavishya_lekha` ← `phala_anchors` — **guarded on first build, fails on rebuild**

`pipeline/orchestrator/writers/ka_bhavishya_lekha.py` lines 249–287: the `phala_anchors` read
only executes `if existing_ids:` (i.e. only when the writer already has previously-built rows
for this chart to reconcile against — the delete-then-insert idempotency check per §N.3). On a
chart's *first* `ka_bhavishya_lekha` build, `existing_ids` is empty and the block is skipped
entirely — no failure. On a **rebuild** (any subsequent build of an already-built chart, which
is the normal operating mode for iterative development on the canonical chart
`482012f1-710e-4a25-994a-93821f5871aa`), `existing_ids` is non-empty, the code runs
`SELECT to_regclass('phala_anchors') IS NOT NULL` (a catalog *existence* check — it returns TRUE
regardless of whether the current role can SELECT the table), passes that check, then executes
`SELECT bhavishya_id FROM phala_anchors WHERE bhavishya_id IN (...)`, which raises
`InsufficientPrivilege` unhandled. **Rebuilds of `ka_bhavishya_lekha` on any chart that already
has rows fail today; the very first build of a fresh chart does not.**

## Summary

**Yes — there is a privilege gap that would block an L3 asset build today, and it is not a
single isolated case.** Two active `ka_*` assets have confirmed, completely unguarded reads
against tables `data_plane_builder` cannot SELECT and will hard-fail on the very next build
attempt:

- **`ka_moorti_nirnaya`** (reads `bg_transit_moorti`, zero exception handling)
- **`ka_kshetra`** (reads `phala_rectification` in its mandatory stage3 substep, zero exception
  handling; separately, its `bg_synthetic_cohort`/`bg_synthetic_cohort_md` read in stage6 has a
  `try/except` that looks like a safety net but is defeated by missing `SAVEPOINT` handling, so
  it fails too, just one statement later and less legibly)

A third asset, **`ka_bhavishya_lekha`**, is safe on a chart's first build but will hard-fail on
any rebuild of a chart it has previously written rows for, because its `phala_anchors` guard
checks table *existence* (`to_regclass`) rather than privilege. Migration 1070's restoration of
core orchestrator privileges did not extend to `bg_transit_moorti`, `phala_rectification`,
`bg_synthetic_cohort`, or `bg_synthetic_cohort_md` — all four need `SELECT` granted to
`data_plane_builder` before these three assets are build-safe; the mismatch between
"looks handled" and "is handled" in `ka_kshetra`'s cohort path (§6.3) is worth a savepoint fix
independent of the grant, since the same unguarded-call pattern could resurface against any
future table this role doesn't have access to.
