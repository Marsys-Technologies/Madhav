is, gets a completely wrong answer** — wrong scope (`global` vs `per_chart`), wrong storage_type

different `depends_on` set entirely. This is qualitatively worse than a stale count: it is a stale

## 6. Does `dag_edge_guard.py` catch any of this?

Read directly: `platform/python-sidecar/pipeline/orchestrator/dag_edge_guard.py`.

**What it actually checks:** the live `asset_registry` table (`_load_registry`, only
`is_active=true` rows) against `FROM`/`JOIN <table>` matches found by regex in writer source
(`_reads`), flagging a HARD violation when a writer reads a table owned 1:1 by another `per_chart`
asset that isn't in its declared `depends_on` transitive closure. Two important self-documented
limits already noted by the module's own docstring (lines 15-47), worth restating precisely:

1. **It has never run as a per-commit CI gate against the live DB.** Its only DB-connected caller is
   `tests/test_dag_edge_guard.py`'s live check, decorated `@pytest.mark.skipif(not DATABASE_URL)`;
   push/PR CI supplies no database, so it always skips there. The live scan only runs on the
   scheduled/`workflow_dispatch` `fresh_chart_smoke.yml` job, and via manual invocation.
2. **It would not have caught either of the two confirmed discrepancies in this report even when
   run**, because both (`ka_muhurta_seva`, `ka_vighnakara`) are **seed-file-vs-live** drift, not
   **code-vs-live** drift — the guard never reads `asset_registry_seed.ts` or MIG345 at all; it
   only compares LIVE against CODE. By the time this audit ran, LIVE already matched CODE for both
   assets (migrations 676 and 730 fixed LIVE, verifying against the writer source first) — so a
   live `dag_edge_guard` scan today would report these two as **clean**, correctly, while the actual
   defect (SEED-TS/MIG345 silently left stale, by explicit policy) remains invisible to it
   permanently. **The guard's blind spot is exactly the defect class this report's F3 finding is
   about**: it protects code-vs-registry consistency, not registry-vs-seed consistency. If a fresh
   database is ever bootstrapped by re-running `asset_registry_seed.ts`'s `runSeed()` *instead of*
   the full migration sequence (345 → 676 → 730 → ...), it would silently resurrect the fictional
   `ka_muhurta_seva → ka_graha_sancara` and stale `ka_vighnakara → ka_gochara` edges with nothing in
   this repo's tooling positioned to notice, since `dag_edge_guard` only ever looks at whatever
   ends up live. (Both `platform/migrations/` and `platform/supabase/migrations/` are read and
   merged by `platform/scripts/migrate.ts:834-835`, and MIG345 (#345) numerically precedes 676 and
   730, so the *normal* migration-replay path does self-correct — the risk is specifically any
   bootstrap path that uses the TS seed script as a substitute for full migration replay.)
3. The guard would also not catch §5's `ka_avadhi`/`ka_dasha_kala` soft coupling — by design,
   Python imports aren't table reads, and `ka_dasha_kala` has no `target_table` to gate on.

## Summary

The highest-severity discrepancy is the **`ka_gochara` identity reuse** (§3): `platform/
supabase/migrations/345_register_ka_assets.sql` still describes an asset that migration 563 deleted
and whose name was reassigned to a structurally unrelated writer (service → data materializer,
different scope, different target table, different dependency set entirely). Its blast radius is
documentation/onboarding risk rather than a live build defect — MIG345's `ON CONFLICT DO NOTHING`
makes it inert against the current database, and the two sources anyone would actually consult to
build or extend the DAG today (SEED-TS and LIVE) agree with each other and with the post-rename
code. But any future reader, generated onboarding doc, or automated tool that treats MIG345 as a
historical-but-valid seed (exactly the role its own header claims: "Source of truth... copied
VERBATIM") will silently absorb a wrong scope, wrong storage type, and wrong dependency set for one
of the two heaviest writers in the whole L3 layer (the other being `ka_sangam`, "THE VALUABLE
CORE"). Combined with the confirmed §2 finding that the *intentional* seed-vs-live staleness policy
("migrations are the living correction layer, the seed file is the as-authored record, re-syncing
it is a separate question") has already produced two real, currently-live divergences
(`ka_muhurta_seva`, `ka_vighnakara`) that `dag_edge_guard.py` structurally cannot detect (§6), and
that the frozen-manifest protection has never been exercised for 12 of the 23 identities including
`ka_sangam` itself (§4), the composite picture is a DAG-of-record that is currently *correct* at the
