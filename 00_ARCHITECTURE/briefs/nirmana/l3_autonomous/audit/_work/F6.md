## 4. Deploy workflow trigger logic (`.github/workflows/deploy.yml`, read-only)

Confirmed **path-gated per surface**, and the gate is self-correcting rather than static:

- Trigger: `workflow_run` (after `CI — Ganga Quality Gate` succeeds on `main`) or
  `workflow_dispatch` (manual, with a `force_all_services` override input).
- The `changes` job (`.github/workflows/deploy.yml` lines 261–362) computes, for **each**
  component independently, `git diff --name-only <that component's own live-deployed SHA> HEAD`
  and greps it against a per-component path pattern — it does **not** diff from any static
  "last deploy" record; it reads the actually-running SHA straight out of Cloud Run
  (`gcloud run services/jobs describe`) each time, specifically to avoid the exact "silent
  self-diff" class of bug the workflow's own comments document being caught and fixed on
  2026-09-07 (pipeline image stale ~3.5h across 17 green deploy runs before the fix).
- Relevant pattern for the builder/pipeline job (`PIPELINE_PATTERN`, line 302):
  ```
  ^(platform/python-sidecar/Dockerfile\.pipeline|platform/python-sidecar/ga_writers/|
    platform/python-sidecar/pipeline/|platform/python-sidecar/services/|
    platform/python-sidecar/brahmagyan/|platform/python-sidecar/pyjhora_adapter/|
    platform/python-sidecar/bodha_writers/|platform/python-sidecar/panchang_engine/|
    platform/python-sidecar/muhurat/|platform/python-sidecar/requirements|035_DISCOVERY_LAYER/)
  ```
  All `ka_*` writer source actually lives under `platform/python-sidecar/pipeline/orchestrator/
  writers/ka_*.py` and `platform/python-sidecar/services/ka_*/` (confirmed via
  `grep -rl "@register('ka_"`), both of which **are** covered by this pattern
  (`.../pipeline/` and `.../services/` prefixes). **A change limited to L3 writer code would
  trigger a pipeline rebuild** — the gate is not blind to L3 changes; it correctly would have
  rebuilt if any of the 5 pending commits had touched writer code. They didn't, so `pipeline`
  correctly resolved `false`.
- Live confirmation, from the actual deploy run that shipped `20f4d02dc` to `amjis-web`
  (`gh run view 35500092042 --log`, job "Gate & detect changed paths"):
  ```
  === Outputs ===
  web=true  sidecar=false  mcp=false  pipeline=false
  ```
  This is the gate correctly deciding — 3 of 5 commits are `platform/scripts/purna/**`
  (matches the broad `WEB_PATTERN` `^platform/`) so `web` rebuilt; none touch
  `platform-mcp/**`, `platform/python-sidecar/**`, so `sidecar`/`mcp`/`pipeline` all
  legitimately skipped.
- Separately, the DB migration step (`migrate` job, "Apply Routine DB Migrations") is **not**
  path-gated — it runs unconditionally on every deploy trigger specifically so a migration can
  never be silently skipped by a path filter (explicit design comment, deploy.yml lines 386–391).
  `deploy-pipeline-job` depends on `migrate` succeeding first, but its own execution is still
  gated by `needs.changes.outputs.pipeline == 'true' || force_all == 'true'` (lines 1922–1927).

Only `force_all_services=true` on a manual `workflow_dispatch` (or a future commit that actually
touches one of the pipeline paths) would rebuild the builder image right now.

## 5. Was migration 1070 (the actual live-blocking bug) already applied, independent of the stale image?

Yes — verified directly from the deploy run that shipped commit `d9070900d` (`gh run view
35491906460 --log`, job "Apply Routine DB Migrations"):
```
Applied: 1070_data_plane_builder_orchestrator_grants.sql
```
at `2026-09-20T05:42:40Z`, and that job reported `success`. The migration file's own tail is a
fail-closed self-check (`DO $$ ... RAISE EXCEPTION 'migration 1070 did not take effect...'`) —
per CLAUDE.md §N.8 this is a real detector, not an assumed-clean flag: had any of the six grants
not taken, the migration itself would have raised and the job would show `failure`, not
`success`. Live re-verification via direct `has_table_privilege(...)` query against the
production DB was attempted (`mcp__postgres__query`) but the DB proxy is not reachable from this
environment (`connect ECONNREFUSED 127.0.0.1:5433`) — the CI log evidence above is what's
available in this session; an operator with DB access could re-run the six `has_*_privilege`
checks from the migration file directly against prod for independent confirmation.

Because this migration is a `GRANT` (a database-side privilege change, not application code), it
took effect the moment `migrate` ran — **it does not require the builder container image itself
to be redeployed.** So the concrete symptom the brief worried about ("every build run of every
asset fails") is resolved in production already, despite the builder image still reporting SHA
`09d998940...`.

## Verdict

**READY — deploy freshness, conditionally.** The builder/pipeline image is genuinely 5 commits
behind `origin/main` by SHA count, and this is a real, currently-true fact — not something that
"looks fine." But the specific detector that would make this a live hazard (does the pending
delta touch anything the builder image executes?) comes back negative: none of the 5 pending
commits touch `platform/python-sidecar/pipeline/`, `platform/python-sidecar/services/`, or any
other builder-image path, confirmed both by direct `git diff --name-only` against the file list
and independently by the deploy workflow's own live gate output (`pipeline=false`) captured from
a real GitHub Actions run log, not inferred. The one commit in the delta that *did* matter
substantively for L3 (`d9070900d`, the `data_plane_builder` grants fix for the exact failure
mode "every build run of every asset fails") is a DB migration, is path-filter-exempt by design,
and has independently confirmed log evidence (`Applied: 1070_...sql`, job conclusion `success`,
behind a fail-closed self-test) that it already took effect in production — so the image's
staleness does not currently gate a known-broken capability.

What would flip this to NOT READY: (a) if the `has_*_privilege` re-check against the live DB
(blocked in this session — no DB proxy reachable) came back false despite the log claiming
`success`, meaning the fail-closed check itself had a defect; (b) if any future commit touches
`platform/python-sidecar/pipeline/**` or `platform/python-sidecar/services/**` and merges to
main without a subsequent automatic or `force_all_services=true` manual deploy — the image would
then be stale *and* substantively behind; (c) if MCP or sidecar staleness (also 5 commits, same
root SHA, same "no relevant path changed" finding) is later found to matter for some surface not
covered by `MCP_PATTERN`/`SIDECAR_PATTERN` — this audit did not exhaustively check MCP/sidecar
path coverage the way it did for the pipeline job, since the brief's specific concern (F6) was
the builder image.
