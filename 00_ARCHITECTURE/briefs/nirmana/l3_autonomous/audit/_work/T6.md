## F16 — knowledge-time (not just event-date) firewalls

Spec text (line 43): "Observations preserve subject, source, event time, knowledge time, precision,
purpose, exposure, confirmation/dispute and revisions. Unknown is not a non-event... Immutable revision
lineage and missingness-aware adjudication."

Searched `knowledge_time`, `knowledgeTime`, `as_of_time`/`asOfTime` (as a knowledge-cutoff concept,
distinct from event-date `as_of` parameters), `information_cutoff`: **zero hits** anywhere in
`platform/` or `platform-mcp/`.

Inspected the actual `life_events` observation table
(`platform/migrations/brahma_mimamsa_lel_intake.sql:45-57`):
```
CREATE TABLE IF NOT EXISTS life_events (
    event_id UUID PRIMARY KEY, event_date DATE NOT NULL, event_type TEXT NOT NULL,
    description TEXT NOT NULL, domain TEXT NOT NULL, outcome_observed TEXT,
    source_citation TEXT NOT NULL, ingested_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
This has `event_date` (event time) and `ingested_at` (a rough proxy for system-knowledge time, but not
a modeled "knowledge time" distinct from ingestion). It has NO `precision`, `purpose`, `exposure`,
`confirmation/dispute` status, or revision-lineage columns. There is no versioning/history table for
`life_events` rows (no `life_events_history`, no soft-delete + supersede pattern found). F16's own
named enforcement test — "immutable revision lineage" — has no corresponding schema or code.

The `as_of` parameters found in L3 code (`kala_permission/permission.py`'s `compute_permission(...,
as_of: date, ...)`, `ka_jivana_parva.py`) are all **event-date filters** (which dasha window covers
this calendar date) — exactly the "merely filtering by event date" pattern the task flagged as
insufficient, not a knowledge-time cutoff.

**Verdict: NOT ENFORCED.** No code path implements a knowledge-time firewall distinct from event-date
filtering; the schema that would need to carry knowledge_time/precision/revision-lineage doesn't have
those columns.

## F17 — issued-claim freezing

Spec text (line 44): "Freeze completed issued claims before later outcomes: proposition, wording,
window, probability, assumptions, cutoff, consumed evidence and eligibility. Never evaluate a
retrospective rewrite... Issuance receipt predates admitted evaluation outcome."

Found the candidate mechanism: `brahma_prospective_ledger` table, read/write logic in
`platform/src/lib/lel/prospective_ledger.ts` (780 lines). Grepped the entire codebase for
`UPDATE brahma_prospective_ledger`: **exactly one** call site exists
(`platform/src/lib/lel/prospective_ledger.ts:748`):
```sql
UPDATE brahma_prospective_ledger
   SET lifecycle_status = 'matched', matched_event_id = $2::uuid, matched_at = now(), match_note = $3
 WHERE prediction_id = $1::uuid
```
This touches only lifecycle/matching metadata — never `claim`, `observation_window`, `confidence`,
`falsifier`, `as_of`, `model`, `formula_version`, or any other content field of an issued claim. That is
consistent with the freeze requirement, and it's empirically true today (single call site, easy to
audit).

However, this is an **application-level** guarantee, not a **database-level** one: no DB trigger,
`REVOKE UPDATE`, or CHECK constraint was found preventing a *future* code path from updating claim-content
columns. Searched for a migration creating this table (`grep -rl "CREATE TABLE.*brahma_prospective_ledger"
platform/migrations`): no match — the table's origin migration is not locatable by that name in the
current migrations directory (only two later migrations, `459_gochara_resonance_map.sql` and
`572_ekv_c01_ledger_empty_daterange_repair.sql`, reference it). Could not locate any immutability
trigger. `grep -rln "issuance_receipt" platform`: zero hits — F17's own named enforcement test
("issuance receipt predates admitted evaluation outcome") has no corresponding artifact in code.

**Verdict: PARTIALLY ENFORCED** — content-freezing is true in practice (one auditable write path,
content columns never touched) but not mechanically guaranteed by a DB constraint; a future PR could
add a second UPDATE touching `claim`/`confidence` and nothing in the schema would stop it. The specific
"issuance receipt" enforcement test named by the spec does not exist.

census for `life_events`/`lel_query`) that would catch a second such import being added elsewhere.

## Verdict: NOT READY

Of the seven items audited, none were fully, unconditionally ENFORCED:
- F15: only 1 of 4 purposes has any enforcement, and only via a proxy target the guard's own docstring
  says must be re-pointed once the real target ships.
- F16: no knowledge-time concept exists in code or schema at all — NOT ENFORCED.
- F17: enforced today by absence of a second write path, not by a DB constraint; the named enforcement
  test doesn't exist.
- F27: inconsistent — roughly half of spot-checked writers lack fact_id-level citation.
- F26: enforced for the 2 writers checked (not exhaustive, but no red flag found).
- Safety exclusions: confirmed real gap — 3+ of 9 `kala_views` surfaces accept the same free-text
  mortality-vector input as `elect`/`ritual` but don't run the check.
- No L4/L5 elevation: one confirmed, documented cross-layer import exists; no CI guard prevents a second.

The strongest positive evidence is the CIRCULARITY GUARD (F15 proxy) and the frozen orchestrator
contract (F26) — both are genuine, testable, CI-enforced detectors matching CLAUDE.md §N.8's standard.
Everything else ranges from "true today by convention" to "not implemented at all."

  `now.ts`, `story.ts` are confirmed zero-hit regardless, so the surface-coverage finding would stand

  file, or as a Postgres RULE), F17 would move from PARTIALLY to fully ENFORCED. Not found in the time
  budgeted; flagged as COULD NOT FULLY VERIFY on the DB-constraint sub-question specifically.
- If a `knowledge_time`-equivalent field exists under a materially different name not tried in this
  search (budget did not permit an exhaustive column-name enumeration of every migration touching
  `life_events`/`chart_facts`), F16 could be less severe than "not enforced at all." The `ingested_at`
  column is the closest candidate found and is not sufficient per the spec's own description (it does
  not carry precision/purpose/exposure/dispute/revision-lineage).
