**1. Schema inspection** (`\d nirmana_evidence.nirmana_elevation_campaign_definitions`,
`\d nirmana_evidence.nirmana_elevation_campaign_events`) — established the two load-bearing tables.
Key finding: `nirmana_elevation_campaign_definitions` has **no explicit parent/supersedes foreign
key column**. The only columns available for lineage are `campaign_id` (single fixed value
`nirmana-elevation` for all rows), `definition_revision`, `definition_status`, `created_at`,
`superseded_at`. Lineage is therefore reconstructible only as a **linear total order by
`created_at`** within the single `campaign_id` — there is no branching/parent structure in the
schema, so "ancestor closure" for every asset is drawn from the same single chain, not a
per-asset DAG of definitions.

**2. Full definition lineage:**

**Critical structural fact:** `definition_status` records only the *current* state of each row, not
a history of state transitions. Every revision before t3 was itself `frozen` for the duration it
was the active definition, then flipped to `superseded` the instant the next revision was created.
There is no separate status-history table. This means **"how many ancestor definitions are frozen"
is 0 for every asset, always** — by construction, only the current chain-head can ever read
`frozen`. The interesting question is not "were any ancestors frozen" (never, now) but "did an
ancestor definition, while it *was* frozen, record evidence for this asset" — answered in section 2
below.

## Options A / B / C — cost, risk, F09/F13 implications

**Do not read this section as a recommendation of which to pick — the native decides.**

### Option A — re-freeze every ancestor definition explicitly under t3

Concretely: re-run whatever build/verify/accept pipeline produces `asset_analysis_accepted` →
`optimization_verdict_accepted` → `implementation_accepted` → `integrity_verified` →
`asset_frozen` (or the current definition's equivalent event set) for every one of the 22 active
identities, this time with events recorded under `definition_revision = t3-2026-09-11-8b884eac`.

- **Cost, tiered by current evidence state** (measurable from the table above, not an estimate of
  effort-hours):
  - 12 assets already reached `asset_frozen` in some ancestor — re-freezing them is the cheapest
    tier if the underlying implementation hasn't drifted (re-verify + re-emit events; no
    reimplementation expected). But `source_kind` for L3 events splits `git_commit`=66,
    `server_reconstructed`=32, `build_run`=8 — roughly 30% of all L3 evidence is
    `server_reconstructed`, i.e. not a live build receipt but a reconstruction after the fact. Any
    re-freeze that leans on "just re-emit the event" without an actual re-run inherits the same
    evidentiary weakness F1 already found in `egate.sql` (treating non-current-definition evidence
    as current). A defensible re-freeze needs an actual re-run for at least the
    `server_reconstructed` fraction.
  - 7 assets reached mid-pipeline states (`asset_analysis_accepted`/`optimization_verdict_accepted`)
    but never `asset_frozen` — these need the remaining pipeline steps completed, not just
    re-verified, i.e. `implementation_accepted` + `integrity_verified` + `asset_frozen` each freshly
    earned under t3.
  - 3 assets (`ka_gochara_v`, `ka_kalasutra`, `ka_vighnakara`) have never been analyzed at all under
    any definition — full pipeline from `asset_analysis_accepted` onward, from zero.
  - Plus `ka_gochara_sweep`: explicitly protected/retired, "never rebuilt" per CLAUDE.md §E — Option
    A should not apply to it regardless of which option the native picks for the 22 active
    identities.
  - **COULD NOT VERIFY**: the actual wall-clock/compute cost per asset-pipeline-step (no timing
    data in the events table's columns queried; `observed_at`/`recorded_at` deltas were not pulled
    within budget). A follow-up query on `observed_at` vs `recorded_at` spread per event_type would
    give a real duration estimate.
- **Risk:** low evidentiary risk (freshest possible evidence, no inheritance ambiguity) but highest
  time/compute cost of the three options, and it re-exposes the process to whatever produced the 30%
  `server_reconstructed` share the first time (unless that root cause is fixed first).
- **F09 implication:** Option A is the only option that cleanly satisfies F09's "select compatible
  dependency sets... preserve generations, consumed values, snapshots" *without* an explicit
  cross-generation compatibility argument — every dependency and its consumer are frozen under the
  same `t3` generation by construction, so there is no manifest to write justifying a
  cross-definition read.
- **F13 implication:** re-freezing re-establishes "present" and "qualified" rungs fresh under t3,
  but does **not** by itself advance anything to "consumed / effect traceable / served / value
  evaluated" — those rungs (per the F2 background and T3 in the same prompt file) may have **no
  campaign event type at all** for L3 (query 6's event_type list has no `consumer_integrated` or
  `value_evaluated`-shaped event). Re-freezing closes the "0/23 under t3" gap but does not, on its
  own, touch F13's downstream rungs — a separate receipt design is still needed for those regardless
  of which of A/B/C is chosen here.

### Option B — explicit evidenced inheritance ruling (native declares specific ancestor evidence admissible under t3, no re-run)

Concretely: the native records a ruling (e.g. in `NATIVE_DIRECTIVES_FOR_REVISION_v1_0.md` or an
equivalent artifact) naming which ancestor `asset_frozen` (or other) events count as admissible
evidence under t3, without re-running the pipeline for those assets.

- **Cost:** near-zero compute cost — this is a governance action, not a rebuild. The cheapest option
  by far for the 12 assets that already reached `asset_frozen`.
- **Risk:**
  - **Staleness/code-drift** — the 12 `asset_frozen` events span t0(09-01) through t2(09-10), i.e.
    up to ~17 days old at t3's freeze (2026-09-11) and now 11 days further stale as of this audit
    (2026-09-22). Nothing in the events table (`evidence_payload` was not inspected in depth here —
    COULD NOT VERIFY its exact contents beyond existence within budget) proves the code state that
    earned the freeze is the same code state live today. Given the campaign's own F1 finding (a real
    admission-scoping bug shipped and had to be repaired in PR #2706) and F3 (three sources disagree
    on the DAG for `ka_sangam`/`ka_kalasutra`/`ka_muhurta_seva`/`ka_vighnakara`), there is
    independent evidence the codebase has moved under some of these assets since their ancestor
    freeze — an inheritance ruling risks certifying evidence against a definition (DAG shape,
    dependency set) that no longer matches production.
  - **Selective admissibility risk** — a ruling that admits some ancestors but not others (e.g. only
    `asset_frozen` events, not `asset_analysis_accepted`-only ones) needs its own explicit boundary
    or it re-creates exactly the ambiguity F1 already exploited.
  - This option covers at most 12 of 22 cleanly (the `asset_frozen` set); the 7 mid-pipeline assets
    and 3 zero-evidence assets have no ancestor evidence strong enough to inherit regardless of the
    ruling's generosity — Option B does not eliminate Option A/C work for those 10.
- **F09 implication:** this is precisely the cross-generation "compatible dependency set" case F09
  is written for — the ruling **is** the compatibility manifest. F09 requires it be explicit and
  preserve "generations, consumed values, snapshots, invalidation, cache scope, correction
  propagation, history and rollback" — a bare "these 12 count" ruling without naming which
  generation's dependency snapshot each inherited asset is being certified against would not meet
  F09's bar; the ruling would need to enumerate, per asset, which ancestor generation's dependency
  set it is vouching for.
- **F13 implication:** inheriting an ancestor's `asset_frozen` event under t3 would still only
  establish "present/qualified" rungs (by declaration rather than fresh measurement) — same downstream
  gap as Option A: F13's later rungs (consumed, effect traceable, served, value evaluated) have no
  event type in the L3 data at all, ancestor or current, so Option B doesn't close that gap either,
  it just makes the early rungs cheaper to claim.

### Option C — partial/hybrid inheritance, and other options visible from the schema/data

- **C1 — Tiered by evidence strength.** Inherit only the 12 `asset_frozen`-bearing assets (Option B
  scoped narrowly), run Option A in full for the 7 mid-pipeline + 3 zero-evidence assets. This is
  the schema-supported middle ground: the data already partitions cleanly into these three tiers (12
  / 7 / 3), so a tiered ruling maps directly onto measured evidence rather than an
  all-or-nothing choice. Cost = Option A's cost for 10 assets only; risk = Option B's staleness risk,
  but scoped to the assets where it's strongest (an actual `asset_frozen`, not a partial pipeline
  state).
- **C2 — Re-verify, don't re-build, the 12 `asset_frozen` assets.** A middle cost between A and B:
  instead of a bare governance ruling (B) or a full pipeline re-run (A), run only the
  `integrity_verified`-equivalent check fresh under t3 for the 12 already-frozen assets, using the
  existing frozen artifact as the object under test rather than rebuilding it. This directly answers
  the code-drift risk Option B carries without paying Option A's full rebuild cost — but needs a
  cheap, fast verifier to exist for this to be worth it over A (COULD NOT VERIFY whether such a
  lightweight verifier currently exists separate from the full build path).
- **C3 — Retire the ancestor-inheritance question entirely for the 3 zero-evidence assets and the 7
  mid-pipeline assets**, and only apply any inheritance ruling to the 12/22 with `asset_frozen`
  ancestors, explicitly declaring the other 10 "not eligible for inheritance, must earn t3 evidence
  from scratch regardless of option chosen." This removes the ambiguity risk Option B's "selective
  admissibility" bullet raises, by making the scope binary and evidence-shaped rather than a judgment
  call per asset.
- **F09/F13 implications for C1–C3:** same shape as A/B's analysis, applied per-tier — the tiered
  options make the F09 compatibility-manifest requirement easier to write precisely (each tier names
  its own generation), but none of A/B/C1-3 touch F13's "consumed → served → value evaluated" rungs;
  that is a separate, still-open receipt-design gap regardless of which option is chosen here.
