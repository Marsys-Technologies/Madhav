## 3. Is the dispatcher hardcoded-path bug still live on `main` right now?

**Yes — confirmed present, unpatched.**

Current `main` (this worktree, `platform/scripts/dispatch_frozen_rebuild.py`, diffed clean against `origin/main`):

```python
WRITER_DIGESTS_PATH = Path("/Users/Dev/nirmana-s/l3/platform/src/generated/nirmana-writer-digests.json")
```

This is a developer-machine-absolute path outside the repository entirely. It is **not** `platform/src/generated/nirmana-writer-digests.json` under the actual repo root.

Both paths exist on this machine right now, and they diverge:

- `/Users/Dev/nirmana-s/l3/platform/src/generated/nirmana-writer-digests.json` — a stale copy (file mtime 2026-09-10), which the hardcoded path resolves to.
- `/Users/Dev/madhav-l3/audit/platform/src/generated/nirmana-writer-digests.json` — the real repo-tracked file (last git-committed 2026-09-16, commit `fa9857f00e45ab2c2052ffd37eb0910a4d7b6fcd`).

PR #2695's fix (present in `origin/codex/madhav-l3-claude-code`, not merged):

```python

```

This resolves the path relative to the script's own location instead of a hardcoded absolute dev path — correct and portable.

## 4. Is the dasha-eligibility wrong-default-ayanamsha bug still live on `main` right now?

**Yes — confirmed present, unpatched.**

`platform/src/lib/retrieval/registry/layers/L3_kala/call_service_wrappers.ts` defines five service wrappers (`callTransitSearchCapability`, `callEphemerisAtTCapability`, `callDashaEligibilityCapability`, `callMuhurtaScoreCapability`, `callPriorityRankingCapability`). The file imports and correctly uses the canonical constant

```ts
import { DEFAULT_AYANAMSHA } from '../../constants'   // = 'lahiri_chitrapaksha'
```

in `callEphemerisAtTCapability` (line 227) and `callPriorityRankingCapability` (line 595). **But `callDashaEligibilityCapability` (starts line 271) does not** — at line 328 (and its JSDoc-style param description at line 301) it hardcodes the literal `'lahiri'`:

```ts
description: "Ayanamsha (default: 'lahiri').",
...
const ayanamsha_id  = (args['ayanamsha_id'] as string | undefined) ?? 'lahiri'
```

`'lahiri'` is **not** the canonical ayanamsha key stored in `bodha_*`/`kala_*`/`phala_*` tables — the codebase's own `constants.ts` comment says: *"The canonical ayanamsha key as stored in all bodha_* / kala_* / phala_* tables"* is `'lahiri_chitrapaksha'`. A caller of `call_dasha_eligibility` who omits `ayanamsha_id` (the common case) gets a default that will not string-match the ayanamsha key actually used to populate `kala_activation`/related tables, producing either silently empty results or a lookup against the wrong ayanamsha convention — a correctness bug, not cosmetic.

PR #2695's fix (`origin/codex/madhav-l3-claude-code`, diffed against `origin/main`):

```diff
-      description: "Ayanamsha (default: 'lahiri').",
+      description: `Ayanamsha (default: '${DEFAULT_AYANAMSHA}').`,
...
-    const ayanamsha_id  = (args['ayanamsha_id'] as string | undefined) ?? 'lahiri'
+    const ayanamsha_id  = (args['ayanamsha_id'] as string | undefined) ?? DEFAULT_AYANAMSHA
```

This brings `call_dasha_eligibility` in line with the other four wrappers in the same file, all of which already use `DEFAULT_AYANAMSHA`.

## 5. Would dispatching `dispatch_frozen_rebuild.py` right now, unpatched, through `main` produce a false provenance receipt?

**Yes.** Walking through what the script does with §N.8 (Earned-Signal Principle) in mind — "what does this signal claim, and what code path would have to run, and fail, for it to correctly read false":

- `dispatch_frozen_rebuild.py`'s `WRITER_DIGESTS_PATH` on `main` resolves to `/Users/Dev/nirmana-s/l3/platform/src/generated/nirmana-writer-digests.json`, a stale, non-repo-tracked file that is demonstrably different (every digest value differs) from the actual current repo state.
- `_load_writer_digest(asset_id)` reads `expected_code_digest` straight from that stale file and folds it into `build_manifest(...)` as `manifest["expected_code_digest"]`, which becomes part of the canonical-JSON-hashed manifest (`manifest_digest = sha256(canonical_json(manifest))`) that gets **committed as the provenance receipt** for the rebuild.
- Nothing in the script checks that the loaded digest file matches the code that is actually about to run — there is no drift detector between "digest source path" and "current writer source" in this script. The path is simply wrong, silently, and the script has no way to notice.
- On a machine without `/Users/Dev/nirmana-s/...` present at all, this would `FileNotFoundError` loudly (fail-safe by accident). But on this machine, where that stale file *does* exist (confirmed above), the script runs to completion and emits a manifest asserting `expected_code_digest` values that do not correspond to the writer code that would actually execute the rebuild — i.e. a receipt that claims a code identity that never ran. This is exactly the defect class §N.8 names: a signal (the provenance receipt) whose backing check does not test what it claims to test.
- Separately, `call_dasha_eligibility`'s wrong default ayanamsha (`'lahiri'` vs. canonical `'lahiri_chitrapaksha'`) is a live correctness bug independent of the dispatcher: any campaign step that calls this tool without an explicit `ayanamsha_id` gets silently wrong/empty results against the real `kala_*` tables, with no error surfaced.

Both defects are orthogonal to, and do not depend on, the Pūrṇa-owned `BEYOND_ACARYA_ACCEPTANCE_v5.json`/`route_ports/baseline` regeneration blocking the PR's merge — the PR's own fix is correct and complete for both, but sits un-mergeable behind someone else's unrelated baseline drift.

## Verdict

**Not currently safe to dispatch `dispatch_frozen_rebuild.py` through `main`.** As of this audit (2026-09-22), `main` still carries both defects PR #2695 fixes: (1) a hardcoded, non-repo-relative `WRITER_DIGESTS_PATH` that on at least this machine resolves to a stale, demonstrably-divergent digest file, meaning any rebuild dispatched right now would commit a provenance receipt asserting a code-identity digest that does not correspond to the code that actually ran — a genuine §N.8 earned-signal violation, not a hypothetical; and (2) `call_dasha_eligibility` defaulting to the non-canonical ayanamsha key `'lahiri'` instead of `'lahiri_chitrapaksha'`, silently mismatching every other `kala_*`/`bodha_*`/`phala_*` table convention in the codebase for any caller that omits `ayanamsha_id`. PR #2695 already contains the correct, minimal fix for both (`REPO_ROOT`-relative path resolution; `DEFAULT_AYANAMSHA` reuse matching the other four L3 service wrappers in the same file) and is textually mergeable — it is blocked only by one failing named CI check (`Unit Tests`, under `CI — Ganga Quality Gate`), which fails on `BEYOND_ACARYA_ACCEPTANCE_v4→v5.json` receipt/digest divergence and `tests/pariprashna/route_ports/baseline/*` golden-stream hash divergence, both Pūrṇa-owned artifacts explicitly out of scope for this PR and this audit to touch. What must land before dispatch is safe: either (a) the Pūrṇa-owned baseline regeneration lands (on its own track, by its own owner) so `Unit Tests` goes green and #2695 can merge as-is, or (b) native/governance grants an explicit, scoped override to merge #2695 despite that one unrelated failing check — but either way, #2695's own two fixes should land before any further `dispatch_frozen_rebuild.py` run is trusted for provenance, and the dasha-eligibility ayanamsha default should not be relied on until then.
