# Madhav data plane — L3 Kāla elevation plan

## 1. Recommendation and decision delta

Elevate Kāla as the temporal expression of the same qualified structures accepted
from Bodha. Preserve numerical and scholarly capital, expose the data distinctions
that current consumers flatten, and reduce avoidable computation before scheduling
large rebuilds. Every asset packet must change or justify its actual data and use;
adding a contract wrapper or passing a synthetic slice is insufficient.

This is the approved L3 strategy; execution authority is bounded by the paired
DP-SD-017 brief. Historical L3 proposals, receipts and
code fixes retain their bounded meaning. Product v3.0, DP-SD-009, the accepted
L0–L2 contracts and the frozen WriterBase remain the authority hierarchy. The
previous uncommitted L3 drafts in worktree `0ee2` remain research sources. This
proposal does not change their historical status or adopt an old six-view design.

The first audit's broad direction is retained, with these material corrections:

| Earlier recommendation | Revised recommendation and reason |
|---|---|
| A portfolio inventory and common L3 generation contract | Add field-by-field producer coverage, real row transformations, input-use proofs and data acceptance for each asset. Generation correctness alone does not prove semantic elevation. |
| An illustrative largely linear L3 sequence | Use the source-derived computational DAG, resolve undeclared/dynamic edges, and distinguish shared services from similarly named materializers. Taranga does not consume Avadhi; Darshana does not consume Kalasutra. |
| Kshetra and century builds are expensive separate work | Study and redesign their computation before expensive rebuilds. Preserve complete qualified coverage and expose remaining search gaps. A hold is a disposition, not an elevated expensive asset. |
| `PRODUCER_READY` as the execution terminal | Keep it as an intermediate deliverable. The user's eventual complete-layer objective also requires accepted physical data in a named authorized environment, coherent publication and consumer proof. These later stages require the corresponding execution authority. |
| One structure-time slice as the main proof | Use that slice to establish the path, then propagate and prove every applicable asset contract; add a real source-qualified positive route and ordinary/rare/negative cases. The accepted Bhavat fixture remains engineering-only. |
| Approximately 1.5–2.5 times L2 effort | Withdraw the numerical estimate as unmeasured. L3 has additional semantic and temporal dimensions; total effort remains unmeasured pending per-packet estimates and representative benchmarks. |

For every material field, the asset dossier must identify the actual producer
column/path, data type, unit, cardinality, natural key, null semantics, context,
qualification, transformation, persistence, receiving operator and falsifying
test. Classify the gap as missing, computed-but-discarded, persisted-but-unused,
flattened, unqualified, stale or unserved. A fetched or cited field with no
declared effect has not met the use contract. An effect can change eligibility,
uncertainty or explanation without changing a score.

The accepted L2 contract and engineering slice are available. Their complete
shape must not be assumed present on every legacy output row. Build a
producer-coverage map against immutable snapshots: some L2 fields are physically
emitted, some need deterministic hydration across rows, and some may remain
unqualified/unavailable. Any new upstream factual/source requirement returns to
its owner as a bounded amendment; it is not fabricated in L3.

The connected-database check reinforces this distinction: the inspected L1/L2
generation-head relations are absent there, six core L3 output/snapshot tables
have zero rows for the governed chart, and 79 predicate signal IDs do not join
to current same-chart MSR. Other L3 tables contain substantial data. These are
bounded current-schema/count observations, not a deployment certification or
revocation of prior producer acceptance; details and denominators are in the
review record §2.1. Resolve physical upstream generation and reference integrity
before using that connection for an elevated L3 rebuild.

## 4. Dependency and data-readiness rules

Maintain two related maps: the computational build DAG and the semantic
relationship/use graph. Only genuine computation prerequisites constrain build
order. Shared definitions, serving hydration, protected evaluation and separately
admitted future artifacts retain their distinct edge types. Bidirectional
investigation does not create a bidirectional forecast-build dependency.

Derive computational edges from registry metadata, writer SQL, views/functions,
helper/service calls, dynamic reads and applicable database relationships.
Record each edge's role, source, generation selector and required coverage.
Compare this graph to `depends_on`; unexplained omissions and cycles prevent
dispatch of the affected packet. Foreign keys also define preservation/cascade
constraints; they are not automatically evidence or computational inputs.

For every asset, execute the following lifecycle in topological order:

1. Accept the required upstream contracts and source implementation.
2. Materialize or select the upstream data in the named authorized environment;
   verify its semantic payload, snapshot identity, coverage, context and content
   digest. A Git SHA or old production row count does not satisfy this step.
3. Bind one compatible transitive dependency vector plus the asset's complete
   partition/substep plan. All input reads use those snapshots, including empty
   generations; no implicit fall-through to mutable `public` rows.
4. Elevate and verify the consumer implementation against those inputs; build
   its candidate data with the caller-owned transaction/savepoint contract.
5. Independently verify exact partitions, row identities, semantic fields,
   lineage, value controls and applicable performance evidence. Resume only
   compatible completed work. A saved checkpoint from another dependency vector
   is rejected or enters an explicitly admitted reuse path.
6. Publish/select the complete compatible generation; downstream eligibility
   opens only after this data acceptance. Recheck compatibility at publication.
   If upstream advances during a long build, retain the old-vector candidate as
   such; never label it current by switching its metadata.
7. On correction, invalidate affected current descendants and caches by actual
   dependency, preserve immutable consumed history, and rebuild only the changed
   closure. A reuse claim requires compatible inputs and identical semantic
   meaning, not an unchanged asset name.

The application may select a compatible dependency set; it need not impose one
global build ID on every layer. A publication manifest/head can point to retained
immutable partitions so publication is atomic without a long AI-spanning
transaction. Reuse existing machinery wherever sufficient. Any proposed change
to WriterBase/orchestrator requires a separately named architecture decision.

Before replacement, inventory transitive FK `CASCADE`/`SET NULL` actions and
non-FK referrers, preserve restorable snapshots and prove rollback. In particular,
the accepted L2 guard deliberately refuses unsafe cross-layer deletion. L3 cannot
silently disable that guard in order to rebuild. `ka_gochara_sweep` remains
retired, snapshot-protected and never rebuildable.

These gates reduce stale-input, partial-publication and repeat-build failures.
They do not guarantee that no calculation, database or infrastructure error can
occur. Cancellation, crash, dependency-change and resume tests must demonstrate
bounded recovery and an honest state.

## 5. Efficient computation without reducing the question

Optimize repeated preparation, scalar inner loops, redundant searches and dense
storage before trading away time resolution or method coverage. Establish
separate cost for a new chart, an unchanged replay, a dependency correction, an
extended horizon and a precise on-demand inquiry.

Use three complementary physical representations when justified:

- Shared reusable astronomical calculation under exact conventions and applicable
  location scope; no per-chart copies of identical global data.
- Chart-specific structural bindings and contacts represented by complete
  intervals, transitions and component evidence where that is lossless.
- Dense samples or exact refinement where the particular operator requires them,
  with explicit coverage/error bounds and recoverable provenance.

Sparse or coarse-to-fine search is acceptable only with an argument for candidate
coverage and an explicit exact-refinement contract. Stations, retrograde
re-entries, tangencies, narrow windows and overlapping boundaries must survive.
Where a bound cannot be established, retain exhaustive computation for that
primitive or mark the unresolved coverage; a top-K cutoff cannot establish that
no window exists. On-demand computation can complete an inquiry but must not make
an incomplete full-horizon asset appear built.

Separate semantics-preserving optimization from semantic/model repair. If the
current method has a defect, the old output is not the unquestioned parity oracle.
Use an independently specified small reference calculation and publish the
intentional semantic/version change. Learned/null-model reductions need their
own statistical proof; fewer simulations, approximate quantiles or fewer years
are not equivalent performance repairs.

Keep the existing complete Swiss-state serialization span. Factor work outside
repeated state-sensitive calls where proven safe; adding threads around a global
lock is not a speedup strategy. Process isolation or a changed lock span is a
separate architecture proposal, not an assumed part of this plan.

### Benchmark contract

For each candidate, record the exact source/dependency/model versions, hardware,
ephemeris files, workload dimensions, cache state, thread settings, storage and
concurrency. Use synthetic non-person cases and a bounded disposable database
first; authorized real-chart builds follow at their own gate.

Measure wall and CPU time, peak RSS, time in Swiss calls/lock, SQL count and
round-trip time, rows/bytes/WAL, serialization cost, checkpoint/recovery cost and
time until the first qualified consumer result. Use repeated matched runs and
report spread; a single run cannot establish a tail percentile.

Baseline/alternative comparisons must preserve the declared scope, methods,
precision and input vector. Test cold, warm, resume, horizon-extension,
upstream-correction, no-window, dense-window and rare-boundary workloads. Prove
geometry/interval parity, exact evidence identities and null semantics; declare
tolerances before measurement. For any intended semantic repair, compare to the
qualified reference as well as the old version and retain the explained delta.

Savings and runtime budgets will be set after the first measured profile. No
specific factor or minutes-per-chart promise is made by this strategic study.
