## bg_concordance

1. **Pillars.** D-SERVICE (it exists to let L2+ synthesis pull chunk pointers by topic×school at query time) and, indirectly, D-GROUNDING (it is the substrate a `sruti` citation would resolve through). It is the right instrument for that job — a deterministic JOIN index is exactly what a chunk-pointer bridge should be — but per plan §5 it is explicitly named as a **built-but-unplugged** instance, so its *role* is correct while its *wiring* is not yet real.
2. **Dependencies.** Declared `depends_on`: `bg_texts`, `bg_text_index`, `bg_reference`, `bg_rules`. Reading `platform/python-sidecar/pipeline/orchestrator/writers/bg_concordance.py`: it reads `reference_topic_tags` (← bg_reference), `classical_text_chunks` filtered on `topic_tag IS NOT NULL` (← bg_texts / bg_text_index, which is the writer that populates `topic_tag`), and `sutravali_rules` (← bg_rules). All four declared dependencies are genuinely read. No mismatch.
3. **Leverage.** The designed consumer is the MCP tool `classical_attribution_lookup` (`platform/src/lib/tools/classical_attribution_lookup.ts`, registered in `platform/src/lib/tools/index.ts` and present in `mcp_tool_registrations.generated.json` / `mcp_surface_profiles.generated.ts`). Its own docstring says: *"classical_attributions, classical_chunks, classical_texts dropped in WS-0. Stub returns empty results. TODO(ws-2): repoint to brahmagyan.texts + bodha_signals citation scaffolds..."* — it unconditionally returns `attributions: []`. This is a textbook built-but-unplugged defect: a registered, described MCP tool reads NOTHING instead of `classical_attributions`, even though bg_concordance computed the answer. Confirms the plan's own citation of this asset as the standing D-SERVICE defect instance.
4. **Grounding.** Not itself an interpretive claim — it is a pointer index (topic_id × school → text_ids/rule_ids), not a graded assertion. It is the *substrate* a future `sruti` grounding_tier would resolve through (per D-GROUNDING's "concordance pointers" language), but it does not carry `grounding_tier` itself and arguably should not — that vocabulary belongs on the consuming interpretive signal, not the index row.
5. **Temporal identity.** N/A — not a temporal engine.
6. **Service.** No live consumer today (see #3 — the stub is a no-op). `target_floor = 721`; `count_sql` is a plain `SELECT count(*)`; `integrity_check_sql` is present and unusually thorough (row-count pins, distinct-topic/school pins, FK-resolution `NOT EXISTS` checks against `classical_text_chunks` and `sutravali_rules`, and a full content-hash pin) — this looks sane and load-bearing, not decorative.
7. **Cost.** Unmeasured — would need runtime instrumentation. No documented build/serve cost figure found in the repo for this writer.
8. **Findings → W2.**
   - **MUST**: none identified — the writer itself is internally consistent and its integrity check is real (not a defect in the data).
   - **NOW** (per plan §5's own explicit instruction): WIRE `classical_attribution_lookup.ts` to read live `classical_attributions` instead of stubbing empty — this is the named work item in plan §5 ("its consumer lands at L2 — disposition here is WIRE, not retire"). Value: closes a confirmed D-SERVICE built-but-unplugged defect on a tool that is already registered and described to callers as functional. Cost: bounded — repoint one TS query function to `classical_attributions`, no new schema.
   - **Pointer-freshness caveat for W2**: `BA_FULL_ASSET_AUDIT_REGISTER_v1_0.md` (historical, not re-verified live here) records `classical_text_chunks` topic-tagging stuck at 3,716/10,651 (35%) with `count(DISTINCT topic_tag) = 361` — which is *consistent* with bg_concordance's own integrity check (`count(DISTINCT topic_id) = 361`, `count(*) = 721` rows across the 4 schools). This is not necessarily a defect — 721/361 may simply be the correct floor for the topics that ARE tagged today — but W2 should confirm live whether `bg_text_index` has since progressed past 35% coverage, since if it has, bg_concordance's floor of 721 is now stale-low and needs a rebuild, not just a wiring fix. Flagged as **NOW** (verification-only, cheap) rather than MUST since I cannot query the live DB from this read-only pass.
   - **NEVER/LATER**: none.

## bg_panchanga

1. **Pillars.** D-TIME centrally (it computes the five classical angas — tithi, vara, yoga, karana, nakshatra — plus timing windows and 9 graha states; this is a foundational temporal-question answerer) and, as a deterministic zero-LLM instrument feeding L1 chart facts, D-GROUNDING-adjacent in the sense that its outputs become `pratyaksa`-tier (instrument-emergent, computational-provenance) facts once consumed downstream. It is the right instrument — swisseph-backed, Drik-parity, explicitly "Zero LLM" per its own description, and the health probe validates it directly against all 5 FORENSIC anchors (vara/yoga/tithi/karana/nakshatra) at the native's exact birth instant.
2. **Dependencies.** `has_writer=false`, `depends_on=[]` — this is a service, not a data writer, so the rubric's dependency question becomes "what does it need to run," and the answer is genuinely nothing upstream in the asset DAG: it's a self-contained swisseph wrapper (`panchang_engine` package). No mismatch to flag since there's nothing declared to contradict.
3. **Leverage — real, multiple consumers confirmed.** `panchang_engine.panchanga_instant` is called directly by: `ga_writers/ga_panchanga_writer.py` (the L1 `ga_panchanga` writer — birth panchāṅga persisted to chart facts), `pipeline/orchestrator/writers/ph_muhurta.py` (L4 muhurta candidate scoring), and `services/ka_muhurta_seva/writer.py` (L3 muhurta seva, with its own FORENSIC AC6 test asserting the 5-anchor match). This is a well-plugged service, not a built-but-unplugged instance — no defect found here.
4. **Grounding.** Not itself an interpretive claim generator — it's a deterministic computation service. Its outputs (angas, graha states) become the `pratyaksa` (instrument-emergent) grounding tier once consumed by an interpretive layer; the service itself correctly carries no `grounding_tier`.
5. **Temporal identity.** Squarely a temporal-identity asset. Question it answers: "what are the five classical angas + timing windows + 9 graha states at a given instant or for a given day (sunrise-based)?" — exposed as two distinct APIs, `panchanga_instant` (exact-moment angas) and `panchanga_day` (sunrise-based angas), which per the module's own comments (`service_probes.py` lines ~145-181) are deliberately NOT duplicates of each other — an F-06 fix specifically hardened the `panchanga_day` probe check because a prior version's `passed: result is not None` couldn't have caught a wrong-day-object bug. As for who arbitrates disagreement: I did not find a dedicated cross-engine temporal arbiter (per plan §5 L3's Temporal Concordance Contract, which is explicitly planned/future work, not yet built) that reconciles `panchanga_instant` vs `panchanga_day` outputs when they'd disagree (e.g., an anga that changes between the exact birth moment and the day's sunrise-anchored value) — today, callers choose one or the other by convention (birth-instant work uses `panchanga_instant`; day-level work uses `panchanga_day`), not through a stored adjudication.
6. **Service.** Real consumers (see #3). `target_floor = null` (correctly — this is a service asset, no row-count floor applies) and `count_sql = null` (also correct for a service). No `integrity_check_sql` (also expected for a service — verification is via `health_probe` instead), and the `health_probe` itself is genuinely specific and load-bearing: pins forensic lat/lon/instant/tz_offset and all 5 expected anga values, checked by `service_probes.py`'s `_probe_panchanga` (dispatched via `probe_type == "panchanga_engine"`... actually confirmed dispatcher handles `"ephemeris_engine"`; the panchanga probe function exists at line ~93 per the grep, `_probe_panchanga`-equivalent — not fully traced function name but the dispatch table and FORENSIC checks are real and match the registry's `health_probe` block exactly).
7. **Cost.** Unmeasured — would need runtime instrumentation. No documented latency/cost figure found for `panchanga_instant`/`panchanga_day` calls in the repo.
8. **Findings → W2.**
   - **MUST**: none found — this looks like one of the healthiest assets in the batch (multiple real consumers, an honestly-scoped probe with a documented self-critique of its own past bug (F-06), explicit zero-LLM discipline).
   - **NOW**: none specific — already strong per D-TIME.
   - **NEVER/LATER**: a formal instant-vs-day cross-check/arbiter for panchanga specifically — LATER, reason: this is exactly the class of work plan §5 L3 scopes to the Temporal Concordance Contract ("one arbiter surface per (domain, range)"); building a bespoke one here would pre-empt that generalized L3 mechanism.

## bg_ephemeris_engine

1. **Pillars.** D-TIME (foundation for all sidereal planetary positions — literally described in its own registry row as "Foundation for all computational Jyotish in MARSYS-JIS") and, transitively, every other pillar depends on it being correct since nearly the entire system's chart math sits on top of it. Right instrument: pinned SHA-256-verified `sepl_18`/`semo_18`/`seas_18` ephemeris files, Lahiri ayanamsha canonical, `MEAN_NODE` convention explicit in its own description — this is exactly the kind of hard-pinned, provenance-locked service a foundational engine should be.
2. **Dependencies.** `has_writer=false`, `depends_on=[]`. As a service, "dependencies" here means what it needs to run (pinned ephemeris data files, verified by SHA-256 in its `health_probe`) rather than upstream assets — nothing to flag as a mismatch since nothing is declared.
3. **Leverage — real, very broad consumer base.** Direct or `panchang_engine`-mediated consumers found across: `routers/ephemeris.py`, `routers/pyhora.py`, `routers/transit_search.py`, `pipeline/orchestrator/writers/ka_gochara.py`, `bg_muhurta_lattice.py`, `bg_sky_calendar.py`, `ka_sangam.py`, `bg_cohort.py`, `ka_vighnakara.py`, `ka_gochara_v3_century_materialize.py`, `bg_ephemeris.py` (the *separate* L0 `ephemeris_daily` materializer — note this is a distinct asset from `bg_ephemeris_engine` and not in this batch, but worth flagging the near-identical naming as a potential source of confusion for anyone auditing "the ephemeris asset"), `pyjhora_adapter/_jhora.py`/`transits.py`, and the full `brahmagyan/ganita/l1_*` L1 writer family (positions, divisionals, dashas). This is unambiguously the most heavily leveraged asset in this batch — no unplugged-consumer concern.
4. **Grounding.** Not interpretive — a raw positional-computation service. Correctly carries no `grounding_tier`; its outputs feed `pratyaksa`-tier facts once interpreted downstream, same as bg_panchanga.
5. **Temporal identity.** The foundational temporal-identity asset: it answers "what is the sidereal longitude of each graha (incl. mean-node Rahu) at a given Julian Day, under Lahiri ayanamsha?" Its `health_probe` pins the exact FORENSIC JD (`2445735.717361111` = 1984-02-05 10:43 IST), `expected_sun_sign=10` (Capricorn/Makara), `expected_mean_node_rahu_sign=2` (Vrishabha), and an `allowed_ephemeris_backends: ["swiss_ephemeris_file"]` allowlist — meaning the probe would catch a silent fallback to a different ephemeris backend (e.g., an algorithmic approximation) if one were substituted. Given its role as THE foundational engine, there is no single "arbiter" above it in L3 the way there might be for competing dasha systems or gochara versions — it is itself the ground truth every other temporal engine measures against, which is architecturally correct (a foundation doesn't need an arbiter; things built on it might disagree with each other, but not with it).
6. **Service.** Extremely well-consumed (see #3). `target_floor = null`, `count_sql = null` — correct for a service. No `integrity_check_sql` — correct; verification is via `health_probe`, which is unusually rigorous here: it pins the SHA-256 of all three ephemeris data files (`sepl_18.se1`, `semo_18.se1`, `seas_18.se1`) directly in the registry row, meaning a corrupted or swapped ephemeris file would be independently detectable.
7. **Cost.** Unmeasured — would need runtime instrumentation. `build_ephemeris_1900_2150.py`'s docstring documents it as a "Stream B bulk ephemeris build runner" (for the separate `bg_ephemeris`/`ephemeris_daily` materialization, ~825,075 rows × 9 bodies per that writer's own docstring) — but that is `bg_ephemeris`'s bulk-build cost, not `bg_ephemeris_engine`'s per-call service cost, and I did not find a per-call latency figure for the engine itself.
8. **Findings → W2.**
   - **MUST**: none found — this is the most rigorously self-verified asset in the batch (file-hash-pinned health probe, explicit backend allowlist, FORENSIC JD/sign pins).
   - **NOW**: none — already strong.
   - **NEVER/LATER**: none. Note for the record only: the naming proximity between `bg_ephemeris_engine` (this service) and `bg_ephemeris` (the separate `ephemeris_daily` bulk-materialization writer, not in this batch) is a minor documentation-hygiene risk worth a one-line disambiguation note in a future asset-registry pass, but is not a functional defect and does not rise to NOW.
