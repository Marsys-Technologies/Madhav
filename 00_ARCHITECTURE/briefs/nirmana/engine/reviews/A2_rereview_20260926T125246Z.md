## C4 — test-bed fidelity. **LANDED, and the causal claim is correct.**

`build_runs.chart_id uuid NOT NULL` is now in the throwaway schema, and the docstring credits the
right fact. I verified the causal claim rather than the wording:

* Production `pg_attribute.attnotnull` for `build_runs.chart_id` = **`t`**; 0 of 769 rows NULL.
* The index really is a **plain** unique index — `CREATE UNIQUE INDEX
  build_runs_one_active_per_chart_idx ON public.build_runs USING btree (chart_id) WHERE (state = ANY
  (ARRAY['planned','running','paused']))`. No `NULLS NOT DISTINCT`. So under it alone, NULL
  `chart_id` values *would* be mutually distinct and several active runs could coexist for a
  "chart" of NULL — at which point `br.chart_id IS NOT DISTINCT FROM s.chart_id` in site 2's CTE
  could fan out across them. The `NOT NULL` is what forecloses that. The implementer's revised
  attribution is right, and it is right for the right reason.

**On "what if a future migration relaxes it":** the test bed would not notice — it hardcodes `NOT
NULL` in its own DDL, so it pins the *assumption* without detecting production drifting away from
it. That is an honest limit of a throwaway-schema test, not a defect in this pass (asserting live
production DDL is outside a packet's reasonable scope), and the docstring now states the dependency
explicitly, which is the thing that makes it reviewable at all. I am recording it as an observation,
not a correction — the shape of a durable fix is a schema-pin guard alongside the existing
`platform/scripts/governance/schema_pin_*` / `check_migration_ledger_vs_production.py` family, which
belongs to a governance lane and not to A2.

## The mock-queue renumbering — **the risky part, and it holds**

This was flagged as the likeliest hiding place for an off-by-one, so I checked it structurally and
then adversarially.

Structurally, the route issues 5 queries on a nothing-to-reap tick — `orphanRuns`,
`stuckCandidates`, `undispatchedRuns`, and the two M-4 `DELETE`s (the `stuckAssets` CTE is skipped
entirely when `trulyStuck` is empty). `noOrphans()` now queues exactly 5. Every test's queue is
balanced against consumption, which matters specifically because I established last pass that
`vi.clearAllMocks()` does **not** drain the `mockResolvedValueOnce` queue in this Vitest.

Each renumbered assertion **positively identifies the statement it indexes** rather than trusting the
index: `calls[2]` is asserted to match `state = 'planned'` + `started_at IS NULL` + `10 minutes`, and
in the first test to match `UPDATE build_runs` + `UPDATE build_run_assets` + `state = 'aborted'` +
`last_error = $1` + `error = $1`. An off-by-one could not pass these silently — it would land on the
wrong SQL and fail the content match. The untouched assertions in describes D and E index `calls[0]`
and `calls[1]`, which M-5's deletion (slot 3) cannot have shifted, and they too match on content.

Adversarially: I ran the mocked suite three times with `--sequence.shuffle`. **12/12 every time.** A
leaked queue entry from an unbalanced test would surface as order-dependent failures; none appeared.
No test passes by consuming a mock meant for another statement.
