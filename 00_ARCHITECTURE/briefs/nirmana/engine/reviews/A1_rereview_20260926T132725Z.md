## The question that decides this verdict: **are light writers timed?**

**Answer: YES. The hypothesized defect does not exist.** I proved this empirically rather than by
reading the diff.

**Mechanism.** `WriterBase.plan_substeps` **default** returns exactly one `SubStep`;
`WriterBase.run_substep` **default** delegates to `self.run(ctx)`. `_drive_substeps` therefore loops
once for a light writer and calls `writer.run_substep(ctx, step)` — and C1's `time.monotonic()`
bracket is around **that** call. The bracket consequently encloses the light writer's entire
`run(ctx)`. Timing a heavy writer's `run_substep` and timing a light writer's `run` are the *same
call site*.

**Empirical proof.** I constructed a genuine light writer (`run()` only, `WriterResult` with **no**
`duration_seconds`, a real `time.sleep(0.25)`) and drove it through the real `_drive_substeps` with
a real clock:

```
plan_substeps default returned 1 substep(s)
rows=500  engine-measured duration=0.2528s
persisted -> duration_seconds=0.2528  rows_per_second=1977.5
```

A writer that self-reports nothing now gets a real duration and a real rate.

**Registry census (all 123 registered writers, by shape):**

| shape | count |
|---|---|
| light (`run()` only) | **98** |
| heavy (`plan_substeps` + `run_substep`) | 25 |
| implements neither (would raise) | **0** |

Light writers are the overwhelming majority — 98 of 123 — so the question was exactly the right one
to ask. Per layer: bg 34 light/2 heavy · bo 21/2 · ga 5/14 · ka 18/4 · mi 11/3 · ph 9/0.

**Does every writer funnel through `_drive_substeps`?** I traced `run_asset`'s dispatch. Data assets
→ `_run_data_writer`. Service assets **with a registered writer** → `_run_data_writer`. The
probe-fail regenerate path → `_run_data_writer(force=True)`. `_run_data_writer` calls
`_drive_substeps` and nothing else invokes writer code. So yes — both shapes, all six layers.

**Re-derived post-change coverage: coverage no longer depends on the writer at all.** The old
per-layer lottery (bg 30/32, mi 14/14, ka 2/23, ga 1/19, bo 0/24, ph 0/8) is gone as a *concept*,
not merely improved. Every executed sub-step of every writer shape is timed by the engine. **F-1 is
fixed at the root.** This is the right fix, and it is contract-preserving: no writer signature
changed, no writer asked to do anything new.

The residual NULL paths are not writer-shape-dependent — they are enumerated under N-1 below, and
they are the reason one sentence in D-1 is still wrong.

## My judgments on the three questions you asked me to rule on

**Timing boundary — excluding SAVEPOINT/RELEASE is the right call.** The column now explicitly claims
"seconds the orchestrator measured around each `writer.run_substep()` call", and the bracket measures
exactly that. Including the orchestrator's own bookkeeping would attribute engine overhead to the
writer. It does mean the figure is *writer-time, not asset-build-time*: it also excludes the
per-substep heartbeat UPDATE and commit, which for a heavy writer with many sub-steps is not nothing,
so a rate derived from it is mildly flattering versus end-to-end. That is acceptable **because the

from `build_run_assets.started_at/ended_at` — which A1's own before-measurement already established
is 100% populated for `state='complete'` — not from this column.

## Findings

### N-1 · MODERATE — D-1 still carries a false coverage absolute, in the sentence that steers the decision

D-1's closing "Note on scale" reads:

> "with the orchestrator now timing writers itself, this legacy path is the ***only*** remaining
> source of NULL rates, so (a) is a materially smaller concession…"

**That is false.** I grepped the whole of `asset_runner.py`: exactly one site writes these columns.
Every other completion path leaves them untouched:

1. **`_run_service_health_probe`** — legacy health-probe service assets (`bg_*` with a `health_probe`
   spec and no registered writer). `SET state='lit', rows_written=0` — no duration. The registry has
   **8** `storage_type='service'` assets.
2. **`_mark_probe_green`** (skip-if-green) — the writer never runs, so no duration.
3. **`_skip_no_delta`** (delta-skip) — same.
4. **The C2 degraded branch** — every asset, in any environment where 1094 has not applied.
5. **A resumable writer whose sub-steps were all already completed** — every step skipped via
   `completed_keys`, duration sums to `0.0` → NULL. Honest, but still a NULL.

Items 2 and 3 are the *common steady-state path*: on a rebuild of an already-built chart most assets
skip and never receive a fresh duration.

This is **the same defect class as F-1** — a coverage absolute asserted without checking the other
paths — now one scale down, and again in the sentence that tilts the native toward option (a). The
correction pass fixed the large overstatement and introduced a smaller one of identical kind. That is
precisely what this gate exists to catch, and it is why this is not a clean ACCEPT.

### N-2 · MODERATE — the degraded branch is correct, but silent

C2 is the right behaviour: a missing column must never be build-fatal. §N.8's *letter* is satisfied —
nothing green is asserted, the column is honestly NULL.

But the **reason** for the NULL is unobservable. An operator seeing NULL cannot distinguish:

- *"this particular build wasn't timed"* (a skip path, or no sub-steps), from
- *"migration 1094 never applied in this environment, so nothing will **ever** be timed."*

The second is a silent, permanent, fleet-wide degradation wearing the first one's clothes. That is
the §N.4 `[[feedback-deploy-migrations-silent-noop]]` hazard reappearing one layer up: the migration
silently does nothing, the code now silently does nothing *about* it, and the deploy reports success.
"We shipped duration tracking" could be true in the code and false in every environment
simultaneously, with nothing anywhere saying so.

**My answer: the absence must be observable.** The probe is already once-per-process, so a single
`logger.warning` on the absent branch (ideally plus an `emit_event`) costs one line per process and
makes a measurement outage visible. §N.8 asks what code path would have to run for a signal to
correctly read false; here the *subsystem-health* signal has no such path at all.

### N-6 · LOW, latent — the presence probe is not schema-qualified

`_duration_columns_present` runs `SELECT 1 FROM information_schema.columns WHERE
table_name='asset_throughput' AND column_name='duration_seconds'` with **no `table_schema` filter**.
I verified it cannot misfire today: only `public.asset_throughput` exists and `search_path` is
`"$user", public`. But in any multi-schema deployment a same-named table in another schema yields a
false `True`, the UPDATE then raises, and you get exactly the build-fatal outcome C2 exists to
prevent. `table_schema = current_schema()`, or `to_regclass`, closes it.

Cache staleness itself I judge **acceptable**: a `False` cached before 1094 applies persists until
process restart (cost: some rows lack a duration for one process lifetime), and the docstring states
plainly that a mid-process schema change is not a supported deploy shape. That is an honest,
documented limit, not a hidden one.
