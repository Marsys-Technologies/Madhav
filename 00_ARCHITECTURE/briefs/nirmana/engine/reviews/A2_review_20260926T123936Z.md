## 7. Regression — **one real one**

### The M-5 resurrection writes a confidently-wrong error onto healthy, in-flight assets.

This is the finding that moves the verdict. M-5's corrected statement is:

```sql
UPDATE build_run_assets bra SET error = $1   -- 'orphan-watchdog: writer never reported back'
FROM build_runs br
WHERE bra.run_id = br.id AND bra.state = 'building' AND br.state = 'running'
  AND br.started_at < NOW() - INTERVAL '30 minutes' AND bra.error IS NULL
```

**It contains no staleness test on the asset.** Its only time predicate is the age of the *run*. So
on any build that has been running longer than 30 minutes, the asset that happens to be building at
that moment is stamped "writer never reported back" — while its writer is reporting back perfectly
well. The route's own header documents that heavy writers heartbeat every ≤15 min precisely so they
are *not* reaped; M-5 stamps them anyway, because it never looks at the heartbeat.

This is not hypothetical, and it is not my inference — **the packet's own site-3 test seeds exactly
this case and asserts the stamp as desired behaviour**: a run started 35 minutes ago, a `building`
asset, and an `asset_throughput` heartbeat **1 minute old**. The test's comment even says the fresh
heartbeat is there to keep the row out of the real stuck-asset reaper. A row with a 1-minute-old
heartbeat is a healthy row. The test pins a false statement about it.

Production evidence that this fires: **156** completed runs exceeded 30 minutes, and across the
history there are assets whose `started_at` is more than 30 minutes after their run's `started_at`
(17 occurrences each for `ph_sankrama`, `mi_pariksha`, `ph_pramana`, `mi_sambandha`, and eight
others — the late waves of a full rebuild). The watchdog ticks every 5 minutes. Every long build will
hit this.

And the text does not go away. `mark_asset_complete` (`asset_runner.py:898`) sets
`state='complete', ended_at=NOW()` and **does not clear `error`**; the `building` transition
(`asset_runner.py:1458`) sets `state='building', started_at=NOW()` and does not clear it either. So
the false stamp survives into a `complete` row — growing exactly the data-integrity anomaly family
the diagnostician already flagged ("7 rows carry BLOCKED text while `state='complete'`"). And
`/api/cockpit/runs/[id]/assets` serves `COALESCE(bra.error, at2.last_error)`, so the cockpit shows
the falsehood next to a live, progressing asset.

Before the fix this statement was inert. After it, the packet whose purpose is *attributable* failure
text starts writing *mis*attributed text onto non-failures. Per the packet's own framing, a
misattributed error is worse than an empty one. The implementer's comment — "will simply no-op on
rows the fix above already handled" — is wrong in the one direction that matters: it does not no-op
on healthy rows, it stamps them.

Mitigating, and why this is not a REJECT: site 2 now covers M-5's genuine cohort properly (with a
real staleness gate, via `classifyStuckCandidate`), so M-5 has no remaining job that is done
correctly elsewhere. The correction is small and bounded.

### Regressions checked and cleared

* **Site 2's join cannot misattribute in production.** I checked what actually guarantees it. The
  index is `UNIQUE ... ON build_runs (chart_id) WHERE state IN ('planned','running','paused')` — a
  plain unique index, so NULL `chart_id` values would be mutually distinct and the join could fan out
  across several active runs. What closes that hole is not the index but a fact the implementer did
  not cite: **`build_runs.chart_id` is `NOT NULL`** in production (0 of 769 rows NULL). Combined, at
  most one `running` run exists per chart, and `br.chart_id IS NOT DISTINCT FROM s.chart_id` can
  resolve to exactly one run. The join is also *stricter* than the pre-existing rescue path
  immediately above it (which omits `br.state='running'` entirely). Verdict: safe — but see C4, the
  test schema does not reproduce the fact that makes it safe.
* **Transactional change from collapsing two statements into one CTE.** Strictly an improvement: the
  run-fail and the asset-abort now succeed or fail together, where before the second could fail
  independently and leave the exact empty-error rows this packet exists to eliminate. Postgres executes a
  data-modifying CTE exactly once and to completion even when the primary query does not read it, and
  the `WHERE run_id IN (SELECT id FROM failed_run)` reference forces the ordering; confirmed
  empirically by the live site-1 test, where both the `queued`→`aborted` and `building`→`error` CTEs
  applied.
* **Do failure counts change?** Yes, in an honest direction: site 1 now terminalizes `building` rows
  to `error` that previously sat in `building` forever, so `build_run_assets` error counts will rise.
  Those rows genuinely belong to a run the engine just declared dead. The response counters
  (`orphan_runs_failed`, `undispatched_runs_failed`) still read the `RETURNING`/`SELECT` row count of
  the run-level CTE and were verified to report 1 and 0 correctly live.
* **The fallback constant is genuinely distinguishable.** It is reachable only when a caller passes
  empty/whitespace text, i.e. `(err as Error).message === ''` from `invokeRunJob` — a narrow,
  nameable case. All three watchdog sites pass module constants that can never be blank, so no
  watchdog row can reach it. It names its own cause rather than asserting a diagnosis, which is the
  §N.7 item 6 shape (honest null over invented judgment). It does not create a new way to be
  uninformative: a run that reports it is reporting a true fact about its exception.

## Corrections

**C1 — BLOCKS MERGE. M-5 must stop stamping healthy assets.**
Either (a) delete M-5 outright — site 2 now covers its real cohort with a genuine staleness gate and
a state transition, which M-5 never had; or (b) add the missing evidence predicate, so it can only
fire where something actually went stale (e.g. `AND EXISTS (SELECT 1 FROM asset_throughput at WHERE
at.chart_id = br.chart_id AND at.asset_id = bra.asset_id AND at.state='building' AND at.last_built_at
< NOW() - INTERVAL '15 minutes')`, plus the same treatment for the `build_substep_progress` signal the
route already trusts elsewhere). (a) is cleaner and I would take it. Whichever is chosen, a row that
is healthy at tick time must come out of the tick with `error IS NULL`.

**C2 — BLOCKS MERGE. The site-3 test must stop asserting the falsehood, and the negative test must
grow the case it is missing.**
The current site-3 test pins "a 35-minute-old run with a 1-minute-old heartbeat gets stamped 'writer
never reported back'" as correct. Invert it: that row must come out untouched. Separately, the §N.8
negative test only exercises a 2-minute-old run — it cannot fail if the code starts writing text to
healthy *long* runs, which is precisely the hole C1 lives in. Add a healthy run older than 30 minutes
with a `building` asset and a fresh heartbeat, and assert `error IS NULL`.

**C3 — BLOCKS acceptance of the packet report as the record (not the code).**
Two statements must be corrected in place before the report is filed: (i) claim 4's "each on the exact
defect it targets" is false for sites 2 and 4 in the literal `git show HEAD` form — record instead
that the isolated form (constants retained, body reverted) is the proof that holds, and that it was
independently re-run and still fails 5/6 on the real defects; (ii) the "fixed a pre-existing mock-leak
defect" claim must be restated as "re-balanced the once-queue to the new query count, a necessary
consequence of collapsing two queries into one" — no leak fix was made, and
`vi.clearAllMocks()`-does-not-drain-the-once-queue remains an open hazard in that file. Also restate
claim 5's test figure as 12,416/3/713 with the 3 attributed to A1's digest regeneration.

**C4 — BLOCKS the A2 after-measurement / packet close (not merge).**
`watchdog_failure_attribution.db.test.ts`'s throwaway schema declares `build_runs.chart_id uuid`
(nullable), while production declares it `NOT NULL`. The docstring claims the schema carries "the real
`build_runs_one_active_per_chart_idx` UNIQUE index (the fact the stuck-asset fix's `build_runs` join
relies on)" — but the index alone does **not** make that join total; the `NOT NULL` does. As written,
the test bed is laxer than production in exactly the dimension the join's safety argument rests on.
Add `NOT NULL` and say so in the docstring.

**C5 — non-blocking findings, carry to A2b / the campaign register.**
(i) Site 2's join cannot reach global assets: 43 `asset_throughput` rows carry `chart_id IS NULL`, and
`br.chart_id IS NOT DISTINCT FROM s.chart_id` can never match them because `build_runs.chart_id` is
`NOT NULL`. A stuck global asset gets its `asset_throughput` row errored and its `build_run_assets`
row left alone — an honest under-reach, but it is not stated anywhere and it is the cohort M-5 was
silently covering.
(ii) `terminalizeFailedRun` narrows behaviour at the three `invokeRunJob` sites: pre-fix the
`build_run_assets` abort ran unconditionally, post-fix it runs only if the `build_runs` row was not
already terminal. If a run is concurrently terminalized between dispatch and the catch block, its
queued asset rows now stay `queued` where they used to become `aborted`. Narrow, but it is a
behaviour change the packet does not name.

C1 and C2 landed — M-5 either removed or gated on real staleness evidence, and the site-3 test

generic "unknown error." Neither is the case: the §N.8 discipline is genuinely present (just not
extended far enough), and the fallback names its own cause honestly. The 295/301 fix itself is
correct, proven, atomic, idempotent, and worth shipping once M-5 is dealt with.
