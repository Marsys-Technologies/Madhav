## R-7 — `table_schema = 'public'`: **adequate. I accept the deviation from my own suggestion.**

I verified the deployment facts rather than reasoning about them:

| fact | value |
|---|---|
| `current_schema()` | `public` |
| `search_path` | `"$user", public` |
| schemas present | `auth`, `nirmana_evidence`, `public` |
| tables named `asset_throughput` | **only** `public.asset_throughput` |

So `'public'` **equals `current_schema()` in this deployment** and the probe is correct today. It is
also a *strict improvement*: it closes precisely the other-schema false positive N-6 named. The idiom
argument is legitimate and the three cited precedents are real.

**It remains weaker in principle, and I want that on the record.** The completion `UPDATE` is
unqualified, so it resolves through `search_path`. The question the probe must answer is therefore
"does the column exist in the schema *this statement will actually hit*" — which `current_schema()`
answers and a literal cannot. A `search_path = tenant, public` deployment holding a column-less
`tenant.asset_throughput` would make the probe answer `True`, the UPDATE raise, and reintroduce the
exact build-fatal outcome C2 exists to prevent.

**On §N.7 item 3:** you are right that it is in the territory, but I ruled last round that item 3 is
specifically about a constant shadowing an **L1-computed value** — a data-authority question.
`'public'` shadows an *environment* fact, so the doctrine does not literally apply. Its underlying
intuition — a reference cannot drift, a constant can — does favour `current_schema()`. Not blocking;
re-bound to the same multi-schema gate it had before.

## R-2 — the warning and event **reach a real operator**. Accept.

- Both fire **only** on the absent branch, inside the `_DURATION_COLUMNS_PRESENT is None` cache guard.
- **Cardinality holds.** There is exactly **one** call site (`asset_runner.py:1348`), and even with
  many the cache guard admits one execution per process.
- **Not an event into a void.** `emit_event` with no `cur` either publishes to the configured pubsub
  topic or prints `[event] {…}` to stdout — the sidecar's live operator surface.
- **No spurious noise.** I confirmed `asset.duration_columns_absent` is *not* in
  `DEFAULT_DURABLE_EVENT_TYPES`, so it does not trip `events.py`'s "emitted WITHOUT a cursor" wiring-gap
  warning.
- The warning text names the column and `migration 1094_asset_throughput_duration_seconds.sql`
  explicitly, and distinguishes a fleet-wide outage from an ordinary per-row NULL. That is what N-2
  asked for.

**One honest limit worth recording (not a failure of R-2 as I wrote it):** because `emit_event` is
called **without `cur=`**, the event is not persisted to `orchestrator_event_register`. The signal is
observable **live but not retrospectively** — an operator investigating NULL durations a week later
finds nothing, and the `ORCHESTRATOR_DURABLE_EVENT_TYPES` escape hatch cannot help because durability
also requires a cursor. I asked for a warning "ideally plus an `emit_event`" and got both, so this is
a refinement, not a shortfall.
