## 7. Regression — one real latency cost, one real latent hazard, one seam

**Latency, measured (the report does not quantify it).** One extra query per stats poll, registry-wide.
On the throwaway DB with the real 129-row registry: **8.4 ms**. Against live production through the
cloud-sql-proxy: **80 / 163 / 266 ms** across three runs, against a **~50 ms** baseline round trip
(`SELECT 1`, `SELECT count(*) FROM asset_registry`) — so roughly **+30 to +200 ms of real compute per
poll, per client**. Acceptable for this route, but it is a cost, it was not stated, and it should be.

**The `UNION ALL` hazard is worse than "the test can't see it".** I measured what the mutation the
suite cannot catch actually does *on the real graph*: the `UNION ALL` closure **blew a 512 MB
`temp_file_limit` in 3.1 seconds** on the real 129-asset registry. (This is the same combinatorial
diamond-reconvergence explosion the before-measurement hit with a path-tracking CTE.) So the one
regression the proof is blind to is precisely the one that would take the stats poll down in
production. The current code is right; the guard against it drifting is missing. See correction C-3.

**The two protections do not overlap at their seam.** `await downstreamDependentsViewPresent()` sits
**outside** the local try/catch — it is the `if (…)` condition. If the `information_schema.views`
probe itself throws (a DB blip on a cold process), it escapes to the route-level catch and fails the
whole poll, which is strictly a new failure surface. Mitigations, which is why this is not blocking:
the probe runs **once per process** (proven: the "probes only once across three requests" test goes
red if the cache is removed), nothing is cached on a throw so the next poll retries, and this is
byte-for-byte the pattern B1's `blockedByAssetIdColumnPresent()` already established and this gate
already accepted. Recorded, one-line fix available (move the call inside the `try`).

**Process-lifetime cache ordering, stated for the record:** a process that is already warm when
migration 1096 applies will serve `null` for this field until it recycles. That is honest degradation
(`null`, never `0`), it logs a warning once, and it matches the accepted C-1 precedent. Correct here.

**One schema-qualification inconsistency, non-blocking:** the migration creates the view unqualified
and grants via `current_schema()`, while `viewPresence.ts` probes `table_schema = 'public'`. If the
migrator's `search_path` ever pointed elsewhere, the feature would silently never appear (degrading
to `null` — honest, but permanently inert). Every other migration in this repo assumes `public`, so
this is a note, not a finding.

## The Decision-4 question: is a SQL view plus a test-only BFS a second implementation?

**On the letter: no, and the choice was right.** The view had to be SQL — the stats route cannot hold
the registry in-process for every poll — and a test's independent recomputation is not a second
implementation, it is what makes the first one falsifiable. Calling `plan.ts` from the test would have
been the *worse* choice: it would have proven the two agree by construction while proving neither
correct. The implementer's reading of Decision 4 is sound.

**On the substance: they do not agree, and I measured it.** This is correction C-1.

`transitiveDownstream()` runs over the registry that `runs/route.ts` actually loads, which is
`WHERE is_active = true` — **127** of the 129 rows. The view filters nothing. Running the real
`computeDownstreamClosure()` (via `tsx`, against the real registry export) both ways:

- registry = all 129 rows → **0 disagreements with the view**, all 129 assets. The algorithms are
  genuinely the same closure.
- registry = `is_active = true` only, **which is what production actually feeds it** →
  **13 assets disagree**:

```
bg_ephemeris        plan 35 / view 36      ka_gochara_resonance  plan 30 / view 32
bg_kota_chakra_rings plan 1 / view 2       ka_kota_chakra        plan  0 / view  1
bg_phaladeepika_latta plan 31 / view 32    ka_moorti_nirnaya     plan 27 / view 28
bg_sarvatobhadra_grid plan 31 / view 32    ka_tithi_pravesha     plan  0 / view  1
bg_sky_calendar      plan  0 / view  1     ka_vedha_gochara      plan 30 / view 31
bg_transit_rules     plan 34 / view 36     ga_positions          plan 79 / view 80
bg_vedha_malefic_scale plan 31 / view 32
```

The cause is exactly two rows: `ka_gochara_v3_century_materialize` (`is_active=false`) and
`ka_gochara_sweep` (`is_active=false`, `catalog_status='RETIRED'`). Both are leaves — nothing depends
on them — so they inflate only their ancestors' counts, by 1 or 2.

**Why this is not a rounding error.** `stats/route.ts` loads its own asset list with the *same*
`WHERE is_active = true` filter, so the route ships a count computed over a population its own
response does not contain. And three of the thirteen — `bg_sky_calendar`, `ka_kota_chakra`,
`ka_tithi_pravesha`, all three live, `CURRENT`, `is_active=true` assets the cockpit lists — flip from
**0 to 1**, which is not a quantitative drift but a **change of category**: on a genuine failure the
operator is told *"could affect up to 1 downstream"* where the honest reading, and the one the build
planner would give, is *"no downstream impact"*. The packet built a deliberate, tested distinction
between those two renderings and then fed it a number that crosses the line in the wrong direction
for three assets. `ga_positions`'s headline 80 is likewise 79 by the planner's own reckoning.

"Upper bound" does not cover this. The view's own header defines the quantity as "how many OTHER
assets would need a **rebuild**", and a retired, inactive asset will never be rebuilt by anything.
This is the two-traversals-that-disagree outcome Decision 4 named, arriving through a filter rather
than through a second algorithm.
