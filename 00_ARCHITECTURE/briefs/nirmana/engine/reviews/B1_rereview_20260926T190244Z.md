## 3. C-5(c), the chart-unscoped query — **sound, no leakage** ✓

*(Attack item 2.)*

I went looking for cross-chart leakage and did not find it.

- The second query is restricted to `bra.asset_id = ANY($1)` where `$1` is built from
  `assets.filter(a => a.scope === 'global')` — the registry's own scope column. A `per_chart` asset can
  never enter that list, so no per-chart row from another chart can reach this chart's map.
- What it *can* carry across charts is a **global** asset's disposition — which is correct by construction:
  a global asset has exactly one `asset_throughput` row with `chart_id IS NULL`, shared by every chart's
  cockpit already. The fields carried are an asset_id, an enum and a timestamp. No chart-identifying data
  crosses.
- **C-5(b) gates it**, and this is the part that makes it safe rather than merely harmless: the cross-chart
  row is only trusted when its `ended_at` equals the shared throughput row's `last_built_at` — i.e. only
  when it is *the same write* that produced the row this chart is already reading.
- Measured impact today: **zero**. Of the 1,183 backfill-eligible rows, 1,182 map to `per_chart` assets and
  1 to an id no longer in `asset_registry`; **none** is global-scope (measured 2026-09-26T18:17:34Z).

Ruled: correct, well-bounded, currently inert. Not scope creep — it closes a real asymmetry I named.

## 4. C-5(b), the `ended_at` binding — **sound design, no detector**

*(Attack item 3.)*

The mechanism is right, and better than I expected when I raised it:

- Both writes happen inside one `_mark_asset_error_terminal` transaction, so `NOW()` is identical. A match
  is genuine shared-fact evidence, not a heuristic.
- The comparison is valid: `platform/src/lib/db/client.ts` calls
  `types.setTypeParser(types.builtins.TIMESTAMPTZ, v => v)`, so both sides arrive as **strings**. Had they
  arrived as `Date` objects, `===` would have been false forever and this guard would have been a silent
  kill-switch. It is not.
- It holds in production: of the `(asset, chart)` pairs whose latest run-asset row is a genuine block,
  **10 of 10 match** (measured 2026-09-26T18:49:48Z).
- Does it trade a wrong label for a lost one? Rarely, and honestly. It degrades only when the disposition
  is genuinely from a different attempt than the current throughput row — and in that case a later
  successful build has already moved `asset_throughput` off `error`, so there is no error being mislabelled
  anyway. Losing a stale label is the correct outcome.

**But N4 removed the guard entirely and no test noticed.** C-5(b) has no detector. Smaller stakes than
C-1 — the mechanism is right and measured 10/10 — but it is the same class, and with C-1's proof already
hollow I will not wave a second one through on reasoning alone.
