## 6. Honesty of the report — **this is where the packet falls short**

### F-1 · MATERIAL — the central coverage claim is false

`DECISIONS_FOR_THE_NATIVE.md` D-1 states:

> "**The orchestrator path** — `pipeline/orchestrator/asset_runner.py`. A1 fixed this. **Any asset
> built through the normal Build flow now records a real duration and a real rate.**"

It does not, for most assets. The orchestrator **never times the writer**. `_drive_substeps` only
sums `float(result.duration_seconds or 0.0)` — a value the *writer* self-reports — and
`WriterResult.duration_seconds` defaults to `0.0`, which the guard correctly maps to NULL. There is
no `time.monotonic()` around the `writer.run_substep(ctx, step)` call.

I counted how many registered writers actually set it:

| layer | writers setting `duration_seconds` | `asset_throughput` rows (before-measurement) |
|---|---|---|
| bg (L0) | **30 / 32** | 39 |
| mi (L5) | **14 / 14** | 28 |
| ka (L3) | **2 / 23** | 57 |
| ga (L1) | **1 / 19** | 57 |
| bo (L2) | **0 / 24** | 67 |
| ph (L4) | **0 / 8** | 20 |

Spot-checked and confirmed: `bo_bimba`, `ph_nimitta`, `ga_yoga` all return `WriterResult(...)`
without a duration. So after A1, **every L2 Bodha asset and every L4 Phala asset still writes NULL
through the very orchestrator path the document says was fixed**, as does nearly all of L1 and L3.
Upper bound on post-A1 coverage: roughly **67 of 268 rows (~25%)**; about 201 stay NULL.

The packet's own test file knows this — `_UntimedWriter`'s docstring reads *"This is the common case
today (most of the 129 writers)"*. So the honest fact is recorded in a test docstring while the
document the native will act on states the opposite.

This is not merely cosmetic: **it misframes the decision D-1 asks the native to make.** D-1 presents
the legacy 7-caller path as *the* remaining gap and offers three options about it. It is the
*smaller* gap. The larger one — writers not self-reporting a duration — is also a writer-edit stop
condition under §8(2) and belongs in the same decision, with the same three options.

## 7. Regression — what this packet makes worse

### F-2 · MATERIAL — a new deploy-ordering hazard with build-fatal blast radius

The completion `UPDATE` unconditionally names `duration_seconds = %s`. The column **does not exist
in production** (I verified read-only: only `rows_per_second` is present on `asset_throughput`).
There is no feature flag, no column probe, no fallback. If the sidecar carrying this
`asset_runner.py` reaches production before migration 1094 is *actually applied* — or if the
migration silently no-ops while the deploy reports success, which is the exact hazard CLAUDE.md §N.4
`[[feedback-deploy-migrations-silent-noop]]` names — then **every data-writer completion write raises
`column "duration_seconds" does not exist`, and no asset can complete a build.**

Before A1 the failure mode of this area was "a column reads NULL." After A1 it is "no build
succeeds." That is a real blast-radius increase and it must be gated, not left to the bulk runner.

### F-3 · MODERATE — the migration's own `COMMENT ON` contradicts the code it documents

`COMMENT ON COLUMN asset_throughput.rows_per_second` says the value is NULL when `duration_seconds`
is NULL, zero, *"or the asset produced no rows this run (e.g. a 0-row service-asset health probe)."*
The code does the **exact opposite** — claim 2's entire point is that 0 rows over a positive
duration yields `0.0`, deliberately, as an honest measured zero. The durable DB-level documentation
states the inverse of the behaviour.

Two further inaccuracies in the same comments: (a) both columns are scoped to *"the most recent
SUCCESSFUL build"*, but the code writes them on `final_state` of `dormant` and `incomplete` too —
states the engine explicitly defines as not-success (`incomplete`: *"downstream deps stay blocked
until the plan actually finishes"*); (b) `rows_per_second` is defined as `rows_written /
duration_seconds`, which is false in the no-op-completion case (F-4).

### F-4 · MODERATE — the pin's honest side-effect is an internally contradictory row

**On claim 2's asymmetry, my judgment: `(duration, 0.0)` is correct in principle.** A measured zero
is genuinely different information from an unknown, and §N.8's spirit is that a real detector's real
answer beats a null; nulling it would discard a fact the engine actually measured. For a
`target_floor=0` asset like `ga_prashna` that legitimately writes nothing, "ran 0.4s, wrote 0 rows,
0 rows/sec" is the honest and useful record. I would keep it.

**But it is applied without a discriminator in the one case claim 3 was built to protect.** In the
no-op-completion promotion branch the row is written with `rows_written = present` (say 50,000)
while `rows_per_second` was computed from the pre-promotion count of 0. The persisted row then reads
*50,000 rows at 0.0 rows/sec over 0.2s*, and `rows_written / duration_seconds ≠ rows_per_second`.
The packet was right to refuse the inflated rate and right to keep the promotion — but a third
option went unexercised: NULL the rate when reclassification changes `rows_written`, which is the
honest "this run's rate is not comparable to this row's count." Nothing flags the divergence.

Mitigating: **zero consumers today.** I grepped `platform/src` — no TypeScript reads
`rows_per_second` at all. So no dashboard lies today; this is latent, not live. That is why it binds
to the first consumer rather than to this commit.

Note also an inconsistency worth a decision: a healthy `skip_no_delta` leaves duration untouched
(retains the prior build's value), while a healthy 0-row build writes `0.0`. Two "healthy did-no-work"
outcomes are signalled two different ways.

## Verdict: **ACCEPT_WITH_CORRECTIONS**

**Why not REJECT.** The proof ran, could have failed, and passed — reproduced to the number. The
frozen contract is intact. The migration is correctly numbered, idempotent, unapplied and unedited.
No signal is green without a detector: the columns read NULL, honestly, wherever nothing measured
them. And claim 3 — the thing most likely to have hidden a fabricated number — is genuinely correct
in the code, not just in the report. Every figure I could re-run reproduced except one caller count.

**Why not plain ACCEPT.** The native-facing decision document asserts a coverage claim that is false
and, on the strength of it, misframes the decision the native is being asked to make. That is the
"report overstates" condition. It is a documentation defect sitting on top of correct code — fixable
without touching the implementation — which is why it binds as a correction rather than flipping the
verdict. **Had the code itself claimed that coverage, this would be a REJECT.**
