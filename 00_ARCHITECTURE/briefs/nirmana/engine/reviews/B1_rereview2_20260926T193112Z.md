## 2. The `tp.state === 'error'` gate — **right semantic, and the deviation was the right call**

*(Attack item 2. The coordinator asked me to rule on a deviation from its own instruction.)*

**The deviation was correct and I would have called the unconditional pass-through a defect.** Measured
live at 19:25:03Z, `asset_throughput` holds exactly **two** rows carrying `last_error` on a non-`error`
state:

| asset | state | consequence of a blind pass-through |
|---|---|---|
| `bg_transit_engine` | `lit` | would flip a healthy asset to **`error`** — a real, user-visible regression |
| `ga_dashas` | `incomplete` | no badge change (`deriveState` returns `incomplete` before the error block) |

So the implementer's "exactly one row" is exact **as scoped to `state='lit'`**, which is the scope that
matters. There is a second stale-text row it did not mention (C-2 below).

The semantic is right on its own merits, independent of the count. `asset_throughput.state` is the
authoritative computed column; `last_error` is a diagnostic column that success paths demonstrably forget
to clear — the same family as the 7 anomalous `state='complete'`-with-`BLOCKED:`-text rows this packet
already protects, and as A2b-5. Reading the text without the state is re-deriving a verdict from stale
narration, which is exactly what §N.7 item 1 and §N.8 forbid. Checking production before choosing, rather
than following the instruction into a regression, is the behaviour this gate exists to reward.

**On the stated limit** ("the gate can rarely hide a genuine `count_sql` failure if `tp.state` is `'error'`
for an unrelated reason"): I could not find that limit written anywhere in the code, and **I could not
construct the scenario**. A genuine `count_sql` failure is caught by `fetchAllCounts`' own `catch`, which
sets its own `error` message and is not touched by `errorFromThroughput`. The limit appears over-cautious
rather than real. If it is real, it is not evidenced, and an unevidenced limit is its own small §N.8
problem — see C-5.

**Is `bg_transit_engine` a reason to gate, or a separate defect?** Both, and the second half must not be
lost behind the first. A never-cleared `last_error` on a healthy asset is the A2b-5 family. The gate makes
it harmless *to this surface*; it does not make it correct, and if it is only ever recorded as "the reason
we gate," nobody will ever fix it. Bound in C-2.

## 4. R-6 — AtlasView's guard is real; the AssetProgressBar refusal does not survive contact

*(Attack item 4.)*

**AtlasView: verified.** R6a (a fake `'quarantined'` member) produces exactly **3 real `tsc` errors**, one
per switch. Not theatre.

**The refusal I am overruling, on evidence rather than principle.** The argument is that `effectiveState`
is `sseState ?? state`, `sseState` is an untyped SSE-payload string, and casting would be type theatre.
The reasoning is good — but two measured facts undercut it:

1. **No caller anywhere passes `sseState`.** I grepped all of `platform/src`: the prop is declared on
   `AssetProgressBarProps` and never supplied. (The only other `sseState` is a separate parameter of
   `buildStage.ts`'s own function.) So `effectiveState` is **always** `state`, which `AssetRow` passes as
   the server-typed `derivedState`. The untyped boundary the refusal rests on has zero live callers.
2. **Two typed `AssetState` values are unmapped in `SEG` right now:** `partial` and `incomplete`. `SEG` has
   `lit, service_ok, building, stale, error, service_down, dormant, blocked, not_migrated, reconnecting,
   retired` — and `AssetRow` passes `derivedState` straight in, so both of those states silently render
   **dormant** styling in production today. That is the same defect the packet's own comment says it exists
   to remove, two entries away from the one it fixed, and the assessment walked past it.

A non-theatrical check exists and would have caught all three: keep `SEG: Record<string, …>` for the
runtime lookup and add a compile-time witness, `const _exhaustive: Record<AssetState, SegmentColors> = SEG`.
That verifies something real — every *typed* state has a mapping — while leaving the runtime fallback to
handle genuinely untyped input. It would fail to compile today, which is the point.

The dev-only `console.warn` is a net improvement over silence but does nothing in production and nothing at
compile time. **This is pre-existing, B1 mapped `blocked` correctly, and it does not block.** Bound in C-3.
