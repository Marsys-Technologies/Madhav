## §7 — The after-figure: **not an honest pair as framed**

The before (100%) is measured from production records — real instrument, real population of 8 runs,
re-derivable SQL. The after (2/10 = 20%) is asserted inside a pytest fixture with a hand-built
10-asset plan and a fake cursor. Different instrument, different population, synthetic subject.

It is worse than a generic apples-to-oranges concern, and the evidence is in the test's own log
stream. **The headline test passes while the very `execute_run` it drives ends by declaring
`run run-1 failed with 10 failed/blocked asset(s)`.** The fake cursor does not answer
`SELECT asset_id, state FROM build_run_assets WHERE run_id = %s` (it falls through to the `else`
branch), so `_reconcile_failed_assets_from_db` sees every asset in a non-terminal state and
reconciles all ten to failed. The "2/10" is read off the test's own in-memory `state` dict, never off
the engine's accounting.

**What is nonetheless genuinely proven — and it is the substantive win:** 8 of 10 writers actually
executed, where before **zero** executed in any of the 8 production runs. That is the real claim and
it holds.

**The honest framing, which the report should use:**

> Before, in production: all 8 runs lost 100% of their plan; in the worst case 10 of 10 L0 writers
> never ran. After, in a unit-level reconstruction of that run: 8 of 10 writers execute and commit,
> and 2 of 10 (the diverged asset plus its dependent) fail. The run itself still reports `failed`,
> correctly. **The production after-figure is unmeasured and will remain so until a real divergence
> occurs post-deploy.**

One thing the fixture artefact does *not* hide: I traced the real rollup.
`final_state = "failed" if failed_assets else "completed"` (runner.py:1281) means a narrowed run
still reports `failed` in production. **A3 does not turn a partially-failed run green.** That is the
correct behaviour and it survives the change.

## §8 — Regression: what this packet made worse

### The deferred terminal write — **a divergence can be detected and then never recorded**

I judged this by probe, not by argument. `_WRITER_GAP_MODE` defaults to **`"enforce"`**
(runner.py:165), and the writer-gap block (1143–1160) sits *between* divergence detection and
`claim_runnable_run`. On a gap it calls `mark_run_state(failed)` and `sys.exit(1)` — terminalizing
no asset row at all.

I wrote a throwaway probe against the packet's own harness (in my scratchpad, not the repo): inject
a writer gap alongside a genuine divergence, then record every `UPDATE build_run_assets SET
state='error'`. Result: `SystemExit(1)`, and **`writes == {}`** — the assertion passed. The run ends
`failed`, every `build_run_assets` row stays `queued`, and the only trace of the divergence is one
`logger.error` line. Under HEAD this was impossible: the check raised *before* the writer-gap block,
so `_terminalize_preflight_failure` always stamped a reason onto every queued row.

Narrow (it needs a concurrent writer gap) but real, and it is precisely the defect class packet A2
just closed one file over. **This is C-1.**

On the crash question the brief asked: between the claim and the write, a process death leaves the
run `'running'` with the divergence unrecorded. Because `claim_runnable_run` requires `'planned'`,
no retry can double-write — so the write is **at-most-once, not exactly-once**. The exposure is no
worse than the pre-existing claim→execute window, so I do not block on it; but the comment should
not claim more than the code delivers (**C-4**).

### `asset_throughput` is now written where it previously was not — accepted, worth stating

Under HEAD a preflight abort touched `asset_throughput` not at all. A3 now sets the diverged asset's
row to `state='error', last_built_at=NOW()`. If the divergence is a transient false positive — and
the before-measurement found **both** witnessed incidents were transient — this downgrades a
possibly-`lit` asset to red in the cockpit and stomps its `last_built_at`, which
`asset_runner.py:258-266` consults for delta/freshness. I am **not** treating this as a correction:
it is the file's established loud-over-silent convention (`_mark_asset_blocked` has always done
exactly this to blocked dependents), and the predicate fix targets the very false-positive source
that would trigger it. But it is the honest answer to "which dashboard now lies in a different
direction," and it belongs in the report.

### State class changed for this family: `aborted` → `error`

Registry divergences previously landed as `state='aborted'` (the watchdog's own convention at
route.ts:138 — *"'queued' rows (never got a chance) -> 'aborted'"*); they now land as `'error'`.
`AssetNode.tsx` treats these as distinct. Monitoring that greps the message is unaffected (the
before-measurement's own query is state-agnostic and still matches); monitoring that filters on
`state='aborted'` will stop seeing this family. Minor, defensible, but undocumented.

### Checked and clear

- New event `run.registry_divergence_narrowed` is outside `DEFAULT_DURABLE_EVENT_TYPES`, so it
  raises no "emitted without a cursor" warning and adds no register load. No constraint on
  `build_events.type` to violate. Log/pubsub-only, consistent with the other `run.*` events; the
  divergence remains DB-observable via `build_run_assets.error`.
- No new latency; no widened blast radius; commits are safe against the session-level advisory lock.
- An all-diverged plan degrades to the old whole-run failure, with better per-asset attribution.
- A diverged asset that is also skip-if-complete ends up in both `completed` and `failed`;
  `execute_dag` checks `failed` first, so dependents block. Conservative, correct.

## §9 — Corrections, each bound to the gate it blocks

**C-1 — BLOCKS the A3 commit.** Close the writer-gap swallow. A detected divergence must not be able
to vanish from the database. Cheapest correct fix: move `_verify_registry_still_matches_manifest`
to *after* the writer-gap block, so no terminal exit sits between detection and the claim. Failing
that, record the divergence on the `exit(1)` path. **Evidence it is real:** the probe in §8 —
`SystemExit(1)` with `writes == {}`. **Gate:** re-run that probe; it must now fail.

**C-2 — BLOCKS the packet report and its campaign EVENTS entry (not the code).** Replace the bare
"2/10 = 20% after" with the framing in §7, naming population and instrument for each side, stating
that the run-level rollup in the fixture reports 10/10 failed because the fake cursor does not
answer the reconcile query, and stating that the production after-figure is unmeasured. **Gate:** the
report may not carry a 20% figure without that sentence attached.

**C-3 — BLOCKS the next packet that touches `_mark_asset_error_terminal`.** Add a test that fails
when the helper's `asset_throughput` upsert or its `asset.state_change` emission is removed, for
both callers. **Evidence:** mutation M5 deleted both upsert branches outright and 21/21 tests stayed
green. **Gate:** re-run M5; it must go red. Not blocking A3's own commit — the refactor is
behaviourally identical by textual comparison — but the shared helper must not go one more packet
without a detector.

**C-4 — BLOCKS the A3 commit (one comment edit).** runner.py:1119 says the write is "safe exactly
once" and enumerates only `exit(3)`/defer paths. Both are wrong. State at-most-once, and name the
`exit(1)` writer-gap path. A comment that misdescribes its own failure window is how C-1 stayed
invisible.
