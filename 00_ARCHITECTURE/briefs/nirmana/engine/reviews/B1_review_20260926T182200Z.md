## 2. The frozen contract is intact — **PASS**, with one wording correction

No `WriterBase` signature changed. No writer is asked to do anything new. `ctx.db_conn` is untouched.
`asset_throughput` is still written only from the engine's own terminal helper, not from a writer.

`_mark_asset_error_terminal` gained two **keyword-only** params with `None` defaults; both existing
callers pass neither, so their call sites are untouched. There is one real behavioural delta, and the
implementer's docstring understates it: the UPDATE now writes `disposition=NULL` **unconditionally**,
where before it left the column alone. "disposition stays NULL" should read "is set to NULL".

I checked whether that can destroy a disposition someone else wrote. It cannot. The only other writers
of `build_run_assets.disposition` are `asset_runner.py:1065` (`skip_no_delta`) and `:1370` (`build`),

execute **before** `_schedule_parallel` — every row is still `queued` with `disposition` NULL at that
point. And a blocked asset is by construction one that never ran, so it can never have been marked
`build`/`skip_no_delta` first. Unreachable as a difference. Existing callers' behaviour is unchanged
in effect.

Both `_block` call sites in `execute_dag` (lines 695, 715) are genuine: a dep in `failed`, and the
deadlock sweep over unsatisfiable deps. Both pass real asset ids drawn from `deps_of` — no fabricated
names remain anywhere.

# Corrections

### C-1 — BLOCKS the deploy that ships this code
`route.ts` unconditionally selects `bra.blocked_by_asset_id`. That column does not exist in production
(verified: `information_schema.columns` returns only `disposition` for `build_run_assets`). If the app
deploys before 1095 applies, the query throws, the **outer** `catch` in `GET` swallows it, and the route
returns `data: { assets: [] }` with **HTTP 200** — the entire cockpit reads as zero assets, for every
chart, with a 200. Not a degraded surface; a blank one that looks successful.

This is not hypothetical here. Migrations **1092, 1093, 1094** exist in the tree and are **absent from
`_migrations_applied`** (highest applied: 1079, 2026-09-23). I confirmed the objects are genuinely
missing — `to_regclass('kala_convergence_episodes')` is NULL and `asset_throughput.duration_seconds`
does not exist. There is a live 3-migration backlog on this database, so "the deploy applies it" is
currently false in observable fact.

**Fix:** wrap the disposition query in its own `try/catch` that degrades to an empty map (the packet's
whole design already tolerates a NULL disposition — it falls back to `'error'`, i.e. today's behaviour),
**or** gate the deploy on verified application of 1095. CLAUDE.md §N.4 as re-scoped by DVA Ruling 58
names this exact hazard: the danger was never bulk migration, it was *migrations silently doing nothing
while the deploy reports success.* Here the deploy would report success while the cockpit went blank.

### C-2 — BLOCKS quoting "four surfaces fixed for free" anywhere downstream
Three sub-corrections. The outcome for the three named surfaces is correct; the *claim* is not.

**(a) `CockpitHeader` does not filter on `state === 'error'`.** It has no such filter. It receives
`errorCount` as a prop, computed in `CockpitShell.tsx:149`. Same correct result, wrong stated mechanism —
and the wrong mechanism is what a future reader would rely on. `LayerPanel.tsx:135` genuinely does read
`stats.get(id)?.state`, and `CockpitShell`'s `assetStates` genuinely trace to the server-derived state via
`DataAssetsView`'s `onAssetsReady`. Two of three verified as described; restate the third.

**(b) The before-measurement's seven-surface census is wrong in both directions.** It named
`AssetNode.tsx` (dead — see §5) and missed at least these live ones:

- **`AgentsView.tsx:106`** — `runAssets.filter(ra => ra.state === 'error')`. Reads the **raw**
  `build_run_assets.state` through `useActiveRun`, never the derived value. A blocked dependent still
  appears under "Errors" here, completely unchanged by this packet. This is the live surface the packet
  should have named in place of the dead one it did name.
- **`AtlasView.tsx:475`** — reads derived stats, so a blocked asset no longer counts red; but it falls
  to the `else` and is binned **grey** (the "no stat at all" bucket), not amber. And its own mirrored
  union at `AtlasView.tsx:14`, carrying the comment *"Mirrors AssetState in
  src/app/api/cockpit/stats/deriveState.ts — keep in step"*, was **not** updated — while the identical
  mirror in `LiveDependencyGraph.tsx` was. `tsc` does not catch it because the stats fetch is `r.json()`.
  One of two sibling mirrors fixed.
- **`AssetProgressBar.tsx:145`** — `const c = SEG[effectiveState] ?? SEG.dormant`. `'blocked'` is
  unmapped and silently renders with dormant styling. This is precisely the anti-pattern
  `AssetNode.tsx`'s own docstring warns about: *"The fallback is a crash guard, NOT a licence to leave a
  known state unmapped."* The packet quoted that discipline while introducing a new instance of it.

**(c)** Restate the headline as what it actually is: *one derived-state change propagates correctly to
every consumer that reads `AssetStats.state`; consumers that read raw DB state (`AgentsView`) or that
enumerate states exhaustively (`AssetProgressBar`, `AtlasView`) are not covered and were not checked.*

### C-3 — BLOCKS B2 (which the campaign sequences onto these same surfaces)
`AssetRow.tsx` is the **live** surface and its blocked branch has **no test**.
`AssetRow_CockpitPolishR2.test.tsx` contains zero occurrences of "blocked". The packet replaced a
working classifier with a structurally better one on the only surface an operator actually looks at, and
proved it one layer below, at `deriveState`. §N.7 item 5: a verified fact is not a verified sentence; the
narration layer that assembles a verdict from facts needs its own test. Add one before B1's surfaces are
built on.

### C-4 — BLOCKS using the census as an acceptance gate for a new or never-built asset
`_grade_build_history` returns PASS for `complete == 0` with an all-cascade history (R-1 above; probe
output quoted there). Guard on `h['complete'] == 0` — a distinct verdict, or PARTIAL — before the census
is trusted for a freshly-added downstream asset. Today: 0 assets affected, so this blocks nothing now.

### C-5 — BLOCKS nothing; fix opportunistically
**(a)** The `dispositionMap` query's `ORDER BY bra.asset_id, br.created_at DESC` has no tiebreaker. Two
runs sharing `created_at` resolve nondeterministically. §N.7 item 2 requires a **total** `ORDER BY`
wherever a set is reduced to one row. Add `, bra.run_id DESC`.
**(b)** The disposition is bound to *the chart's latest run*, while `error` comes from
`asset_throughput.last_error`, which is bound to no run at all. Nothing ties the two to the same event,
so a stale `blocked_dependency` can colour an error written later by a non-run path. Narrow, but this
packet's entire thesis is *don't re-derive a classification from evidence that isn't the fact you cited.*
**(c)** Scope asymmetry, currently zero-impact: `throughputMap` handles `chart_id = $1 OR chart_id IS
NULL`; `dispositionMap` handles only `br.chart_id = $1`, despite the comment claiming it mirrors the
former. Harmless today — all 762 `build_runs` rows have a non-NULL `chart_id` and all 1,183 eligible rows
map to `per_chart` assets, zero to `global` — but a global-scope asset's `asset_throughput` row is
chart-independent while its disposition is not, so the same asset could read amber on one chart and red
on another.

### C-6 — record only, no gate
`build_history`'s `d[state] = d.get(state, 0) + 1` shares a key namespace with the disposition counters.
`d['skipped']` **already** collides with the permitted state `'skipped'` (pre-existing, not B1's).
B1's new `d['blocked']` is safe *only because* Decision 1 declined to add a `'blocked'` state value —
verified: the CHECK permits `queued/building/complete/skipped/error/aborted` and nothing else. If a later
packet ever adds one, `genuine_error = error - blocked` silently double-counts and goes wrong. Record the
coupling next to Decision 1, so the reason not to add the state is preserved along with the decision.
