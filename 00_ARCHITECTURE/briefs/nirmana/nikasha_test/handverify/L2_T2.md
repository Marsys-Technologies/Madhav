## DISAGREE reproductions

### 1. Build.completion — all 8 sampled assets (census internally inconsistent)

Census: `N/A, "no count_sql; build state='lit|stale'"` for 7 assets; `PASS, "rows_written=1, live=0"` for bo_samvada.

Reproduction:
```
SELECT asset_id, count_sql IS NOT NULL FROM asset_registry WHERE asset_id IN (...8 ids...);
-- count_sql IS NOT NULL = true for ALL 8 (see count_sql values, e.g.
-- bo_anveshana: SELECT (SELECT count(*) FROM bodha_discoveries WHERE chart_id=$1) + ... ;
-- bo_samvada:  SELECT 0 AS count).
```
So the stated precondition "no count_sql" is **false** for all 7 N/A assets — and contradicts the census's own
Build.count_integrity ("count_sql=yes") on the same assets. Separately, `build_run_assets` has no `rows_written`
column at all (`\d build_run_assets`), so the protocol's completion comparison (rows_written vs live) is only possible
via `asset_throughput.rows_written`; for bo_samvada that gives rows_written=1 vs count_sql-live=0 — a mismatch the
census nonetheless scored PASS.

### 2. Build.dep_liveness — bo_anveshana, bo_samvada, bo_pramana_mapa, bo_yantra_mechanism (measured string false)

Census measured: "all declared dependencies are lit".

Reproduction:
```
SELECT d.asset_id, d.dep, t.state FROM (
  SELECT a.asset_id, unnest(a.depends_on) dep FROM asset_registry a WHERE a.asset_id IN (...)) d
LEFT JOIN (SELECT DISTINCT ON (asset_id) asset_id, state FROM asset_throughput
           ORDER BY asset_id, last_built_at DESC NULLS LAST) t ON t.asset_id = d.dep;
-- bo_anveshana:     bo_drishti = stale
-- bo_pramana_mapa:  bo_anveshana = stale, bo_drishti = stale, bo_upaya = stale
-- bo_samvada:       bo_pramana_mapa = stale, bo_upaya = stale
-- bo_yantra_mechanism: bo_cgm_motifs = stale, bo_cgm_paths = stale
```
"All lit" is literally false for these 4. The PASS verdict is defensible only under the protocol's weaker
"lit-reachable / has_writer exists" reading (stale implies previously lit). Recorded as evidence DISAGREE, not a
verdict false-positive.

### 3. Idem.pattern — bo_samvada (measured string false)

Census measured: "no idempotency pattern in the writer's own SQL — it likely delegates; verify there".

Reproduction: `platform/python-sidecar/pipeline/orchestrator/writers/bo_samvada.py` — the writer contains no write SQL
at all; `run()` only logs and returns `WriterResult(rows_inserted=0, rows_skipped=1)` ("legacy serving projection
preserved"). There is nothing delegated to a seeder. PARTIAL verdict is arguably still apt, but the delegation claim
is wrong.
