It remains the right instrument: a chart-agnostic, versioned ontology table is exactly what a shared taxonomy should be, and it is heavily consumed (below).
2. **Dependencies.** Registry declares `depends_on: []`. Writer (`writers/bg_ghatana.py`) delegates entirely to `brahmagyan.l0_ghatana.seed_ghatana()`, which contains no `SELECT ... FROM` beyond an `information_schema.tables` existence probe — no other asset's data is read. Declared and real dependencies match.
3. **Leverage.** `brahma_event_ontology`/`brahma_activity_ontology` are read by a very large, active consumer set: L3 (`ka_yojaka`, `ka_taranga`, `ka_avadhi`, `ka_gochara_v3_century_materialize`, `gochara_v3/*`, `gochara_grammar/*`, `gochara_intensity/*`), L4 (`ph_muhurta`, `ph_nimitta`, `brahmagyan/phala/muhurta.py`), L5 (`mi_pramana`, `mi_darshana`, `mi_jivanaghatana`), plus TS-side LEL/prediction machinery (`event_classes.ts`, `event_ontology_shapes.ts`, `prospective_ledger.ts`, `lel_event_writer.ts`, `register_d8/d9`, `L5_mimamsa/*`, `L4_phala/*`) and MCP tools (`register_p1_synthesis.ts`, `kala_views/upaya.ts`, `register_gochara_windows.ts`). No evidence of a built-but-unplugged consumer reading NULL in place of this table — it is one of the most heavily leveraged L0 assets in the whole registry.
4. **Grounding.** The ontology rows themselves are a taxonomy (event classes, signature models, matching rules) rather than a per-instance interpretive claim; `citations` is already a stored JSONB field per-row (seen in the integrity-hash column list), so classical grounding is present as data, just not yet expressed as a formal `grounding_tier` enum. Whether the *downstream* firings that use this taxonomy (yoga/dosha, dasha-phala) need `grounding_tier` is a W2/L2+ question, not this asset's.
5. **Temporal identity.** Relevant: the 12 electional-activity classes plus DR-13 temporal-shape/duration_prior fields are consumed directly by muhurta and gochara-timing engines (`ph_muhurta`, `ka_gochara_v3_century_materialize`, `gochara_grammar/*`). The question this asset answers for L3/L4 is "what event/activity class is this, and what temporal shape (duration prior, milestone template) should its timing engine assume?" Arbitration of *disagreements* about timing itself is not this asset's job — it supplies the vocabulary the L3 Temporal Concordance Contract arbiter (per plan §D-TIME) would consume, not the arbiter itself.
6. **Service.** Real, dense consumer set confirmed above. `target_floor=39` (27 events + 12 activities) matches `count_sql` exactly. `integrity_check_sql` is a strict byte-hash over both tables plus row-count checks (27/12) — present and sane.
7. **Cost.** Unmeasured — would need runtime instrumentation. No stored historical build/serve cost figure found in the repo for this asset.
8. **Findings → W2.**
   - NOW: formalize a `grounding_tier` label for the taxonomy's `citations` field if L2+ signal classes start requiring it uniformly (cite D-GROUNDING) — currently not a defect, just an opportunity, and the plan explicitly scopes grounding to ~15–20 interpretive signal classes at L2, not L0 taxonomy rows.
   - NEVER/LATER: no correctness defect found; asset is well-instrumented and heavily leveraged already.
