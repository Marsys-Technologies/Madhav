## §C · The gate list (A8 §3, verbatim; the whole rulebook)

Precedence (A8:7): where this list and any other document disagree, this list governs. **A rule not listed here is NOT binding on any job, lane or session, whatever document still states it, until it is recorded under A3 D-26 with its cost.** Text below is A8:38-61 unchanged.

**Per code change**
1. One branch, one PR. The launcher commits, pushes, opens the PR, merges `main` in once, runs the local pre-flight, and arms auto-merge when the review is ACCEPTED and CI is green (A3 D-24, A7 D-48). Agents never run git writes or `gh`.
2. **One independent review**, reviewer ≠ author, one round, under the owner's testing standard (D-OWNER-TESTS-20261016): the reviewer enumerates the distinct claims, each has one source-cited oracle, each oracle is shown to fail on one planted reversion. A second round only for a BLOCKING finding. Non-blocking findings are posted on the PR; they never create a child item or a second job.
3. **The verdict binds to the diff**, not the head commit: `git patch-id --stable` of `base..head`. A merge from `main` that leaves the patch-id unchanged and merges cleanly inherits the verdict automatically. A rebase with the same patch-id inherits too.
4. **Required CI green** at the PR head: the 16 required checks including Kāla DB Tests and the Earned-Signal Gate (A3 D-22). Markdown and plan-model PRs merge on CI alone (A3 D-25.1). Generated outputs are produced only by CI from `main` (A5 D-33).
5. **DONE = merged + accepted + contained in a successful deploy of `main`** (A7 D-46). Dependencies on other code items close when those are merged and deployed; chain activation is `activation_pending: <gate>`, shown beside DONE, never a step receipt. Operation items are done by their executor receipt.
6. Six jobs per item; the seventh parks the item with a one-line note (A2 D-17.5, without the ruling ceremony).

**Per migration**
7. Additive; number from the allocator; applied in the job's guarded local fixture; protected-class files go through the automated window after merge (A4 D-31) with the GitHub environment approval recorded via API under the surrogate's decision id (A1 D-10); applied-ness is proven by the `verify-migrations-deployed` CI check plus a mechanical `migration_readback`. No post-deploy reviewer job.

**Per production data operation (the executor is the only credential holder)**
8. Read-only kinds need no reviewer and no fence; they are accepted mechanically on COMPLETED (A7 D-44.1). `*_dryrun` kinds are read-only with a credential: rollback proof in the receipt, no acceptance, no fence.
9. Writing kinds (backup, restore proof, teardown, dispatch, protected windows): **one** independent signer (V1) on a fixed checklist, bound to `{operation_id, kind, item_id, args, reviewed_commit, chart_id}` and nothing else, valid until the request bytes it binds change (A7 D-44.2, D-45). No post-receipt verdict, no step verdict, no quiescence review; post-acceptance and quiescence are executor-written mechanical checks.
10. A scoped backup with restore proof before the first data-changing operation of a window, valid until a scope table's content hash changes (measured at dispatch), not on a clock.
11. One coordination lease per production window, taken for the whole window, auto-renewed, checked at execute. The fence is set only for remote-asynchronous kinds (dispatch, century, verification job) and released by the executor's own completion read (`cloudrun_job_readback` SUCCEEDED/FAILED). Synchronous kinds release on receipt.
12. Identities are minted per attempt automatically; a FAILED attempt never needs a preparation job; a lapsed label never needs a new pack version.
13. D-13 order and stop-at-first-failure; D-14 automatic stops (red `main` → HOLD_MERGES; a production failure → HOLD). The small test closes with one clean run (A7 D-49).

**Decisions and records**
14. The surrogate decides everything except the four hard stops, as conditional approvals (A4 D-29); one `ky decide … --delegated --detail` line is the record; the owner may veto after the fact. A new restriction is a recorded decision with its cost or it is not binding (A3 D-26).
15. One owner report a day plus incidents (A5 D-38). One SESSION_OPEN/CLOSE pair with SESSION_LOG and CURRENT_STATE at campaign open and close (`CLAUDE.md` §G/§H). One red-team at macro-phase close.

That is the whole list. Everything below is retired.

## §E · The fast lane is the engine

**One engine (A4 D-28; A4:21-26).** The cockpit's fast lane — `cx.sh` → one Claude job in a working copy → `cx_post.sh` → independent review → merge queue — is the campaign's only model-job engine. The executor, tracker, test cluster, watchdog and launcher are kept and used by the fast lane (A4:25 (g)).

**A job (cx.sh:1-41).** `cx.sh <slug> <worktree> <task.md> [full|locked]` writes `prompt.md` = `COMMON_HEADER` + task into `FAST/jobs/X-<UTC>-<slug>/`, picks the model by slug (§D), and runs `claude -p --model <m> --effort high` in the working copy as a launchd service that survives cockpit restarts (cx.sh:19-40); rate-limit answers retry up to six times with backoff (cx.sh:20-30). The default sandbox mode is `full`; `locked` is only for jobs that change no code or tests (A2 D-18.2, A2:49). The header is `fleet/COMMON_HEADER_v3.md` (A8:97: it names the authority order and the kept rules; the testing standard appears once; no Codex branches).

**The launcher lands the work (A3 D-24, A5 D-34, A7 D-48; §C.1).** When `result.json` says `status: done` with a `commit_message`, `cx_post.sh` — outside the sandbox, as the user — commits the working copy, merges `origin/main` in once, pushes the branch and opens or updates the PR (cx_post.sh:12-49). It refuses on a detached review copy, a protected branch (`main`, `master`, `shared/*`), a FROZEN path in the diff, a job that is not `done`, or no commit message; every outcome is written to `post.json`; a refusal leaves the copy exactly as the agent left it (A3:43-44; cx_post.sh:17-27). A merge conflict is not resolved by the launcher: it aborts, pushes the agent's commit, records `main merged: conflict:<files>` and the cockpit routes a conflict job (A5:47; cx_post.sh:33-38). A held PR is merged up once, when it enters the live set (A7:52); repeated re-merge, re-pin and relabel cycles are retired (§I). The agent never runs git writes or `gh` (A3:43; header "Your box").

**Launch on ready (A4 D-28.4, A5 D-36).** `autolaunch.sh` runs every 10 minutes from launchd (`com.madhav.kalayantra.autolaunch`): for every tracker item `ready` with no live job, no open PR and no launch in the last 24 h it builds the task from the packet on `origin/main` or, absent one, from the plan-model entry itself (title, brief, contract, tests, owns, depends_on) and launches a `full` build job (autolaunch.sh:1-68; A5:57). It skips verdict (`V-*`), decision (`D-*`), owner (`N-*`), join and operation items (autolaunch.sh:26-29); it does nothing under `run/HOLD_AUTOLAUNCH` or when CPU idle < 15 % or free memory < 20 % (autolaunch.sh:14-17; A6:29). Review, acceptance and merge stay with the cockpit (A4:26).

**The cockpit's lane rules.** Merge order is a priority: Wave 4 spine and packages, then items that unblock a `ready` or `review` item, then everything else; small PRs rebase behind the critical path (A5 D-32, A5:35-37). Shared files are not edited per change: tests are discovered by pattern, generated outputs are produced by CI from `main`, plan-model edits ride in their own small PRs (A5 D-33, A5:41-43; §C.4). Review is proportionate: Markdown and plan-model PRs merge on green required checks without a review job; tooling code keeps its one review (A3 D-25, A3:49-51; §C.4). A verdict survives a main-merge by patch-id (A5 D-35 → §C.3). Non-blocking findings are posted on the PR and never fan out into child items or jobs (§C.2; A5 D-37 superseded). Six jobs per item, the seventh parks it (A2 D-17.5 → §C.6). Agents decide and continue: scope lists are footprints, open questions are `(I) INTERPRETATION`, `blocked` is only for a missing tool, a missing input or a severe-risk finding (A3 D-23, A3:37-38). ## §H · Completion and reporting

**Implemented is the headline; activated is tracked beside it (A7 D-46, A7:42-44; §C.5).** A code or artifact item is DONE (implemented) when its code is merged, accepted under criterion v2 and contained in a successful deployment of `main`; its code-verifiable steps are covered by that acceptance, and separate step-receipt agent jobs for code items are abolished. An item whose only open dependency is another item or a chain gate is DONE and carries `activation_pending: <gate>`. The tracker shows **implemented / total** as the headline and **activated / total** beside it; the campaign closes when both are complete. Operation items keep their receipts (the receipt is the operation); decision (D-*) and verdict (V-*) items are unchanged. Strict ordered completion (SR-A4-01) is retired for code items (A7:43). Three lines: Wave 4, everything else, total; scope changes marked on the history chart with time and size. Daily closures split into capability items and verdict/planning items. Velocity = agent-hours per closed item (2026-10-14: about 5.6; target below 2).

**Cadence (A5 D-38, A7 D-50; §C.15).** One owner report a day at 06:00Z with the measured numbers, plus one on any stop, breach or hard-stop event; three reports a day to the owner's analysis session (06:00Z, 12:00Z, 18:00Z) plus incidents; the tracker logs closures continuously; no hourly or per-tick narration (A5:65; A7:60). A report carries no decision ask (A4:31). Measures the owner reads: ceremony share of agent-hours (target under 15 %), reviewer signatures per production write (1), reviewer jobs per read-only operation (0), pack versions per window (1), gate conditions from build to DONE for a code item (8), hand-written briefs (under 20 % of jobs), repeats of any §I item in a brief, template or script (0, a D-26 breach) (A8:103-114).

**Campaign close.** The retained acceptance set (§A) is met; implemented and activated are both complete (A7:43); one SESSION_OPEN/CLOSE pair with SESSION_LOG and CURRENT_STATE at campaign open and close, validated by `platform/scripts/governance/schema_validator.py` (CLAUDE.md §G/§H; §C.15); one red-team at macro-phase close (§C.15).
