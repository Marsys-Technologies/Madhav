# V5 small test — teardown runbook

## 1. Run it within 90 days of the small test
The cockpit watchdog deletes terminal build runs (completed, failed, stopped) 90 days after their creation (`platform/src/app/api/cockpit/watchdog/route.ts`, "M-4"). `asset_provenance_receipts.build_id` is `ON DELETE SET NULL`, so the small test's receipts then carry no run link. The teardown **refuses a receipt with no run link, for good** (a pruned test run and a pruned real run look the same; the Nirmana monitor's rule N-137 reads such a receipt as non-test evidence too). So the clock is: **creation time of the small-test run + 90 days.** The dry run prints each owned run's creation time and the days remaining; the dispatch prints the same deadline when it stages the run. Tear down well inside it.

## 2. Connect DIRECTLY, then run the usual sequence
**Use a DIRECT connection to the database's own host and port. Never a pooler** (PgBouncer or any transaction-mode pooler). The orchestrator exclusion lock is a SESSION advisory lock; through a transaction-mode pooler it silently holds nothing, and the script's other protections lean on it. The script reads `pg_backend_pid()` in three separate transactions and refuses if the backend changes, and checks that the lock is held by the backend running the transaction; that catches a busy pooler but cannot prove a quiet one is absent, so the direct connection is a requirement of this runbook, not only of the code.

1. Dry run (the default; it runs every statement an execution runs, then rolls back, zero commits): `DATABASE_URL=... python3 scripts/teardown_v5_small_test_job.py`. Read the counts and the retention lines.
2. Execute only on steward go: add `--execute --i-am-steward`.
3. Afterwards: the registry row is inert (`is_active = false`, migration-1304 shape), the Nirmana monitor's N-137 end state holds (checked again by the script before it claims success), and nothing of the test remains for the pinned chart and generation `5.0`.
4. If a run ends with "COMMIT OUTCOME UNKNOWN": do not retry blindly. Run the dry run: it lists what remains. Nothing remaining and a clean N-137 check means the commit landed.

### What the locks do and do not do
The advisory lock excludes **orchestrator build runs** (`runner.acquire_chart_lock`); the Gochara chart lock excludes **Gochara writers**. Neither excludes the **cockpit watchdog**, which takes no advisory lock. What does protect the rows the script has selected is the **row lock**: the owned `build_runs` rows and the manifest row are locked `FOR UPDATE` before anything is validated and stay locked until the transaction ends, so a watchdog that tries to DELETE one of those parent rows **WAITS** for the teardown to finish (a run the watchdog had already pruned before the lock was taken is simply not selected). The lock does **not** cover the watchdog's separate deletion of a run's CHILD rows (`build_run_assets`): a child-row deletion is a different statement on a different table and is not blocked by the parent lock; the script's reads and DELETEs are by id inside one transaction, so that can only remove run-asset bookkeeping the same transaction deletes anyway.

## 2b. Before the dry run: read back every incoming foreign key
Run `platform/scripts/v5_small_test_incoming_fks_readback.sql` (read only) and send the output to the steward. It lists every foreign key into `build_runs` and `kala_gochara_publication` with complete child and parent column lists. The scripts refuse BY NAME any key that is composite or does not target `id` / `manifest_id`; the readback shows beforehand whether that will happen. Production today (Stream B, read-only, 2026-10-05): all nine incoming keys are single-column, none deferrable — `build_run_assets.run_id` (CASCADE), `asset_provenance_receipts.build_id` (SET NULL), `conversations.archived_by_run_id` (SET NULL), and `chart_context_superseded_by_run_id` (SET NULL) on `event_chart_state_index`, `mimamsa_predictions`, `mimamsa_calibration_snapshot`, `brahma_prospective_ledger`, `brahma_mimamsa_prediction_ledger`, all into `build_runs.id`; and `kala_gochara_contacts.input_generation_vector_id` (NO ACTION) into `kala_gochara_publication.manifest_id`. The script finds them from the catalog, so none of these names is hard-coded.

## 3. When it refuses because receipts have no run link (recovery) — **NOT FOR USE until reviewed**
**This section is NOT FOR USE until a reviewer has accepted it; it is not needed for a timely teardown (section 1), and nobody should reach for it before the 90 days are up.** It is written down so that the rule is not silently worked around, and so the review has something concrete to review.

**The rule is not weakened and the script is not patched around.** The recovery is a steward-run, logged procedure that restores a link only from evidence that does not depend on the rows being questioned, and only for the exact receipt version whose origin was proved.

1. **Stop.** Delete nothing. Record, for each receipt, its full identity from the refusal message and from `SELECT partition_key, observed_at, code_digest, config_digest, upstream_digest, partition_digest, output_digest, output_digest_spec_sha256, receipt_version FROM asset_provenance_receipts WHERE asset_id = 'ka_gochara_v5' AND chart_id = '482012f1-710e-4a25-994a-93821f5871aa' AND build_id IS NULL`. **A receipt can be REPLACED under the same key** (the provenance writer upserts on `(asset_id, scope_key, partition_key)`), so a key alone proves nothing: the recorded identity is `observed_at` plus all five digests plus `output_digest_spec_sha256` plus `receipt_version`.
2. **A link may be restored for a receipt only if ALL THREE hold, each recorded in a decision file under `00_ARCHITECTURE/briefs/pravaha/decisions/` before anything is changed:**
   - **the window:** the receipt's `observed_at` lies inside the recorded dispatch window — the Cloud Run job execution of `brahma-build-pipeline-job` for the run id the dispatch printed (`--args=--run-id,<id>`), whose start and end times and the dispatch output are kept in the tracker;
   - **the digests:** the receipt's `code_digest` equals the **writer digest of `ka_gochara_v5` at the dispatch commit** (`platform/src/generated/nirmana-writer-digests.json` at that commit, from git history) and its `config_digest` equals the **digest of the chart configuration** (birth parameters) at dispatch, and `output_digest_spec_sha256` is recorded with the rest. (The stamped manifest's input vector carries the kernel's stage-module digests, NOT the receipt writer's code and configuration digests — those live in the run's `plan_manifest`, which is exactly what a prune removes — so the manifest cannot be the reference here. The dry run proves the manifest's stamp, snapshot and inventory identities, nothing about receipts.);
   - **nobody else:** no other run touched the asset in that window — no other `build_run_assets` row or Cloud Run execution for `ka_gochara_v5` inside it, on any chart.
3. **The change itself runs in ONE transaction, under the same locks the teardown takes** (the orchestrator's `pg_try_advisory_lock(hashtext(<chart>))` on a direct connection, then `ka_gochara_lock_chart`), and **re-validates the full receipt identity inside that transaction and must roll back on any mismatch**:
   - If the run row still exists: `UPDATE asset_provenance_receipts SET build_id = '<run id>' WHERE asset_id = 'ka_gochara_v5' AND chart_id = '482012f1-710e-4a25-994a-93821f5871aa' AND partition_key = '<key>' AND build_id IS NULL AND observed_at = '<recorded>' AND code_digest = '<recorded>' AND config_digest = '<recorded>' AND upstream_digest = '<recorded>' AND partition_digest = '<recorded>' AND output_digest = '<recorded>' AND output_digest_spec_sha256 = '<recorded>' AND receipt_version = '<recorded>'`, one statement per receipt, then check the total updated row count equals the number of recorded receipts; **if it does not, ROLLBACK** (a receipt was replaced or already re-linked since the proof) and start again from step 1.
   - If the run row was pruned (the usual case after 90 days): a link cannot be restored to a row that no longer exists, and a placeholder run row is never fabricated. If, and only if, all three conditions hold, the steward authorises ONE deletion of exactly those receipts, in the same shape: `DELETE FROM asset_provenance_receipts WHERE <the same full-identity predicate>` per receipt, row count checked against the record, `ROLLBACK` on any mismatch.
4. Then re-run the dry run, and only then the execution. If any condition cannot be shown, the receipts stay and the asset stays out of the monitor's excluded set until the steward decides otherwise.

## 4. Which role the script runs as
**The role choice is the owner's; this runbook changes no grant.** The script runs as ONE database role and never assumes the admin role. `REQUIRED_PRIVILEGES` in the script is the machine-readable list (a real-database test runs the script as a role holding exactly it, and shows a missing grant fails the dry run). From the migrations, and verified read-only on production by Stream B:

| Object (schema `public`) | Privilege |
|---|---|
| `asset_provenance_receipts`, `asset_freshness`, `build_run_assets`, `build_runs`, `asset_throughput` | SELECT, DELETE |
| `ka_gochara_eval_window`, `ka_gochara_relationship_record`, `ka_gochara_contact`, `kala_gochara_coverage`, `ka_gochara_search_interval`, `ka_gochara_search_obligation`, `ka_gochara_search_path_pin`, `ka_gochara_search_inventory`, `ka_gochara_search_input_snapshot`, `kala_gochara_publication` | SELECT, DELETE |
| `build_runs` and `kala_gochara_publication` (additionally) | UPDATE: the rows are locked `FOR UPDATE` before validation and held through the delete (Codex round 4 T1), and `FOR UPDATE` needs UPDATE on the table |
| `ka_gochara_generation_seal`, `kala_gochara_authority`, `kala_gochara_windows`, `kala_gochara_contacts` | SELECT |
| `asset_registry` | SELECT always; UPDATE(`is_active`) **only if the row is found active** — an already-inert row is not updated (production's is inert) |
| `asset_freshness` (additionally, **only if the registry row is found active**) | SELECT and UPDATE: the registry restore is a real `is_active` change, so migration 596's trigger runs `nirmana_invalidate_registry_receipts`, an **invoker-rights** function (not SECURITY DEFINER) that UPDATEs `asset_freshness` as the caller. With the row already inert (production's is) the script does not issue the UPDATE and none of this applies |
| every table the catalog shows referencing an owned `build_runs` row or the manifest: `conversations`, `event_chart_state_index`, `mimamsa_predictions`, `mimamsa_calibration_snapshot`, `brahma_prospective_ledger`, `brahma_mimamsa_prediction_ledger` | SELECT, to count the rows that reference them (the script refuses by name if any do) |
| `ka_gochara_lock_chart(uuid)` and `ka_gochara_generation_is_sealed(uuid, text)` (the DELETE guards on the chain tables call it as the invoker; a real-database test with PUBLIC EXECUTE revoked, as production has it, found it missing from the first draft of this table) | EXECUTE |
| the two verification tables (`ka_gochara_eval_window_verification`, `ka_gochara_search_inventory_verification`) | none: removed by foreign-key cascade (the cascade runs as the child's owner; the 1240 write guard on them refuses only a sealed generation) |

What each candidate holds (production catalog, read-only, Stream B, 2026-10-05; every table's owner is `amjis_app`):
- **`amjis_app`** (the application's owner role, not the admin role): owns every object above, so it holds every privilege implicitly, including EXECUTE on the lock. **It is the only existing role that holds all of them.**
- **`data_plane_builder`** (the builder; the identity of the `brahma-build-pipeline-job`, whose migration header says "deliberately NO DELETE"): holds SELECT, INSERT, UPDATE, DELETE on `build_runs`, `build_run_assets`, `asset_throughput` and `kala_gochara_authority`, and UPDATE on `kala_gochara_publication`, so the row locks work for it. (An earlier draft of this runbook said it held no grant on those four tables: that was WRONG on production.) Its real shortfall for this teardown is: **DELETE on `asset_freshness`** (it has S, I, U; migration 1217 forbids DELETE), **DELETE on `asset_provenance_receipts`**, **DELETE on `kala_gochara_publication`**, **SELECT on `conversations`, `event_chart_state_index`, `mimamsa_calibration_snapshot`, `brahma_prospective_ledger`, `brahma_mimamsa_prediction_ledger`** (it has S, D on `mimamsa_predictions`), and **UPDATE(`is_active`) on `asset_registry` only if the row is found active** (it holds UPDATE only on the four probe columns). It has EXECUTE on both guard functions.
- **`gochara_verifier`, `gochara_sealer`**: read-mostly; no DELETE on any parent table. **`role_orchestrator`**: holds the pre-576 orchestrator tables and nothing else here (no receipts, no freshness, no publication, no guard-function EXECUTE).

Recommendation, for the owner: `amjis_app` for the one-off teardown, because no narrower role exists today and creating one is a grant change that belongs in a protected migration window; if least privilege is preferred, a dedicated `gochara_teardown` role with exactly the table above is the follow-up (its own migration and review, including the open decision about the builder's `asset_freshness` DELETE that 1217 forbids).

## 5. What the dry run proves, and what it does not
It proves the locks can be taken (on a direct connection), every refusal check passes, every DELETE is accepted by the real foreign keys, guards and **privileges of the role it ran as**, the registry row ends in its 1304 shape, and the N-137 end state holds afterwards — all in the transaction an execution would commit, then rolled back. It does not prove anything about a COMMIT failing, or about another session writing between the dry run and the execution (run the execution soon after, on the same locks).

## 6. The dispatch that precedes it (companion notes; the dispatch script is `platform/scripts/dispatch_v5_small_test_job.py`)
- **Role: `data_plane_builder` SUFFICES** (production catalog, read-only, 2026-10-05; `amjis_app` is NOT needed). The staging transaction needs only: SELECT on `asset_registry`, `asset_provenance_receipts`, `asset_freshness`, `ka_gochara_generation_seal`, `kala_gochara_authority`, `kala_gochara_publication` and the chain and inventory tables; SELECT and INSERT on `build_runs` and `build_run_assets`; SELECT, INSERT and UPDATE on `asset_throughput`; EXECUTE on `ka_gochara_lock_chart(uuid)`; and the column UPDATE on `asset_registry` that the builder holds (it is what makes the `FOR SHARE` row lock work). It never updates `asset_registry.is_active`, deletes nothing, and does not need `ka_gochara_generation_is_sealed`. A real-database test runs it as a role holding exactly that.
- **The job image MUST be the one built from the SAME commit as the checkout the dispatch runs from.** The manifest pins the writer digest of that checkout (`nirmana-writer-digests.json`), and `execute_run` REFUSES a run whose image has a different writer digest ("sidecar code digest does not match"; the run ends `failed`). The dispatch prints the expected digest and the commit, and warns when the checkout has uncommitted changes under the sidecar. After ANY later writer change, re-dispatch from the matching checkout.
- **Read the result from the database, never from Cloud Run:** the orchestrator process exits 0 even when the run ends `failed`. Read `build_runs.state` and `build_run_assets` (state, error) for the run id.
- **Look a run up (read-only) with `--lookup <run id>` or `--list-runs`**, never with a dry run: once a staged run exists, the dry run refuses (an active run) by design.
- **Before the dispatch dry run**, run the read-only readbacks as the steward: `platform/scripts/v5_small_test_predispatch_readback.sql` (registry shape, dependencies lit and fresh, chart birth data, nothing of the small test exists, no resumption-ledger rows, concurrency cap, the writer-gap check, the role's privileges) and `platform/scripts/v5_small_test_registry_row_readback.sql`.
- **Any prior generation '5.0' output refuses the dispatch** (proven small test or not): clear it with the teardown first. A staged run that was never executed is failed by the cockpit watchdog after 10 minutes and then carries no receipts and no output, so the teardown removes it; before the watchdog acts it is an active run and blocks both scripts by name. Execute within 10 minutes of staging or re-stage.
