# V5 small test — teardown runbook

## 1. Run it within 90 days of the small test
The cockpit watchdog deletes terminal build runs (completed, failed, stopped) 90 days after their creation (`platform/src/app/api/cockpit/watchdog/route.ts`, "M-4"). `asset_provenance_receipts.build_id` is `ON DELETE SET NULL`, so the small test's receipts then carry no run link. The teardown **refuses a receipt with no run link, for good** (a pruned test run and a pruned real run look the same; the Nirmana monitor's rule N-137 reads such a receipt as non-test evidence too). So the clock is: **creation time of the small-test run + 90 days.** The dry run prints each owned run's creation time and the days remaining; the dispatch prints the same deadline when it stages the run. Tear down well inside it.

## 2. Connect DIRECTLY, then run the usual sequence
**Use a DIRECT connection to the database's own host and port. Never a pooler** (PgBouncer or any transaction-mode pooler). The orchestrator exclusion lock is a SESSION advisory lock; through a transaction-mode pooler it silently holds nothing, and the script's other protections lean on it. The script reads `pg_backend_pid()` in three separate transactions and refuses if the backend changes, and checks that the lock is held by the backend running the transaction; that catches a busy pooler but cannot prove a quiet one is absent, so the direct connection is a requirement of this runbook, not only of the code.

Before either the dry run or execution, satisfy and record the process-quiescence gate in §6. Terminal database state and acquired advisory locks do not prove the writer has exited; the teardown script does not collect this external evidence.

The Wave 4 operations run through the governed executor, under the existing owner authorization `OWNER-AUTH-TEARDOWN-20261015`. A direct invocation with only DATABASE_URL and steward flags now refuses: the executor supplies the independently accepted complete request in `KY_OPERATION_REQUEST`.

1. The request's `smalltest_scope` identifies the canonical chart, asset and generation, the accepted staged launch UUID (`run_id`), `plan_manifest_digest`, candidate `manifest_id`, and `input_vector_sha256`. Its `dispatch_receipt` and `dispatch_acceptance` references are `{name, sha256}`: exact JSON bytes under `run/ops/receipts/` and `run/ops/acceptance/`. Only completed, accepted J-2a/J-2c launches qualify. Extra tagged runs, a pruned run, a mismatching candidate/vector and coverage created by another run refuse. A staged run that died before producing any candidate uses paired null candidate/vector identities; any output then refuses. The initial empty rehearsal alone uses `{empty: true}`.
2. Submit `smalltest_teardown_dryrun`. For each table in the deletion scope it first COUNTS the scoped rows by SELECT (under the table locks, with the DELETE's own predicate) and executes the guarded DELETE only when that count is above zero; a table with no scoped rows is recorded as measured-absent and gets no DELETE statement at all, and `teardown_proof` and the transaction-local `absence_proof` list those tables under `skipped_empty_tables`. (A zero-row DELETE would still fire migration 1379's statement-level `*_statement_lock` triggers, which lock every chart present in the table, so it could fail on another chart's rows although it deletes nothing; the empty rehearsal therefore issues no DELETE.) It then checks absence in its own transaction, and rolls back. Only a confirmed rollback emits `teardown_proof` with status `ROLLED_BACK`, `rollback_confirmed: true`, the exact scope and a content digest of the selected rows, cascade children and registry state. Retain the executor receipt and V's acceptance.
3. Submit `smalltest_teardown` with the identical scope plus `dryrun_receipt` and `dryrun_acceptance` references. The script checks that the preceding rehearsal used the same reviewed source and that the current selected rows have the same digest. It commits only after the existing end-state and transaction-local absence checks pass. Its status is `COMMITTED_AWAITING_ABSENCE`; the executor receipt is `AWAITING_ABSENCE` and its production fence remains.
4. Produce the independent SELECT with `v5_small_test_shared.absence_readback_sql(committed_receipt)` and submit it through `readback_sql`. It measures every deleted scope and cascade child and registry inertness, emitting one JSON text column named `absence_proof`. V's acceptance binds the readback receipt/request and output bytes and includes that measured JSON under `absence`, adding `output_sha256`.
5. The teardown's existing quiescence acceptance must reference that readback using `absence_receipt` and `absence_acceptance`. The executor requires the same run, scope, row-set digest, teardown operation/request/receipt and a readback later than commit. Only then does its foreground reconciliation emit `run/ops/receipts/<operation_id>.completion.json` (`ky.smalltest_completion/1`, `COMPLETED`). The commit receipt remains immutable; the owner-controlled fence is retained for the existing release procedure. A generic quiescence boolean is insufficient.
6. The next small-test dispatch carries these absence references and `prior_teardown_receipt`; the first dispatch instead uses the measured empty baseline from `absence_readback_sql()`. A baseline cannot bypass earlier launch/teardown history. Small-test dispatch refuses the disabled measuring profile; the conditional full-horizon small test is limited to marriage. Its actual writer validator still enforces the marker's classes and horizon.
7. On an unknown commit outcome, use governed read-only lookup/readback for the identified run before any retry. Missing run rows do not authorize reconstruction or a second deletion. The transaction-local `absence_proof` is diagnostic rehearsal/commit evidence; it is never the independent post-commit proof.

(I) INTERPRETATION: independent absence is necessarily a separate post-commit operation, with completion derived from its accepted evidence. Alternative: accept the deleting transaction's own counts or unreferenced booleans. The same-row-set and evidence-reference rules implement the owner's per-run rehearsal/absence condition and CLAUDE.md §N.8.

### What the locks cover
The orchestrator advisory lock and Gochara chart lock remain. Before ownership checks, bounded `SHARE ROW EXCLUSIVE` locks on all deletion tables and cascade children prevent direct DML, including watchdog child deletion, from changing the selected scopes between validation, row hashing and DELETE. The run and manifest row locks and catalog-discovered foreign-key refusals remain. A lock timeout refuses and rolls back. The locks last only for the teardown transaction; the content digest detects changes between separate rehearsal and execution transactions.

## 3. When it refuses because receipts have no run link (recovery) — **NOT FOR USE until reviewed**
**This section is NOT FOR USE until a reviewer has accepted it; it is not needed for a timely teardown (section 1), and nobody should reach for it before the 90 days are up.** It is written down so that the rule is not silently worked around, and so the review has something concrete to review.

**The rule is not weakened and the script is not patched around.** The recovery is a steward-run, logged procedure that restores a link only from evidence that does not depend on the rows being questioned, and only for the exact receipt version whose origin was proved.

1. **Stop.** Delete nothing. Record, for each receipt, its full identity from the refusal message and from `SELECT partition_key, observed_at, code_digest, config_digest, upstream_digest, partition_digest, output_digest, output_digest_spec_sha256, receipt_version FROM asset_provenance_receipts WHERE asset_id = 'ka_gochara_v5' AND chart_id = '482012f1-710e-4a25-994a-93821f5871aa' AND build_id IS NULL`. **A receipt can be REPLACED under the same key** (the provenance writer upserts on `(asset_id, scope_key, partition_key)`), so a key alone proves nothing: the recorded identity is `observed_at` plus all five digests plus `output_digest_spec_sha256` plus `receipt_version`.
2. **A link may be restored for a receipt only if ALL THREE hold, each recorded in a decision file under `00_ARCHITECTURE/briefs/pravaha/decisions/` before anything is changed:**
   - **the window:** the receipt's `observed_at` lies inside the recorded dispatch window — the Cloud Run job execution of `brahma-build-pipeline-job` for the run id the dispatch printed (`--args=--run-id,<id>`), whose start and end times and the dispatch output are kept in the tracker;
   - **the digests:** the receipt's `code_digest` equals the **writer digest of `ka_gochara_v5` at the dispatch commit** (`platform/src/generated/nirmana-writer-digests.json` at that commit, from git history) and its `config_digest` equals the **digest of the chart configuration** (birth parameters) at dispatch, and `output_digest_spec_sha256` is recorded with the rest. (The stamped manifest's input vector carries the kernel's stage-module digests, NOT the receipt writer's code and configuration digests — those live in the run's `plan_manifest`, which is exactly what a prune removes — so the manifest cannot be the reference here. The dry run proves the manifest's stamp, snapshot and inventory identities, nothing about receipts.);
   - **nobody else:** no other run touched the asset in that window — no other `build_run_assets` row or Cloud Run execution for `ka_gochara_v5` inside it, on any chart.
3. **The change itself runs in ONE transaction, under the same locks the teardown takes** (the orchestrator's `pg_try_advisory_lock(hashtext(<chart>))` on a direct connection, then `ka_gochara_lock_chart`), and **re-validates the full receipt identity inside that transaction and must roll back on any mismatch**:
   - If the run row still exists: `UPDATE asset_provenance_receipts SET build_id = '<run id>' WHERE asset_id = 'ka_gochara_v5' AND chart_id = '482012f1-710e-4a25-994a-93821f5871aa' AND partition_key = '<key>' AND build_id IS NULL AND observed_at = '<recorded>' AND code_digest = '<recorded>' AND config_digest = '<recorded>' AND upstream_digest = '<recorded>' AND partition_digest = '<recorded>' AND output_digest = '<recorded>' AND output_digest_spec_sha256 = '<recorded>' AND receipt_version = '<recorded>'`, one statement per receipt, then check the total updated row count equals the number of recorded receipts; **if it does not, ROLLBACK** (a receipt was replaced or already re-linked since the proof) and start again from step 1.
   - If the run row was pruned (the usual case after 90 days): a link cannot be restored to a row that no longer exists, and a placeholder run row is never fabricated. If, and only if, all three conditions hold, the steward authorises ONE deletion of exactly those receipts, in the same shape: `DELETE FROM asset_provenance_receipts WHERE <the same full-identity predicate>` per receipt, row count checked against the record, `ROLLBACK` on any mismatch.
4. Then re-run the dry run, and only then the execution. If any condition cannot be shown, the receipts stay and the asset stays out of the monitor's excluded set until the steward decides otherwise.

## 5. What the dry run proves, and what it does not
It proves the locks can be taken (on a direct connection), every refusal check passes, every DELETE it issues (a table with no scoped rows gets none, see §2 step 2) is accepted by the real foreign keys, guards and **privileges of the role it ran as**, the registry row ends in its 1304 shape, and the N-137 end state holds afterwards — all in the transaction an execution would commit, then rolled back. It does not prove that COMMIT will succeed or that no later write will occur. Execution therefore rechecks the exact row-content digest under its own locks, and completion waits for a separate independent absence readback.

## 6. If the writer timeout fires (operating note; steward TIMEOUT-RULING, 2026-10-05)
**The cap.** The migration-1304 registry row carries `writer_timeout_seconds = 28800` (8 h), one value for the small test and the measuring build, so no second registry migration is needed. The orchestrator applies it to the WHOLE asset as wall-clock from the asset's dispatch (not per substep), and the registry value wins over the job's `WRITER_TIMEOUT_SECONDS`. A healthy run must never be ended by the cap; the cost of a large cap is slower detection of a genuinely hung writer, and every run is supervised. Before dispatch, the pre-dispatch readback notes must show that the Cloud Run job task timeout (86400 s per Stream B's read-only describe) is above the cap.

**Detect from state, never message text (MB-4.2).** Read `build_runs.state = 'failed'`, `build_run_assets.state = 'error'` for the run and asset, and an unfinished substep plan (no `asset.substep` event at `index = total`). Record the last `index/total` and the observation window. The current diagnostic is `TIMEOUT: writer exceeded its writer_timeout_seconds budget (Ns) — …`, with disposition NULL; the old `BLOCKED: upstream dependency(ies) timeout` diagnostic is withdrawn and must not be used as the detector. A missing or incomplete event record is unknown, never proof of completion. The runner can exit 0 while the run is failed.

**What it leaves behind.** The orchestrator marks the asset and stops waiting; it does not cancel the writer thread. An in-flight substep can still commit after the error state is written. If it finishes the whole plan, the asset can read `lit` under a failed run; read the run state first and refuse `asset_lit_under_failed_run` (MB-4.4). A fired cap requires teardown and re-dispatch from zero, with no resume ledger or hand-edit, only after the following gate.

**Required process-quiescence gate before teardown (MB-4.5).** For the exact Cloud Run execution dispatched with this run id, retain in the sitting log:

1. The execution identity, run id and readback showing terminal execution with `status.completionTime` set. A terminal database run/asset row, the process exit code or an acquired advisory lock is insufficient. If completionTime is absent, refuse `run_not_terminal_for_teardown` and delete nothing.
2. After that completionTime, read the same execution/run's `asset.substep` events through a recorded observation cutoff. Record the completionTime, cutoff, log-query scope and last substep's event timestamp and `index/total`; establish that no later `asset.substep` event exists. If a later event appears, or log coverage cannot establish absence, do not tear down: preserve the evidence and resolve the execution/log mismatch with the steward. Do not infer quiescence from silence during the writer's timeout.
3. Only with both receipts recorded, follow §2: the governed, accepted same-row-set rehearsal, execution and independent post-commit absence procedure. Preserve the failed run/unfinished-plan evidence before deletion. The script's database checks and locks supplement this gate; they do not establish process completion or event quiescence. The FROZEN runner is unchanged.
