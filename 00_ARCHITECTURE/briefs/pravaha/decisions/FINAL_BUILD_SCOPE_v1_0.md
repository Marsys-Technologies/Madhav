# FINAL BUILD SCOPE — one consolidated specification

## 0. What this is, what it is not, how to read it

**Is.** The implementable scope of the FINAL sealed build of Gochara 5 (`'5.0'` generation for the pinned chart `482012f1-710e-4a25-994a-93821f5871aa`), assembled from ruled inputs only: owner Rulings 7, 8, 9, 10, 11, 12, 13 (`decisions/NATIVE_DIRECT_RULINGS_20261005.md`), the sealed decisions `ND-H-20261005` and `ND-P2-20261005` (copied unchanged into `decisions/`), and the campaign gaps G6, G8, G9, G10, G11, G12. Every clause is an implementable statement with an ORACLE (what a test must prove) and a SIDE (builder = Stream A; independent verifier = Stream B).

**Is not.** Work for the small test or for the first unsealed full build, which run on today's rules (§13). Not the SERVING path: this document specifies a sealed, verifiable generation; "served" is stated only as preconditions (FB-54) and several of them are the owner's (§12b). Nothing here decides a point the owner left open (§12, §12b list them). Nothing here is coded before the steward says so.

**Source kinds** (every clause carries one): **K1** a citation with its locus (a verse or sutra in the served corpus; a K1 supports a house or planet MEANING only); **K2** an owner ruling or a sealed decision by delegate (the only source of SCORED use of a derived rule, spec §0: a derived event rule scores only as `uncited_extension` under a ruling); **K3** a derivation (a step from a K1/K2 premise to an event rule or an engineering consequence; never scoring authority on its own). Verse loci quoted in the two delegate decisions are UNVERIFIED by any reviewer; the Stream B verse check (ref G10-VERSE-CHECK, `run/G10_VERSE_VERIFICATION_20261005.md`) governs the K1 status of those loci. Until it closes, a clause's K1 locus is a pointer, not evidence.

**Clause ids** `FB-<n>`. **Independence rule:** the verifier side is written from THIS text alone, with its own tables, never imported from the builder (`inventory_verifier.py` already states this; `record_verifier.py` and `record_derivation.py` import only the verifier's `_`-prefixed tables). FB-38 pins that the two sides' tables are equal and equal to the ruling.

## 2. FB-1 … FB-9 — the horizon (Ruling 13, Ruling 7) [K2 unless marked]

**FB-1 (the rule; K2 for the pinned chart, K3 for the general rule; review FBS-1.3, FBS-2.4).** Owner Ruling 7 says, verbatim, "the life event log's first event is what we will consider the starting date"; Ruling 13 approved the pinned chart's outcome (1998 → 2084). The GENERAL rule below is Stream B's derivation from those two texts and carries THREE narrowings the owner has not ruled on (recorded as OPEN OWNER DECISION OD-3): "birth entry aside", "fully dated only", "1 January of the year". For any chart: horizon END = birth date + 100 years; horizon START = 1 January of the year of the first FULLY DATED life event, the birth entry aside; if none, START = the build date (a UTC date, recorded in the manifest). Half-open `[start, end)` in UTC at midnight as everywhere in the writer. The pinned chart: START **1998-01-01** (Ruling 7 read by the steward, put back to the owner in case he meant 16 February), END **2084-02-05**.
**Fully dated, exactly (FB-55).** The life-event log is the table `life_events` (`001_baseline.sql:463`, extended by `457_lel_schema_v2_event_shapes.sql`: `shape ∈ {point, interval, chain}`, `date_confidence ∈ {exact, month_known, year_only}`, `interval_start`, `interval_end`, `chain_parent_event_id`, `date_tightened_at`). An event is FULLY DATED iff `date_confidence = 'exact'` AND its date is: `event_date` for shape `point`; `interval_start` for shape `interval`; the `event_date` of the chain's ROOT (follow `chain_parent_event_id` until it is NULL; a cycle or a missing parent refuses the derivation by name `lel_chain_unresolvable`) for shape `chain`. `month_known` and `year_only` are NOT fully dated (their stored `event_date` is a proxy such as YYYY-07-01 and opens nothing). The birth entry is the event whose type is birth (the verifier's own reading of the log; to be confirmed with the log's owner). `life_events` carries no `chart_id` (`958_...sql:75` says the table is global, not chart-scoped): "for any chart" is therefore NOT implemented by this scope; the rule is single-chart (the native's log), and a second chart needs a chart key first (out of scope; refused).

**FB-2 (what changes in code, K3).** Today the horizon is ONE constant: `DEFAULT_HORIZON = (1998-01-01, 2026-04-17)` at `pipeline/orchestrator/writers/ka_gochara_v5.py:157-158`, consumed by `_effective_horizon` (`:433-446`, `ctx.config.get("horizon", DEFAULT_HORIZON)`), by the test-slice validator (`:312-314`: a slice horizon outside `DEFAULT_HORIZON` is refused "never clipped") and by the `one_class_full` run rule (`:355`: horizon must equal `DEFAULT_HORIZON`). The change: `DEFAULT_HORIZON` stops being the authority for a chart. A pure function `derive_chart_horizon(birth_date, lel_rows, build_date) -> (start, end, basis, basis_event)` (basis ∈ `first_dated_event | build_date`; `lel_rows` are RAW log rows, so the fully-dated rule of FB-1 is applied by the function, not by its caller; the number of rows excluded as not fully dated is returned for the report) is the single authority; its result is pinned into the manifest as `horizon_basis` (FB-8) and every consumer reads the pinned value. `DEFAULT_HORIZON` may remain ONLY as the outer bound the test-slice validator compares against, redefined as the derived horizon (a slice can be narrower than the full build, never wider). The one-chart discipline (`CHART_ID` refusal at plan time) stays.
- Oracle: for the pinned chart the function returns `(1998-01-01, 2084-02-05, first_dated_event, <the 1998 event>)`; for a chart whose log has no fully dated event it returns the build date and `basis=build_date`; two builds on different dates of such a chart produce different manifests; a year-only entry (1995) opens nothing; the same entry after `date_tightened_at` (now `exact`) makes the derivation REFUSE with `horizon_start_before_substrate_domain` (FB-3), never clip.
- Verifier side (FB-55): the independent input check re-derives the horizon from the PINNED `horizon_basis` (not the live log) and compares with the manifest's horizon; the life-event log is read live ONLY to report `lel_drift` (below).
- Drift rule (review FBS-1.3, G12 principle applied to the log): `horizon_basis` stores the basis event's id, date, `date_confidence`, `shape`, plus a digest of the (id, date, date_confidence, shape) of EVERY row the derivation consumed. A later change of the live log (a 47-event rework, a tightened date) is `lel_drift` — SOFT, reported, never blocking and never a failure to verify a sealed generation; a generation is replayable under the log it used.
