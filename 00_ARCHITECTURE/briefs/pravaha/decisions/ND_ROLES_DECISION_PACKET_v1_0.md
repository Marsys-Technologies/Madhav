# ND-ROLES — who holds the "verified" stamp and the "published" seal?

## In plain words
The build writes thousands of rows. Two later acts must be done by someone **other than the builder**, or they mean nothing:
* **Verification** — an independent re-derivation that says "these windows are exactly what the inputs imply". If the builder can write that stamp itself, the stamp proves nothing.
* **Sealing** — the act that freezes a generation as published (the first step toward the flip, which is yours alone).
Today **neither principal exists in a usable form**, and the builder is even *allowed* to write the verification stamp (migration 1206 §7 grants it). You are asked **how the pipeline gets its two extra keys**: who holds them, where the passwords live, and what we change in the database and in the deployment gates. Each option below says what has to be built, who does it, and what it costs.

## The governance rules any option must respect (each is enforced by a deploy gate)
1. **Exact-membership gate (DP-SD-018, `data-plane-ownership-status.ts`; `normalizeDataPlaneMemberships` in the preflight).** Any membership edge that involves `data_plane_builder`, `data_plane_verifier` or `data_plane_migrator`, other than the three owner → migrator edges, is *drift*: the preflight **revokes** it and the status gate **fails the deploy**.
2. **Name gate.** A role named `data_plane_<anything>` outside the six is rejected ("unknown data-plane principal collision"). New principals must not use that prefix.
3. **Secret isolation (GCP IAM gate).** A runtime job may bind only its own secret; every additional database credential needs its own service account, secret, IAM binding and an extension of `data-plane-secret-isolation-preflight.ts`.
4. **Production default privileges** revoke PUBLIC EXECUTE on everything `amjis_app` creates, so each principal needs explicit table *and* function grants (the live suites derive them).
5. **Role creation is not a migration.** `amjis_app` has no CREATEROLE; creating a login role is an administrative act (the ownership-admin path, `DATA_PLANE_OWNERSHIP_ADMIN_DATABASE_URL`), not something a numbered migration can do.

### Reuse `data_plane_verifier`, or a new `gochara_verifier`? (inside option A)
* **Reuse:** one fewer principal, the login, SA-able secret path and the gates already know it. But it is defined (and its ACL asserted) as a **read-only L1 verifier**; making it write verification rows changes the meaning of a governed role and must not break its protected-table assertions (they cover only the L1/L2 protected sets, not `ka_gochara_*`).
* **New `gochara_verifier`:** clean purpose, untouched governance set, but a new login/secret/SA and a name outside `data_plane_`. **Recommendation: new `gochara_verifier`** (least surprise for the governance gates), unless you prefer the smaller change.

## A consequence of the frozen build contract (surfaced by Stream A) — in plain words
The orchestrator's frozen contract gives every writer **exactly one database connection: the builder's**. Migration 1240 (the window-verification gate) makes its verification table writable **only by the verifier principal** and grants the builder **nothing** on it. Put those two facts together and **no step inside the build can record a verification result** — which is exactly what independence means, but it has a price: **verification must happen as a separate act, after the build, under the verifier's own identity — and until it has happened the candidate gate stays closed (a first seal is refused).**
* **Under option A this is by design.** The orchestrator contract is **not** changed (it is frozen). Inventory verification (1206) and window verification (1240) are both persisted by the separate job below; 1240 grants the builder nothing on its table, and 1206 §7's builder grant is removed (see the 1206 section).
* **Under options B and C the builder's own session would do the persisting** — the same login (B: after switching role; C: with a second credential it also holds). The rows would exist, but the database could not tell a builder-written "independent" verification from a real one: nominal (B) or weak (C) separation.
* The role names in 1240 — **`gochara_verifier`** and **`gochara_sealer`** — are the **proposed** ones (outside the `data_plane_` prefix, so the name gate is untouched). Neither exists in production today (creating a login role is an administrative act, not a migration).

## Option A in concrete terms: the separate verification job
**What it is.** A second Cloud Run job, **proposed name `gochara-verification-job`**, built from the **same pipeline image** as `brahma-build-pipeline-job` with a different entry point. It runs under its **own service account** (proposed `gochara-verifier-runtime@…`) bound to its **own secret** (proposed `gochara-verifier-db-url`, login `gochara_verifier`). It is **not** the builder's job and never holds the builder's credential.
**What it does (read-only on the build's data).** It calls the **independent verifier modules that already exist in the sidecar** — the inventory re-derivation (`inventory_verifier`), the window-semantics verifier (`window_verifier`), the P1 record verifiers (`record_verifier`) and the input-identity verifier (`input_vector_verifier`) — each of which already takes a database connection; it re-derives what the stored inventory and windows **should** be from the inputs, compares with what the builder stored, and **inserts one verification row per (chart, generation, class, path, rule version)** into the two verification tables (`ka_gochara_search_inventory_verification`, `ka_gochara_eval_window_verification`). Its privileges: `SELECT` on the build and input data, `INSERT` (and, before a seal, `DELETE`, so a re-run replaces) on **only** those two tables; nothing else, and nothing on any table the builder writes. A sealed generation refuses further verification writes (the existing write guards).
**What it needs that does not exist yet.** (1) the login role (admin act); (2) service account, secret and IAM binding, and the **secret-isolation gate extended** for it; (3) a small **runner** (Stream A) that opens the verifier's connection, calls the existing verifier functions and writes the rows — the verifier logic itself is unchanged; (4) the writer's in-build re-derivation of the inventory (it now runs inside the builder's session) becomes a **report only** — persistence moves to the job; (5) the job definition in the deploy workflow.
**What triggers it.** **A person, after the build** — an operator executes the job for one (chart, generation) (recommended; the candidate gate is meant to stay closed until someone has looked at the build's outcome). It is **never** chained to the build by the orchestrator (frozen). An automatic trigger (a workflow reacting to the build job's completion) is possible later but is a new deployment surface and is not proposed now. The job **refuses to start** unless the generation has a candidate (unsealed) manifest and its build is complete, and it **writes nothing** on refusal.
**What the cockpit shows between build and verification.** **Today:** only that rows are present and the build's steps finished ("lit") — it has **no verification state**, so a green tick would read as "done" when it only means "built". **Proposed (small, unbuilt):** a candidate line derived **from the database**, not from the orchestrator: **"BUILT · NOT VERIFIED · gate CLOSED (n reasons)"**, computed by the same function the seal uses (`ka_gochara_candidate_gate_violations`), turning to **"VERIFIED (policy vN, m of m paths)"** after the job, and **"SEALED"** after the sealing step. Until that exists the tick must be read as "built, not verified".
**Then the seal.** A **separate, approval-gated** sealing step runs as `gochara_sealer` (it inserts the seal row); the seal triggers (1206 and 1240) refuse unless every required verification row exists, is `VERIFIED` and still matches the stored data. Verification and sealing are two principals, two secrets, two acts.
**If the job fails halfway.** Rows already written for a (chart, generation) are replaceable before a seal (re-run), never after; a failed run leaves the gate closed, which is the safe state.
**What does not change.** The orchestrator contract, the builder's privileges (it still writes the windows and records), and the independence of the verification logic from the build's writer code.

## What a minimal provisioning migration contains (option A)
A **grants-only, routine, owner-run** migration (**1241 — DRAFT PR #2949, 36 grants each proven necessary under first seal AND replay; role-guarded with a post-check that PRINTS which principals were found; MERGE ONLY AFTER the protected window** — the routine runner refuses loudly at the first pending protected file; from the 1230–1249 block; it MUST be above 1240: a number below 1240 would be an unapplied routine predecessor that the protected window's `--only` run refuses (R9-6 i). It is a routine file applied by the ordinary deploy AFTER the window, so the verifier/sealer have no privileges until it runs — the safe order; role creation itself is the admin act above):
* `GRANT USAGE ON SCHEMA public` and `SELECT` on the verification read set (inventory, snapshot, pin, obligation, interval, records, windows, window membership, coverage, `chart_facts`, `chart_dashas`) **to the verifier**; `INSERT` (and pre-seal `DELETE`) on the verification tables (1206's `ka_gochara_search_inventory_verification` and Stream A's 1240 table) **to the verifier only**; `EXECUTE` on the functions those inserts' guards call.
* **To the sealer:** the table/function grants the live suites already grant it (SELECT on the seven tables the seal reads, `INSERT` on `ka_gochara_generation_seal`, `UPDATE` on `kala_gochara_publication`, `EXECUTE` on the 23 seal-side functions, including 1232's two).
* **From the builder:** nothing is revoked here — under option A the builder's grant on `ka_gochara_search_inventory_verification` is removed **at source** by the stacked PC-4 edit to 1206 §7 (draft PR #2934, applied only if the native chooses option A), and the builder is never granted anything on 1240's table. (The 1241 file therefore carries no `REVOKE`.) **Open item NOT in 1241 (data-plane ACL owner):** both principals also need SELECT on the L1 tables `chart_facts` and `chart_dashas` (measured: the verification-then-seal flow fails without them) — those ACLs are managed by `platform/scripts/data-plane-ownership-preflight.ts`, so a hand grant by a Gochara migration risks its allowlist-drift gate; it must be provisioned by that owner before the first verification run. **The verification runner must record the four window verifications BEFORE the class inventory verification** (the `verify:` step runs the candidate gate first). The builder's own record-table gap is **1242** (PR #2940).
* Role-existence guards for the sealer/verifier (the roles are created by an admin act that may run after the migration), **plus a post-check that prints which principals were found** — a grants migration that silently granted to nobody is the standing hazard (`CLAUDE.md §N.4`).
