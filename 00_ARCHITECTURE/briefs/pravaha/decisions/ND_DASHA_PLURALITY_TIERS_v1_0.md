# Which timing systems get a vote in the old (4.x) engine's "permission" — and what should happen to the ones that silently cannot?

## In plain words
The old engine decides how "open" a time is by letting **twelve timing systems vote** (DR-14: no single system may be exclusive; Vimśottarī is the *default*, never a gate). Eight of the twelve are daśā systems. Each vote has a weight; the total of all weights is 1.0.

**Today only three of the eight daśā systems can vote at all**, because the engine reads only rows whose checking level is "two-pass verified", and for five systems the stored rows are at a lower level. So **34 % of the voting weight can never be used**: the engine's "permission" can never exceed **0.66** however well the systems agree. Nothing tells a reader that. (Stream A's change, PR #2954, keeps today's numbers exactly but now *says* which systems are unavailable and marks the permission as partial.)

**Your decision:** what should the plurality do about the five systems it cannot read?

Weights: `services/gochara_intensity/permission.py:100–113` (disclosed structural priors, never fitted); the arithmetic `permission = active weight ÷ total weight (1.0)`: `:362–364`. **What the levels mean** (`brahmagyan/verification_vocab.py:89–95, 282`): *two-pass verified* = a value independently re-derived; *classical-match* = checked against a classical reference table — "a real check, but a relay-fidelity check rather than an independent re-derivation", held out of the verified set pending a per-site audit (residual R-VOCAB-1); *single* = no second check at all.

## What the ratified doctrine says (DR-14, quoted)
> "Activation windows are generated by a PLURALITY of timing systems … the Vimśottarī spine (all levels …) as the DEFAULT generator — never an absolute container; Jaimini rāśi-daśās (Chara, Nārāyaṇa); Tājaka/varṣaphala year-lord + Mudda … **No system's window may be served as exclusive.** Cross-system confluence raises confidence … **Per-system weights are LEARNED (D-4b hierarchical calibration), never assumed; until fitted, weights serve as classical structural priors with `calibration_state` disclosed.**"

Two consequences: (1) the weights are priors, not measurements, so a system that cannot vote makes the prior silently smaller; (2) DR-15(d): "thresholds, event sets, and win criteria commit to the ledger BEFORE any scoring run; **post-hoc adjustment is gate-gaming**" — so whichever option you choose must be fixed before any `'4.1'` output is looked at.

## The four options
| | what it does | what changes numerically (in principle; no run) | honesty cost |
|---|---|---|---|
| **(a) Keep** | only two-pass-verified rows vote; the five unavailable systems stay in the denominator as zero — today's arithmetic — now disclosed as "partial" | **nothing**: ceiling stays 0.66, values identical to today | none — it is exactly what runs, and it is now said |
| **(b) Admit honestly-labelled level-1 rows** | the classical-match / single level-1 rows of the other systems vote, with their level carried through into each window's detail | up to **+0.34** of weight becomes reachable (86 extra level-1 rows in all); permission rises wherever those systems' running lord coincides with the target — by 0.05–0.10 per system, more where several coincide | the new votes rest on relay-checks, not independent re-derivations — allowed only if the label travels with them, and R-VOCAB-1 (the earnedness audit of exactly this tier) is still open; Kālacakra is entirely "single" |
| **(c) Drop the unavailable systems from the denominator** | permission = active weight ÷ 0.66 | every non-zero value is multiplied by **1.52**; order within a build unchanged; any absolute threshold on permission moves; ceiling becomes 1.0 | **hides** that a third of the prior is missing — it makes the number look complete |
| **(d) Admit the deeper "single" levels too** | levels 2–4 of every system vote | about **86,000** extra period rows; deep periods are short and dense, so some system is "active" almost always — permission inflates and loses discrimination (Stream A: "not neutral") | most unverified rows of all, in the largest numbers |

## Interaction with the `'4.1'` diagnostic measurement
The `'4.1'` candidate is built by the 4.x chain, whose stored intensities include the permission arithmetic; any policy change other than (a) therefore changes every stored `'4.1'` value and so every ranking and false-alarm figure the measurement reports (to be confirmed by Stream A for the exact stored field). The measurement's rule is that the extract commands, inputs and conventions are **frozen in Stage 1 before any `'4.1'` output exists**. So the policy must be named **now**, and its version is added to the Stage-1 freeze draft as a **frozen input** (done in `FREEZE_STAGE1_4_1_v1.DRAFT.json`; the verifier will refuse the freeze while that placeholder is unfilled).

## Recommendation (Stream B; yours to overrule)
**(a) for the `'4.1'` freeze.** It measures what the old engine really does, adds no new unverified votes, and the disclosure (partial permission, unavailable systems named) is the honest part of the change. **Reject (c)** (it fakes completeness) and **(d)** (it floods the vote with unchecked rows). **Take (b) later, as its own decision for the governed `'5.x'` permission** — with a per-(system, level) accepted set, the tier carried into every window, and only after R-VOCAB-1 says what "classical-match" is worth for the daśā writers; Kālacakra should stay out until a second check exists. If you prefer to see the effect of (b) on the diagnostic now, it must be chosen **before** the freeze and the measurement run once, never both ways.
