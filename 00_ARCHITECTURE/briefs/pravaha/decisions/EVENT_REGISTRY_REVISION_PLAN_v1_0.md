# What a later re-run on a revised life event log needs

Context: Ruling 9 (owner, 2026-10-05): Gochara 5 is tested, fixed and made live on the CURRENT life event log; the revised log comes later, in a new template, and the tested engine is run again on it. Nothing below blocks the small test, the full build or going live.

1. **A new event-registry version** (the held-out events, with process events recorded as a span, dated milestones and one defining moment, per Ruling 8 as the owner now sequences it), with its own version, status and changelog; the current registry stays as the first scored record.
2. **Life-event-log annotations** for that version, in the template the strategy conversation designs with the owner; by Ruling 7 the log's earliest event also sets the horizon START per chart.
3. **A protocol version note** for the scoring rule (window overlap with the span AND peak distance to the defining moment; the random controls already use each event's own span length).
4. **A re-run of the 3.0 baseline** on the revised registry, so the 5.0 comparison is like for like.
5. **The horizon start of a re-run is pinned by the manifest vector's horizon**: a revised log that moves the earliest event moves the horizon, so the re-run is a NEW generation (new horizon, new manifest), never an in-place change of a sealed one; the earlier generation stays as the first scored record.
6. **Method (stated, not hidden):** once 5.0 is scored on the current record and the record is revised afterwards, the later score is not a clean test. Mitigation: the template and any event revision are produced blind to 5.0 output, and no 5.0 windows or scores for the pinned chart are sent to the strategy conversation.
