# G12 Route 1 — the input snapshot owns a COPY of the L1 rows it consumed

**Goal.** A sealed (or candidate) generation stays self-contained and verifiable after any later `ga_positions` / `ga_dashas` rebuild: no row id, build id, engine bump or new L1 column can make it unverifiable. Values that actually changed show as HARD drift; everything else as SOFT drift.

**What is stored (additive columns on `ka_gochara_search_input_snapshot`, immutable like the rest of the row).**
`consumed_fact_rows jsonb` and `consumed_dasha_rows jsonb`: arrays of `{key, content, metadata}`; `l1_facts_metadata_digest`, `dasha_metadata_digest` text. The old `consumed_fact_ids` / `consumed_dasha_row_ids` stay as informational provenance (ids at build time) and no longer decide anything. A `CHECK ... NOT VALID` makes the copies mandatory for every NEW row (0 snapshots exist on production; no backfill).

**Content (identity) vs metadata.** INVARIANT (round 6, R3): *the identity (key + content) holds only values of rows the snapshot consumed.* A value that can change because of a row the search never read is metadata.
- *Fact row* (10 today, `graha_position`, tier single, build 15862437). key = the NATURAL key `ayanamsha_id, fact_category, fact_key, fact_subject` (`fact_id` is metadata: a rebuild that re-issues ids is not drift). content = `fact_value_text, fact_value_num, fact_value_jsonb, unit` (every number scale-trimmed, also inside the jsonb). metadata = `fact_id, build_id, verification_pass_status, engine_version, salience_formula_ver, tolerance_arcsec, citation_*, source_calculation, formula_*, near_*_flag, vargottama_flag_at_point, cross_ayanamsha_divergence_arcsec`. `computed_at` is in neither (audit).
- *Daśā row* (levels 1 to 3 of Vimśottarī / lahiri over the bound horizon). key = `ayanamsha_id, system_id, level_n, start_iso, coalesce(kp_sublevel,'')`. content = `lord_graha, end_iso, parent_level_n, parent_start_iso` (the parent is a natural pointer, never `parent_row_id`) and `lord_path` (the lords from the root MD down to the row: a function of the row and of its ancestors, which are always consumed with it — a period over the horizon has its parent over the horizon too — and the contract checks that the path is derivable from the copy alone). metadata = `dasha_row_id, build_id, parent_row_id, verification_pass_status, engine_version` and **`ordinal_path`** (the 1-based index of the period among its siblings at every level). The ordinal path counts EVERY sibling in the table, including periods wholly outside the horizon that the snapshot never consumed: in round 5 it sat in the content, so one upstream Mahādaśā added before the horizon flipped every consumed row to HARD drift although no consumed value had changed. It now only NAMES a moved boundary ("the 2nd AD of the 3rd MD moved by N s", with the full lord path) and decides nothing.

**Digest recipes (both recomputable from the copy alone, same helpers as today: `ka_gochara_canonical_json`, `ka_gochara_sha256_hex`).** IDENTITY digest = sha256 over the lines `canonical_json(key)|sha256(canonical_json(content))`, sorted by the FULL line in "C" collation and joined by newline (stored in the EXISTING columns `l1_facts_digest` / `dasha_digest`, so `input_digest` and every inventory / ledger digest keep their recipe, only their input values change). METADATA digest = the same over `canonical_json(key)|sha256(canonical_json(metadata))` (informational; never enters `input_digest`). A missing block contributes `MISSING`. The digest is a function of the MULTISET of lines and of nothing else (ordering by the key alone left the order of conflicting duplicates unspecified). **This recipe freezes at the first production capture (0 production snapshots on 2026-10-06): a later change of what is content needs a new column or a recipe version, never an edit.**

**Capture (the BEFORE INSERT trigger): what is validated is exactly what is stored.** The builder submits KEYS (the consumed ids) and the identity digests. The database builds both copies and reads the upstream scope in ONE statement (one upstream snapshot; READ COMMITTED under the per-chart lock is enough), assigns the copies to the row, and then judges THE STORED VALUE: (a) the capture CONTRACT over the copy itself, a pure function of the two copies and the bound manifest horizon (`ka_gochara_search_copy_violations`): the ten natal longitude facts each exactly once and each with a number; Vimśottarī MD, AD, PD of the canonical ayanāṃśa only, each row overlapping the horizon and of positive length, row ids unique; each level present, unique by start, contiguous and covering the horizon; the hierarchy closed INSIDE the copy — every AD and PD names, by natural pointer, a period of the copy at the level above that contains it, that period's row id is the row's `parent_row_id`, and the lord path is the parent's plus the row's lord; and ELIGIBILITY, decided here once: every row of the copy carries tier `two_pass_verified`, a build, and the copy holds one build. (b) the copy is the WHOLE upstream scope and nothing else: every upstream row of the scope, WHATEVER its tier or build, is in the copy (a row the copy lacks is refused by its key, row id, tier and build). (c) the submitted identity digests are the copy's. An independent Python statement of (a) (`inventory_verifier.copy_contract_violations`) is run by the writer and by every verification, and a test runs every shape through both.

**What the functions compare after capture. TIER AND BUILD ARE METADATA: nothing below reads a tier.**
- *Upstream scope*: `ka_gochara_search_facts_live_population(chart)` and `ka_gochara_search_dasha_live_population(chart, horizon)` return, in the copy's shape, every upstream row of the scope (canonical ayanāṃśa; the ten subjects / Vimśottarī MD, AD, PD overlapping the horizon). They filter by what a row IS, never by its tier or build.
- *Completeness* (`ka_gochara_search_completeness_violations`, the 1232 body with ONE block replaced, which for a copy-bearing snapshot is one call to `ka_gochara_search_snapshot_copy_violations`): `input_snapshot_copy_inconsistent` — the STORED copy does not recompute to its STORED identity, metadata or input digest, or no longer satisfies the capture contract (a statement about the row; nothing upstream is read); `input_snapshot_required_scope` — the upstream scope is structurally broken (the contract with eligibility OFF); `input_snapshot_drift` — the identity digest of the upstream scope is not the stored one: a value changed, a row is gone, or an extra or conflicting row exists, whatever tier it carries (HARD: blocks seal; the detail names the keys). A metadata-only difference is NOT a violation row.
- *Moon-resolved domain* (`ka_gochara_search_moon_resolved_domain`): reads the snapshot's copy (`jsonb_array_elements`), not live `chart_dashas`.
- *Staleness* (`staleness.py`): components `l1_facts`, `dasha`, `input` (identity: hard), `l1_metadata`, `dasha_metadata` (soft) and `copy` (hard: the stored copy is consistent); `drifted` = any hard; `self_contained` is true only for a copy-bearing snapshot whose copy is consistent (`copy_consistent`, `copy_inconsistencies`); for daśā, the ordinal and lord path (read from metadata and content) name a moved boundary.
- *Verification job and seal brief*: read the copy only. `validate_consumed_dasha_population`, `rederive_ledger_digest`, `inventory_store.consumed_dasha_rows`, the natal chart and the P1 anchor SQL (`record_verifier`) take their rows from the copy, and the capture contract is checked ON THE COPY; the comparison with live L1 is the drift REPORT. The frozen-build constant `_C_BUILD` stays only as the writer's BUILD-time acceptance (`assert_single_pinned_build`, and the writer's capture-time `validate_consumed_dasha_population(against_live=True)`, which derives the upstream scope itself and requires the stored copy to equal it row for row); a sealed generation is never rejected for a later re-pin.

**Horizon implication (Ruling 7), read from production (read-only).** Consumed daśā rows (levels 1 to 3, the pinned build): scored horizon 1998-01-01..2026-04-17 = **151**; owner formula with start 1998-02-16 = **636** (8 + 64 + 564); start = birth 1984-02-05 = **712** (9 + 71 + 632); start = build date 2026-10-05 = **486**; the whole table for the chart (levels 1 to 3, 1950 to 2100) = **1,040**. At about 140 bytes of compact jsonb per row the copy is about 90 KB (636 rows) and at most about 150 KB (all 1,040); facts add 10 rows (about 3 KB). Negligible against the 5,962+ contacts a full build writes.

**Migration.** One additive PROTECTED migration (proposed number 1305, so it applies BEFORE G8's 1306, which re-syncs onto it: both replace `ka_gochara_search_completeness_violations` in full): preflight (objects exist, not already applied, as 1232 does); `ADD COLUMN`s; the copy / upstream-scope / contract / difference / digest functions (new names, nothing dropped); the additive copy-build trigger; the two replaced functions; grants (EXECUTE for the builder and verifier roles as 1206/1232 do); a read-only readback SQL; never edited after applied; verified applied, not assumed.

**Tests (real migration chain, disposable DB; `tests/l3/gochara/test_g12_snapshot_copy.py`).** (1) Build a candidate-shaped snapshot, then REBUILD the L1 rows with NEW row ids and a NEW build id and the same values: completeness returns no violation, the verifier and ledger re-derivation pass on the copy, staleness reports metadata-only drift. (2) Change ONE VALUE (a fact value, a daśā `end_iso`): completeness `input_snapshot_drift` and staleness identity drift = HARD. (3) A moved boundary: the ordinal and lord path name it. (4) Every shape of an incomplete, duplicated, inconsistent or false copy is refused by name at capture, and the database contract and the Python checker agree on every shape (one test runs them all through both and requires every code to be reached). (5) Moon-domain function unchanged result when L1 is rebuilt. (6) An upstream period wholly outside the horizon added after capture: gate unchanged, soft only. (7) An extra upstream row inside the scope: a violation at any tier. (8) A stored copy that does not recompute: `input_snapshot_copy_inconsistent`, never `self_contained`.

**Owner decision needed?** No: no policy is open. Choices recorded for the reviewers: tier (`verification_pass_status`) is METADATA after capture (a later second derivation of the natal positions is a verification, not a value, per Suvarṇa and Ruling S7) and an ELIGIBILITY condition of the daśā copy at capture; `computed_at` is audit and in neither digest; the ordinal path is metadata (round 6, R3). The first two are reversible in code; **what is in the identity block is NOT reversible once a production snapshot exists** (see the digest recipe). **Not in scope:** deterministic L1 ids (Suvarṇa's deferred item): v5 does not need them.
