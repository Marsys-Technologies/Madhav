# Node series, STEP 3 — the specification

## 0. What step 3 is, and the state it starts from
`ephemeris_daily` stores the **TRUE** node for Rāhu/Ketu (`node_mode='true'`, 183 352 rows; the 7 other bodies carry NULL; **0 `mean` rows today** — production, read-only). Native decision N-69 makes **MEAN** the system standard. Step 1 (#2877) and 1b (#2882) pinned every Pravāha reader to `node_mode='true'` through one helper (`services/w2g/node_series.py:26,33`) so MEAN rows can arrive without being read by accident. **Step 3 flips that pin to MEAN, makes TRUE-derived and MEAN-derived rows distinguishable in the data, and closes the freshness gate's blindness to the L1 inputs and the node series.** Everything below is what changes, where, and how it is proved.

Three facts that shape the design (production, 2026-10-02, canonical chart `482012f1…`):
* `kala_moorti_nirnaya`: 74 rows, `formula_version=ka_moorti_nirnaya_v1.0`. `kala_vedha_gochara`: 171 rows, `formula_version=ka_vedha_gochara_v1.0` (**main's writer already says `v1.1`** — production rows lag the code by one version and nothing noticed, because the gate never looks at `formula_version`; §5 closes that too).
* Existing rows already contain **TRUE-series consequences**: the Rāhu Capricorn run `2026-11-26 → 2027-11-01` graded `tamra`/`instant_grain`; the Moon `house_vedha` row `2026-11-28 → 2026-11-29` is *obstructed by Rāhu* and *cancelled by Ketu* — both statements are true only under the TRUE node (§8).
* Existing `house_vedha` rows carry `detail.upstream_fingerprint = {algorithm, n_transit_rules, bg_transit_rules, n_malefic_scale_rows, bg_vedha_malefic_scale}` (127 of 171 rows; the other 44 — `sarvatobhadra` and `latta` kinds — carry none), moorti rows carry `upstream_fingerprint = {algorithm, bg_transit_moorti, n_moorti_rows}`. **Neither contains an L1 or a node-series component.**

## 3. Row stamps (PROPOSED — exact names; "agreed with Suvarṇa" covered the *principle*: stamp every row, explicit where Rāhu/Ketu are involved, bump `formula_version`; the literal keys below are for her confirmation)
**`kala_vedha_gochara`** (all three kinds — `house_vedha` writer `:768–821`, `sarvatobhadra` `:841–887`, `latta` `:905–943`; every row serialises `detail` at `:959`):
* `detail.node_series = {"mode": "mean"}` on **every** row. Query form: `detail->'node_series'->>'mode'`.
* `detail.node_series_involved` (boolean) — `true` iff the row's `graha` ∈ {Rāhu, Ketu} **or** any interval's `obstructor_body` ∈ {Rāhu, Ketu} (house_vedha); for sarvatobhadra/latta, iff `graha` ∈ {Rāhu, Ketu}. This is the "explicit on rows whose obstruction set involved Rāhu/Ketu" requirement, and it is what lets a reader say *which* rows could differ between series.
* per interval in `detail.vedha_intervals[]` (`_house_vedha_detail` `:463–493`): `obstructor_node_series: "mean"` when `obstructor_body` is a node (absent otherwise).
* `detail.upstream_fingerprint` is **added to sarvatobhadra and latta rows** (today only house_vedha carries it) — otherwise the gate cannot see those kinds (§4).
**`kala_moorti_nirnaya`** (no `detail` column; adding one would be a migration — avoided): the series key rides the existing jsonb `upstream_fingerprint` (every row carries it, `writer.py:462`) as `node_series: {"mode": "mean"}` (uniform across rows, as the gate requires); per-row involvement is **derivable from the `graha` column** (`graha ∈ {Rahu, Ketu}`), so no per-row key is added. `formula_version` carries the bump (`:474`).
**Classification helper (the "never read TRUE as MEAN" rule)** — one function `stamped_node_series(row) -> 'mean' | 'true' | 'true_legacy' | 'unknown'`: a row with `node_series.mode` returns it; a row **without** the key returns `'true_legacy'` iff its `formula_version` is one of the pre-step-3 values (vedha v1.0/v1.1, moorti v1.0 — built when only the TRUE series existed), else `'unknown'`. **It never defaults to `'mean'`.**

## 4. The fingerprint (new requirement): fold the consumed L1 identity and the node series into both upstream fingerprints
**The defect (CLAUDE.md §N.8).** `services/ka_vedha_gochara/freshness.py` answers "built from what the reference tables say now?" from L0 tables only (`current_fingerprint` :46–48; `current_moorti_fingerprint` :77–79; `moorti_upstream_fingerprint` carries a comment, `ka_moorti_nirnaya/logic.py:196–198`, that `ephemeris_daily` is *deliberately not fingerprinted*). Rows built from an **old L1 build** therefore read `fresh`; so would rows from the wrong node series. A freshness signal with no detector for the claim it makes is null, not green.
**Design.**
1. **L1 identity** — the natal operands each writer *actually reads*. Both writers read exactly one L1 fact: `graha_position / MOON / longitude_sidereal` for `(chart_id, 'lahiri_chitrapaksha')` (`ka_vedha_gochara/writer.py:146–151,232–247`; `ka_moorti_nirnaya/writer.py:90–95,147–163`). Add one shared helper `l1_operand_identity(conn, chart_id, ayanamsha_id, operands)` returning `{"operands": [{category, subject, key, fact_id, build_id, value}], "digest": sha256}` where `value` is `fact_value_num` **as stored text** and `build_id` is added to the SELECT. Each writer declares its operand tuple as a **module constant next to its own SQL** and the writer, the freshness check and the 4.1 manifest all call the helper (the existing "same fetch path as the writer" principle, `freshness.py:5–6`). A missing operand ⇒ the identity cannot be computed ⇒ the state is `stale` (reason `l1_operand_absent`), never `fresh`.
2. **Node series** — `{"mode": "mean", "rows": <count>, "digest": <sha256 over the ordered (date, body, tropical_longitude::text) of the node_mode='mean' rows of Rāhu and Ketu>}`, computed **in SQL** (≈183 k rows; one aggregate per freshness check — acceptable for a gate that runs at build time, not per request; if Suvarṇa's L0 already publishes a digest of those rows for `bg_ephemeris`, reuse it instead — the point is a *content* identity, because a label alone cannot distinguish two builds of the same series). Zero MEAN rows ⇒ the fingerprint raises (`NodeSeriesError`), no silent default. Alternative if the cost is rejected: definition-only identity `{mode, swe_id: 10, ketu: "rahu+180"}` — weaker (blind to a corrected L0 rebuild); **recommended: the content digest**.
3. **Writer version** — fold `formula_version` into each fingerprint, so a writer version bump alone makes older rows stale (the v1.0-vs-v1.1 lag found above would have been caught).
4. **Shape.** vedha: `{algorithm, bg_transit_rules, n_transit_rules, bg_vedha_malefic_scale, n_malefic_scale_rows, node_series, l1, formula_version}` (`ka_vedha_gochara/logic.py:524–547` gains parameters; `ALGORITHM` string unchanged). moorti: `{algorithm, bg_transit_moorti, n_moorti_rows, node_series, l1, formula_version}` (`ka_moorti_nirnaya/logic.py:202–217`). Both still digest through the one `canonical_digest` (`gochara_kernel/fingerprint.py:12–18`).
5. **API.** `current_fingerprint(conn)` / `current_moorti_fingerprint(conn)` (`freshness.py:46,77`) take `chart_id` (every caller already has it: `check_*_freshness(conn, chart_id)` :51,82). `FreshnessReport` (:34–43) gains `components: dict` — how many rows differ in each component (`rules`, `scale`, `node_series`, `l1`, `formula_version`, `unstamped`) — so a stale verdict is diagnosable. The vedha check reads **all** kinds (`:56–61` today selects `vedha_kind='house_vedha'` only).
**What `stale` then means.** *The row's recorded input identity is not the input identity a rebuild would stamp now* — a **provenance** statement, not a materiality judgement: an L1 rebuild that moves the Moon by 0.7″ makes the rows stale even though they are numerically valid (Suvarṇa's interval note). That is the honest signal; whether the change matters is a separate question the gate does not answer.
**What happens to existing rows on the day the code deploys — they read `stale`, by construction, with no migration and no row rewrite.** The gate compares the stored fingerprint to the recomputed one by dict equality (`freshness.py:66,108`); the stored dicts lack `node_series`/`l1`/`formula_version`, so they differ ⇒ `mismatched` ⇒ `stale`. The 44 sarvatobhadra/latta rows (no fingerprint at all) now count as `missing` ⇒ `stale`. Test: build rows with the *old* fingerprint shape → `stale`; this is the regression that proves "stale, not fresh".
**Consequence to state plainly.** From the deploy until the rebuild the overlay gate is **closed** for every chart: the governed `'4.1'` run and `step06_*` refuse (`StaleOverlayRefusal`); the served engine does not (§5). That is the intended safe state.

## 5. The served `gochara_v3` engine reads both tables with no freshness gate — decision: **a named limit, plus a stamp-only provenance disclosure; no recompute gate**
Sites: `services/gochara_v3/context.py:520–578` (`_fetch_vedha_rows`, already selects `detail` and `formula_version`) and `:581–627` (`_fetch_moorti_rows`, selects neither), consumed at `engine.py:497` (`make_gate`) and the W2.2 mechanism.
**Why not a gate.** (a) A gate would zero the overlay modifiers for the canonical chart from the deploy day until the rebuild — a served-quality regression with **no numerical cause** (Suvarṇa: the L1 rebuild moves the Moon ≤ 0.665″, nearest sign edge 62″). (b) A recompute-based gate costs a node digest per request. (c) Only Rāhu/Ketu-involved rows can differ between series, ~10 days per ingress; the stamps identify them exactly. (d) The engine makes no freshness *claim*, so it is not an §N.8 earned-signal violation — the defect is silent consumption of unstamped provenance, which a disclosure repairs.
**What step 3 adds (no extra query):** the vedha SELECT already returns `detail`/`formula_version`; add `formula_version, upstream_fingerprint` to the moorti SELECT (`:601–609`) and expose per-row `stamped_node_series` (§3 helper). The engine's response carries `overlay_provenance = {node_series: {mean: n, true_legacy: m, unknown: k}, formula_versions: {…}, involved_rows_by_series: {…}}` in its disclosure/`judgment_flags` — **numerical behaviour unchanged**. **Named limit L-V3-1:** *the served engine does not gate on overlay freshness; between the L1 rebuild and the step-3 rebuild it answers from the existing rows, provenance-stale only; the disclosure above names which rows are TRUE-derived.* The step-3 rebuild closes it.
**Other unguarded overlay readers — same named limit, same disclosure (no gate):** `pipeline/orchestrator/writers/ka_sangam.py:1039–1062` and `services/ka_sangam/engine.py:73` (vedha windows); `scripts/kala_gochara_cutover/step06b_windows_projection.py:1868–1880` (read *after* the gate at :2219–2227); the TS served tools `platform/src/lib/retrieval/registry/layers/L3_kala/query_vedha_gochara.ts:138–150` (already returns `detail`, so `node_series` is served as soon as it is stamped) and `query_moorti_nirnaya.ts:100–112` (add `formula_version` and the fingerprint's `node_series` to its SELECT — Suvarṇa's layer).
