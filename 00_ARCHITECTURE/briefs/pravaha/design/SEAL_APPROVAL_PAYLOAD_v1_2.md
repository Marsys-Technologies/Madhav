# The seal approval — payload, flow, receipt, and exactly what each layer enforces

## 1. The payload (`seal_approval_payload/1`) — IMPLEMENTED (Stream A `seal_brief.py`)
Canonical JSON, produced by the verifier identity's `--brief` mode and hashed (sha256 = the **brief digest**): schema; chart/generation; manifest identity; result policy; the candidate adapter's gate (must be empty or no brief is produced); per-class inventory/ledger digests and the persisted, VERIFIED, pinned-runner window attestations; the persisted attestation rows as stored; **the generation-wide output identity** (every column except `created_at` of ten generation-scoped tables — the record, prerequisite, contact, window, window-record, path-pin and inventory tables plus the input snapshot, obligations and interval ledger — and, through the shared boundary module, the build coverage partitions, the publication content digest and the legacy-projection count); code identity (the verification runners, the manifest-pinned implementation digest, the sealing commit); migration-ledger evidence (1204, 1206, 1232, 1233, 1240, 1241); disclosures; "a seal is not a flip". **Round 12 (R12-1) widens the candidate boundary** — Stream A's plan: one shared boundary module covering the build's coverage partitions (every column but `created_at`), the manifest's `writer_asset_id` and `ephemeris_backend`, the exact publication `content_digest`, and a gate arm forbidding legacy `kala_gochara_contacts` / `kala_gochara_windows` rows for a governed generation. The claim is about **semantic candidate identity**, not every possible byte (`created_at` and the deliberately excluded on-demand Moon query receipts, AM-4, are outside it).

## 2. The flow — what runs where
1. **Brief** — the Cloud Run verification job under the **verifier** identity, `--brief` mode (not `--report-only`). Produces `{brief, sha256}`; refuses (exit 3, reasons named) if the gate has any violation, a class has no persisted verification, a grain is not VERIFIED, the runner is not the manifest's pinned code, or the manifest is not a candidate.
2. **The workflow's `brief` job** (draft PR #2975; no environment, no sealer credential; runs only from `main` at one reviewed commit): extracts the brief from the execution's logs (exactly one entry or refuse), **re-checks it** (digest recomputed, gate clean, every grain VERIFIED, policy `all_null_candidate/1`, sealing revision = this commit), **displays** it in the run summary and **retains** it as an artifact.
3. **Approval** — the `gochara-seal` environment gate; the approver (the steward, under the owner's ruling #2) approves with a comment line `brief-digest: <hex>  run: <id>  attempt: <n>`.
4. **The workflow's `seal` job** (the sealer credential exists only here): re-checks the retained brief, **retrieves THIS run's approval** from the approval API, and refuses an absent, malformed, wrong-run, wrong-attempt or stale approval **before any database contact**; then calls Stream A's **seal job** (`pipeline/orchestrator/seal_job.py`), which reads only the sealer DSN, refuses unless the session is the sealer, owns **one explicit transaction** — recompute the payload under the seal locks, refuse on mismatch, publish, the authoritative SQL seal (the combined gate on the published row), the receipt — and requires policy `all_null_candidate/1`. Any non-zero exit fails the run; a failure after publication rolls publication back with the rest.

**The transport (v1.2, F-R13-2, MEASURED).** The brief is the verifier job's one stdout line `{"brief": <payload>, "persisted": {brief_id, manifest_id, state_digest}, "sha256": <digest>}`; `persisted` is the database's own attestation that THIS brief was written to `ka_gochara_seal_brief` and is not part of the digest. On the composed rig the line is 18,275 bytes (≈ 8.0 KB fixed + ≈ 10.3 KB per class), ≈ 275 KB projected at 26 classes × 4 grains — above Cloud Logging's 256 KiB entry limit — so the emit is **chunked** above 200,000 bytes (`{"brief_chunk": {index, total, sha256 of the whole line, data}}`, 60,000-character slices) and the sealing workflow's extractor reassembles by index. The emit side is Stream A's, not yet written; until it lands a full-generation brief does not transport (fail-closed).

## 3. The receipt — DECIDED: R1, a database table in 1240 (no extra migration)
`ka_gochara_seal_approval(chart_id, generation, manifest_id, brief_digest, approver_login, approved_by_note, run_id bigint, run_attempt, workflow_commit, sealed_by, approved_at)`, PK `(chart_id, generation)`, FK to the seal row (deferred), append-only triggers, plus the **first-seal constraint trigger** and `ka_gochara_seal_receipt_missing(uuid,text)`.
**What SQL enforces (and only this):**
- the receipt table is **append-only** (UPDATE / DELETE / TRUNCATE refused);
- a **first** seal cannot COMMIT unless a receipt row exists for that (chart, generation) naming **that manifest** and carrying a **well-formed 64-hex digest** (a deferred constraint trigger, AFTER INSERT on the seal table — so a REPLAY, which inserts no row, and every seal that predates 1240 are untouched);
- the receipt's FK to the seal row means a receipt cannot exist without a seal; because a first seal cannot commit without the receipt, "exists" means "written in the sealing transaction";
- the publication flip and the seal row are in whatever transaction the caller opens; **same-transaction publication is supplied by the seal job, not by SQL**.
**The persisted-brief binding (1240, F-R12-4).** `--brief` also INSERTs the brief into the append-only `ka_gochara_seal_brief` (the verifier identity inserts, the sealer only reads; the database attests the manifest, the state digest of the candidate it was produced for, the session login and the time). The receipt's deferred trigger refuses a digest that is not the CURRENT persisted brief for that manifest and state: `receipt_brief_not_persisted`, `receipt_brief_superseded`, `receipt_brief_state_changed`. So "the receipt names a digest the verifier computed for this very candidate" is database-enforced; **who persisted it** is not checked by the trigger (it rests on 1241 v6 granting INSERT to the verifier alone; `seal_flow` is asked to also check `produced_by`, F-R13-4). `sealed_by` / `approved_at` are database-attested by a BEFORE INSERT trigger.
**What SQL does NOT enforce:** that the digest **equals** the one the approver saw (a sealer role could write any well-formed digest — the seal job's recompute is what binds approval to the exact output); that the approver login or note is true; that `approved_at` / `sealed_by` are anything but **defaults** — `sealed_by DEFAULT session_user` and `approved_at DEFAULT now()` can be overridden by an INSERT that names them, because 1241 grants the sealer table-wide INSERT. **Stream A's plan** makes them database-attested (a BEFORE INSERT trigger sets both) and adds a deferred check that the seal is this transaction's first seal with the same manifest; **it landed in 1240** (BEFORE INSERT attestation trigger; `sealed_by` and `approved_at` are database-attested). Also: the FK references only `(chart_id, generation)`, so a receipt added later to a pre-1240 seal does not get the first-seal trigger's manifest validation.

## 4. What the whole arrangement claims — and does not
**Claims** (when the workflow and the seal job are accepted and executed): the approved candidate identity still matches under the seal locks; the required verification state is current; the authoritative SQL checks passed on the published row; a permanent seal/receipt pair committed. **Does not claim:** independent human judgment or a second actor (same account — native ruling #2); attribution beyond the shared login and the supplied approval note; honest computation by a compromised verifier or sealer; exact contact-multiset completeness beyond the declared certification limits; numerical validity or activation; serving activation. A seal is not a flip.
