# The seal approval — payload, flow, receipt, and exactly what each layer enforces

## 1. The payload (`seal_approval_payload/1`) — IMPLEMENTED (Stream A `seal_brief.py`)
Canonical JSON, produced by the verifier identity's `--brief` mode and hashed (sha256 = the **brief digest**): schema; chart/generation; manifest identity; result policy; the candidate adapter's gate (must be empty or no brief is produced); per-class inventory/ledger digests and the persisted, VERIFIED, pinned-runner window attestations; the persisted attestation rows as stored; **the generation-wide output identity** (every column except `created_at` of ten generation-scoped tables — the record, prerequisite, contact, window, window-record, path-pin and inventory tables plus the input snapshot, obligations and interval ledger — and, through the shared boundary module, the build coverage partitions, the publication content digest and the legacy-projection count); code identity (the verification runners, the manifest-pinned implementation digest, the sealing commit); migration-ledger evidence (1204, 1206, 1232, 1233, 1240, 1241); disclosures; "a seal is not a flip". **The candidate boundary (R12-1, IMPLEMENTED in `candidate_boundary.py`):** one shared boundary module covering the build's coverage partitions (every column but `created_at`), the manifest's `writer_asset_id` and `ephemeris_backend`, the exact publication `content_digest`, and the gate arm `legacy_projection_rows_present` forbidding legacy `kala_gochara_contacts` / `kala_gochara_windows` rows for a governed generation. The claim is about **semantic candidate identity**, not every possible byte (`created_at` and the deliberately excluded on-demand Moon query receipts, AM-4, are outside it).

## 2. The flow — what runs where (current; workflow draft #2975, job definition draft #2976)
1. **Brief** — the Cloud Run verification job under the **verifier** identity, `--brief` mode (not `--report-only`). It refuses (exit 3, reasons named) if the gate has any violation, a class has no persisted verification, a grain is not VERIFIED, the runner is not the manifest's pinned code, or the manifest is not a candidate; otherwise it **persists** the brief (`ka_gochara_seal_brief`, DB-attested) and prints chunk lines then one compact `BRIEFED` line (below).
2. **The workflow's `brief` job** (no environment, no sealer credential; `main` only, one reviewed commit): checks the verification job is DEFINED with the immutable image digest the registry holds for this commit; starts the execution **asynchronously**, records its id at once, polls to a terminal state, and **cancels** a still-running execution after any non-success exit; reads the **EXECUTED resource** (image digest, service account, runner commit, exact args, the one secret, one task, no retries); reassembles the brief from the **root `jsonPayload`** of the execution's logs; **re-checks** it (digest over the file bytes, persisted receipt names the manifest, gate clean, every grain VERIFIED, policy `all_null_candidate/1`, sealing revision = this commit); writes the **envelope** (execution id, image digest, run, attempt, commit, brief digest, persisted brief id); **displays** it and **retains** it under a name carrying run id + attempt. **Log labels are not producer attestation.**
3. **Approval** — the `gochara-seal` environment gate; the approver (the steward, under the owner's ruling #2) approves with the comment line `brief-digest: <hex>  run: <id>  attempt: <n>  brief-id: <n>`.
4. **The workflow's `seal` job** (the sealer credential exists only here): downloads the artifact of **this run and attempt**; re-checks the brief and the envelope against this run/attempt/commit; selects the approval **by what its comment names** (never by API order; any ambiguity refuses and requires a fresh run) **before any database contact**; then calls Stream A's **seal job** (`pipeline/orchestrator/seal_job.py`), which reads only the sealer DSN, refuses unless the session is the sealer, owns **one explicit transaction** (statement timeout 15 min, lock timeout 2 min) — recompute the payload under the seal locks, refuse on mismatch, publish, the authoritative SQL seal (the combined gate on the published row), the receipt — and requires policy `all_null_candidate/1`. Any non-zero exit fails the run; a failure after publication rolls publication back with the rest.
5. **Reconcile** — always after the seal step: a read-only step reports SEALED / NOT_SEALED / INCONSISTENT / UNREADABLE from the publication, seal and receipt rows (a lost COMMIT acknowledgement is not inferred from the run status).

**The transport (v1.2, F-R13-2, MEASURED then CHOSEN).** The brief is the canonical JSON of the payload; its sha256 is the digest. On the composed rig it is ≈ 17.7 KB (≈ 7.4 KB fixed + ≈ 10.3 KB per class), ≈ 255–274 KB at 26 classes × 4 grains — at or above Cloud Logging's 256 KiB entry limit. So the verifier's `--brief` (always chunked since Stream A head a289b38eb, ST-TRANSPORT-FREEZE-1) prints chunk lines `{"b64", "brief_chunk": i, "of": N, "sha256"}` (≤ 48 KiB raw each) and a final compact line `{"brief_bytes", "brief_chunks", "brief_file", "persisted": {brief_id, manifest_id, state_digest}, "sha256", "status": "BRIEFED"}`; the sealing workflow reassembles the bytes from the execution's logs and checks them against the compact line. `persisted` is the database's attestation that this brief was written to `ka_gochara_seal_brief`; it is not part of the digest. **ST-WIRE-2 (final):** the compact line also carries `contract_version: "seal_brief_transport/1"` on the compact line (chunk lines carry no version key) and `producer: {commit, image_digest, execution_id}`; the approval file is `seal_approval/2` with the required `brief_id` and `producer_execution_id`; Cloud Run's Struct logging loses key order and turns every number into a double, so every integer is read through a strict integral conversion and printed text is never compared.

**Fresh versus reuse (v1.2, F-R14-5).** The seal job accepts a still-current earlier brief named by a fresh approval from a different run — a property of the database/seal-job rule that the workflow never exercises (every run briefs afresh, so the earlier brief is `receipt_brief_superseded`; a seal-only re-run has no artifact). Reaching it needs a hand-run `seal_job` with the sealer DSN: inside the trusted system, outside the ceremony. A cancelled execution that persists its brief after the next run's brief supersedes it and the seal refuses — fail-closed; confirm CANCELLED before a fresh run.

## 3. The receipt — DECIDED: R1, a database table in 1240 (no extra migration)
`ka_gochara_seal_approval(chart_id, generation, manifest_id, brief_digest, brief_id bigint NOT NULL, producer_execution_id text NOT NULL, approver_login, approved_by_note, run_id bigint, run_attempt, workflow_commit, sealed_by, approved_at)` (`brief_id` and `producer_execution_id` are NOT NULL: the receipt names the SPECIFIC persisted brief and the verifier execution that produced it), PK `(chart_id, generation)`, FK to the seal row (deferred), append-only triggers, plus the **first-seal constraint trigger** and `ka_gochara_seal_receipt_missing(uuid,text)`.
**What SQL enforces (the receipt table's own rules; the persisted-brief binding follows):**
- the receipt table is **append-only** (UPDATE / DELETE / TRUNCATE refused);
- a **first** seal cannot COMMIT unless a receipt row exists for that (chart, generation) naming **that manifest** and carrying a **64-hex digest that is the current verifier-persisted brief**, by its **`brief_id`**, its **`producer_execution_id`** and its **producer commit = the receipt's `workflow_commit`** (below) (a deferred constraint trigger, AFTER INSERT on the seal table — so a REPLAY, which inserts no row, and every seal that predates 1240 are untouched);
- the receipt's FK to the seal row means a receipt cannot exist without a seal; because a first seal cannot commit without the receipt, "exists" means "written in the sealing transaction";
- the publication flip and the seal row are in whatever transaction the caller opens; **same-transaction publication is supplied by the seal job, not by SQL**.
**The persisted-brief binding (1240, F-R12-4, F-R13-4).** `--brief` also INSERTs the brief into the append-only `ka_gochara_seal_brief` (the verifier identity inserts, the sealer only reads; the database attests the manifest, the state digest of the candidate it was produced for, the session login and the time). The receipt's deferred trigger refuses a digest that is not the CURRENT persisted brief for that manifest and state, a receipt whose `brief_id` is not that brief's (`receipt_brief_id_mismatch`), whose `producer_execution_id` is not that brief's execution (`receipt_brief_execution_mismatch`) or whose commit is not that brief's producer commit (`receipt_brief_producer_commit_mismatch`) — `receipt_brief_not_persisted`, `receipt_brief_superseded`, `receipt_brief_state_changed` — **nor one whose attested `produced_by` is not `gochara_verifier`** (`receipt_brief_not_from_verifier`, Stream A `d85125c2e`). So "the receipt names a digest the verifier computed for this very candidate" is database-enforced, including WHO persisted it. `sealed_by` / `approved_at` are database-attested by a BEFORE INSERT trigger.
**What SQL does NOT enforce (current):** that the approver login or note names the hand that clicked; that the approver saw the digest; that the sealing workflow computed the digest honestly with the brief code (it is part of the trusted system); that a genuine OLDER same-state brief — still the current persisted one — was not replayed by an approval the approver already gave (the digest, brief-id, run and attempt in the approval and the retained envelope, and the fresh-run rule, close this procedurally; SQL sees only "the current persisted brief by the verifier for this state"); that publication happens in the same transaction (the seal job supplies that). **Enforced by SQL (current):** append-only receipt; no first seal without a receipt naming that manifest, the specific persisted brief (`brief_id`), its execution and its producer commit; the receipt's digest is the CURRENT brief **persisted by the `gochara_verifier` login** for the unchanged state (`receipt_brief_not_persisted` / `_superseded` / `_state_changed` / `receipt_brief_not_from_verifier`); `sealed_by` and `approved_at` are database-attested (a BEFORE INSERT trigger overwrites what the insert names).

**Correction to 1240's §4c comment (F-R14-3; the comment text itself is not corrected in the file, but 1240's BYTES HAVE CHANGED since it was first noted — current candidate hash `9c9f113a97ac864d3a1908fb94a87df517b1d77616bf1e4e956c81f17df1a893`, authoritative = the committed `EXPECTED_WINDOW_SHA256.txt` at the sitting):** the comment says legacy writers of non-governed generations "neither take the lock nor need EXECUTE on any function". True for the ROW guard; NOT for the STATEMENT-level trigger on `kala_gochara_publication`, which fires for every UPDATE/DELETE statement and locks every chart that has a governed row — so every such writer needs EXECUTE on `ka_gochara_lock_chart(uuid)` and READ COMMITTED, and a governed row for any non-canonical chart makes every publication UPDATE/DELETE raise. Runbook §4.1 carries the pre-window read-only checks. **TRUNCATE (R15-4, stated as it is):** 1240 installs a CONDITIONAL `ka_gochara_boundary_2_no_truncate` guard on the four boundary relations (refuses when the table holds a governed row); builder/verifier/sealer hold NO TRUNCATE privilege (ACL). The condition is sound at READ COMMITTED; an owner maintenance transaction at REPEATABLE READ with a stale snapshot could miss a governed row committed after it (owner-only hardening, Stream A's fix pending) — so the claim is: ordinary roles cannot TRUNCATE; owner maintenance is guarded only under READ COMMITTED. **Paths outside the guard (disclosed):** the table owner, trigger disabling / `session_replication_role`, and a legacy relation created after 1240 (counted but unguarded until a follow-up adds the guard — rule: the same migration that (re)creates it adds the guard).

## 4. What the whole arrangement claims — and does not
**Claims** (when the workflow and the seal job are accepted and executed): the approved candidate identity still matches under the seal locks; the required verification state is current; the authoritative SQL checks passed on the published row; a permanent seal/receipt pair committed. **Does not claim:** independent human judgment or a second actor (same account — native ruling #2); attribution beyond the shared login and the supplied approval note; honest computation by a compromised verifier or sealer; exact contact-multiset completeness beyond the declared certification limits; numerical validity or activation; serving activation. A seal is not a flip.

**Honesty sentence (F-R14-7).** In the single-account flow `approver_login` and the note's `actor:` are the same login whenever the steward dispatches under the owner's account: the receipt records the login twice and the hand zero times; the steward's report to the owner is the only record that distinguishes them.
