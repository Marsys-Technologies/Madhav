## 4. The sealing chain end to end — what enforces what

The question: can a seal be committed without (i) a brief persisted by the verifier identity for the current state of the generation, (ii) an approval for this workflow run and attempt naming that digest, (iii) the environment gate? Read against 1240 (`db27905a…`), 1241 v6, `seal_brief.py`, `seal_flow.py`, `seal_job.py`, the #2975 workflow and scripts.

**(i) A persisted brief for the current state — ENFORCED BY THE DATABASE, with one precise qualification.** At COMMIT of any first seal: the seal row needs a receipt naming its manifest with a 64-hex digest (`zz_receipt_required`, 1240:971–987); the receipt needs a seal row of the same manifest written in THIS transaction (`zz_first_seal`, 834–849; `sealed_at = transaction_timestamp()`); and the receipt's digest must equal the LATEST `ka_gochara_seal_brief` row for (chart, generation), for the same manifest, whose attested `state_digest` still equals `ka_gochara_brief_state_digest()` evaluated now, under the seal locks (`zz_persisted_brief`, 854–869 → 751–767). The brief row's `manifest_id`, `state_digest`, `produced_by`, `produced_at` are overwritten by the attest trigger whatever the INSERT said (722–741), and a brief for a non-candidate manifest is refused there. So: a **fabricated digest** is refused (`receipt_brief_not_persisted`; composed 1211 does it as the real sealer login); a **brief for another manifest** cannot exist (the attest trigger pins the current candidate; `persist_brief` raises `manifest_changed` if the payload disagrees, 252–254); a **superseded brief** is refused by the latest-row rule (1229); **state changed after the brief** — any row of the twelve covered tables, the build coverage, the manifest identity or the legacy count — is refused by the state digest (762–763), and that digest is computed inside the brief transaction under the same advisory locks the builder takes (`brief()` → `take_locks`, seal_brief.py:232, 267–269), so nothing can slip between the payload read and the attestation. **Qualification:** the database enforces "persisted by a session holding INSERT on `ka_gochara_seal_brief`" — by 1241 v6 that is `gochara_verifier` only (and the table owner / a superuser, who are outside every guard here) — not "persisted by the verifier identity" as a trigger predicate (F-R13-4). And the database cannot know that the persisted digest is the sha256 of a payload: that equality is workflow code — the check script recomputes it from the retained text (`gochara_seal_brief_check.py:67–70`) and the sealer recomputes it from the database under the locks (`recompute_under_locks`, 272–287; post-publication again, seal_flow.py:46–55). A compromised verifier login could persist an arbitrary string and a modified sealing workflow could receipt it; both are inside the stated trusted system.

**(ii) An approval for this run and attempt naming that digest — ENFORCED BY WORKFLOW CODE ONLY.** `gochara_seal_approval.py` reads this run's approval history with the run's own token, takes the LATEST review of `gochara-seal`, requires state `approved`, a non-empty login, and exactly one distinct well-formed line `brief-digest: <64 hex>  run: <id>  attempt: <n>` whose run and attempt are this run's and whose digest is the retained brief's (36–71); it writes the approval file with a MECHANICAL note `ruling:<id>; actor:<github.triggering_actor>` (25–29). `seal_flow.parse_approval` / `check_approval_note` / `execute_seal` re-check the schema, the note grammar (`NOTE_FORMAT`, 81), the actor against `GITHUB_TRIGGERING_ACTOR` (124–137) and the run/attempt against `GITHUB_RUN_ID`/`GITHUB_RUN_ATTEMPT` (184–186). **Near-miss notes** (uppercase hex, a truncated digest, extra words on the line, `attempt: 2` on attempt 1) are refused — tests 164–180; a free-typed note never reaches the receipt because the workflow writes the note, not the approver. **Trailing newlines** are harmless everywhere (per-line regex; `strip()` in the extractor; the digest is recomputed over parsed JSON; `$(…)` strips). **Re-runs/second attempts**: an attempt-1 approval does not satisfy attempt 2 (the comment names the attempt; `execute_seal` compares the env). **Concurrent runs**: serialised by the concurrency group (yml 45–47); a second seal of a sealed generation refuses at `_current_and_complete` ("the manifest is 'published'", exit 3) and the SQL seal is idempotent. **What the database does here: nothing.** `run_id`, `run_attempt`, `approver_login`, `approved_by_note`, `workflow_commit` are stored as supplied, with only non-blank/`>= 1` CHECKs (1240:792–795). Anyone holding the sealer DSN and a current persisted brief can run `seal_job.py` with a hand-written approval file and the database will commit the receipt. That is the disclosed trusted-system boundary; say it in exactly these words (the packet's §R12a already does, nearly).

**(iii) The environment gate — ENFORCED BY GITHUB CONFIGURATION ONLY.** The seal job declares `environment: gochara-seal` (yml 143) and the DSN is read nowhere else (static test 22–33); GitHub holds the job and the secret until the single reviewer approves, admins cannot bypass, only protected branches may use it (runbook act 5). Neither the database nor `seal_job.py` can tell whether it is running inside that gate; the only evidence is possession of the DSN. If the DSN ever leaves the environment (a reviewed workflow printing it; a repo admin re-scoping the secret), (iii) is enforced by nothing. Disclosed; keep it disclosed.

**Split or injected log entries.** The extractor requires exactly one distinct `{"brief"…` entry that parses (16–36) and refuses a split; injection of a second brief refuses (two distinct); an injected brief with the real one absent WOULD pass the brief job's check and be displayed — but the seal then fails at `persisted_brief_problem` because it was never persisted by the verifier. Note that anyone with `logging.logEntries.create` on the project can write an entry carrying the execution's labels; the log view filters, it does not authenticate. The transport's integrity therefore rests entirely on (i), which is the right place for it. **A brief from an older job execution** is excluded by the `execution_name` label filter (yml 101) and, if replayed, decided by the state digest.

**What is enforced by nothing:** that the approver read the brief; that the sealing workflow at the dispatched commit is honest (CI + merge queue + Codex review, no second human); that `GITHUB_RUN_ID`/`GITHUB_TRIGGERING_ACTOR` in the seal job's environment are truthful (GitHub's, assumed).

## 5. The in-database state digest (`ka_gochara_brief_state_digest`, 1240:655–688)

**Complete for "the approved brief describes exactly what is sealed"?** Yes, for the semantic candidate identity the authors claim, with the exclusions they name. I enumerated every `ka_gochara_*`/`kala_gochara_*` relation whose DDL carries both `chart_id` and `generation` across every migration on the integration ref: `contact`, `eval_window`, `eval_window_record`, `eval_window_verification`, `generation_seal`, `record_prerequisite`, `relationship_record`, `seal_approval`, `seal_brief`, `search_input_snapshot`, `search_interval`, `search_inventory`, `search_inventory_verification`, `search_obligation`, `search_path_pin`, `kala_gochara_contacts`, `kala_gochara_coverage`, `kala_gochara_publication`, plus the legacy `kala_gochara_windows`. The digest hashes twelve of them row by row (every column but `created_at`), the build-kind coverage rows, the manifest's identity columns (never its publication columns, so `publish` cannot move it — I read `ledger.publish`, 593–648: it updates only `status`, `published_at`, `content_digest`, `row_counts`), and the legacy row count, whose only acceptable value is 0. Not hashed, correctly: the seal, receipt and brief tables themselves; the on-demand coverage kinds (AM-4); global referenced tables (physical objects, contacts' identities, sky events, the sealed registry) — covered by their own immutability guards and the 1206 census, stated in `candidate_boundary.NOT_COVERED`. I found no generation-scoped relation that is both semantic and unhashed.

**Deterministic?** Yes. Rows are ordered by `j::text COLLATE "C"`, the four rendering settings are pinned in the function definition (`TimeZone`, `DateStyle`, `IntervalStyle`, `extra_float_digits = 1` — the last matters because `to_jsonb(float)` goes through `float8out`), and identical rows are counted, not deduplicated. The Python payload digest orders by the database's default collation without `COLLATE "C"` (seal_brief.py:74–75) — self-consistent within one database, but a latent divergence from the SQL implementation; harmless today, worth a one-token fix.

**Too slow on a full generation?** Unmeasured, and the only published seal timing (453 ms at 7,488 obligations / 59,904 intervals, M3) predates the brief entirely. The approved flow now computes, under the chart EXCLUSIVE lock: the state digest three times (brief attest, the sealer's early check, the commit-time trigger), the Python payload three times (brief, recompute, post-publication re-check — each streaming every row of twelve tables to the client), and `_canonical_row_set` three times (two inside payloads, one in `publish`). At the M3 volumes that is on the order of 10⁵ rows × 6 client round-trips over a Cloud SQL proxy from a GitHub runner — plausibly tens of seconds, not minutes, but a number nobody has. Measure it on the composed rig at the real class count before the first seal (F-R13-9); it is not a correctness issue.
