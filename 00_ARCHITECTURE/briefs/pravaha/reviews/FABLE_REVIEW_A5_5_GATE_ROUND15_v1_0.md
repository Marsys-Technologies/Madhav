## 5. Lock order and liveness introduced by the new guards

Keys: the chart family key (one chart only — `ka_gochara_lock_chart` refuses any non-canonical chart `1153:445–448` and binds the transaction to one chart `:441–444`), the global key (EXCLUSIVE for registry writers `1153:517–527`, SHARED for chart writers), tuple locks. Order chart → global-SHARED is enforced by markers (`1153:449–452, 462–468`). New in 1240: the boundary row guards take the chart key inside BEFORE ROW triggers (`:962`); the publication statement trigger takes it BEFORE STATEMENT for every governed chart (`:994–1004`), i.e. before any tuple lock; the brief attest takes chart then global-shared inside a BEFORE ROW INSERT (`:741–742`, no unique index on the brief table, so no index lock precedes it).

**Who can block whom.** Any transaction holding the canonical chart key blocks the sealer at `take_locks` (`verification_job.py:243–247`, called at `seal_flow.py:239` as the first act after `set_local_timeouts :237`) and the verifier's brief (`verification_job.py:101–102`); both end in a NAMED refusal after `lock_timeout` 2 min (`seal_brief.py:418–420`; `seal_flow.py:246–249` `seal_lock_timeout`; `verification_job.py:106–110` `brief_lock_timeout`) with nothing written — a clean rollback, because the lock is the first statement of the transaction. A builder (an orchestrator build of the canonical chart, which holds the key for a whole substep) can therefore make the sealer fail by being alive; the GitHub concurrency group (`#2975 yml:60–62`) covers only the two workflows, not the orchestrator build. This is liveness, not integrity; it wants one explicit pre-condition line (F-R15-5 (b)). **The sealer blocks** every governed writer for the length of its transaction (measured ≈ 0.7 s synthetic; real counts unmeasured).

**Deadlock.** The sealer only READS coverage, contacts, records and the legacy relations (no tuple locks), UPDATEs the publication row (statement lock taken first, re-entrant) and INSERTs into tables the builder cannot write — so no cycle involving the sealer exists through any guarded path. The residue Codex named stands: UPDATE/DELETE on coverage / `kala_gochara_contacts` / `kala_gochara_windows` / contact / record by a NON-protocol writer locks the tuple before its row trigger asks for the chart key (no statement lock on the three legacy relations), and a `SELECT … FOR UPDATE` on `kala_gochara_publication` (no trigger fires) held by a transaction that then needs the key can form a cycle with the sealer's publish UPDATE; PostgreSQL aborts one participant. If the victim is the sealer: `DeadlockDetected` is caught as a generic error (`seal_job.py:85–87`, exit 5), the transaction is rolled back, reconcile reads NOT_SEALED, a fresh run is the retry. If the victim is the writer: the sealer proceeds and the writer is refused after COMMIT. Integrity holds either way; disclosed at `1240:944–947`. **Every failure path I traced is a rollback:** `conn.transaction()` scopes the seal (`seal_flow.py:236`); refusals before the transaction write nothing; a lost COMMIT acknowledgement is handled by reading state, never inferring it (`gochara_seal_reconcile.py:23–31`; yml `:296–311`).
