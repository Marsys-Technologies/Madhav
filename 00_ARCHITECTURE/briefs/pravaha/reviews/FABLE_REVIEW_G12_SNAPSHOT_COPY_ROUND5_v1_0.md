## Findings

**P2-1 — `ordinal_path` sits in the IDENTITY block, so the gate depends on rows the snapshot never consumed.** `content` includes `ordinal_path` [1305.sql:244-246], computed by counting ALL same-parent siblings in the table [218-237]; the completeness drift block hashes it [512-516]. Executed: adding one MD row entirely before the horizon → `input_snapshot_drift` plus six `content_differs: ['ordinal_path']`, `drifted=True`. Legitimate causes: a change of `WINDOW_START` [ga_dashas_writer.py:102] or of the backdating. Ruling 5 only needs the ordinal for naming moves; it can live in `metadata` and `_changes` can read it there. **Settle before the protected window applies 1305** (the recipe is frozen into every stored digest; today 0 production snapshots, so the cost is zero now and high later). Requires a steward nod because the design note lists it as content. Not merge-blocking if the HOLD status is kept.

**P2-2 — Capture binds a copy whose own tier/build the database never checks.** The trigger compares content digests only [420-425]; the required population is tier-filtered but the copy's rows are not. Executed scenario above: DB-accepted, Python-refused (`inventory_verifier.py:761-762`). Writer path refuses earlier (`dasha_builds_mixed`, dasha_read.py `assert_single_pinned_build`), and the gate closes immediately after, so no false seal — but the "contract fixed in the database independent of the builder" [1305.sql:26-29] is not fully independent. Fix: assert in the trigger that every copy element's metadata tier is `two_pass_verified` and one build (or compare the metadata digest of the required population). Can follow up.

**P3-1 — No post-insert detector that the stored copy recomputes to the stored digest** [505-516 compare live vs stored only; staleness likewise]. Executed: tampered copy reads clean in both. Mitigated by 1206's insert-only guard and by the Python job's re-derivation. Add `input_snapshot_copy_inconsistent` + a staleness field (§N.8). Follow up.

**P3-2 — Builder-omitted/extra row refusal is not by name** [421, 424 generic messages]; Python's by-name message [775] never runs because the INSERT fails first. Name the key difference. Follow up.

**P3-3 — Capture is not a single snapshot** (see B). Re-run the scope check in drift mode on the built copy after building, or use REPEATABLE READ for the snapshot substep. Follow up.

**P3-4 — `copy_digest` sorts lines by key only** [125]; with conflicting duplicates the concatenation order among equal keys is unspecified, so the live digest shown in staleness can flip between calls (never equals the stored one, so no false pass). Order by the full line. Follow up.

**P3-5 — `_answers_from_the_copy` launders any exception into `pytest.fail`** [test_g12:89-97], so a mutant that merely breaks copy parsing in those tests would count as CAUGHT by an otherwise honest harness. Narrow to database errors and `Unverifiable`. Follow up.

**P3-6 — Fixture fidelity:** stub `fact_value_num double precision` [test_a53_inventory.py:276] vs production NUMERIC [204_chart_facts.sql:19]. Under the stub, `trim_scale(f.fact_value_num::numeric)` [1305.sql:167] keeps only 15 significant digits (verified on PG 17: `(0.1+0.2)::numeric = 0.3` while `to_jsonb` gives `0.30000000000000004`); the exactness test passes only because it first ALTERs the column to numeric [test:528, 550]. Production is numeric, so the exact-comparison claim holds there; align the stub. Follow up.

**P3-7 — Header "WHY" partly stale:** `dasha_row_id` is a UUID5 stabilised across rebuilds [ga_dashas_writer.py:3474-3485], not a `gen_random_uuid` re-issue; the premise still holds via `build_id`/`engine_version`. Cosmetic.
