## 5. R13-2 — is every write that can change the digested state serialized through the sealer's COMMIT and refused afterwards?

**5.2 Deadlock.** Locks in play: the chart family key (one chart only — `ka_gochara_lock_chart` refuses any chart but the canonical one, 1153 `:445–448`, so no cross-chart ABBA is possible), the global family key (EXCLUSIVE for registry mutations via `ka_gochara_global_write_guard` 1153 `:517–527`; SHARED for chart writers), and tuple locks. Within one transaction the order chart → global-SHARED is enforced by 1153's markers (`:440–452, 465–469`): a transaction holding global-EXCLUSIVE cannot take a chart key and vice versa, and registry mutations never hold chart keys — so the wait graph between a sealer (chart, then global-shared) and a registry writer (global-exclusive) has no cycle. The new statement-level publication lock exists precisely to prevent the one cycle the sealer could enter — a writer holding the publication TUPLE while waiting for the chart key the sealer holds while the sealer waits for that tuple in `publish` (1240 `:950–953`); it takes the key in a BEFORE STATEMENT trigger, before `ExecBRUpdateTriggers` locks any tuple (1153 `:529–533`). The brief attest trigger takes chart then global-shared inside a BEFORE ROW INSERT trigger — before the heap insert and any unique-index lock — and in the `--brief` transaction both keys are already held re-entrantly (`take_locks`, `kernel verification_job.py:243–247`, called at `seal_brief.py:332`). The sealer's own `publish` fires the statement trigger with the key already held (re-entrant). **No deadlock path involving the sealer remains.** Residual, not involving the sealer: coverage/contacts/windows have the row guard but no statement lock, so a non-protocol UPDATE/DELETE of governed rows there holds tuples while waiting for the key; the only production writer of governed rows in those tables is the builder, which takes the key first (`ka_gochara_v5._take_chart_lock`), and PostgreSQL's deadlock detection resolves the hypothetical case fail-closed (F-R14-4).

**5.3 Remaining paths.** (i) **TRUNCATE** on `kala_gochara_coverage`, `kala_gochara_contacts`, `kala_gochara_publication`: no row trigger fires; 1240 adds no TRUNCATE refusal there (it does on every `ka_gochara_*` table and on the brief/receipt tables). (ii) **Table owner / trigger disable / `session_replication_role`**: outside the model, as every round has said — `perf_a53_seal_cost.py` itself uses `session_replication_role = replica` to clone, which shows the path.
