## 2. Handling secrets (applies to every act that sets a password)
```
# run inside ONE subshell; PW exists only there; xtrace OFF; nothing is echoed
( set +x; umask 077
  PW="$(openssl rand -hex 48)"                                  # 384 bits, URL-safe (hex), generated at execution
  printf "ALTER ROLE %s PASSWORD '%s';\n" "$ROLE" "$PW" | psql "$ADMIN_CONN" -v ON_ERROR_STOP=1 -X -q      # statement goes over stdin, not argv
  printf '%s' "postgresql://${ROLE}:${PW}@${DSN_HOST_PATH_AND_PARAMS}" | <secret-store write from stdin>    # same variable, second pipe
  unset PW )
```
- `printf` is a shell builtin: the password is in no process's argument list. `psql -c "…PASSWORD '…'"` and `--set=pw=…` are **forbidden** (argv is visible in `ps`).
- `DSN_HOST_PATH_AND_PARAMS` (host or `/cloudsql/<instance>` socket, port, database, `sslmode`) is copied from the **shape** of the builder's DSN with user and password blanked — obtained with a redacting transform (`sed -E 's#//[^@]*@#//USER:PASS@#'`), recorded in the act's report, never the builder's secret value.
- **The report carries only:** the secret's resource name and version id, the role name, and the read-only verification output.

## 5.3 Seal approval — the SAME account; the steward approves on the owner's authority (native ruling #2, overriding NRS-SEAL-APPROVER)
**The ruling.** No separate approver identity. The owner's account is the sole required reviewer of `gochara-seal`, and **the native has authorised the steward to access that account and approve seals on his behalf.** This overrides "no delegate ever" (NRS-SEAL-APPROVER §3).

**What the seal approval now is — and is not.** It is **NOT an independent human check**: the person who dispatches and the person who approves can be the same hand, under the same login, and GitHub records only the login. What stands between a bad generation and a seal is exactly: **(a) the database gate** — the combined candidate gate = 0, every window `VERIFIED` by the separate verifier job, the runner's code pinned to the manifest; **(b) the sealer step re-computing the gate against the briefed digest** and refusing on any difference; **(c) the steward approving ONLY when the seal brief (§6) shows gate = 0 and m of m `VERIFIED`**, and **reporting every approval to the owner immediately, with the brief attached.** No claim of "a human approved this seal" may rest on the approval click alone.

**What GitHub can and cannot enforce with ONE account (stated precisely):**
| setting | with a single reviewer account that is also the dispatcher | decision |
|---|---|---|
| required reviewers (one: the owner's login) | **Enforced:** a job in `gochara-seal` does not start, and its secret is not exposed, until an approval is recorded; the approval is recorded in the run and the audit log under the owner's login. It cannot tell the steward from the owner. | KEEP |
| `prevent_self_review` | Blocks the **user who triggered the run** from approving it. The steward dispatches under the owner's account, so with the flag `true` the only reviewer could never approve (a deadlock), and with a different dispatcher the flag would protect nothing against the steward's authority. **It cannot give independence here.** (Behaviour to be confirmed by the live-gate proof, not assumed.) | **`false`** — set deliberately and recorded |
| `can_admins_bypass` | **Enforceable:** repository admins cannot skip the environment's rules. | `false` |
| deployment branches | **Enforceable:** only protected branches can use the environment and its secret; the proof's step (2) shows a non-protected branch refused. | protected branches only |
| the sealing workflow's own text | **Enforceable by branch protection (reviewed pull request required to change a workflow on a protected branch)** — this is what stops an unreviewed workflow from reading the sealer secret after approval. **Confirmed read-only on 2026-10-02:** repository ruleset "main protection (org migration, merge queue)" is active on `main` and requires `pull_request`, status checks and the merge queue (no classic branch protection). Re-confirm before act 5. | CONFIRMED |
| attribution of who approved | **Not enforceable.** Mitigated by the approval **comment** (the API takes one): "approved by the steward under the owner's ruling #2; brief sha256 <digest>", and by the immediate report to the owner. | by procedure |

**The configuration that keeps the most protection:** `reviewers = [owner's account]`, `prevent_self_review: false`, `can_admins_bypass: false`, protected branches only, a sealing workflow that can only be changed through a reviewed pull request, the sealer DSN **only** as a `gochara-seal` environment secret, the brief digest re-checked inside the gated job, and the steward's report-with-brief to the owner after **every** approval. A stronger configuration (a second, non-agent identity) was available and the native chose not to use it; no second reviewer is added.

## 6. The seal brief the sealing workflow must show before the gate (ruling M20261002T123258-4613)
**Who produces it: the VERIFIER identity, never a third login.** The brief is a read-only `--report-only` step of the verification job, run **immediately before the seal**. The verifier already holds the reads and the gate EXECUTE; it writes nothing in this step. It emits the brief as a **workflow artifact together with its sha256** (the "briefed digest"). The sealing workflow **DISPLAYS that artifact before the approval gate**; after approval the **sealer step re-computes the combined gate itself and refuses if its result differs from the briefed digest.** **A stale brief makes the seal refuse:** any change after the brief was produced (a verification row, a manifest field, a grain status, the migration ledger, the code identity) changes the digest, so the seal exits with a named refusal and writes nothing; the owner re-requests a fresh brief and approves again.
