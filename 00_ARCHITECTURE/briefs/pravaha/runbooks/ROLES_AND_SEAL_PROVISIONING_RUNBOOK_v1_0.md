# Roles and seal provisioning — the runbook

## 0. What this is, in plain words
Option A needs two new database logins (a **verifier** and a **sealer**), a place for each password, a machine identity for the verification job, and an approval gate. This runbook is the exact, checkable sequence the **steward** follows — **once, in one sitting, immediately before the protected-window dispatch**, **after the steward has told the owner the sequence is starting** (the native's timing rule) — so that migration 1240's role-guarded grants fire on their own. The steward acts under the owner's authority: the native's direct rulings of 2026-10-02 (`decisions/NATIVE_DIRECT_RULINGS_20261002.md`) chose the one-shot workflow route (option A), the **same account** for seal approval with the steward approving on his behalf, and the tenth and eleventh acts. Only the **protected-window dispatch** and the **D-FLIP / D-T2** decisions remain reserved to the owner personally. Nothing here is run until the steward says so. Nobody sees a password.

## 1. Facts and standing rules this runbook rests on
1. **Order (NRS-CREDENTIAL-ACTS §2.5):** **7** (now, code only) → *[window preconditions hold; dispatch scheduled]* → **3 → 10 → 4 → 11 → 1 → (11 removed) → 5 → 2a** → *[live-gate proof, after 5 and before 2b]* → **9** (owner dispatches the window) → **8** (1241 by the ordinary deploy, then verify) → *[L1 read ACLs by the data-plane owner]* → *[Codex ACCEPT of the verification job]* → **2b → 6** → first operator-dispatched verification → first seal (owner approves).
2. **Identity.** Both CLIs on the steward's machine run as the owner's accounts (verified read-only: `gh api user` → `amonty84`; `gcloud auth list` → `mail.abhisek.mohanty@gmail.com`, project `madhav-astrology`). Every act therefore appears in the audit logs under the owner's identity. **The native has ruled (NATIVE_DIRECT_RULINGS_20261002 #2) that the SAME account is used for seal approval and that the steward may approve on his behalf — so the machine identity IS the reviewer, and the seal approval is not an independent human check (§5.3 states what remains).** Every report states the identity used.
3. **Roles are created by SQL `CREATE ROLE` over the ownership-admin path ONLY.** **Never** `gcloud sql users create` and never the console: both make the new user a member of `cloudsqlsuperuser`. Every role act ends with `SELECT pg_has_role('<role>','cloudsqlsuperuser','MEMBER')` = **false**.
4. **Passwords are never seen by anyone** (§2). Generated at execution, written once into the SQL statement and once into the secret store by `stdin` pipes, never echoed, never in argv, never in a file, never in a message.
5. **No grants are made in any act.** Grant sources for the two roles are 1240 (role-guarded, fires because the roles exist when it runs) and 1241 (belt-and-braces backfill carrying 1240's set too). A role created here holds **nothing** and belongs to **no** role.
6. **Pre-existence is a stop condition** for every resource named below.
7. **No production query beyond the read-only checks named here; none touches chart data.**
8. **No act is performed by analogy.** If a step is not written here, it is not authorised.

## 2. Handling secrets (applies to every act that generates a password)
**Under option A the verifier's password is generated and written INSIDE the reviewed workflow script** (`platform/scripts/gochara-provision-roles.sh`, PR #2963). It checks every exit, writes the secret store FIRST, discards server stderr (a server error can quote the statement and so the password), **rolls back its own partial work on EVERY exit path including a cancelled run** (`trap` on EXIT/TERM/INT), and — R12-3 — takes **the admin connection out of argv**: it parses `ADMIN_DATABASE_URL` once into the libpq environment of its own process (`PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/PGSSLMODE`), unsets the URL, and calls `psql` with no connection argument. **Corrected claim:** the secrets are in **no process's argument list**; the admin password **is** in that process's *environment* (readable only by the same user/root on the runner) and the generated password is in a shell variable and pipes only.
**The only place a person-run unit still generates a password is act 2b step 1 (the sealer's, on the steward's machine): `platform/scripts/gochara-sealer-stage-secrets.sh`** (R12-5 — an executable unit with explicit exit codes and a tested outermost boundary, replacing the inline wrapper that returned success after a failed write). Invoke it as:
```
DSN_TAIL='@/<db>?host=/cloudsql/<connection-name>' bash platform/scripts/gochara-sealer-stage-secrets.sh || { echo "STOP: act 2b step 1 failed — do NOT proceed to step 2" >&2; exit 1; }
```
**Exit codes (the caller stops on any non-zero):** 0 both written · 11 password generation/length (nothing written) · 12 the `gochara-seal` secret write failed (removal of it attempted) · 13 the staging secret write failed ((a) removed, (b) removal attempted) · 14 a write failed **and** the rollback could not be completed ((a) or (b) may remain — list both environments' secrets and delete by hand) · 2 bad input. The password is generated once, written as **(a)** the full DSN into `GOCHARA_SEALER_DB_URL` of `gochara-seal` (GitHub secret names cannot contain hyphens; `gh secret set` reads **stdin** when `--body` is omitted — it has no `--body-file`) and **(b)** alone into the TEMPORARY `GOCHARA_SEALER_PASSWORD_STAGING` of the cutover environment; never printed, never in argv, never in a file; unset on every exit path.
- **Partial-failure recovery (CORRECTED, R12-4):**
  | failed at | state left | do |
  |---|---|---|
  | step 1: exit 11 | nothing written | re-run step 1 |
  | step 1: exit 12 / 13 | the unit removed what it wrote (it says so) | confirm `gh secret list --env gochara-seal` lacks `GOCHARA_SEALER_DB_URL` and the cutover environment lacks `GOCHARA_SEALER_PASSWORD_STAGING`; re-run |
  | step 1: exit 14 | (a) and/or (b) MAY exist | delete by hand, verify absence in BOTH environments, then re-run |
  | step 2 (workflow `sealer-password`) fails **before** activation | the role is unchanged (`PASSWORD NULL`, or `NOLOGIN` in the fallback) | the script says so; delete BOTH secrets (verified), re-run step 1 |
  | step 2 fails **after** the activation committed, or the run is cancelled mid-flight | the script **compensates** (`ALTER ROLE … PASSWORD NULL`, `NOLOGIN` restored if it was NOLOGIN) **and verifies** (`rolpassword IS NULL`) — it prints `compensated and VERIFIED` | **do not assume the role is unset: read that line.** Only after `compensated and VERIFIED` may the secrets be deleted and step 1 re-run |
  | step 2: exit 70 (`ROLLBACK INCOMPLETE — THE SEALER MAY BE ACTIVE`) | the sealer may hold a live password | **incident:** run `ALTER ROLE gochara_sealer PASSWORD NULL;` (`NOLOGIN` too if it was `NOLOGIN`) by an authorised admin path, verify `rolpassword IS NULL`, and **only then** delete any secret — the stored copies are recovery material until the role's state is confirmed |
  | step 3 (deletion) fails | staging secret may remain | repeat until `gh secret list --env data-plane-production-cutover` lacks `GOCHARA_SEALER_PASSWORD_STAGING`; **do not proceed** to act 6 |
  The sealer keeps **`PASSWORD NULL`** until the human gate has been proven (the live-gate proof); activation is **one transaction with its postconditions** (R12-4): a failed postcondition commits nothing.
- `printf` is a shell builtin: the password is in no process's argument list. `psql -c "…PASSWORD '…'"`, `--set=pw=…`, and `gh secret set --body "$PW"` are **forbidden** (argv is visible in `ps`).
- `DSN_TAIL` (host or `/cloudsql/<instance>` socket, port, database, `sslmode`) is copied from the **shape** of the builder's DSN with user and password blanked — obtained with a redacting transform (`sed -E 's#//[^@]*@#//USER:PASS@#'`), recorded in the act's report, never the builder's secret value.
- **The report carries only:** the secret names/versions, the role name, and the read-only verification output.

## 5.3 Seal approval — the SAME account; the steward approves on the owner's authority (native ruling #2, overriding NRS-SEAL-APPROVER)
**The ruling.** No separate approver identity. The owner's account is the sole required reviewer of `gochara-seal`, and **the native has authorised the steward to access that account and approve seals on his behalf.** This overrides "no delegate ever" (NRS-SEAL-APPROVER §3).

**What the seal approval now is — and is not.** It is **NOT an independent human check**: the person who dispatches and the person who approves can be the same hand, under the same login, and GitHub records only the login. What stands between a bad generation and a seal is exactly: **(a) the database gate** — the combined candidate gate = 0, every window `VERIFIED` by the separate verifier job, the runner's code pinned to the manifest; **(b) the sealer step re-computing the gate against the briefed digest** and refusing on any difference; **(c) the steward approving ONLY when the seal brief (§6) shows gate = 0 and m of m `VERIFIED`**, and **reporting every approval to the owner immediately, with the brief attached.** No claim of "a human approved this seal" may rest on the approval click alone.

**What GitHub can and cannot enforce with ONE account (stated precisely):**
| setting | with a single reviewer account that is also the dispatcher | decision |
|---|---|---|
| required reviewers (one: the owner's login) | **Enforced:** a job in `gochara-seal` does not start, and its secret is not exposed, until an approval is recorded; the approval is recorded in the run and the audit log under the owner's login. It cannot tell the steward from the owner. | KEEP |
| `prevent_self_review` | Blocks the **user who triggered the run** from approving it. The steward dispatches under the owner's account, so with the flag `true` the only reviewer could never approve (a deadlock), and with a different dispatcher the flag would protect nothing against the steward's authority. **It cannot give independence here.** (Behaviour to be confirmed by the live-gate proof, not assumed.) | **`false`** — set deliberately and recorded |
| `can_admins_bypass` | **Enforceable:** repository admins cannot skip the environment's rules. | `false` |
| deployment branches | **Enforceable:** only protected branches can use the environment and its secret; the proof's step (2) shows a non-protected branch refused. | protected branches only |
| the sealing workflow's own text | **Enforceable by branch protection (reviewed pull request required to change a workflow on a protected branch)** — this is what stops an unreviewed workflow from reading the sealer secret after approval. **Confirmed read-only on 2026-10-02:** repository ruleset "main protection (org migration, merge queue)" is active on `main` and requires `pull_request`, status checks and the merge queue (no classic branch protection). Re-confirm before act 5. | CONFIRMED |
| attribution of who approved | **Not enforceable.** Mitigated by the approval **comment** (the API takes one): "approved by the steward under the owner's ruling #2; brief sha256 <digest>", and by the immediate report to the owner. | by procedure |

**The configuration that keeps the most protection:** `reviewers = [owner's account]`, `prevent_self_review: false`, `can_admins_bypass: false`, protected branches only, a sealing workflow that can only be changed through a reviewed pull request, the sealer DSN **only** as a `gochara-seal` environment secret, the brief digest re-checked inside the gated job, and the steward's report-with-brief to the owner after **every** approval. A stronger configuration (a second, non-agent identity) was available and the native chose not to use it; no second reviewer is added.

## 6. The seal approval payload and the sealing flow (R11-3; full design: `design/SEAL_APPROVAL_PAYLOAD_v1_0.md` — a PROPOSAL until Stream A's job-side functions exist)
**What this section replaces (and why):** v1.2 let the verifier's `--report-only` step produce the "brief" and the sealer re-check "the gate". Codex round 11 found that `--report-only` **skips** the gate; that the runbook required the **raw SQL function** to return zero on a **candidate** row (it cannot — the **candidate adapter** is what applies to a candidate; the raw function runs inside the seal, on the **published** row); that re-checking a gate result does not prove the approved candidate is unchanged (two different valid candidates can both give `[]`); and that the promised approver login/run id are not columns of the seal table.
**The flow:** (1) the **verifier identity** runs a **`--brief` mode** (not `--report-only`): the candidate adapter over the combined gate (it refuses to produce a brief if any violation exists), the **persisted attestations**, and the **generation-wide output identity** (every record, prerequisite, contact, window, member link, path pin and inventory header, including held/superseded-version rows), the code identity (the job's `DEPLOY_SHA` and implementation digest), the migration-ledger evidence (1204, 1206, 1232, 1233, 1240, 1241: filename, sha256, applied_at) and the disclosures, hashed as **one canonical complete approval payload** (`seal_approval_payload/1`) — the **brief digest**; emitted as a workflow artifact with its sha256. (2) The brief is **displayed** before the approval gate. (3) The approval comment carries **the brief digest**. (4) The **sealer**, in ONE transaction: takes the **seal locks** (chart, then global), **recomputes the payload**, **refuses on any mismatch** (a changed candidate with an empty gate invalidates the approval), publishes, runs the **authoritative SQL seal checks** (`ka_gochara_seal_generation`, whose triggers run the combined gate on the published row) and writes the **approval receipt**; a failure anywhere rolls everything back. (5) **Receipt storage:** a durable receipt linked to the seal — **DB table (R1, a protected-window migration) or repository receipt by pull request (R2, recommended for the all-NULL milestone)**: the steward/owner decides; the claim never says "recorded on the seal row". The brief still states: **a seal is not a flip**, the `DEPLOY_SHA` of the sealing code, and a link to the accepting review.
**Who approves, and what that is:** per §5.3 — the steward, on the owner's authority; the approval is **not** an independent human check; the guarantees are the adapter result, the pinned verification, that **the exact shown output is what is sealed**, and the authoritative SQL checks on the published row. The steward approves **only when the brief shows gate = 0 and m of m VERIFIED**, and reports every approval to the owner with the brief attached.
**Dependencies:** Stream A builds the `--brief` mode, the shared output-identity function and the sealer-side recompute; the narrow read grants (e.g. a column-level SELECT on the migration ledger) go into 1241 v4 only after the brief exists and each is proven necessary.
