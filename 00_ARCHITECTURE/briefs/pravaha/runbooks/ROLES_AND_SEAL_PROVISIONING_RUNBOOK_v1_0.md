# Roles and seal provisioning — the runbook

## 0. What this is, in plain words
Option A needs two new database logins (a **verifier** and a **sealer**), a place for each password, a machine identity for the verification job, and an approval gate. This runbook is the exact, checkable sequence the **steward** follows — **once, in one sitting, immediately before the protected-window dispatch**, **after the steward has told the owner the sequence is starting** (the native's timing rule) — so that migration 1240's role-guarded grants fire on their own. The steward acts under the owner's authority: the native's direct rulings of 2026-10-02 (`decisions/NATIVE_DIRECT_RULINGS_20261002.md`) chose the one-shot workflow route (option A), the **same account** for seal approval with the steward approving on his behalf, and the tenth and eleventh acts. Only the **protected-window dispatch** and the **D-FLIP / D-T2** decisions remain reserved to the owner personally. Nothing here is run until the steward says so. Nobody sees a password.

## 2. Handling secrets (applies to every act that generates a password)
**Under option A the verifier's password is generated INSIDE the reviewed workflow script and written to Secret Manager (a lasting secret version; the role's database password also persists — neither expires with the run)** (`platform/scripts/gochara-provision-roles.sh`, PR #2963). It checks every exit, writes the secret store FIRST, discards server stderr (a server error can quote the statement and so the password), **rolls back its own partial work on every exit path it can observe** (`trap` on EXIT/TERM/INT) — **not** after SIGKILL, runner loss or a lost acknowledgement: see the unknown-state inventory in §2, and — R12-3 — takes **the admin connection out of argv**: it parses `ADMIN_DATABASE_URL` once into the libpq environment of its own process (`PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/PGSSLMODE`), unsets the URL, and calls `psql` with no connection argument. **Corrected claim:** the secrets are in **no process's argument list**; the admin password **is** in that process's *environment* (readable only by the same user/root on the runner) and the generated password is in a shell variable and pipes only.
**The only place a person-run unit still generates a password is act 2b step 1 (the sealer's, on the steward's machine): `platform/scripts/gochara-sealer-stage-secrets.sh`** (R12-5 — an executable unit with explicit exit codes and a tested outermost boundary, replacing the inline wrapper that returned success after a failed write). Invoke it as:
```
# The SEALER's tail is the runner's LOOPBACK proxy form (the unit REFUSES the Cloud Run /cloudsql socket form — F-R13-7(d); the VERIFIER's act-1 tail is the socket form).
# The failure handler below is ACTIVE (it was a comment before): any non-zero exit stops the sitting here.
DSN_TAIL='@127.0.0.1:5432/<db>' bash platform/scripts/gochara-sealer-stage-secrets.sh || { echo "STOP: act 2b step 1 failed — do NOT proceed to step 2" >&2; exit 1; }
```
**Exit codes (the caller stops on any non-zero):** 0 both written · 11 password generation/length (nothing written) · 12 the `gochara-seal` secret write failed (removal of it attempted) · 13 the staging secret write failed ((a) removed, (b) removal attempted) · 14 a write failed **and** the rollback could not be completed ((a) or (b) may remain — list both environments' secrets and delete by hand) · 2 bad input. The password is generated once, written as **(a)** the full DSN into `GOCHARA_SEALER_DB_URL` of `gochara-seal` (GitHub secret names cannot contain hyphens; `gh secret set` reads **stdin** when `--body` is omitted — it has no `--body-file`) and **(b)** alone into the TEMPORARY `GOCHARA_SEALER_PASSWORD_STAGING` of the cutover environment; never printed, never in argv, never in a file; unset on every exit path.
- **Partial-failure recovery (CORRECTED, R12-4):**
  | failed at | state left | do |
  |---|---|---|
  | step 1: exit 11 | nothing written | re-run step 1 |
  | step 1: exit 12 / 13 | the unit removed what it wrote (it says so) | confirm `gh secret list --env gochara-seal` lacks `GOCHARA_SEALER_DB_URL` and the cutover environment lacks `GOCHARA_SEALER_PASSWORD_STAGING`; re-run |
  | step 1: exit 14 | (a) and/or (b) MAY exist | delete by hand, verify absence in BOTH environments, then re-run |
  | step 2 (workflow `sealer-password`) fails **before** activation | the role is unchanged (`PASSWORD NULL`, or `NOLOGIN` in the fallback) | the script says so; delete BOTH secrets (verified), re-run step 1 |
  | step 2 fails **after** the activation committed, or the run is cancelled mid-flight | the script **attempts compensation** (`ALTER ROLE … PASSWORD NULL`, `NOLOGIN` restored if it was NOLOGIN) **and verifies** with the evidence this admin path CAN produce (see "What proves the sealer has no password" below) — it prints `compensated and VERIFIED` ONLY when that evidence was obtained; **if the run was killed, lost its runner or lost an acknowledgement there is NO such line — classify the state as UNKNOWN and run the unknown-state inventory below before anything else.** Only after `compensated and VERIFIED` (or a completed inventory) may the secrets be deleted and step 1 re-run |
  | step 2: exit 70 (`ROLLBACK INCOMPLETE — THE SEALER MAY BE ACTIVE`) | the sealer may hold a live password | **incident:** run `ALTER ROLE gochara_sealer PASSWORD NULL;` (`NOLOGIN` too if it was `NOLOGIN`) by an authorised admin path, set the role comment to `gochara-provision:sealer-password-null`, collect the evidence listed under "What proves the sealer has no password", and **only then** delete any secret — the stored copies are recovery material until the role's state is confirmed |
  | step 3 (deletion) fails | staging secret may remain | repeat until `gh secret list --env data-plane-production-cutover` lacks `GOCHARA_SEALER_PASSWORD_STAGING`; **do not proceed** to act 6 |
  **What proves the sealer has no password — the REAL evidence (the admin route cannot read `rolpassword`; that unreadability is what broke the first design, F-R12-3).** The absence of a password is not directly observable through the Cloud SQL admin path, so the runbook never claims it was "read". The evidence is: (1) the compensating `ALTER ROLE gochara_sealer PASSWORD NULL` **returned success** in a logged admin session; (2) the role comment reads `gochara-provision:sealer-password-null` (`SELECT shobj_description(oid,'pg_authid') FROM pg_roles WHERE rolname='gochara_sealer'`; the script sets it in the same step); (3) **a loopback login attempt with the password that was staged is REFUSED** (the unit makes this attempt itself and prints it; by hand it needs the password, which only the unit ever held — so after a lost run, treat (3) as unavailable and rely on (1)+(2) plus the inventory below). Where the admin path happens to be allowed to read `pg_authid`, `rolpassword IS NULL` is an extra confirmation, never the required one.
  **Cleanup is best-effort, not guaranteed.** The scripts clean up on every exit path they can OBSERVE (EXIT, TERM, INT). After **SIGKILL, runner loss, a lost acknowledgement of an external mutation, or a cancellation that did not reach the runner**, the state is UNKNOWN. Do not infer safety from an absent final log line: run the **unknown-state inventory** before any retry — (i) roles: `SELECT rolname, rolcanlogin, shobj_description(oid,'pg_authid') FROM pg_roles WHERE rolname IN ('gochara_verifier','gochara_sealer')`; (ii) secret versions: `gcloud secrets versions list gochara-verifier-db-url` (exactly the expected versions, none unexpected-enabled); (iii) environment secrets: `gh secret list --env gochara-seal` and `--env data-plane-production-cutover` (the staging secret present or absent, as intended); (iv) IAM: `gcloud secrets get-iam-policy gochara-verifier-db-url` (act 11's temporary binding present or removed — the condition expiry is the backstop); (v) the act-7 preflight run. Report the inventory verbatim.
  The sealer keeps **`PASSWORD NULL`** until the human gate has been proven (the live-gate proof); activation is **one transaction with its postconditions** (R12-4): a failed postcondition commits nothing.
- `printf` is a shell builtin: the password is in no process's argument list. `psql -c "…PASSWORD '…'"`, `--set=pw=…`, and `gh secret set --body "$PW"` are **forbidden** (argv is visible in `ps`).
- `DSN_TAIL` is **different for the two roles**: the **VERIFIER's** tail (act 1; used by the Cloud Run job) is the Cloud SQL **socket** form `@/<db>?host=/cloudsql/<instance>`; the **SEALER's** tail (act 2b; used by the GitHub runner) is the **TCP loopback proxy** form `@127.0.0.1:5432/<db>` and the staging unit refuses any other. The verifier's tail is copied from the **shape** of the builder's DSN with user and password blanked — obtained with a redacting transform (`sed -E 's#//[^@]*@#//USER:PASS@#'`), recorded in the act's report, never the builder's secret value.
- **The report carries only:** the secret names/versions, the role name, and the read-only verification output.

**W2 statements (read-only):**
```sql
-- (a) effective table-level AND column-level UPDATE/DELETE holders, direct or inherited, plus the owner (superusers listed too)
SELECT c.relname, r.rolname, r.rolsuper, (c.relowner = r.oid) AS is_owner,
       has_table_privilege(r.oid, c.oid, 'UPDATE') AS tbl_update, has_table_privilege(r.oid, c.oid, 'DELETE') AS tbl_delete,
       (SELECT string_agg(a.attname, ',' ORDER BY a.attnum) FROM pg_attribute a
         WHERE a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped AND has_column_privilege(r.oid, c.oid, a.attnum, 'UPDATE')) AS col_update
FROM pg_class c CROSS JOIN pg_roles r
WHERE c.oid IN ('public.kala_gochara_coverage'::regclass, 'public.kala_gochara_publication'::regclass, 'public.kala_gochara_contacts'::regclass, 'public.kala_gochara_windows'::regclass)

       OR EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped AND has_column_privilege(r.oid, c.oid, a.attnum, 'UPDATE')))
```

**The decision is made: the approval receipt is a DATABASE table in 1240 (R1)** — not a proposal and not a repository file. (The earlier v1.2–v1.3 text that offered R1/R2 as undecided is superseded.)
**The flow (the contract at Stream A's frozen head — ST-TRANSPORT-FREEZE-1 / ST-WIRE-4, `df65685d0` and successors; workflow #2975):** (1) the **verifier identity** runs `--brief` in the Cloud Run verification job: the candidate adapter over the combined gate (no brief is produced if any violation exists), the persisted attestations, the **generation-wide output identity** (ten tables + the candidate boundary), the code identity, the migration-ledger evidence and the disclosures, hashed as ONE canonical payload — the **brief digest**; it **persists** the brief (`ka_gochara_seal_brief`) and prints chunk lines then ONE compact `BRIEFED` line (§6 transport below). (2) The **`brief` job** of the sealing workflow (no environment, no sealer credential, `main` only, one reviewed commit) first checks that the verification job is DEFINED with the immutable image digest the registry holds for this commit, starts the execution **asynchronously** (recording its id at once; cancelling it on any non-success exit of the step), reads the **EXECUTED resource** (image digest, service account, runner commit, exact arguments, the one secret, one task, no retries), reassembles the brief from the **root `jsonPayload`** of the execution's logs, **re-checks** it (digest recomputed over the file bytes; persisted receipt names the manifest; gate clean; every grain VERIFIED; policy `all_null_candidate/1`; sealing revision = this commit), writes the **envelope** (execution id, image digest, run, attempt, commit, brief digest, persisted brief id), **displays** it in the run summary and **retains** it under a name carrying **run id + attempt**. **Log labels are not producer attestation** (Cloud Logging does not authenticate who wrote an entry): the producer is established by the execution resource, the database-attested `produced_by` of the persisted brief, and the digest. (3) The steward approves the `gochara-seal` deployment with the comment line `brief-digest: <hex>  run: <id>  attempt: <n>  brief-id: <n>` — **only when the brief shows gate = 0 and m of m VERIFIED** — and reports the approval to the owner with the brief attached. (4) The **`seal` job** (the sealer credential exists only here) downloads the artifact of **this run and attempt** (a seal-only re-run has none and FAILS — it must not reuse an older attempt's brief; start a fresh run), re-checks the brief and the envelope against this run/attempt/commit, selects the approval **by what its comment names** (never by API order; any ambiguity — an approval and a refusal of one attempt, two approvals, an unattributable review — refuses and requires a fresh run) before any database contact, then calls Stream A's **seal job**, which owns ONE transaction (statement timeout 15 min, lock timeout 2 min): recompute under the seal locks → refuse on mismatch → publish → the authoritative SQL seal on the published row → the receipt; any failure rolls publication back too; any non-zero exit fails the run. (5) The job **always reconciles**: it READS the publication, seal and receipt rows and reports SEALED / NOT_SEALED / INCONSISTENT / UNREADABLE — a failed or cancelled status does not prove the transaction rolled back (a lost COMMIT acknowledgement), so the state is read, not inferred. INCONSISTENT or UNREADABLE = STOP and report; NOT_SEALED = nothing was published, a fresh run may be started.
**The wire contract (ST-WIRE-4 — the names of ST-WIRE-2 / ST-TRANSPORT-2 stand; ST-WIRE-3 withdrawn; FINAL — in Stream A's code and in #2975/#2976):** the compact line carries `contract_version: "seal_brief_transport/1"` (an unknown or MISSING value is refused; chunk lines carry no version key) and `producer: {commit, image_digest, execution_id}` — the commit of the code that produced the brief, the IMMUTABLE image digest and the Cloud Run execution, taken by the verifier from its own environment (`GOCHARA_RUNNER_COMMIT`, `GOCHARA_RUNNER_IMAGE_DIGEST` — set by #2976 at deploy from the digest it resolves — and Cloud Run's `CLOUD_RUN_EXECUTION`); a brief without a producer identity is refused by the verifier (`producer_identity_absent`). The approval file is **`seal_approval/2`** with the REQUIRED `brief_id` (positive integer) and `producer_execution_id` (non-blank) — `/1` is refused by the seal job — and the receipt records both. The workflow binds: the executed resource's image digest == the envelope's == the compact line's `producer.image_digest`; the execution id likewise (Cloud Run's `CLOUD_RUN_EXECUTION` is the execution NAME; the long `…/executions/<name>` form is accepted as the same execution — the first real execution settles which form it prints); `producer.commit == github.sha`.
**Log-entry facts the extractor is built for (Stream A):** Cloud Run parses a JSON object printed on stdout into the ROOT `jsonPayload`, a protobuf **Struct** — so **key order is lost and every number arrives as a double (3 → 3.0)**; delivery is at-least-once and unordered. The extractor therefore never compares printed text and reads every integer (`brief_chunk`, `of`, `brief_bytes`, `persisted.brief_id`) through a strict integral-double conversion (3.0 → 3; 3.5, a boolean or NaN is refused).
**The seal job's exit codes and named refusals (Stream A `eb6be1f41`):** 0 sealed · 2 refused, nothing written (named: `approval_malformed` — a `/1` file or missing fields —, `run_identity_absent`, `seal_lock_timeout`, `seal_statement_timeout`, `receipt_brief_id_mismatch` / `_execution_mismatch` / `_producer_commit_mismatch` / `_superseded` / `_not_persisted` / `_not_from_verifier` / `_state_changed`, `approval_note_not_mechanical`) · 3 the approval does not match the recomputed candidate · **4 identity or OWN-CHECKOUT check failed** (`identity_not_sealer`, or **`own_checkout_digest_mismatch` / `own_checkout_digest_unregistered`**: before ANY database contact the seal job compares the implementation digest of the checkout it runs from with `services/gochara_kernel/implementation_digest.lock.json`; the workflow therefore MUST run it from the checkout of `github.sha`, and a changed implementation module needs its lock regenerated in the same reviewed commit) · 5 unexpected error, transaction rolled back. The orchestrator maps each to a message and propagates the status unchanged.
**Fresh versus reuse (Fable F-R14-5).** The seal job's acceptance of a still-current EARLIER brief named by a fresh approval from a different run is a property of the DATABASE/seal-job rule ("the approval names the CURRENT brief, by id and execution, for THIS run and attempt") that **this workflow never exercises**: every full run executes `--brief`, which persists a NEW brief row, so any earlier brief is `receipt_brief_superseded` before a seal could name it, and a seal-only re-run has no artifact of its attempt and fails. The only way to exercise the reuse path is a hand-run `seal_job` with the sealer DSN — inside the trusted system and outside the ceremony; it is not a supported operator path. **The cancelled-execution race is fail-closed:** a cancelled execution that persists its brief AFTER the next run's brief supersedes that newer brief and the seal refuses; the procedural guard is the workflow's own warning — **confirm the cancelled execution reached CANCELLED before starting a fresh run**.
**Precondition: NO concurrent build or verification (F-R15-5).** No orchestrator build, rebuild or verification of the canonical chart may be in progress while the brief → seal run executes: any transaction holding the canonical chart's lock key blocks the sealer at its lock, which ends in `seal_lock_timeout` after 2 minutes (and the brief in `brief_lock_timeout`); #2975's concurrency group does NOT cover the orchestrator. Check before dispatch (the steward confirms no build is running) and do not start one until the run's reconciliation reports SEALED or NOT_SEALED.
**A reconcile after a later supersede reports INCONSISTENT BY DESIGN:** reconcile reads `published` + one seal + one receipt as SEALED; once the generation has been marked `superseded` (metadata-only withdrawal) the same reading is INCONSISTENT — it describes a lifecycle this workflow cannot produce, not an error; read the publication status before concluding anything.
**What SQL enforces about the receipt (scoped, current):** append-only; a **first** seal cannot commit without a receipt naming that manifest; the receipt's digest must equal the CURRENT brief that was **persisted by the `gochara_verifier` login** (database-attested `produced_by`) for that manifest and unchanged state — `receipt_brief_not_persisted` / `_superseded` / `_state_changed` / `receipt_brief_not_from_verifier`; `sealed_by` and `approved_at` are **database-attested** (a BEFORE INSERT trigger overwrites whatever the insert names); the receipt cannot exist without the seal row. **What it does not:** that the approver LOGIN names the hand that clicked; that the approver saw the digest; that a genuine OLDER same-state brief was not replayed by a still-valid approval (the digest/brief-id/run/attempt binding in the approval and envelope and the fresh-run rule address this procedurally); that the sealing workflow computed anything honestly (it is part of the trusted system); publication in the same transaction is the seal job's, not SQL's. The claim never says "recorded on the seal row".
**Who approves, and what that is:** per §5.3 — the steward, on the owner's authority; **not an independent human check**; the guarantees are the adapter result, the pinned verification, that **the exact shown output is what is sealed**, the authoritative SQL checks, and the receipt.
**The log transport — MEASURED, then CHOSEN (F-R13-2).** The full brief on the composed rig (one class, four grains) is **≈ 17.7 KB** of canonical JSON = ≈ 7.4 KB fixed + ≈ 10.3 KB per class (the `classes[]` entry 2.8 KB + the persisted attestation rows 7.4 KB, embedded as JSON-text strings). Projected to 26 classes × 4 grains: **≈ 274 KB (B's projection; Stream A's own measurement ≈ 255 KB) — at or above Cloud Logging's documented 256 KiB entry limit**, so one log entry cannot carry it (assumes 26 classes of four grains; the margin is inside the projection's error). **Decision (Stream A's implementation, steward-confirmed): the verifier's `--brief` (always chunked — there is no `--brief-chunks` flag; the only knob is `--brief-chunk-bytes`, default 48 KiB raw per chunk line) prints the full brief as chunk lines `{"b64": <base64 of a ≤ 48 KiB slice>, "brief_chunk": i, "of": N, "sha256": <digest of the whole brief>}` and ends with ONE compact result line `{"brief_bytes", "brief_chunks": true, "brief_file", "contract_version": "seal_brief_transport/1", "persisted": {brief_id, manifest_id, state_digest}, "producer": {commit, image_digest, execution_id}, "sha256", "status": "BRIEFED"}`** (ST-WIRE-4). The brief is the canonical JSON of the approval payload; **its sha256 IS the brief digest** (Stream A: `brief_bytes` refuses anything that does not hash to it). The sealing workflow runs the job with `--brief`, reassembles by index from the execution's logs (`gochara_seal_brief_extract.py`: arrival order never relied on; missing / different-duplicate / altered / mixed-brief / wrongly-sized chunks refused; an identical repeat collapsed), and checks the bytes against the compact line (`gochara_seal_brief_check.py`: sha256 of the file's bytes, the `persisted` receipt, the manifest, canonical form, gate, policy, revision). **Why chunks and not a file:** `--brief-out FILE` writes inside the Cloud Run container, which is gone when the execution ends — a file would need a bucket, a verifier write grant and a workflow read grant; the logs need only act 12. **State (historical heads are in the packet, not here — they go stale):** Stream A's emit side is written and frozen; the extractor/check are adapted; a **cross-PR round-trip test runs the real chunked output through the real scripts into the real seal job** on the composed integration ref (passes; see the current packet for the exact heads). **Not yet measured in a real Cloud Run execution** (Cloud Logging's per-entry limit applies to the 64 KB chunk lines — far below it — but only the first real run shows it).
