Option A needs two new database logins (a **verifier** and a **sealer**), a place for each password, a machine identity for the verification job, and an approval gate. This runbook is the exact, checkable sequence the **steward** follows — **once, in one sitting, immediately before the protected-window dispatch**, **after the steward has told the owner the sequence is starting** (the native's timing rule) — so that migration 1240's role-guarded grants fire on their own. Only the **protected-window dispatch** and the **D-FLIP / D-T2** decisions remain reserved to the owner personally. Nothing here is run until the steward says so. Nobody sees a password.

## 2. Handling secrets (applies to every act that generates a password)
**Under option A the verifier's password is generated and written INSIDE the reviewed workflow script** (`platform/scripts/gochara-provision-roles.sh`, PR #2963). It checks every exit, writes the secret store FIRST, discards server stderr (a server error can quote the statement and so the password), **rolls back its own partial work on EVERY exit path including a cancelled run** (`trap` on EXIT/TERM/INT), and — R12-3 — takes **the admin connection out of argv**: it parses `ADMIN_DATABASE_URL` once into the libpq environment of its own process (`PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE/PGSSLMODE`), unsets the URL, and calls `psql` with no connection argument. **Corrected claim:** the secrets are in **no process's argument list**; the admin password **is** in that process's *environment* (readable only by the same user/root on the runner) and the generated password is in a shell variable and pipes only.
**The only place a person-run unit still generates a password is act 2b step 1 (the sealer's, on the steward's machine): `platform/scripts/gochara-sealer-stage-secrets.sh`** (R12-5 — an executable unit with explicit exit codes and a tested outermost boundary, replacing the inline wrapper that returned success after a failed write). Invoke it as:
```
DSN_TAIL='@127.0.0.1:5432/<db>' bash platform/scripts/gochara-sealer-stage-secrets.sh   # the SEALER's tail is the runner's LOOPBACK proxy form (the unit REFUSES the Cloud Run /cloudsql socket form — F-R13-7(d); the VERIFIER's act-1 tail is the socket form) || { echo "STOP: act 2b step 1 failed — do NOT proceed to step 2" >&2; exit 1; }
```
**Exit codes (the caller stops on any non-zero):** 0 both written · 11 password generation/length (nothing written) · 12 the `gochara-seal` secret write failed (removal of it attempted) · 13 the staging secret write failed ((a) removed, (b) removal attempted) · 14 a write failed **and** the rollback could not be completed ((a) or (b) may remain — list both environments' secrets and delete by hand) · 2 bad input. The password is generated once, written as **(a)** the full DSN into `GOCHARA_SEALER_DB_URL` of `gochara-seal` (GitHub secret names cannot contain hyphens; `gh secret set` reads **stdin** when `--body` is omitted — it has no `--body-file`) and **(b)** alone into the TEMPORARY `GOCHARA_SEALER_PASSWORD_STAGING` of the cutover environment; never printed, never in argv, never in a file; unset on every exit path.
- **Partial-failure recovery (CORRECTED, R12-4):**
  | failed at | state left | do |
  |---|---|---|
  | step 1: exit 11 | nothing written | re-run step 1 |
  | step 1: exit 12 / 13 | the unit removed what it wrote (it says so) | confirm `gh secret list --env gochara-seal` lacks `GOCHARA_SEALER_DB_URL` and the cutover environment lacks `GOCHARA_SEALER_PASSWORD_STAGING`; re-run |
  | step 1: exit 14 | (a) and/or (b) MAY exist | delete by hand, verify absence in BOTH environments, then re-run |
  | step 2 (workflow `sealer-password`) fails **before** activation | the role is unchanged (`PASSWORD NULL`, or `NOLOGIN` in the fallback) | the script says so; delete BOTH secrets (verified), re-run step 1 |
  | step 2 fails **after** the activation committed, or the run is cancelled mid-flight | the script **compensates** (`ALTER ROLE … PASSWORD NULL`, `NOLOGIN` restored if it was NOLOGIN) **and verifies** (`rolpassword IS NULL`) — it prints `compensated and VERIFIED` | **do not assume the role is unset: read that line.** Only after `compensated and VERIFIED` may the secrets be deleted and step 1 re-run |
  | step 2: exit 70 (`ROLLBACK INCOMPLETE — THE SEALER MAY BE ACTIVE`) | the sealer may hold a live password | **incident:** run `ALTER ROLE gochara_sealer PASSWORD NULL;` (`NOLOGIN` too if it was `NOLOGIN`) by an authorised admin path, verify `rolpassword IS NULL`, and **only then** delete any secret — the stored copies are recovery material until the role's state is confirmed |
  | step 3 (deletion) fails | staging secret may remain | repeat until `gh secret list --env data-plane-production-cutover` lacks `GOCHARA_SEALER_PASSWORD_STAGING`; **do not proceed** to act 6 |
  The sealer keeps **`PASSWORD NULL`** until the human gate has been proven (the live-gate proof); activation is **one transaction with its postconditions** (R12-4): a failed postcondition commits nothing.
- `printf` is a shell builtin: the password is in no process's argument list. `psql -c "…PASSWORD '…'"`, `--set=pw=…`, and `gh secret set --body "$PW"` are **forbidden** (argv is visible in `ps`).
- `DSN_TAIL` (host or `/cloudsql/<instance>` socket, port, database, `sslmode`) is copied from the **shape** of the builder's DSN with user and password blanked — obtained with a redacting transform (`sed -E 's#//[^@]*@#//USER:PASS@#'`), recorded in the act's report, never the builder's secret value.
- **The report carries only:** the secret names/versions, the role name, and the read-only verification output.

## 5.3 Seal approval — the SAME account; the steward approves on the owner's authority (native ruling #2, overriding NRS-SEAL-APPROVER)
**The ruling.** No separate approver identity. The owner's account is the sole required reviewer of `gochara-seal`, and **the native has authorised the steward to access that account and approve seals on his behalf.** This overrides "no delegate ever" (NRS-SEAL-APPROVER §3).

**What the seal approval now is — and is not.** It is **NOT an independent human check**: the person who dispatches and the person who approves can be the same hand, under the same login, and GitHub records only the login. What stands between a bad generation and a seal is exactly: **(a) the database gate** — the combined candidate gate = 0, every window `VERIFIED` by the separate verifier job, the runner's code pinned to the manifest; **(b) the sealer step re-computing the gate against the briefed digest** and refusing on any difference; **(c) the steward approving ONLY when the seal brief (§6) shows gate = 0 and m of m `VERIFIED`**, and **reporting every approval to the owner immediately, with the brief attached.** No claim of "a human approved this seal" may rest on the approval click alone.

**What GitHub can and cannot enforce with ONE account (stated precisely):**
| setting | with a single reviewer account that is also the dispatcher | decision |
|---|---|---|
| required reviewers (one: the owner's login) | **Enforced:** a job in `gochara-seal` does not start, and its secret is not exposed, until an approval is recorded; the approval is recorded in the run and the audit log under the owner's login. It cannot tell the steward from the owner. | KEEP |
| `prevent_self_review` | Blocks the **user who triggered the run** from approving it. The steward dispatches under the owner's account, so with the flag `true` the only reviewer could never approve (a deadlock), and with a different dispatcher the flag would protect nothing against the steward's authority. **It cannot give independence here.** (Behaviour to be confirmed by the live-gate proof, not assumed.) | **`false`** — set deliberately and recorded |
| `can_admins_bypass` | **Enforceable:** repository admins cannot skip the environment's rules. | `false` |
| deployment branches | **Enforceable:** only protected branches can use the environment and its secret; the proof's step (2) shows a non-protected branch refused. | protected branches only |
| the sealing workflow's own text | **Enforceable by branch protection (a pull request through CI and the merge queue is required to change a workflow on a protected branch; the REVIEW of that change is Codex's, not a second human's — the ruleset cannot require an approving review a single account can't give itself)** — this is what stops a workflow that has not gone through CI and the merge queue (and Codex's review) from reading the sealer secret after approval. **Confirmed read-only on 2026-10-02:** repository ruleset "main protection (org migration, merge queue)" is active on `main` and requires `pull_request`, status checks and the merge queue (no classic branch protection). Re-confirm before act 5. | CONFIRMED |
| attribution of who approved | **Not enforceable.** Mitigated by the approval **comment** (the API takes one), which MUST be exactly the one grammar line `brief-digest: <hex>  run: <id>  attempt: <n>` (anything else is refused by `gochara_seal_approval.py` — the statement "approved by the steward under the owner's ruling #2" lives in the run summary and the receipt's mechanical note, not in the comment), and by the immediate report to the owner. | by procedure |

**The configuration that keeps the most protection:** `reviewers = [owner's account]`, `prevent_self_review: false`, `can_admins_bypass: false`, protected branches only, a sealing workflow that can only be changed through a pull request that passes CI and the merge queue (Codex is the reviewer), the sealer DSN **only** as a `gochara-seal` environment secret, the brief digest re-checked inside the gated job, and the steward's report-with-brief to the owner after **every** approval. ## 6. The seal approval payload and the sealing flow (full record: `design/SEAL_APPROVAL_PAYLOAD_v1_2.md`; the workflow is the draft PR #2975)
**The decision is made: the approval receipt is a DATABASE table in 1240 (R1)** — not a proposal and not a repository file. (The earlier v1.2–v1.3 text that offered R1/R2 as undecided is superseded.)
**The flow:** (1) the **verifier identity** runs `--brief` in the Cloud Run verification job: the candidate adapter over the combined gate (no brief is produced if any violation exists), the persisted attestations, the **generation-wide output identity**, the code identity, the migration-ledger evidence and the disclosures, hashed as ONE canonical payload — the **brief digest**. (2) The **`brief` job** of the sealing workflow (no environment, no sealer credential, `main` only, one reviewed commit) extracts it from the execution's logs, **re-checks** it (digest recomputed; gate clean; every grain VERIFIED; policy `all_null_candidate/1`; sealing revision = this commit), **displays** it in the run summary and **retains** it as an artifact. (3) The steward approves the `gochara-seal` deployment with the comment line `brief-digest: <hex>  run: <id>  attempt: <n>` — **only when the brief shows gate = 0 and m of m VERIFIED** — and reports the approval to the owner with the brief attached. (4) The **`seal` job** (the sealer credential exists only here) re-checks the brief, retrieves **this run's** approval and refuses an absent / malformed / wrong-run / wrong-attempt / stale one before any database contact, then calls Stream A's **seal job**, which owns ONE transaction: recompute under the seal locks → refuse on mismatch → publish → the authoritative SQL seal on the published row → the receipt; any failure rolls publication back too; any non-zero exit fails the run.
**What SQL enforces about the receipt (scoped):** append-only; a **first** seal cannot commit without a receipt naming that manifest with a well-formed 64-hex digest; the receipt cannot exist without the seal row. **What it does not:** that the digest equals the one the approver saw (the seal job's recompute does that; a sealer role could write any well-formed digest), that the approver login or note is true, or that the approver LOGIN names the hand that clicked (`sealed_by` and `approved_at` ARE database-attested — 1240's BEFORE INSERT trigger — and the digest must be the CURRENT brief the verifier persisted in `ka_gochara_seal_brief`: `receipt_brief_not_persisted` / `_superseded` / `_state_changed`); publication in the same transaction is the seal job's, not SQL's. The claim never says "recorded on the seal row".
**Who approves, and what that is:** per §5.3 — the steward, on the owner's authority; **not an independent human check**; the guarantees are the adapter result, the pinned verification, that **the exact shown output is what is sealed**, the authoritative SQL checks, and the receipt.
**The log transport — MEASURED (F-R13-2).** The `--brief` line on the composed rig (one class, four grains) is **18,275 bytes** = ~8.0 KB fixed + ~10.3 KB per class (the `classes[]` entry 2.8 KB + the persisted attestation rows 7.4 KB, embedded as JSON-text strings). Projected to 26 classes × 4 grains: **~275 KB, above Cloud Logging's documented 256 KiB entry limit** (assumes the real candidate has 26 classes of 4 grains — to be confirmed from the manifest; the margin is ~5%, inside the projection's error, so a single entry cannot be relied on). **Decision: chunked emit in the same log channel** — the verifier prints the single-line brief unchanged if it is ≤ 200,000 bytes, otherwise N lines `{"brief_chunk": {index, total, sha256 of the whole line, data: a 60,000-character slice}}`; the sealing workflow's extractor reassembles by index (arrival order never relied on; missing / duplicate-different / altered / mixed chunks refused; reassembly sha256 must match). **State today:** the extractor and its tests are written (#2975); **the verifier's emit side is Stream A's change and DOES NOT EXIST yet — until it lands, a full-generation brief will not transport (the extractor refuses, fail-closed).** (The earlier text "use a chunked emit then" described a mode that was not in code.) The alternative (a GCS object) was not chosen: it adds a bucket, a verifier write grant and a workflow read grant, where chunking adds no infrastructure.
**Dependencies before any dispatch (each stated as an act or a pre-condition with its verification and removal):** Stream A's `seal_job.py` on `main` at the sealing commit (§5.4); the verification job defined by #2976 (act 6) at the **same `main` commit** as the sealing workflow (**same-commit rule**, pre-condition P-SC below); the log view and its accessor binding (act 12 — `roles/logging.viewAccessor` on the view, not `roles/logging.viewer`); the sealing identity's execution right (act 13) and proxy right (act 14); the sealer's database CONNECT (P-CONN); the sealer DSN's tail is the runner's loopback proxy (`@127.0.0.1:5432/<db>`), not the Cloud Run socket form.
