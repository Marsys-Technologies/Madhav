# F-10 SPEC — `prashna_undertaking_get` election-window domain no-op + CL-03 shared harness

## 1. Root-cause statement

`register_p1_synthesis.ts`'s `muhurtaResult` query (election windows) ignores the caller's
`domain` entirely — unlike its sibling `anchorResult` in the same function, which applies
`AND pa.domain = $2` correctly — and the fix is not a simple "add a WHERE clause" because the
domain→action-class lookup (`actionClass`) is computed at line 968, textually and temporally
*after* `muhurtaResult` already executed at lines 921-931; the query has to be reordered, not
just extended.

## 2. Files to change (F-10's own point fix)

**`platform-mcp/src/tools/register_p1_synthesis.ts`:**
1. Hoist the `_DOMAIN_TO_ACTION` lookup + `actionClass` derivation (current lines 957-968) to
   *above* the `muhurtaResult` query (current line 921). No behavior change to the lookup
   itself — pure reorder.
2. Add `AND ($3::text IS NULL OR pm.action_class = $3)` to `muhurtaResult`'s SQL (current lines
   926-929), binding `actionClass` as `$3`. Use a nullable bind (not a hard filter) so a domain
   with no `_DOMAIN_TO_ACTION` entry degrades to the pre-fix behavior (global top-N) rather than
   silently returning zero rows — and that degraded case must set a `judgment_flags` entry (see
   #3) so it's visible, not silent.
3. Add a `judgment_flags` entry when the returned `election_windows` differ from what the
   domain-filtered set would be — specifically: if `actionClass` is null (domain not in
   `_DOMAIN_TO_ACTION`) OR the filtered query returns 0 rows and the handler falls back to the
   unfiltered top-N (to avoid an empty response with real data behind it — an honest-fallback
   case, not a bug), flag it explicitly: `election_windows_domain_unmatched` or
   `election_windows_fallback_unfiltered`. This closes D-2 sub-claim (c) (no disclosure).
4. No change to `anchorResult`, `ontologyResult`, `prashnaResult` — confirmed clean in Stage D
   §4a.

## 3a. Exit test — F-10's own point fix

New file: `platform-mcp/src/tools/__tests__/register_p1_synthesis.f10_domain_filter.test.ts`

- `prashna_undertaking_get({chart_id:'1c826d5a-...', domain:'health'})` vs
  `prashna_undertaking_get({chart_id:'1c826d5a-...', domain:'career'})` — assert
  `election_windows` DIFFER between the two calls (today: byte-identical — this assertion FAILS
  on current code).
- Assert every returned `election_windows[].action_class` equals the request's derived
  `content.action_class` OR a `judgment_flags` entry explains the mismatch (never both absent).
- Regression guard: `anchorResult`'s existing correct domain-filtering behavior is unchanged
  (same anchor rows returned for a fixed domain before/after this patch).

## 3b. THE CL-03 SHARED HARNESS (the actual deliverable of the exemplar lane)

**Mechanism being generalized:** a capability declares a parameter in its public schema
(directly, or forwarded through an alias/primitive boundary), the parameter is silently dropped
before reaching a WHERE clause or equivalent filter, and two otherwise-identical calls differing
only in that parameter return byte-identical results with no disclosure. Confirmed present in
F-10, F-03 (×4 capabilities), F-06, F-08 (routes to S3), F-26 (routes to S5 per lease update),
F-27, F-133 (routes to S3) — 7 distinct capabilities minimum, ~19 unverified candidate sites
found in Stage D census (§4c of F-10's DIAGNOSIS.md).

**New file:** `platform-mcp/src/lib/__tests__/param_parity_harness.ts` (generator, not a test
file itself) + `platform-mcp/src/tools/__tests__/param_parity.generated.test.ts` (generated
suite, checked in, regenerated by a script — not hand-written per tool).

**Design:**
1. **Input:** every registered MCP tool's Zod/JSONSchema `input_schema`, read from the same
   introspection surface `mcp_surface_profiles.generated.ts` already uses (confirmed live and
   current in Stage D — this file is regenerated on build, so the harness free-rides its
   freshness rather than re-deriving schema another way).
2. **Per declared optional/required parameter NOT in a fixed allowlist** (`chart_id`, `limit`,
   `offset`, `top_k` — these are cross-cutting and have their own dedicated coverage elsewhere,
   e.g. limit/offset get F-03's own fix; excluding them here avoids duplicate coverage, not
   avoiding the check):
   a. Construct two calls to the live tool, identical except for that parameter taking two
      distinct valid values (schema-derived where an enum exists; a small hand-authored
      `ADVISORY_TEST_VALUES` map for free-text/UUID params that can't be auto-generated safely).
   b. Call both against a fixed reference chart (the canonical chart_id where the tool needs
      one).
   c. Assert the two responses' `result_hash` (or, where absent, a stable JSON-normalized digest
      excluding known-nondeterministic fields — timestamps, request IDs) DIFFER.
   d. If they do NOT differ, the test FAILS **unless** the parameter is listed in a new
      `ADVISORY_PARAMS` registry (`platform-mcp/src/lib/advisory_params.ts`) with a
      one-sentence, human-authored justification for why this parameter is legitimately
      informational-only (e.g. a `notes` field, a `client_request_id` echo). An empty or
      missing justification does not suppress the failure — the registry entry itself IS the
      required written reason, enforced by a companion unit test that every `ADVISORY_PARAMS`
      key has a non-empty `reason` string.
3. **Recurrence guard is the harness itself**, run in CI on every PR touching
   `platform-mcp/src/tools/**` or `platform/src/lib/retrieval/registry/**` — a new capability
   that declares a filter param and drops it fails CI at merge time, not at the next manual
   audit.
4. **Coverage note:** this harness, run un-scoped (all registered tools, not just the 71's
   findings), will ALSO exercise `query_mantras` and `query_remedies_by_planet` (F-03's disputed
   siblings) and the ~15 unverified candidates from Stage D §4c — this is a feature, not scope
   creep: the harness doesn't "fix" anything by existing, it only fails a future PR that
   regresses one of these. Building the harness broadly does not require building fixes for
   findings outside the 71; a currently-failing assertion for an out-of-scope tool is committed
   as a documented `known_failures` skip-list entry (mirroring the CI cadence pattern in
   `ONGOING_HYGIENE_POLICIES §F`'s exit-code-3 known-residuals whitelist), not silently ignored
   and not silently fixed.

## 6. Dependencies and rollback note

- No dependency on F-03/F-06/F-08/F-26/F-27/F-133's own point fixes to land first — the harness
  is additive tooling; siblings' `known_failures` skip-list entries get removed as each lane's
  own point fix lands (a natural, visible "closing the loop" signal for the conductor/VERIFIER).
- `register_p1_synthesis.ts` is S5's per plan §2.1, ordered handoff to S4 once VERIFIER-passed —
  this spec's §2 point fix is the trigger for that handoff once built + verified.
- Rollback: §2 is a single-file, additive change (reorder + nullable bind + a new flags entry) —
  `git revert` sufficient. §3b (harness) is pure new test infrastructure — reverting it only
  removes a CI check, never touches runtime code.
