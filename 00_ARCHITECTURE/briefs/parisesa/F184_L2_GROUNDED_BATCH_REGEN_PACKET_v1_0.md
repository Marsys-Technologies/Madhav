# F-184 — regenerate `l2_grounded_batch_{1..6}.py` to carry `caveats`

## §1 — What this document is, and what it is not

This is the **rebuild specification** for step 2 of F-184. It is deliberately
**not a rebuild execution**. No production data, DB row, or committed static
module was regenerated by the lane that authored it. It follows the same
disclosed-not-executed shape as `F62_MOOLATRIKONA_REBUILD_PACKET_v1_0.md`.

## §2 — Why this exists (the picture-change this finding turned up)

F-184's originating brief assumed "wire `caveats` into `ground_signal()`'s
return and through the consuming serving surfaces." Investigation (this PR)
found `ground_signal()` and `ground_signals()` have **zero production
callers anywhere in this repository** — confirmed by exhaustive grep, not
inference:

```
grep -rn "ground_signal\b"  --include="*.py" .   # only the definition itself
grep -rn "ground_signals\b" --include="*.py" .   # only the definition itself
```

The engine's real, served output is six **frozen static Python modules**
committed once during the `l2-bodha-grounded` WS-2 session
(`00_ARCHITECTURE/CONDUCTOR/ws2/smriti/l2-bodha-grounded-pass.md`,
2026-06-05, tag `ws2-l2-grounded-complete`):

```
platform/python-sidecar/brahmagyan/bodha/l2_grounded_batch_{1..6}.py
```

Each carries a `GROUNDED_SIGNALS: dict[str, dict[str, Any]]` literal — 569
entries total (`SIG.MSR.001`–`SIG.MSR.569`), each with the same 6 keys
`ground_signal()` used to return (`rule_id`, `grounding_status`,
`source_school`, `verse_citation`, `match_confidence`, `match_rationale`).
**None carries `caveats`.** Adding the field to `ground_signal()`'s return
shape (done in this PR) is a precondition for these modules to ever carry it,
but does not by itself change what any of the six modules contain — nothing
imports `ground_signal`/`ground_signals` to regenerate them at import time or
at request time. `governance/check_earned_signal.py` names this corpus
explicitly (its N2 suppression note) as "the six
`brahmagyan/bodha/l2_grounded_batch_*.py` seed corpora."

## §3 — Why regeneration is a GA-3-class action, not a code change

Regenerating the six modules means re-running the actual grounding
computation — `ground_signals(msr_signals)` against the live ~1,370-rule WS-3
corpus — and overwriting six committed data files with the new output. That
is a **bulk content-regeneration action against a checked-in derived-data
corpus**, not a code edit:

1. **No generator script survives in the repository.** The batches were
   produced by an ad hoc script run inside the `l2-bodha-grounded` WS-2
   session and never committed. `grep -rln "l2_grounded_batch_1.py\|write.*GROUNDED_SIGNALS"
   00_ARCHITECTURE --include="*.py"` returns nothing. Regeneration requires
   re-authoring that script (source signals from `l2_signals_scaffold.py` /
   `MSR_v5_0.md`, or the `msr_signals` DB table — the two have not been
   cross-checked for drift as part of this packet) rather than re-running an
   existing one.
2. **The output is committed, hand-curated-adjacent content**, not a
   deterministic build artifact regenerated on every CI run — six PRs in the
   original session (`1a36db65`, `df0569d6`, `c15b7d6d`, `669988b7`,
   `10697361`, `3d48cefd`) each carried a distinct 100-signal batch, reviewed
   as data. A silent regeneration bypasses that review shape.
3. **`bo_laksana.py` / `l2_lenses_salience.py` and other L2 Bodha writers
   read committed constants derived from this pass** (e.g.
   `GROUNDED_SALIENCE_BASE = 0.82  # Mean match_confidence from l2-bodha-grounded pass`,
   `GROUNDING_STATUS = "GROUNDED"  # Updated from UNGROUNDED after
   l2-bodha-grounded`). A regeneration that changes `match_confidence`
   values (it should not, if scoring is unchanged — but this must be
   *verified*, not assumed) could invalidate those downstream constants.
   That verification is exactly the kind of review a GA-3 packet gates on.

This is the same shape CLAUDE.md §N.3 and the F-62 packet describe for
protected per-chart data — it is not a chart-scoped `chart_facts` rebuild
(no `ga_*`/`bo_*` writer runs against `ctx.db_conn`), but it is a **bulk
regeneration of committed derived content that a code-repair lane must not
execute unreviewed.** Per the hard constraint governing this PR, this
packet is being **queued, not executed.**

## §4 — Blast-radius, measured read-only

Read-only analysis against the current in-repo state (no rebuild run): for
each of the 569 signals in the six batches, look up the `rule_id` the batch
already recorded against the live WS-3 corpus (`load_all_rules()`) and check
whether that rule currently carries a non-null `caveats` value.

```python
from brahmagyan.bodha import _grounding_engine as ge
from brahmagyan.bodha import (
    l2_grounded_batch_1 as b1, l2_grounded_batch_2 as b2, l2_grounded_batch_3 as b3,
    l2_grounded_batch_4 as b4, l2_grounded_batch_5 as b5, l2_grounded_batch_6 as b6,
)
all_signals = {}
for b in (b1, b2, b3, b4, b5, b6):
    all_signals.update(b.GROUNDED_SIGNALS)
rules_by_id = {}
for r in ge.load_all_rules():
    rules_by_id.setdefault(r.get("rule_id"), []).append(r)
```

Results:

| Metric | Value |
|---|---|
| Total signals across the 6 batches | 569 |
| Total rules currently loaded by `load_all_rules()` | 1,370 (1,337 unique `rule_id`) |
| Signals whose recorded `rule_id` is still present in the live corpus | 569 / 569 (0 missing) |
| Signals whose matched rule currently carries a non-null `caveats` | **356 / 569 (62.6%)** |
| `rule_id` values with more than one corpus entry (ambiguous — see §5) | 64 |

**Reading this honestly:** if the six modules were regenerated today with no
other change, roughly 356 of 569 grounding assignments would gain a real
`caveats` string and the remaining 213 would gain an honest `caveats: None`
— consistent with the ws3 corpus occurrence counts already on record in the
F-184 finding brief (82/55/49/42/39 across the five canon batches). This
figure is an **estimate**, not a guarantee of what a real rerun would
produce, for the reason in §5.

## §5 — Open question this packet does not resolve

**Ambiguous `rule_id` collisions (64 ids, multiple corpus entries).**
`load_all_rules()` appends every YAML file's rules into one flat list with
no uniqueness check across files. Where the same `rule_id` string appears in
more than one loaded file/entry, `find_best_rule()`'s `score >
best_score` (strict, first-wins-ties) scoring means only one specific
instance is actually selected at grounding time, and it is not necessarily
the first one this packet's read-only script used for its `caveats` lookup
(§4 used `matches[0]`, the first-loaded instance). This does not affect
`ground_signal()`'s correctness (it always scores and picks a real rule
instance from the list it's given) but it does mean §4's 356-count is an
**upper-bound-adjacent estimate**, not an exact rerun result. A GA-3
execution that regenerates the batches would need to run the real
`ground_signals()` call end-to-end — not this packet's static lookup — to
get the exact per-signal answer. Whether the 64 duplicate `rule_id`s are
themselves a corpus-hygiene defect (same id reused across two WS-3 batch
files) is flagged here but not investigated further — it is a separate,
narrower finding candidate if intake wants it.

## §6 — What a GA-3 execution should do, and verify

1. Re-author (or locate, if one turns up during intake that this packet's
   grep missed) the script that calls `ground_signals()` against the full
   569-signal MSR set and serialises the result into the same
   `GROUNDED_SIGNALS: dict[str, dict[str, Any]]` shape, now including
   `caveats`.
2. Diff the regenerated output against the current six files on every field
   OTHER than `caveats` — `rule_id`, `grounding_status`, `source_school`,
   `verse_citation`, `match_confidence`, `match_rationale` must all be
   **byte-identical** to today's committed values (the scoring algorithm in
   `_grounding_engine.py` was not touched by this PR beyond adding the
   `caveats` key to the return dict — a diff on any other field means
   something in the corpus or algorithm drifted since 2026-06-05 and the
   regeneration is not a clean superset).
3. Re-verify `l2_lenses_salience.py`'s `GROUNDED_SALIENCE_BASE = 0.82` mean
   still holds against the regenerated `match_confidence` values (§3 point 3).
4. Land the six regenerated files as their own reviewed PR(s), following the
   original per-100-signal-batch commit shape if that review granularity is
   still wanted.
