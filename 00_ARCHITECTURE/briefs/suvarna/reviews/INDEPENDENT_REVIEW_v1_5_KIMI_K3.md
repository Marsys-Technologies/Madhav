## 3 · Answers

**Q1 · Who checks Strategic Suvarṇa?** Partially. The recorded rationale, typed fail-closed decisions, veto, and required independent reviews at re-seals/J1/layer closes/closure (plan §4.2) are a real web of checks — but it has holes. A wrong SS decision propagates furthest through the **ordinary, non-review-gated decisions**: an R3 destructive-operation approval, an N-11 addition class, a batched brief approval, or a registry/N-22 applicability rule becomes immediate authority for precondition checks and merges with no second reader. Example: a wrong R3 approval for an L0 wave is consumed by the broker's preflight in the same step (charter §6) — nothing independent ever re-reads it before production data changes. The missing checks: (a) independent review for R3-class decisions above a blast-radius threshold (F14); (b) technical enforcement that the control plane SS is judged by is the pinned release (F14); (c) the log itself currently lets a corrupt superseding line fail open (F4), so even the "latest decision wins" safety net has a hole.

**Q2 · Can SS widen its own authority?** Yes, alone, today — by design it is the trusted root, and the only checks are textual. SS writes the charter (§12), the tracker code and the control release (arch §12.12), and records its own decisions; it runs as the account that owns `authority/` and `control/` (arch §2.4). It could amend the charter to weaken P5/P6, tag a new control release with a weaker gate evaluator, and record a decision blessing both; §12's "independently reviewed first" is enforced by nothing but text (F14). The practical mitigation is not another rule but a tripwire: Monitor verification of the pinned control tag and append-only `authority/` (CODE-37's `decision_log_integrity` — currently absent from monitor.py, Scope A §4), plus making independent-review references a typed, lint-checked field on any decision that touches a gate, the standard, the charter or the registry.

**Q3 · Does anything still depend on the owner being present?** For progress: NS.0–NS.9 and the ruleset click NS.6 before N-1 (NATIVE_SETUP), NP.1 after E7.1 (plan §5.0b), N-1 itself, credential rotations — including the bot token's 90-day expiry landing mid-campaign (F16) — scope/end-state changes, and the veto. That is consistent with N-28's letter. Residual contradictions: stale `delegated` log lines saying "the native seals it" for F-1/F-2/F-4/F-6 (F18); the retired Gochara prompt body instructing native merges/seals/snapshots (F19); CLAUDE.md §N.2 "STOP and raise with the native" (a swarm lane hitting R2 parks to SS per charter, but the build standard it cites says native — minor doc drift); INTERIM_RUNTIME §2 has the native run settings generation (borderline "physical setup"). Also G16's ambiguous in-force wording (F18). No current role file, runbook or start prompt parks anything to the native — the sweep is clean apart from the above.

**Q4 · The native setup.** The v1.1 packaging (one script, five steps, plain language, `--check`/`--apply`/`--verify`/`--undo`, visudo-before-install, idempotency and secret-handling tests — NATIVE_SETUP "Safety notes for reviewers", test_native_setup.py 20/20) is genuinely good for a non-expert. But: it has never run with root (package §6a) — the riskiest operations (account creation, sudoers, `uappnd`, launchd, ACLs) are exactly what simulation cannot prove (F16). Silent half-work candidates: launchd services "skip cleanly" if plists are missing (NS.8) — a setup that reads complete while the runtime is absent until `--verify` catches it; clamshell sleep under pmset (cannot determine from the bundle); the ruleset click NS.6 has no scripted proof the check is required (L.16b is deadlocked anyway, F2); the 90-day token expiry (F16); NS_VERIFY.json landing in swarm-writable evidence (F3). The checks mostly do prove their steps — but only if `--verify` is run and its output is trusted, which loops back to F3/F16.

**Q5 · The serving guard.** Specified well enough to implement: two modes, per-table inventory, a table not listed is not written, canary-gated windows, charter §6 precondition 8 (plan §6.4c; arch §6.6; TRACK_E E5.3/E5.8). Fail-closed as specced. Gaps: the inventory is unbuilt, so no served surface currently has a verified mode (F21); which surfaces lack any authority mechanism (candidate→switch) and must rely on windows is exactly what E5.8 will reveal — cannot determine from the bundle.
