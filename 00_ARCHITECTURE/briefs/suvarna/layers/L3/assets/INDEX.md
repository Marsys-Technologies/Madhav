### 2. CF-21 — Replace-after-candidate: DELETE runs before the empty-upstream early return (five writers)

- **Why this rank:** a writer that deletes its chart partition and then returns "no upstream" commits an empty partition; five L3 writers do exactly that, in a rebuild whose order makes an empty upstream plausible.
- **Gate:** Idem (the claim "a rebuild replaces its own rows"), Build.completion; **assets:** 5 — `ka_kalasutra`, `ka_vighnakara`, `ka_kala_darshana`, `ka_jivana_parva`, `ka_taranga`
- **Evidence:** The DELETE precedes the early return in each: `ka_kalasutra.py:33` DELETE, `:52` return "No predicates"; `ka_vighnakara.py:203` DELETE, `:220` return; `ka_kala_darshana.py:19` DELETE, `:36` return; `ka_jivana_parva.py:75` DELETE, `:97` and `:107` returns; `ka_taranga.py:85` DELETE, `:104` return. A returned `WriterResult` is a success for the orchestrator whatever its notes say (the contract fact the M11 fix cites at `services/ka_dasha_kala/writer.py:150`), so the transaction commits the empty partition. The writers that assemble first and delete after are the model: `ka_avadhi.py:323` ("Replace only after the full dossier candidate has been assembled"), `ka_yojaka.py:441` ("replace only after the full candidate exists"), and `ka_bhavishya_lekha.py:198-205` (a `RuntimeError` when the candidate plan is empty while rows exist; test `tests/l3/test_bhavishya_p0_empty_generation_db.py`). `pipeline/orchestrator/kala_derivation_completeness_guard.py` calls this early return "legitimate, gated behavior" — it is, but only if it leaves the old rows alone; the guard's own docstring says it measures chart presence only (one row satisfies it) and runs live only in `fresh_chart_smoke.yml`, not per rebuild.
- **Design:** Move each DELETE below the point where the candidate row set is known to be non-empty (the ka_avadhi / ka_yojaka pattern), or, where an empty candidate is legitimate for a chart, refuse loudly like `ka_bhavishya_lekha` does when rows would be lost. Which applies per writer is part of each brief's FD (an empty `kala_convergence` for a chart that already has `kala_obstruction` rows is a build-order fault, not a legitimate empty).
- **Failing-first test and mutation:** Failing-first per writer, on the disposable-database harness (`tests/l3/_p0_harness.py`, which the I-8 branch hardens to refuse a non-disposable DSN): seed one chart partition, run the writer with an empty upstream, assert the rows are still there and the result is an error or a preserved-partition note. Mutation: move the DELETE back above the guard → the test fails.
- **Blast radius:** Writer code; no row, id or served field changes on a healthy rebuild. Behaviour changes only when the upstream is empty: the old rows survive and the asset reports the precondition instead of committing zero rows. Consumers are unaffected (rows stop disappearing).
- **Rebuild:** none (exercised by the next rebuild of each asset; no separate run).
