## Answer (a): does `bg_transit_rules` carry Rahu/Ketu rows that muhurta grading (P9) consumes, and from which series would the node position come?
**Rows: yes. Consumed by muhurta grading as significators: no. Consumed as vedha occupants: yes, and that is the one place the node's `ephemeris_daily` position matters.**
- `bg_transit_rules` (global L0; columns `id, rule_type, graha, primary_house, vedha_house, phala, classical_citation, rule_notes`; 76 rows): `graha` values are lowercase, nine of them incl. `rahu` and `ketu`. Rahu/Ketu rows: 18 (favourable `rahu` 3, `ketu` 4; unfavourable `rahu` 6, `ketu` 5); 6 of the 7 favourable ones carry a `vedha_house`, with the citation text "UNSOURCED - no house-transit vedha doctrine for Rahu/Ketu" (ids 187-189, 196-198).
- Rule lookup: `PS/brahmagyan/phala/muhurta.py:605-644` (`_fetch_gochara_rules`: `{(graha_lower, house): rule}`), grading at `:763-807` (`_grade_gochara`, `rules.get((graha, house))`). Who is GRADED: `:884-899` loops `_activity_significators_for_action(action_type)` (`:129-183`, from `brahma_activity_ontology.significators.strengthen_grahas`); the actions mapped by `_ACTION_TO_ACTIVITY_CLASS` (`:115-122`: marriage, travel, business, medical, education, property) contain only Venus, Jupiter, Mercury, Sun, Mars, Saturn, Moon (+ controlled Mars): **Rahu/Ketu are never graded as significators** (the only DB row naming Ketu is `spiritual_initiation`, which is not mapped).
- Where the nodes DO matter: `occupied_houses` (`:861-865`) is built from every key of `transit_signs`, nodes included, and `_grade_gochara` (`:794-797`) cancels a favourable verdict when another graha, a node included, sits in the `vedha_house`.
- **Series of the node position used there:** `_read_transiting_sign_ids` (`:723-750`) calls `get_ephemeris(window_start, ayanamsha="lahiri", db_conn=conn)` (`:737`) = PATH-A of `services/ka_graha_sancara/engine.py` (gate `:413-421`, `_read_from_bg_ephemeris` `:173-279`; SQL `:216-223` has no `node_mode` filter; `ALL_GRAHAS` includes Rahu/Ketu at `:61`): the stored **TRUE** row today. PATH-B (live Swiss, used outside 1900-2150, with `db_conn=None` or when PATH-A is incomplete, `:424-428`) is `scripts/temporal/compute_transits.py:63`, `swe.TRUE_NODE`. The natal anchor (natal Moon) comes from `chart_facts` (`:647-695`), not from this table. With a second row set PATH-A would read both rows and the later one would silently win (`:235-241`): a node's sign, hence `occupied_houses` and the vedha cancellation, would become nondeterministic on days where TRUE and MEAN fall in different signs. Rule lookup and grading do not change. Fix: P8 pin (above).
- Other readers of `bg_transit_rules`: `ka_vedha_gochara/writer.py:153-157` (reads the 6 vedha rows; its node position is pinned via `NODE_SERIES_PREDICATE`, writer.py:159-165,189-195: Pravāha), `services/gochara_grammar/primitives.py:1043-1069` (live Swiss `TRUE_NODE` via `pipeline/transit_search.py:64`, no table read), `ka_gochara_resonance/writer.py:823-828` (rules only, no position), `ka_kshetra/stage0_kinematics.py:705-736` (selects a non-existent `orb_deg` column and falls back to a 3-degree orb: no node effect), `MCP/tools/register_p1_reference.ts:628-648` (table dump), `SRC/L3_kala/query_vedha_gochara.ts:169` (serves `kala_vedha_gochara`). The panchang and muhurta routes: `routers/panchang.py:572` declares `"node_mode": "mean"` and uses `panchang_engine` (`swe.MEAN_NODE`), reading neither the table nor `ephemeris_daily`; `routers/muhurta_score.py` has no node, rules or table reference; `MCP/tools/muhurta_finder.ts` only mentions both in comments (its provider `c5PendingProvider` returns "unavailable").

## Answer (b): can `register_d10_pact` karaka sets include the nodes, and does any pact/karaka path read node longitudes from `ephemeris_daily`?
**Yes to both.**
- Karaka sets come from a static in-code table, not from the database: `pact_query` calls `judgmentQueryCapability.handler` (`SRC/register_d10_pact.ts:250-253`) and reads `about['karakas']` (`:265`) = `spec.karakas` (`SRC/register_d9_judgment.ts:1806`) from `SHASTRA_MAP` (`:173-225`). Entries with nodes: `education`/`vidya` (`:189-190`: Mercury, Jupiter, Ketu), `spirituality` (`:192`: Jupiter, Ketu), `moksha`/`liberation` (`:198-199`: Ketu, Saturn, Jupiter), `transition` (`:220`: Saturn, Rahu, Mars), `travel` (`:224`: Jupiter, Rahu). A bare `bhava:N` takes its karakas from `BHAVA_TO_DOMAIN` (`:248-261`): bhavas 8, 9 and 12 map to moksha/spirituality/moksha, so they pull in Ketu. Domains without nodes: marriage, career, wealth, health, progeny, character, residence, family, general.
- The Jaimini 8-karaka scheme is not in this path (`register_d10_pact.ts` has no karaka-scheme code; `register_d9_judgment.ts:138-140` says no chara-karaka substitution is done; `chart_facts` `karaka_chara_position` has Rahu on 5 rows under `kn_rao_rahu_included`, unread here). `reference_karakas` has 77 rows (8 `chara_jaimini`, 62 `sthira_house`, 7 `sthira_planet`), 8 mentioning Rahu/Ketu, read by no pact/judgment code.
- The TRIGGER stage reads node positions from `ephemeris_daily` through the L0 route: `register_d10_pact.ts:441-443` loops `relevantNames` (bhāveśa plus karakas, nodes included) and calls `GET ${SIDECAR_URL}/brahmagyan/ephemeris/planet_transit?planet=...&start_date=<as_of>&end_date=<as_of>` = `ephemeris_routes.py:81` -> `query_planet_transit` (`l0_ephemeris.py:824`, SQL `:877-884`, no `node_mode`, column list without `node_mode`). With two series a single-day Rahu/Ketu query returns two indistinguishable rows and `pact_query` appends both to `transiting_positions` (`:446`). Fixed at S2. (The node graha code for the natal check is `RAH_MEAN`/`KET_MEAN` from `chart_facts`, already mean: `grahaCodeOf`, `:79-93,117-120`.)

## Answer on `get_av_transit_gating` (free-text planet guard)
`planet` is a free string (`get_av_transit_gating.ts:226`, no enum); only non-emptiness is checked (`:441-454`); it goes straight to `GET .../planet_transit` (`:491-500`). 'Rahu'/'Ketu' are therefore not blocked and, with a second series, return both rows per date, interleaved by date only. Guard or pin in step 1 (SS decision): reject the two node names in the handler, and keep S2's pin as the second line.
