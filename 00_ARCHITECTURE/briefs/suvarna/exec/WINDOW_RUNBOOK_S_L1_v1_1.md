# S-L1 window runbook v1.1

Legend: **A:** = approval point (SS approves; Exec does not proceed without it). **LC** = launch checklist (plan LC-1..LC-5). **Gate** = `run_gated.sh` / gate v2: non-completed main deploy runs = 0 AND planned/running/paused build_runs = 0, read in the same invocation. "not decided" = neither v1.0 nor the accumulated SS decisions say; it is listed in section 7 for SS and is not filled in here.

## 0. Rules that hold throughout
1. A merge is not a deployment (LC-5): per component (web, mcp, sidecar, pipeline job) read `DEPLOY_SHA` from the deploy log AND the Cloud Run label, `git merge-base --is-ancestor`, `_migrations_applied` per migration. A prerequisite is live only when the component that RUNS it carries it (writers: pipeline job image; served: web/mcp; sidecar endpoints: sidecar).
2. No merge by anyone to main during the window after W1 (a merge starts a deploy, whose gate skip/cancel pattern is documented in `DEPLOY_STATE_AND_GATE_FINDING.md`). SS asks the engine session and Pravāha to hold.
3. Every executor runs through the gate; no executor applies on gate v1. Executors v3 carry gate v2, the gate's sha256 in the plan hash, the launch marker, and an outcome file. The launch marker and the `PYTEST_CURRENT_TEST` refusal are ACCIDENT guards, not authentication: they stop a mistaken run, they do not prove who ran it.
4. Nothing is dispatched on a chart with a planned/running/paused run; dispatch protocol (plan LC.1): `started_at` set within 60 s, never re-dispatch before closing the first run through a supported path.
5. The window is announced to the owner and Pūrṇa (Pūrṇa has no run in flight); no `ka_*` or Pravāha dispatch on the chart during it; `fresh_chart_smoke` (Wednesday 03:00 UTC) does not coincide.
6. Serving restored is verified by the RESOLVER SQL (`orphan_receipts/resolver_verdicts.sql`), never by `asset_freshness` alone.
7. Stop rules: any refusal other than a designed one, any C1-C7 failure, any unexpected build state: STOP, report the exact text to SS. The operator script around every executor run captures the wrapper's grep-able `GATE_V2 ...` line AND the exit code into the run log, so a run that stops before its evidence directory exists (exit 93 or 95, bad arguments) still leaves a trace.
8. **No evidence re-bind step (v1.1).** Nothing on the dispatch path reads `plan_adaptation_required` or `evidence_refresh_required`: `dispatch_frozen_rebuild.py` builds its manifest from the live `asset_registry` row and `platform/src/generated/nirmana-writer-digests.json`, with no read of the elevation monitor or the campaign definitions; there are zero hits in `platform/src/lib/build`, `api/cockpit`, `python-sidecar/pipeline`. Only the Nirmāṇa-elevation tracker and `dispatch_nirmana_campaign_wave.py` read those states, and neither is used for S-L1. This was read on `origin/main` on 2026-10-02; the monitor banner was NOT measured at each dispatch. After 1219/1221 apply, the frozen manifests of `ga_strength`, `ga_condition` and `ga_structural` go to `evidence_refresh_required` / `plan_adaptation_required`: tracker-only, not a dispatch gate. The two real gates on the dispatch path are:
   - (a) **`expected_code_digest`**: the dispatching checkout's `nirmana-writer-digests.json` entry for the asset must equal the deployed pipeline code digest. Dispatch from the checkout of the deployed sha.
   - (b) **`depends_on` is frozen into the run manifest at run CREATION time**, and `asset_runner` DEP-ASSERT uses that frozen list. Create every run AFTER the migrations are applied and verified; never pre-create a run.
9. **Every migration PR states its SERVING EFFECT AT APPLY** (the registry trigger columns it touches and the digest specs it retires), not only its build effect (binding PR template text). The effect is verified from production structure after apply, never from the deploy log.
10. Between the 1221 apply and the canonical `ga_structural` rebuild, no `ga_structural` build may run for ANY chart (plan SL1.8 standing check; the W0 pre-check below is its other end).
