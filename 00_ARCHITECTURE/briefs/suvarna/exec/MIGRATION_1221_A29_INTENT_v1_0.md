# Migration 1221: the a29 integrity conjunct and the ga_structural digest-spec swap (HELD)

## 1. What it does

Adds ONE conjunct, (a29) [SS N-61, AR-3; CLAUDE.md N.8], to `ga_structural`'s `integrity_check_sql`: for every argala-offset cell (2, 4, 5, 11) of `argala_natal_matrix`, the cell is NULL with `fact_value_text = 'no_occupant'` exactly when its source sign holds no graha, and a non-NULL score with no text when it does. Conjunct (e27) is vacuously true on a NULL score, so before this a NULL on an occupied cell, or a stale 1.0 on an empty one, passed. Scoped to the canonical chart (migration 904's disclosed tradeoff). Done as a guarded `replace()` at the single `AS integrity_passed` anchor: refuses unless (g28) is present and the anchor occurs exactly once, no-op when (a29) is already there, asserts the result afterwards.

**Corrections to two existing conjuncts, (bb) and (c9), in the same UPDATE** (section 7). Each replaces the live conjunct text (comment plus SQL, verbatim from the read of 2026-10-02) and is guarded the same way: refuses unless the old text occurs exactly once, skipped when its marker (`Migration 1221 (bb tolerance)`, `Migration 1221 (c9 domain)`) is already there. Live text md5 `bb9803524a61427e7f4f179a59911e33` (203539 chars) becomes md5 `99564aa71a950037fd391fe62ae487e5` (206808 chars), verified by applying the file to the real live text on a disposable Postgres.

**Part 2: the ga_structural output-digest spec swap.** Retire the one active spec (migration 914, 81 categories, sha `b2490646...`), insert the same spec plus `argala_graha_natal` (82 categories, sorted and unique, sha `d480c829...` = `canonical_digest`, which reproduces 914's stored sha exactly). Retired, not deleted (609 / 1086 precedent); refuses if any active ga_structural spec is neither of the two shas; asserts one active new row afterwards. It comes after the a29 conjunct in the same file.

**Serving effect at apply.** ga_structural freshness goes stale on every chart (a29: `UPDATE OF integrity_check_sql` fires `nirmana_registry_receipt_invalidation`) AND its receipts read `receipt_spec_retired` until rebuilt. Degraded set at W1 = ga_structural (and with 1222/1223/1226: ga_vargas, ga_dashas, ga_yoga); all rebuilt in the window. Proved by `test_the_combined_effect_ga_structural_freshness_stale_and_its_receipt_spec_retired_nothing_else_moves` against the real trigger function body read from the live database.

## 2. Why it is a separate, held PR

- **Merge = apply.** `platform/scripts/migrate.ts` applies every unapplied file in `platform/migrations` at the next deploy, and every deploy job `needs` the migrate job, so the migration runs before that deploy's images roll.
- **An old-image `ga_structural` rebuild after a29 fails its post-write integrity check** (the old writer still stores 1.0 on empty cells). So a29 must never apply before the new writer image is live.
- **a29 reads red on live canonical data until S-L1 writes the NULL cells** (every empty-source argala cell is stored 1.0 today). It is read at build time (the asset runner's post-write gate), by the Nirmana `integrity_verified` acceptance detector, and is part of the registry-contract fingerprint.
- **`UPDATE OF integrity_check_sql` stales `ga_structural`'s freshness** (trigger 596, `nirmana_registry_receipt_invalidation`): its direct dependents fail DEP-ASSERT until the next governed receipt. Applied immediately before S-L1 this costs nothing, because S-L1 rebuilds `ga_structural` anyway.

## 4. The gap before this file (old 81-category spec still active) and its direction

Between the integration deploy (new argala writer live, migration 1219 applied) and W1, the OLD spec stays active. Nothing builds ga_structural in that gap. If something did, `asset_runner.py` (line 1385) calls `compute_output_digest`, which loads the ACTIVE spec (`load_output_digest_spec`: `retired_at IS NULL`) and filters each component by `where_in` (`fact_category = ANY(...)`). The old `where_in` does not contain `argala_graha_natal`. So the build **succeeds**; the receipt records the **old** spec sha and a digest that does **not** cover the argala rows: a **silent coverage gap, not a loud failure** (nothing compares written categories with the spec). After this file applies, that receipt reads `receipt_spec_retired` anyway. Tested with the real `compute_output_digest` on a real cursor (`test_the_gap_with_the_old_spec_active_argala_rows_do_not_move_the_digest_and_the_build_would_not_fail`): argala rows leave the digest byte-identical under the old spec, a covered category moves it, and after the swap argala rows move it.

## 7. The (bb) and (c9) corrections: which side is right

The data-plane rehearsal built ga_structural from scratch on an anchor-matched synthetic chart (108,167 rows, 5/5 generations complete) and evaluated its `integrity_check_sql`: FALSE, with exactly two of the 256 conjuncts (0-based index 27 = `(bb)`, 103 = `(c9)`) not true. Both are table-wide (no chart filter). Decision for each, with evidence:

**(bb) aspect_tajik orb_strength: the CHECK is wrong; the writer is right.** The check recomputed `round(greatest(0, 1 - orb_deg / deeptamsa_sum_deg), 4)` from the stored `orb_deg` and demanded exact equality with `orb_strength`. The writer (`ga_structural_writer.py`, `_build_aspect_rows`, tajik loop: `orb_strength = round(max(0.0, 1.0 - orb / deeptamsa_sum), 4)`, line 1376 on this branch) rounds the quotient computed from the UNROUNDED `orb`; it stores `orb_deg = round(orb, 4)` (line 1402). The check therefore recomputes from an input that lost up to 5e-5 of precision and compares at a precision (4 dp) finer than that loss supports. At a rounding boundary the two land one unit (0.0001) apart. The rehearsal's five red rows are one pair repeated across the five ayanamshas: orb_deg 13.4585, deeptamsa_sum 22.0, stored 0.3882, check expects 0.3883 (1 - 13.4585/22 = 0.38825 exactly on the boundary; the unrounded orb is a hair larger). The stored value is the more accurate one. Worst-case disagreement of the two roundings: 5e-5 (writer rounding) + 5e-5 / deeptamsa_sum (input rounding) <= 5e-5 + 5e-5/14 < 1e-4, where 14 is the smallest deeptamsa_sum (Mercury 7 + Venus 7; `TAJIK_DEEPTAMSA`, line 168, Tajika Nilakanthi per the writer's own citation). The corrected text compares with a tolerance of 0.0001 (one unit in the 4th decimal) for ithasala / eesarpha; yamaya (1.0) and manaau (0.1) stay exact. Production today: 76 aspect_tajik rows on 3 charts, 0 violations of the old text (the canonical chart is not on a tie), so this is latent there; it turns RED on the first build that lands on a tie. The formula itself (1 - orb/deeptamsa_sum) is the writer's definition, not a corpus-classical value; the check re-derives that definition, it does not assert a classical number.

**(c9) karakatva composite_strength domain: the CHECK is wrong; the writer is right.** The check listed seven values with the comment "four dignity tiers x three house tiers". The writer (lines 4156-4160) computes `(karaka_strength + house_strength) / 2` with `karaka_strength` in {1.0 exalted, 0.875 own_sign, 0.5 neutral, 0.25 debilitated} (default 0.5) and `house_strength` in {1.0 kendra, 0.75 for 5/9, 0.5 otherwise}, and 0.5 when the natural karaka graha is absent. Twelve combinations give nine distinct values: 0.375, 0.5, 0.625, 0.6875, 0.75, 0.8125, 0.875, 0.9375, 1.0. The check omitted 0.6875 (own sign, house not kendra/5/9: the rehearsal chart's Jupiter in its own sign) and 0.875 (exalted, house 5 or 9). The rehearsal chart stored 0.6875 on 30 rows; production holds none of the omitted values today (450 rows on 3 charts, 0 violations), so this too is latent there. The new domain is derived value for value from the writer's two tables, and the test asserts the mirror against the writer's source text. (`(d9)` below it in the same check is the value-for-value re-derivation; `(c9)` is the coarse domain guard.)

**Evidence the corrected check is right and still bites.** On a private copy-on-write clone of the rehearsal's final database (integration build, argala writer included), changing only the chart id: the old text (live + a29) evaluates FALSE with exactly (bb) and (c9) not true; the corrected text (live + a29 + (bb) + (c9)) evaluates TRUE, all 256 conjuncts true. Tests (`test_argala_migration_1221_sql.py`): old (bb) false on the rehearsal row, new accepts it; 4,000 writer-computed rows plus 800 constructed at rounding boundaries: old red on many, new red on none; 11 genuinely wrong values still false (two units off, wrong sum, yamaya 0.9999, manaau 0.1001, ...); old (c9) false and new true on the full writer-reachable set; 9 unreachable values still false; the migration refuses when either old conjunct is missing or duplicated, is idempotent, and corrects a single missing part on its own. Mutants of the new text and of the migration logic (tolerance 0 / 0.01, yamaya-manaau tolerance, dropped zero clamp, manaau 0.2, domain minus / plus one value, old list restored, skipped replace, dropped exactly-once guard, marker never set) are all killed.

**Receipt effect (one time, unchanged by this addition).** The registry trigger `nirmana_registry_receipt_invalidation` fires on `UPDATE OF integrity_check_sql`; the corrections ride in the SAME single UPDATE as a29, so the stale of ga_structural's `asset_freshness` (reason `registry_changed`) happens once, as already described in sections 1 and 2; nothing further moves. Fingerprint effect unchanged: integrity_check_sql is part of the registry-contract fingerprint, already accounted for in the file header.
