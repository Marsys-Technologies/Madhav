# S-L2 window runbook (L2 Bodha rebuild of the canonical chart)

## 1. The paragraph for the operator

S-L2 rebuilds the whole L2 (Bodha) layer for the owner's chart: **all 23 registered `bo_*` assets** (22 data writers, one passive adapter `bo_samvada`), in nine dependency waves, through the real orchestrator, as the production pipeline login `data_plane_builder`. It exists because S-L1 (all 18 `ga_*` lanes) re-keys about 99% of the chart's `chart_facts.fact_id` once (142,094 of 143,299), replaces every `chart_vichara.id` and every `chart_divisionals.id`, and moves a set of L1 values (S_L1_BETWEEN_STATE section 10). Every L2 row that cites those ids dangles from S-L1 close until S-L2: `bodha_msr_signals` cites 73,049 facts of which 71,401 orphan (49,557 of 50,678 signals), and the served surfaces read "quietly degraded" until S-L2 closes (S_L1_BETWEEN_STATE section 3). N-91 refused a re-link: migration 1036 admits L2 writes only from a real producer run, so S-L2 is a **rebuild**, never an id remap. What the rebuild produces is derived from the new L1, not from the old rows: ids move, some row counts move, and `bodha_msr_signals.signal_id` moves for every signal whose configuration moved (section 9).

Three facts change how this window has to be planned, all found by running the shared wrapper on a real PostgreSQL built from the production schema with production owners and ACLs, as `data_plane_builder`, no superuser (section 2):

1. **The L2 data plane has never run end to end.** No L1 or L2 generation or head has been written in production since the stats reset of 2026-09-10 (insert counters 0); the L2 wrapper arrived with #2607 on 2026-09-16 and no `bo_*` asset has run under it. The last `bo_*` build was 2026-09-12, before the wrapper existed.
2. **The wrapper had two bugs that stopped all 23 assets** (a `uuid.UUID` chart id and `open` before `bind`; fixed in PR #3008) and **the database has two more defects behind them** (the builder cannot read the input shadows that `bind_l2_exact_inputs` creates, and cannot execute the identity functions); those are SQL/grant changes for SS (section 2, B3 and B4).
3. **A third defect is a wrapper defect fixed in PR #3029:** while the shadows are alive `integrity_check_sql` and `count_sql` read the shadows instead of the rows the writer wrote (a detector that cannot go red).

The window is **not openable** until every gate of section 5 is green. Clock: N-91 ruling 3 (day 7 checkpoint needs "the rehearsal has passed and the window is scheduled within 72 hours"; day 14 absolute).

## 7. L2 data-plane specifics the operator must know

(From `L2_DATAPLANE_MECHANICS.md`; file:line there.)

- **Admission.** Every `run`/`run_substep` is wrapped by `l2_producer`. Per call, in ONE transaction: resolve the exact upstream vector (every transitive `ga_*` needs a complete L1 head; every transitive `bo_*` a complete L2 head whose stored vector still equals the current heads and the current registry topology), `begin_observation` (content-addressed `generation_id = "l2g:" + sha256(contract, accepted L0/L1 pins, asset, chart, writer source digest, generation context, vector)[:40]`), `set_config('madhav.l2_*')`, **bind** (`bind_l2_exact_inputs`: FOR SHARE locks on the heads, pg_temp shadows named like the protected tables built from the immutable snapshots of ONLY the named generations, the transaction-local bind receipt), **open** (`open_l2_data_plane_generation`: builder-only, the build must be a `running` `build_runs` row whose `build_run_assets` row for this asset is `building`, the receipt must match, inserts the generation, partition context, **run intent** and the persistent **bind receipt**), the writer body, `complete_l2_data_plane_partition`, then the integrity/search-path reset (B6 fix).
- **The guard.** `l2_data_plane_mutation_guard` (BEFORE INSERT/UPDATE/DELETE on each of the 29 active tables) rejects any write unless `session_user = 'data_plane_builder'`, the five `madhav.l2_*` settings are set, the row's chart is the admitted chart, there is an active run intent on a `building` generation, the build is `running`, the asset `building` and the bind receipt exists; per-table ownership rules apply (MSR INSERT stamps `producer_asset_id`; only `bo_laksana_rerank` may UPDATE foreign MSR rows and only six enrichment columns; node/edge ownership between bo_bimba and bo_karanajala). A reaper stamp on the run or asset therefore turns into a hard asset failure of the live writer (B10).
- **MSR delete receipt.** `replace_prior_msr_for_chart` calls `assert_l2_msr_delete_safe` (builder session, admitted chart/asset, active run intent), which locks the producer's rows FOR UPDATE, refuses on cross-layer FK dependents (none exist in the visible catalog) and creates the transaction-local receipt that authorises the DELETE of MSR rows and of the embeddings/contradictions of those signals.
- **Completion.** `complete_l2_data_plane_partition` demands `observed_row_count = rows_inserted + rows_updated` (B12), allows zero rows only when `asset_registry.target_floor = 0` (bo_cgm_motifs, bo_grounding, bo_pratijna, bo_samvada), promotes the head when the last partition lands (`previous_generation_id` keeps the old head). For a light writer this happens before the post-write integrity check; if the check is red the orchestrator rolls the transaction back, head included. For a heavy writer the last substep is already committed, so a red check leaves a promoted head under an `error` asset (mechanics 2.3, 9 item 10).
- **Replay.** Same inputs and writer source = same generation id = a reopen: every captured row must reproduce an existing identity and digest, every partition its counts and digest, the generation its digest; otherwise the transaction fails (`replay changed output`). A crashed heavy writer can only be finished by byte-identical replays. A changed dependency digest or writer source makes a NEW generation. `l2_correction_of_generation_id` is unreachable through the orchestrator (B13).
- **Rebuilding an upstream again after a dependent built, with a changed output digest, makes the dependent stale** (`l2_data_plane_generation_is_compatible` goes false): the whole chain downstream of it must be rebuilt. Never re-run a single early asset in the middle of the window.
- **Why S-L2's first run is a first generation for all 23 assets:** no generation exists today, so there is nothing to compare to and nothing to roll back to (section 12).

## 11. Disclosure detector: the clearing criterion "reads 0 stale"

The detector (draft PR #2986; flag codes `l2_receipts_predate_l1` and `l2_lineage_check_failed`) is a pin comparison, not a timestamp rule: an in-scope L2 receipt (PROVEN, active output-digest spec, registry-current partition, at least one `ga_*` pin) is STALE iff any pinned `ga_*` `output_digest` differs from that asset's CURRENT receipt digest for the chart. After S-L1 close the flag is expected TRUE; it clears when every in-scope `bo_*` receipt is rewritten AFTER the last `ga_*` receipt of S-L1. Criterion for "reads 0 stale":

1. the reader SQL below returns `stale_pins = 0` (an upper-bound reproduction: it does not apply the spec/registry-current scope, so it may count more assets than the detector);
2. the detector scope after S-L2 is 11 assets / 26 pins by arithmetic from today's registry (the 8 in scope today + `bo_laksana_rerank`, `bo_pratijna`, `bo_upaya`; `bo_samvada` never, B11): a scope that SHRINKS is an asset silently dropping out (an unproven receipt, a retired spec), which "0 stale" would hide, so A2-15 requires the scope count too;
3. at least 3 minutes after the last `bo_*` receipt (the served detector is memoised for 60 s; `judgment_query`/`assess_*` ride a 60 s MCP memo; the PR says up to about 120 s), one `judgment_query` and one `assess_*` call: no `l2_receipts_predate_l1`, no `l2_lineage_check_failed`, the normal sentence. `l2_lineage_check_failed` is a failed detector, never a pass.

## 12. Rollback and abort

- **There is no in-database rollback of the active tables.** Writers replace in place (delete-then-insert per chart x scope, CLAUDE.md N.3). `rollback_l2_data_plane_generation` swaps a HEAD to a previous complete generation and is executable only by `data_plane_migrator`; the first generation of every asset has `previous_generation_id` NULL and the immutable snapshot store holds nothing from before the window. So "rollback" means: (a) before W1 a verified Cloud SQL backup / restore point (G-15, SS production step); (b) forward fix by re-running the failed asset and everything downstream of it (an upstream re-run with a changed digest makes dependents stale, section 7); (c) head rollback by the migrator only after a generation exists.
- **Abort rules.** STOP and tell SS on: any `ContractError`/`permission denied`/count-mismatch/`replay changed output`; any asset `error`; an A2-05..A2-09 orphan count above 0; an L1 change in the flip report; any run > 30 minutes without progress (live investigation, no blind kill, N-93 item 8). Never kill a job in its post-write tail (rule c). On abort: leave the run to finish or terminalise it through the governed `POST /api/cockpit/watchdog`, never a hand-made `build_runs` row; resume the watchdog as the LAST step after the abort state is verified; the between-state (S_L1_BETWEEN_STATE) remains and the clock keeps running.
- **A partial wave is a valid, resumable state only for heavy writers** (committed substeps); light writers roll back whole. Do not re-plan a different asset set mid-window: the manifest is frozen.
