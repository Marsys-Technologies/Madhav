# Agreed `chart_dashas` read contract for Kāla F2

This is the interface between Suvarṇa's L1 `ga_dashas` producer and Kāla's F2 clocks, reconciled with Strategic Suvarṇa's acknowledgement in `CAMPAIGN_COORDINATION.md` §6 at coordination commit `a5e7ad23a8eea2ca85b916717bf9558f68dda169`. The acknowledgement agrees to the read set and cutting rules with the six changes recorded below. It is not a settled L1 build or a change to Gochara 5.0's frozen §4.0 pin. The post-certification producer repairs remain open and are not inferred from this agreement.

## Evidence and boundary

- Kāla architecture plan v1.1 §3.1 daśā read inventory, §3.2 `clocks/` row, and §4.1 F2 rows: one pinned read supplies period context, boundaries, applicability, hierarchy, sandhi bands and uncertainty scenarios. The plan is at `00_ARCHITECTURE/briefs/l3_families/KALA_LAYER_CODE_ARCHITECTURE_PLAN_v1_1.md` in the campaign checkout.
- Suvarṇa's `00_ARCHITECTURE/briefs/suvarna/layers/L1/L1_LAYER_INSTANCE_v1_0.md` §2.3 identifies `chart_dashas` as L1's clock output, at `(chart_id, ayanamsha_id, system_id, level_n, start_iso)` grain; §3.10 records 42 columns, with partial population. These are observed inventory facts, not a promise that every optional cell is filled.
- Current table definition: `platform/migrations/_archive/135_chart_dashas.sql`; current row producer: `platform/python-sidecar/ga_writers/ga_dashas_writer.py` (`_jd_to_iso_utc`, row construction, `KP_SYSTEM_ID` and `compute_kp_subperiods`); current pinned Gochara reader: `platform/python-sidecar/services/gochara_kernel/dasha_read.py` and `services/gochara_grammar/dasha_data.py`. They establish the present behavior; the coordination acknowledgement records Suvarṇa's commitments for settled builds. The producer's V-12 correction gives KP rows `system_id = 'vimshottari_kp'`; a past producer put them under `vimshottari` and caused a real level-2/3 collision.
- The producer also writes a `system_id = 'scope_cap'`, `ayanamsha_id = 'INVARIANT'` marker for the excluded KP depth. Its start and end instants are equal, so it is a capability sentinel, not a period. The fifth Prāṇa level is recorded as a `chart_facts` capability fact, not a `chart_dashas` interval (`ga_dashas_writer.py`, `write_dasha_scope_cap_sentinels`).
- The writer's `stabilize_hierarchical_uuids` post-pass replaces the temporary UUID4 period ids with semantic UUID5 ids and rewires parent links before persistence (`ga_dashas_writer.py`, after verification and before DB write). Its identity includes `start_iso` and `end_iso`: a changed boundary can change `dasha_row_id` even for the same chart and named system. The 2026-10-07 Exec Suvarṇa notice says the forthcoming L1 pass rebuilds `ga_dashas`, changes `build_id`, and requires a deliberate `DASHA_READ_CONTRACT` re-pin. Strategic Suvarṇa's later K0-SV acknowledgement confirms that `L1_SETTLED` carries `dash_build` and Kāla re-pins via J-4p; neither the notice nor this contract is the settled-build receipt.
- The current write path calls `replace_prior_chart_dashas` before copying rows. That helper deletes the prior rows for the chart, ayanāṃśa and system namespaces present in the new batch **across all build ids** (`ga_writers/_idempotency.py`). A previously pinned build therefore cannot be assumed to remain readable while the new one is assembled. The frozen Gochara reader explicitly refuses a canonical Vimśottarī build other than its pin (`services/gochara_kernel/dasha_read.py`); it cannot silently bridge this interval. Suvarṇa and Kāla must agree on the settled-build receipt, reader re-pin and availability sequence before relying on the replacement rows. This is a transition risk in the current producer, not a claim that Suvarṇa has accepted a procedure.
- Precision is a producer guarantee, not a property of the `TIMESTAMPTZ` type. Today's `_build_row` callers pass both Julian Day bounds; `_jd_to_iso_utc` rounds each UTC bound to the nearest second. `_build_row` still has a defensive date-only midnight fallback if either Julian Day is missing, and `chart_dashas` has no per-row precision marker. Suvarṇa guarantees second-level UTC bounds **for builds named in an `L1_SETTLED` line**. It measured zero of 482,854 non-sentinel canonical-chart rows with both bounds at midnight; that observation is corroboration, not the guarantee. Suvarṇa will make the writer refuse the fallback in a post-certification repair. F2 must not infer precision for an unlisted build from the column type or a non-midnight value.
- Applicability is likewise not established by the stored Boolean alone. `compute_ashtottari_system` currently passes `applies_to_chart=True` for level 1 with the comment `FORENSIC: Rahu in 5H → applicable`; its deeper `_build_row` calls inherit the same true default. No per-chart Aṣṭottarī applicability condition is evaluated in that function. Suvarṇa agrees that applicability is **unknown**, identifies the hard-coded true as a defect, and plans a post-certification per-chart classical condition with failed-condition evidence. Until that repair is evidenced, F2 cannot present a positive Aṣṭottarī applicability verdict.

## Agreed read surface

All rows are selected from `public.chart_dashas` for one chart, one `ayanamsha_id`, one `system_id`, one `build_id`, and an explicitly accepted `verification_pass_status`. Every field below is an existing column. “Required” means the F2 reader refuses a row missing it; it is not a claim that today's whole table satisfies the rule. Suvarṇa agreed to this read set, the half-open cut, the `sandhi_flag` and `next_dasha_start_iso` annotation limits, `scope_cap` exclusion, truncation flags and system-before-hierarchy rule.

| column | agreed meaning for Kāla | read use |
|---|---|---|
| `chart_id`, `ayanamsha_id`, `system_id`, `build_id` | Exact chart, sidereal convention, named daśā construction, and one L1 build; `chara` and `chara_karaka` are not aliases. Classical `vimshottari` and its KP subdivision namespace `vimshottari_kp` are distinct stored systems. | Required selection and lineage. A mixed or null build is a conflict, not a row-order choice. A classical read selects `vimshottari`; a KP read, if supported, explicitly selects `vimshottari_kp`. |
| `dasha_row_id`, `parent_row_id`, `level_n` | Period identity, direct parent identity, and hierarchy depth. Levels 1–4 are MD, AD, PD, sūkṣma; level 5 is not persisted. | Required identity and ancestry. A classical non-root parent resolves in the same system and pinned build. A KP `sub` row currently points to a classical Vimśottarī MD; a KP `sub_sub` row points to its KP `sub` parent. Both must resolve under the same chart, ayanāṃśa and build, even across those two system namespaces. |
| `lord_graha` | The L1-computed period lord, without a Kāla recomputation. | Required period context and attachment key. |
| `start_iso`, `end_iso` | UTC period bounds; the present producer converts Julian Days to seconds when supplied, but can fall back to date-only midnight bounds. The stored type alone does not disclose which path produced a row. Suvarṇa guarantees second-level UTC bounds for a build named in `L1_SETTLED`, pending the later writer repair that refuses fallback. | Required F2 active-at-time and boundary calculation; use half-open `[start_iso, end_iso)`. At an exact end, the old period is inactive. An unlisted build has no precision guarantee. |
| `start_date`, `end_date` | Date projections of the period bounds; precision is lower than the ISO instants. | Display or coarse date filters only; never replace the ISO fields for an instant-level clock. |
| `verification_pass_status` | The row's actual L1 verification tier. | Required tier predicate and disclosed provenance. No blank, null or divergent row is silently promoted. |
| `applies_to_this_chart_flag` | Stored applicability annotation, where populated. For Aṣṭottarī the current producer writes true from a canonical-chart assumption, so true alone is not a chart-specific assessment; Suvarṇa acknowledged the defect. | Input only after a chart-specific detector and failed-condition evidence exist for that system. False and null remain distinct; until the producer repair, a true Aṣṭottarī flag yields applicability unknown rather than a positive F2 verdict. |
| `sandhi_flag`, `next_dasha_start_iso` | In the current producer, `sandhi_flag` means the row's date-derived `duration_days < 20`; it does not mean the query instant is near a boundary. `next_dasha_start_iso` is filled only on a level-1 row with a following level-1 row in that system; it copies that next row's stored `start_iso` without a new date conversion. It is null on the terminal level-1 row and on deeper rows. | Optional annotations only. F2 derives its own band and uncertainty from pinned ISO bounds and a declared rule; it must not treat `sandhi_flag` as an active-at-time predicate or use `next_dasha_start_iso` to find a level-2/3/4 successor. |
| `is_truncated_at_window_start`, `is_truncated_at_window_end` | Producer's indication that a period is clipped by the calculation window. | Coverage and boundary precision; a clipped edge must not be presented as the natural period edge. |
| `kp_sublevel`, `kp_sub_lord`, `kp_sub_sub_lord` | KP subdivisions of Vimśottarī, stored under `vimshottari_kp` with `kp_sublevel = 'sub'` or `'sub_sub'`; they are not a second independent clock. | A classical `vimshottari` hierarchy does not absorb KP rows. An explicit KP read retains the sublevel and its own applicability and tier; it cannot supply an extra independent-system vote. |

F2's minimal clock projection is the identity and pin fields, `lord_graha`, the ISO bounds, tier, and applicability/coverage state. Other `chart_dashas` fields, including natal-lord condition, `duration_days`, citation and concurrent-system annotations, are outside this F2 read surface. An item that needs another column must amend this contract and record the reason; it must not silently read it. `ka_avadhi` may require a separate attachment contract for natal condition.

## Verification tiers at the agreed producer boundary

The producer code (`ga_dashas_writer.py` and `brahmagyan/verification_vocab.py`) explains the existing tier paths. Suvarṇa additionally measured the canonical chart under Lahiri and acknowledged the exact tier matrix below. That measurement is scoped to this chart and ayanāṃśa; it does not silently upgrade other charts, builds or rows.

| stored row group | current verification behavior | F2 consequence |
|---|---|---|
| Classical `vimshottari`, levels 1–4, without a KP sublevel | Independent period-tree comparison is row by row; Suvarṇa measured `two_pass_verified` for each such row on the canonical Lahiri chart. A divergent row remains `divergent_flagged`. | Accept only a row whose own tier satisfies the explicit read policy. A divergent child cannot inherit a verified parent's tier. |
| `mudda`, level 1 | Suvarṇa measured `classical_match` on the canonical Lahiri chart. | Preserve the actual tier; it is not `two_pass_verified`. |
| `vimshottari_kp` sub/sub-sub and every other system/level, including `mudda` levels 2–4 | Suvarṇa measured `single` on the canonical Lahiri chart. | Do not count a classical MD's two-pass tier as verification of its KP child or promote a deeper row from its parent's tier. A non-classical clock needs an explicitly accepted read policy for its own tier and ancestor chain. |

For an F2 lookup, the tier predicate applies to the **selected row and every required ancestor** under the policy for each row's own system and level; Suvarṇa expressly agreed to this ancestor rule. A missing accepted ancestor, a `divergent_flagged` row, or a KP child whose tier policy is still undecided yields a typed unavailable result; none is replaced by a nearby or lower-tier interval. The current Gochara 5.0 reader's frozen `two_pass_verified` Vimśottarī policy is separate and remains unchanged. The measured `single` and `classical_match` groups do not themselves establish an F2 acceptance policy for those clocks.

## Agreed period and build rules

1. L1 owns calculation and period identity. Its stored hierarchy has levels 1–4; `parent_row_id` links each child to its actual parent. A child interval must lie within that parent's interval. Periods at one system/level/parent do not overlap, and an active-at-time lookup uses the half-open ISO interval. Kāla does not reconstruct the daśā calculation or turn a date-only bound into a timestamp. It also does not call a stored edge more precise than the settled producer guarantee permits. The `system_id` predicate precedes any level-2/3 hierarchy walk: `vimshottari_kp` rows cannot be folded into the classical `vimshottari` MD/AD/PD sequence. An explicit KP ancestry check includes the classical MD parent by ID under the same build, without counting it twice as a KP period. KP tier acceptance remains separate from this structural agreement.
   At every hierarchy level, F2 computes the next boundary from eligible rows at that level and parent, rather than extending the level-1 `next_dasha_start_iso` annotation to descendants. A null annotation on a terminal level-1 row does not make that row's `end_iso` unknown.
2. L1's 1950-01-01 through 2100-12-31 calculation window may clip a natural period. The truncation flags must distinguish that case. Empty coverage, an inapplicable system, an unverified tier, and a broken hierarchy are separate outcomes; none becomes a fabricated period.
   The `scope_cap` sentinel must be excluded before any active-period, boundary or overlap calculation. Its zero-length interval does not establish clock coverage or satisfy an absent period. A request for excluded depth returns a typed scope-cap or unavailable result sourced from the relevant capability marker.
3. L1 publishes a coherent build identity after its rebuild. Kāla pins the `build_id` from the `dash_build` field of the settled `L1_SETTLED` line for the chart and checks the chosen system and ayanāṃśa **before tier filtering**, including rows it will not consume. A mixed or wrong build is refused. Because the present producer replaces prior rows across build ids in each write scope, retaining the old pin is not an availability mechanism; a row set carrying only the new build still requires the governed re-pin. Suvarṇa will rebuild `ga_dashas` in its current pass without holding for Kāla; the frozen Gochara 5.0 pin (`75524b3e-102a-43ec-8cee-3f57fee752c3` for canonical Vimśottarī) becomes unreadable when those rows are replaced, so Gochara daśā reads return `build_not_pinned` until Kāla re-pins via J-4p. This agreement does not itself change the pin.
4. The baseline read tier is `two_pass_verified` for the frozen Gochara §4.0 Vimśottarī read. Other system/level tiers require an explicit, source-backed acceptance policy; an honest lower tier remains labelled as such and never masquerades as two-pass. The measured canonical Lahiri matrix above is the current producer evidence. Kāla's F2 must expose a typed unavailable/unknown result where the accepted tier has no row.
   Applicability is a separate producer fact from row presence and verification tier. Suvarṇa acknowledges Aṣṭottarī applicability as unknown under today's hard-coded true flag and will repair it with a per-chart classical predicate and failed-condition evidence after certification. Until that evidence exists, F2 cannot promote `applies_to_this_chart_flag = true` into a positive applicability verdict or silently use the period as an eligible clock.
5. Persisted row IDs are deterministic for the writer's semantic identity, which includes both ISO bounds. Kāla pins the build as well as the row ID: a changed bound can yield a different ID, while an unchanged ID does not establish equal verification tier or a settled new build. Suvarṇa confirms `build_id` changes on its rebuild; J-4p performs the deliberate re-pin after the `L1_SETTLED` receipt.

## F2 lookup cases for the agreed contract

These cases make the period-cutting and null rules testable. They specify reader behavior, not an assertion that the current L1 rows pass every case. `t` is a UTC instant and `A` and `B` are otherwise eligible rows under one pinned chart, ayanāṃśa, system and build.

| source rows and request | F2 result | failure this case must catch |
|---|---|---|
| `A = [t0,t1)`, `B = [t1,t2)`, lookup at `t1` | `B` only | End-inclusive lookup retaining `A` at the shared boundary. |
| A build has no `L1_SETTLED` precision guarantee, or a stored bound is known to have come from the writer's date-only fallback | No exact timed-transition claim; preserve the period row with a typed precision-unavailable result until the producer supplies a guarantee or detectable precision provenance | Assuming `TIMESTAMPTZ` or a non-midnight string proves astronomical boundary precision. |
| A level-2 child has `next_dasha_start_iso = null` and a level-2 sibling begins at its `end_iso` | The sibling is selected at that boundary from its own `start_iso`; the level-1 annotation is irrelevant | Applying a level-1-only annotation to deeper periods or treating its null as no successor. |
| A period has `sandhi_flag = true` but `t` is far from either ISO boundary | No active sandhi band unless F2's declared band rule independently includes `t` | Interpreting the duration flag as an active-at-time sandhi judgment. |
| `A = [t0,t1)`, `B = [t2,t3)` with `t1 < t < t2` | Typed `coverage_gap`, with no active period | Substituting the nearest interval or a date-only projection. |
| Two eligible rows at the requested level and parent both contain `t` | Typed `ambiguous_period`; reject both | Row order or `LIMIT 1` silently choosing an answer. |
| A selected child has an absent, different-build, or unaccepted-tier required ancestor | Typed `hierarchy_unavailable`; no partial period chain | Borrowing a parent from a prior build or inheriting its tier. |
| An Aṣṭottarī row has `applies_to_this_chart_flag = true`, but the settled producer output lacks a chart-specific applicability test and its failed-condition evidence | Applicability unknown; no eligible Aṣṭottarī clock | Promoting the writer's canonical-chart true default into a per-chart eligibility verdict. |
| The producer has replaced all rows in the requested system and ayanāṃśa with a new build, while the reader still pins the prior build | Typed `build_not_pinned` or unavailable result; no read from the new rows until the governed re-pin | Treating a single new build as permission to change the frozen read contract silently. |
| The only matching row is `scope_cap`, or the selected row's relevant boundary is window-truncated | Excluded depth gives typed `scope_cap`; a clipped edge carries `boundary_truncated` and cannot be called a natural transition | Treating a sentinel or the calculation-window edge as a witnessed daśā change. |

The failure labels here are F2 contract outcomes; Kāla's implementation may map them into its governed closed vocabulary, but it must preserve the distinctions. A later producer repair or new build still needs its own measured evidence.
