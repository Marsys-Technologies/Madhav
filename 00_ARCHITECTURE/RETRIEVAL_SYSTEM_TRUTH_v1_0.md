# Retrieval System Truth — What Paripraśna Gets Designed Against

> **Reading contract.** Every number and behaviour in this document is sourced
> to a PG1 finding id (e.g. `PG1-R1-0003`) or a BIND observation. Nothing here

## 0 — The one-paragraph truth

There is one platform capability registry (`platform/src/lib/retrieval/registry/`,
**119** distinct `marsys://tool/*` URIs) served through the MCP edge as **139**
tool aliases (many-to-one), documented internally by a hand-maintained census
that says **120** (stale, undercounts by 19), and mis-audited at BIND against
`CAPABILITY_MANIFEST.json`'s **113** — which is a governance-artifact catalog,
not an MCP registry at all. Behaviourally the served surface mostly works and is
honest about its density, but carries at least three live defects a first-day
caller hits, a judgment-flags vocabulary far richer than documented, a planning
plane split into two live-but-incompatible planners plus two dead islands, and a
cost/latency observability plane that is schema-present but 100% unpopulated — so
what the acharya floor costs in tools, bytes, and milliseconds is, today,
genuinely unmeasurable. No served conversational reading has ever been produced
or persisted. This is the substrate Paripraśna sits on.

## 1 — Real capability inventory: declared vs observed

### 1.1 The four numbers, and why only two of them are registries

BIND framed the opening question as reconciling `CAPABILITY_MANIFEST.json`
(`entry_count: 113`) against a "~200 observed live" surface, as if they were one
registry at two points of drift. Lane R-1 (`PG1-R1-0001`, `-0002`, `-0003`)
established that this was **two errors stacked**, not one drift:

| Number | Source | What it actually is | Use it as… |
|---|---|---|---|
| **113** | `CAPABILITY_MANIFEST.json` `entry_count` | A **governance-artifact catalog** (canonical_id, path, version, status, layer, expose_to_chat) generated by `platform/src/scripts/manifest/build.ts` from markdown/data assets — its first entry is `CGP_AUDIT_v1_0.md`. Has **no** `input_schema`/`archetype`/`tool_role` field. | **Never** as an MCP-capability count. Comparing it to the tool surface is a category error. (`PG1-R1-0001`, severity high) |
| **119** | `platform/src/lib/retrieval/registry/layers/**` | The **real "one registry"** — distinct `marsys://tool/*` URIs across 104 files, `CapabilityDescriptor`-typed. This is what D-08/A-06/A-08 mean by "one registry". | The **authoritative baseline** for "how many capabilities exist." (`PG1-R1-0003`) |
| **120** | `platform-mcp/src/server.ts:522` `REGISTERED_TOOL_COUNT` | A **hand-maintained census comment** ("BA-P1 recount 2026-07-03 — authoritative") that undercounts four of its own cited files. The health endpoint reports this stale figure. | Nothing — it is wrong in the same GA.1/B.8 drift class the project warns about. (`PG1-R1-0002`, severity high) |
| **139** | live `mcp__marsys-jis-direct__*` listing | The **actual served MCP tool-name surface** — a many-to-one **alias layer** over the 119 registry URIs. **The corrected inventory sentence:** *119 distinct registry capabilities, served
as 139 MCP tool names via an alias layer, documented internally as 120 (stale
undercount), audited at BIND against 113 (wrong artifact entirely).* None of the
four are interchangeable. The architecture's §16.4 "126 actual `server.tool(`
count" is itself an undercount that missed the `regAlias`/`globalAlias` helper
registrations.

## 2 — Behavioural profile per capability (including the dead ones)

### 2.1 The surface mostly works and is honest about density

Every whole-chart / signal-heavy tool triggered the R5 §N.6 response-budget
trimmer, confirming the Serving Density Principle is genuinely load-bearing at
scale, not a rare edge (`PG1-R2-0009`): `ganita_strength_get` 520→65,
`ganita_condition_get` 340→85, `ganita_sade_sati_get` 1259→78, `ganita_dashas_get`
89→44, `bodha_domain_reading_get` capping 3107 signal_id_refs → 200,
`bodha_chart_digest_get` 300→107 family rows→top-20. Drill pointers, when tested
end-to-end on a **registry-backed** pair, resolve to substantively richer data —
`ganita_yogas_get` (7 catalog rows, 3 flagged `catalog_only`) → `ganita_yoga_firings_get`
(12 fired yogas with full bhaṅga ledgers) — so the "reference-don't-repeat"
premise holds on that class (`PG1-R2-0006`). The chart-agnostic gate (A2) held on
all 3 tools probed with sentinel UUIDs: honestly-empty, no leak of the real chart
(`PG1-R2-0004`).

### 2.2 The judgment_flags vocabulary is far richer than "3"

BIND stated only 3 `judgment_flags` values were documented anywhere. R-2's 35-call
sample **alone** surfaced **≥9 distinct served values** (`PG1-R2-0007`):
`catalog_only_rows_present`, `zero_rows_returned`, `bearing_yogas_no_domain_match`,
`bearing_yogas_corroboration_caveat`, `notably_absent_not_checked`,
`afflictions_present`, `response_still_over_12kb_budget_after_full_trim`,
`timing_anchored_forced_false` — plus sibling fields `catalog_only_note` and
`dosha_label_gate`. **Critical behavioural caveat:** flags appear **only** when
`response_format=v3` is requested (or on tools whose only envelope is the v3
shape). Every default-legacy call returned `judgment_flags: []` **even where the
underlying condition was present in `content`** (e.g. catalog-only rows,
bhaṅga-ledger cancellations). The true vocabulary is therefore larger than 9, and
a naive caller on the default envelope never sees the flag at all. **For
Paripraśna:** the density signalling the §N.6 principle depends on is
opt-in-gated behind `response_format=v3` today — the chat projection must request
v3 (or the envelope default must flip) or it inherits the legacy blindness.

### 2.3 Two live defects a first-day caller hits (not adversarial)

| Tool | Defect | Evidence |
|---|---|---|
| `phala_anchors_get` | **422** on its own documented-optional param. `date_range` is `.optional()` in the tool's JSON/Zod schema but **mandatory** one hop downstream at the sidecar `/api/compute/phala/event_anchors`; the alias wrapper synthesizes no default before forwarding. Schema over-promises. | `PG1-R2-0002` (verified: Zod `.optional()` at `register_p1_aliases.ts:1294-1297`) |
| `ref_dignity_reference_get` | **400 `internal_error`** on its flagship documented use — `planet=Saturn`, the exact example in the tool's own description — returning `platform DB query failed: 400` instead of data. A genuinely broken code path on a non-exotic parameter. | `PG1-R2-0003` (severity high) |

### 2.4 Drill pointers degrade to `"unknown_tool"` on sidecar/alias tools

The `drill_pointers`/`recover_via` self-reference — the mechanism A1's
reference-don't-repeat premise rides on — resolves the calling tool's name
correctly on **registry-backed L1 tools** (`ganita_dashas_get`'s own trim_report)
but falls back to the literal string `"unknown_tool"` on **sidecar/alias-backed**
tools: `kala_windows_get` (3× on activations/predicates/signal_id_refs),
`phala_outlook_get` (2× on mitigations/auspicious_windows). The recovery pointer
is unusable as written — the caller is told to "call unknown_tool again"
(`PG1-R2-0001`). The verifier confirmed the literal fallback string at
`register_p1_ganita.ts:148` and `register_p1_aliases.ts:181`.

### 2.5 Three KEYSTONE sidecar tools break the uniform envelope

`mimamsa_calibration_get`, `mimamsa_insight_get`, and `phala_mitigation_get` wrap
their real payload as a **JSON-encoded string** one level deeper than every other
tool (`result.results[0].content` is an escaped string, not an object). A caller
written against the common envelope gets a raw string; `phala_mitigation_get`'s is
additionally **truncated mid-JSON by the budget**, risking an unparseable
fragment (`PG1-R2-0010`). These are near-certainly the "three live KEYSTONE
REQUEST sidecar tools" R-1 found named in `server.ts` comments (`mimamsa_outcome`,
`phala_event_anchors`, `kala_temporal_bundle`) — the concrete A-04
sidecar-pull-in inventory, confirmed independently from the wire shape.

### 2.6 Envelope `total` disclosure is v3-gated too

Under the default legacy envelope, top-level `pagination.total` is frequently
`null` even though the real total sits one level down in `content.total`
(`ganita_strength_get`: `pagination.total=null` / `content.total=520`;
`ganita_condition_get` 340; `ganita_nakshatra_get` 39). A caller reading only the
promoted envelope block gets a false "total unknown". It is populated correctly
only on the v3 path (`PG1-R2-0008`).

### 2.7 Dead capability islands (C-3 dead-code census, 6 confirmed clusters)

Zero-importer code that the retrieval/chat plane carries but never runs:
`classify-error.ts`'s `classifyChatError` (fully-built error classifier, the very
one A-25 wants to adopt — dead, `PG1-C3-0001`); `retrieval/adapters/agentic_loop/`
(7-file island, distinct from the LIVE `synthesis/agentic_loop`, `PG1-C3-0002`);
`AdaptiveMessageList.tsx` + transitively `VirtualizedMessageList.tsx`
(`PG1-C3-0003/0005`); `useChatSession.ts` (`PG1-C3-0004`); the
`consume/lifecycle/` component folder (5 shells, type-only importers of the LIVE
`useChatLifecycle` hook — delete the folder, keep the hook; `PG1-C3-0006`).

## 3 — The planning path as it actually runs

Lane R-3 statically traced the identical question — *"what does my career look
like this year"* — through every planner. The reality is **worse than the doc's
"three planners"**: **four planner surfaces, two live-but-structurally-incompatible,
two dead islands** (`PG1-R3-0001`).

| # | Surface | Wired? | Emits | Floor / dark / CR / capability_version? |
|---|---|---|---|---|
| 1 | `pipeline_planner.ts:269` `callPipelinePlanner` (web consult) | **LIVE** — `consult/route.ts:436` `runPlanner(...)` | `PipelinePlan` (query_class + LLM-chosen `tool_calls[{tool_name,params,priority,reason}]` + asset_bundle) | **NO — none of it** |
| 2 | `plan_builder.ts:52` `buildVidhiPlan` (MCP `plan_retrieval`) | **LIVE** — `server.ts:388` | `VidhiPlan` (floor + machine_band + `completeness_receipt` served/empty/dark + `capability_version`) | **YES — all of it** |
| 3 | `retrieval/router/router.ts` `route()` ("D2 Query Router") | **DEAD ISLAND** — zero production importer | `RouteResult` | partial, unused |
| 4 | `lib/vidhi/compiler.ts` `compileContract` | **DEAD ISLAND** — zero production importer (duplicate of #2's compiler) | `CompiledContract` | yes, unused |

**The determinative fact:** the identical career question yields a `PipelinePlan`
on the web channel and a `VidhiPlan` on the MCP channel — **two non-interoperating
plan objects** — while two more planner implementations sit unwired.

**`single_pass` is NOT dead** — but the architecture doc AND C-3 both mis-state it
(`PG1-R3-0004`, supersedes both). Precise status: a **test-load-bearing structural
scaffold NOT on the runtime path**. The module has exactly two production
importers (both internal to `lib/pipelines/`: the barrel + `selector.ts`), the
selector's own exports have **zero** production importers (the selector never runs
live), and `singlePassPipeline` is an inert descriptor (`{kind, describe()}`, no
`run()`). The **actual** runtime single-vs-agentic decision is made inline at
`run_adapter_dispatch.ts:314` (`useAgenticLoop && loopConfig ? runAgenticLoop(...)
: adapter.chat(...)`), with onfinish hardcoded `pipelineKind:'agentic'` at `:494`.
So the arch doc is right the selector never reaches it; C-3 is right it is not
orphan-deletable (barrel + tests break); **neither is precise** — the live
single-pass path is the inline `adapter.chat` branch, not the module.

**`PlanReceipt` is absent from code entirely** (`PG1-R3-0005`, reconciling R-1/R-2's
"zero hits" to definitive absent-not-type-only): zero `.ts` matches across
`platform/src` + `platform-mcp/src`; it lives only in docs/audit artifacts. Its
de-facto shipped analogue is the MCP `VidhiPlan` + `CompletenessReceipt` — the same
idea, never named `PlanReceipt` in code.

## 4 — What the acharya floor costs in tools / bytes / milliseconds

**It is genuinely unmeasurable today.** Lane D-2 established this empirically, not
by absence-of-grep (`PG1-D2-0001`, `-0002`):

- **Cost:** the cost-accounting tables exist with exactly the right shape —
  `llm_usage_events` (columns `input_tokens`, `output_tokens`, `cache_read/write_tokens`,
  `reasoning_tokens`, `computed_cost_usd`, `pricing_version_id`, `latency_ms`,
  `provider`, `model`, `pipeline_stage`, `status`, …), `llm_provider_cost_reports`,
  `llm_cost_reconciliation` — and **all three hold 0 rows**. Dead schema, never
  wired into the request path. Cost-per-turn-by-model, cost-by-phase: **not
  computable**.
- **Latency:** the one populated telemetry table, `query_trace_steps` (493→495
  rows, 2026-07-01→2026-07-18), has `latency_ms` **NULL on every row**, and
  `step_type` is `'sql'` for all rows (no planner/retrieval/synthesis phase tag).
  p50/p95 TTFT, planner-latency distribution, tool-fetch latency: **not
  computable even in principle** from what is logged. Grep for
  `ttft|first_token|histogram` across `src`: zero matches.

**Byte-size observations from R-2's live sweep** (the only real cost data that
exists): responses are large enough that the trimmer fires on every whole-chart
tool (§2.1 counts above); `judgment_query` on `marriage` emitted a flag
`response_still_over_12kb_budget_after_full_trim` — i.e. a single
whole-chart-read response exceeds the 12 KB budget even after a full trim pass
(`PG1-R2-0007`). `bodha_domain_reading_get` alone carries 3134 (career) / 5599
(progeny) ranked signals before capping. **For §17.4/§17.8:** the latency budgets
(POST→turn.open <300ms; first activity <1s) are **design targets against zero
measured baseline** — the remediation is "wire the existing `llm_usage_events`
schema + populate `query_trace_steps.latency_ms` + add phase tagging," not "design
a cost schema."

## 5 — Known-dark territory

The "dark" concept — a compiled floor item whose backing primitive has a non-null
`known_gap` (a `CR-N` pointer) and was not served — is **real and shipped, on the
MCP channel only** (`PG1-R3-0006`). Emitted in `completeness_receipt.ts`'s `dark[]`
bucket as `{floor_item_id, cr_row}`, `cr_row` matching `/^CR-\d+$/`, guaranteed
OPEN/LOGGED (never CLOSED). Receipt invariant: `served ∪ empty ∪ dark` = the full
deduped floor set, pairwise disjoint.

**Concrete for the traced career question** (`career_deepdive`, 12 floor items):
**5 dark at plan issuance**, citing:

| CR | Gap | Note |
|---|---|---|
| **CR-56** | `dhana_yoga_scan` — house-lord yoga detector absent | ELEVATED #1 acharya-grade blocker |
| **CR-64** | `nakshatra_semantics` — never rank | |
| **CR-24** | `mechanism_read` — chain/circuit motif not first-class | |
| **CR-66** | `taranga_curve` — Phala domain anchors still zero | |
| **CR-69** | `intervention_synthesis` — no leverage_index axis | |

Registry-wide: **12 `known_gap` primitives out of 114** (CR-16/24/30/37/56/61/64/66/67/68/69/73);
a single-intent plan carries only the subset on its floor.

**The channel asymmetry Paripraśna must close:** the live **web `PipelinePlan`
carries NO dark concept at all** — no floor, no receipt, no CR pointers, no
`capability_version`. A native asking the same question on the portal today
receives an answer with **no machine-readable account of what was structurally
unavailable**, while an MCP `plan_retrieval` caller receives the full dark ledger.
This is the single sharpest current-state gap between the two channels.

## 6 — Recommended chat projection (Z-1 synthesis judgment)

> **This is the author's own synthesis recommendation for architecture §8.3, not
> an observed fact.** It is offered as direct input to the "Chat (planner-filtered
> per turn)" projection design.

Given the observed behaviour, the chat projection should be defined by four
non-negotiables drawn from what the sweep found:

1. **Request `response_format=v3` unconditionally.** §2.2/§2.6 show the entire
   density-and-total disclosure apparatus (judgment_flags, `coverage.total`,
   catalog-only separation) is opt-in-gated behind v3. A legacy-envelope chat
   projection silently inherits the blindness the §N.6 Serving Density Principle
   exists to prevent. This is the cheapest single correctness win available.
2. **Route the chat plan through the MCP `VidhiPlan` compiler, not the web
   `PipelinePlan`.** §3 and §5 show the floor/dark/CR/`capability_version`
   machinery — the whole B.11-enforcement and honest-gap apparatus — exists only
   on the MCP side. The chat projection should emit the dark ledger too; the
   asymmetry is the defect, and R-3's falsification (item 7 of Deliverable 2)
   shows unifying onto `VidhiPlan` is week-scale, not a contradiction.
3. **Exclude the sidecar/alias-backed tools with broken recovery pointers from
   the drill surface until F-25j/k/l/n are fixed**, or the chat's own
   reference-don't-repeat pointers will emit `"unknown_tool"` and its
   `phala_anchors`/`ref_dignity` calls will hard-error on first use.
4. **Size the projection against 119 registry URIs, not 113 or 120 or 139.** The
   MCP-compact "~25–35 umbrellas" target (A-03) collapses the 139 alias names, but
   the umbrella-to-capability mapping must be built from the 119 registry URIs
   (R-1's authoritative baseline), because most of the 139→119 excess is
   Phase-1 naming aliases (many-to-one) that A-02 deletes anyway.

The chat projection is therefore *"v3 envelope + VidhiPlan floor + drill surface
minus the broken sidecar tools, filtered per turn from the 119-URI registry."*

## 7 — Envelope self-sufficiency assessment (Z-1 reasoned judgment)

> **This is my own analytical assessment, not a literal blind test.** I cannot
> spawn a genuinely fresh, memory-free LLM and put a live envelope in front of it;
> what follows is a reasoned read of three real envelopes from R-2's sweep against
> the question "would a naive reader catch the density/catalog signal?" — and I
> flag it as reasoning, not measurement, per the standard the brief sets.

**Envelope A — `ganita_yogas_get`, default legacy.** Returns 7 `yoga_label` rows,
3 of them catalog-only/`requires_pass`, but `judgment_flags: []` and no
`catalog_only_note` promoted (both are v3-gated). **A naive reader would NOT catch
it.** The raw row array reads as "7 confirmed yogas." The catalog-vs-confirmed
distinction the §N.6 principle Part 1 mandates is present in the data model but
invisible on the default envelope — the exact flattening §N.6 names as the
violation. Verdict: **not self-sufficient** on legacy.

**Envelope B — `ganita_yogas_get`, `response_format=v3`.** Same call carries
`judgment_flags: ["catalog_only_rows_present: 3 row(s)… (JL-004)…"]`,
`coverage: {served:10, total:10}`, and a drill pointer to the firings-authoritative
`ganita_yoga_firings_get`. **A careful reader would catch it**; a hurried one might
still read the 10-row array first and the flag second. Verdict: **self-sufficient
for a reader who parses `judgment_flags`** — which is precisely why the chat
projection must both request v3 AND surface the flag prominently, not bury it.

**Envelope C — `judgment_query` on `marriage`, v3.** Emits six flags at once
(`bearing_yogas_no_domain_match`, `bearing_yogas_corroboration_caveat`,
`notably_absent_not_checked`, `afflictions_present`,
`response_still_over_12kb_budget_after_full_trim`, `timing_anchored_forced_false`)
alongside `verdict: contested, composite_score: -3.5`. **This is the honest case
working as designed** — the verdict layer is non-empty, the gaps are declared as
flags rather than silently substituted (§N.6 Part 3). But `coverage: null` even on
v3 for this specific tool means a reader cannot tell served-vs-total family size.
Verdict: **mostly self-sufficient, with a residual `coverage:null` hole.**

**Overall reasoned assessment:** envelope self-sufficiency is a **function of
`response_format`, not a property of the system.** On v3 the envelopes are largely
honest and a diligent reader catches the density/catalog signal; on the default
legacy envelope the same underlying condition is silent and a naive reader is
actively misled into reading catalog matches as confirmed findings. Since the
default is legacy, **the system as a whole is not envelope-self-sufficient today** —
and the single highest-leverage fix is making v3 the chat projection's default
(item 6.1). I hold this at medium confidence: it is an analytical read of three
envelopes, not a controlled blind-reader trial, and a real fresh-LLM test across a
wider sample should be run before this is treated as settled.
