# §1 Mission

The F.3 forensic L1 + L2 findings (plus plan §7 decision 5, plus an empty-state-specific addendum from operator screenshot review 2026-05-18):

- **L1**: chat content is visually offset right of viewport center because the sidebar is a `fixed inset-y-0 left-0 z-40` overlay *AND* the chat-column has `md:ml-10` (collapsed) or `md:ml-56` (expanded) on top of that. The offset compounds with `MarkdownContent`'s own redundant `mx-auto max-w-[68ch]`. Visual center drifts unpredictably with viewport width.

- **L2**: two sidebar toggles render simultaneously — the canonical header toggle (`v2-desktop-sidebar-toggle`) AND a vestigial in-sidebar "Collapse" `<` button (`v2-sidebar-collapse`) that was never removed when `ConversationSidebarV2` was adopted in Phase C.2.

- **Decision 5**: the decorative three-dot menu at `ConversationSidebarV2.tsx:106-128` is a `<span aria-hidden>` with no onClick — purely visual. Plan §7 decides to hide it via `display:none` until R7 wires rename/delete.

- **L1.2 (NEW — empty-state hero, v1.1)**: the empty-state hero ("Hi {name}, What's on your mind?") rendered via `<ThreadPrimitive.Empty><EmptyState ...></ThreadPrimitive.Empty>` at `ConsumeChatV2.tsx:1197-1204` visually appears far-left at large viewport widths even though `EmptyState.tsx:25` has `mx-auto flex h-full w-full max-w-2xl flex-col items-center justify-center px-4`. By CSS spec the hero should center. It doesn't — operator screenshot at 2600px viewport (2026-05-18) shows the "Hi Abhisek," text starting at ~17% from left of viewport, not at viewport center. The most likely defeat path: `ThreadPrimitive.Viewport` is `flex-1 overflow-y-auto` (a flex child with overflow + no flex centering of its own), wrapped by `<main className="flex-1 overflow-hidden">` between Viewport and chat-column, producing a width context where mx-auto fails to center the absolutely-positioned content. Forensic L1's original analysis covered the chat-message render path (`<V2Message>` with its own `max-w-4xl mx-auto`), not the empty-state render path which routes through `<ThreadPrimitive.Empty>` and never touches V2Message. The empty-state path needs its own explicit centering wrapper.

R6.4 ships all five surgical edits in a single PR. Visual outcome: chat content centers in the full viewport at all sidebar states — including the empty-state hero and the composer; exactly one collapse control (header); no decorative menu artifact.

## §3.5 — Empty-state hero centering (NEW in v1.1)

**Site:** `platform/src/components/consume/ConsumeChatV2.tsx:1197-1204`, the `ThreadPrimitive.Empty` block.

**Why the existing mx-auto fails empirically:** Operator screenshot at 2600px viewport (2026-05-18) shows the EmptyState hero at ~17% from left edge despite `EmptyState.tsx:25` declaring `mx-auto flex h-full w-full max-w-2xl flex-col items-center justify-center px-4`. The most likely cause is the chain `<main className="flex-1 overflow-hidden">` → `<ThreadPrimitive.Root className="flex h-full flex-col">` → `<ThreadPrimitive.Viewport className="flex-1 overflow-y-auto scroll-smooth py-4">` producing a width context where Viewport's overflow + flex-1 sizing interacts with assistant-ui's internal rendering of `<ThreadPrimitive.Empty>` such that the EmptyState's mx-auto resolves against the wrong containing block. We do NOT need to fully diagnose this — we add an explicit centering layer that's robust regardless of the underlying cause.

**Current code at line 1197-1204:**

```tsx
<ThreadPrimitive.Empty>
  <EmptyState
    chartId={chartId}
    chartName={chartName}
    className="h-full"
    data-testid="v2-thread-empty"
  />
</ThreadPrimitive.Empty>
```

**Target — wrap with explicit centering container:**

```tsx
<ThreadPrimitive.Empty>
  <div
    className="mx-auto flex h-full w-full max-w-4xl items-center justify-center px-4"
    data-testid="v2-thread-empty-wrap"
  >
    <EmptyState
      chartId={chartId}
      chartName={chartName}
      data-testid="v2-thread-empty"
    />
  </div>
</ThreadPrimitive.Empty>
```

Notes on the wrapper className:

- `flex items-center justify-center` — flex row centering both axes (default flex-direction: row). This is more robust than relying on a child's mx-auto because the flex parent has explicit horizontal centering rule.
- `mx-auto max-w-4xl w-full` — caps width at the same `max-w-4xl` (1024px) the V2Message wrappers use, so the empty-state hero width matches the message column width. Visual consistency between empty and populated states.
- `h-full` — fills the Viewport vertically so vertical centering works.
- `px-4` — matches the EmptyState's own inner padding so removing EmptyState's mx-auto doesn't shift the hero text.
- `data-testid="v2-thread-empty-wrap"` — distinct from the inner `v2-thread-empty` testid; lets R6-SMOKE or future tests assert against either layer.

**Also simplify EmptyState.tsx** to drop the now-redundant outer centering (the wrapper handles it):

**Current `EmptyState.tsx:22-35`:**

```tsx

    )}
  >

      {firstName ? `Hi ${firstName},` : 'Hi,'}
      <br />
      What&rsquo;s on your mind?
    </p>
  </div>
)
```

**Target:**

```tsx
return (
  <div
    className={cn(
      'flex h-full w-full flex-col items-center justify-center',
      className
    )}
  >
    <p className="font-serif text-center text-[2rem] font-normal leading-snug text-foreground/85">
      {firstName ? `Hi ${firstName},` : 'Hi,'}
      <br />
      What&rsquo;s on your mind?
    </p>
  </div>

```

Changes:

- Drop `mx-auto` (the wrap layer handles horizontal centering)
- Drop `max-w-2xl` (the wrap layer applies `max-w-4xl` for visual consistency with message column width — slightly wider canvas is correct for the empty-state hero)
- Drop `px-4` (the wrap layer applies `px-4` once)
- Keep `flex flex-col items-center justify-center` for inner alignment of any future children
- Keep `h-full w-full` for filling the wrap layer

**Why a width cap of `max-w-4xl` on the wrap (not 2xl):** the V2Message wrappers use `max-w-4xl mx-auto` (≈1024px). Aligning the empty-state hero to the same horizontal width column means the visual centerline stays consistent between empty-state and chat-message states. Operator transitions from empty → first-message will not see a horizontal layout jump.

**Composer parity check:** the composer at `ConsumeChatV2.tsx` (around lines 988, 1040, 1200 per forensic) uses `mx-auto max-w-4xl` on its own wrapper. After §3.1 drops the chat-column ml-* offset, the composer should center via the existing mx-auto on its wrapper. If operator visual review post-merge shows the composer is STILL offset (as the screenshot suggests it might be), file a follow-up tightening — but expect §3.1 alone to resolve it because the composer wrapper is structurally simpler than the empty-state path (it's a direct child of ThreadPrimitive.Root, not nested inside Viewport's flex+overflow chain).
