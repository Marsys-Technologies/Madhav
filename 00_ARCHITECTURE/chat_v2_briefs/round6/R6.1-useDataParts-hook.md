# §1 Mission

The F.3 forensic Pattern A finding: V2Message reads `message.metadata?.unstable_data` but assistant-ui lands route data-part emissions in `message.content` as `{type:'data', name:'<x>'}`. The citation and correction code paths already defend against both sources (and work correctly — these are the WORKING REFERENCE implementations at ConsumeChatV2.tsx:204-222 and 422-440). The stage, tool, panel, citation_gate, and prediction code paths only check `metadata.unstable_data`. Result: five live-UI surfaces are silently invisible in production today — StageStepper, ToolCallCard array, panel confidence ribbon, validator gate band, prediction candidate chips.

R6.1 consolidates the dual-source read into a single `useDataParts(message)` hook and migrates all five non-working call sites. Citation + correction call sites are migrated for uniformity (already work — this is consolidation, not a behavior change).

Plus: forensic §4 O1 observed that route.ts emits `stagePart('synthesis', 'running')` at line 889 but never the matching `'done'` event. Even after the stepper renders, the synthesis pip pulses indefinitely. R6.1 adds the closing emit in `onFinish` after stream merge completes, before the SSE `done` event at line 1061.

Together, R6.1 is the highest-leverage P0 in Round 6: one PR turns five orphan surfaces back on and closes the stage state machine.

# §3 Implementation specification

## §3.1 The hook — `platform/src/lib/chat-v2/useDataParts.ts`

```ts
import type { UIMessage } from 'ai'
import { useMemo } from 'react'

/**
 * A normalized data part as seen by V2 consumers.
 * Live-stream (during request) and post-stream (after persistence) data parts
 * are surfaced with the same shape regardless of which transport landed them.
 */
export interface NormalizedDataPart {
  /** Discriminator e.g. 'data-stage', 'data-citation', 'data-correction', 'data-tool', 'data-panel-member', 'data-panel-meta', 'data-citation-gate', 'data-prediction-candidate', 'data-out-of-domain', 'data-title'. */
  type: `data-${string}`
  data: unknown
  /** Provenance — useful for tests + debugging. */
  source: 'metadata' | 'content'
}

/**
 * Returns the merged set of data parts associated with `message`, drawn from
 * both `message.metadata.unstable_data` (live-stream during request) and
 * `message.content` filtered to assistant-ui DataMessagePart shape
 * (`{type:'data', name:'<x>', data:...}` — post-stream after persistence).
 *
 * The two sources may emit the same logical part once each (during a session
 * that streams then persists). De-duplication is intentionally not applied
 * here — consumers that need uniqueness should de-dupe on a semantic key
 * (e.g. by `data.signal_id` for citations). Most consumers use array
 * .filter()/.find() and tolerate duplicate-but-identical entries.
 */
export function useDataParts(message: Pick<UIMessage, 'metadata' | 'content'>): readonly NormalizedDataPart[] {
  return useMemo(() => {
    const result: NormalizedDataPart[] = []

    // Source 1: live-stream — message.metadata.unstable_data
    const metaParts = (message.metadata as { unstable_data?: ReadonlyArray<unknown> } | undefined)?.unstable_data ?? []
    for (const d of metaParts) {
      if (typeof d === 'object' && d !== null) {
        const obj = d as Record<string, unknown>
        if (typeof obj.type === 'string' && obj.type.startsWith('data-')) {
          result.push({ type: obj.type as `data-${string}`, data: obj.data, source: 'metadata' })
        }
      }
    }

    // Source 2: post-stream — message.content as DataMessagePart array
    const contentParts = (message.content as ReadonlyArray<unknown>) ?? []
    for (const p of contentParts) {
      if (typeof p === 'object' && p !== null) {
        const obj = p as Record<string, unknown>
        if (obj.type === 'data' && typeof obj.name === 'string') {
          result.push({ type: `data-${obj.name}` as `data-${string}`, data: obj.data, source: 'content' })
        }
      }
    }

    return result
  }, [message.metadata, message.content])
}
```

Type-safety notes:

- The hook does not assert the shape of `data` — each consumer narrows downstream as it does today.
- `useMemo` keyed on the two source references means re-renders triggered by other message props (text, role, etc.) do not invalidate the merged list.
- The hook is `readonly` so consumers cannot accidentally mutate the merged list.

## §3.2 Unit tests — `platform/src/lib/chat-v2/__tests__/useDataParts.test.ts`

Cover:

1. **Empty case** — both sources absent → returns `[]`.
2. **Metadata-only** — `unstable_data: [{type:'data-stage', data:{name:'planning',state:'running'}}]` → returns one part with `source: 'metadata'`.
3. **Content-only** — `content: [{type:'data', name:'citation', data:{signal_id:'SIG.MSR.001'}}]` → returns one part with `type: 'data-citation'`, `source: 'content'`.
4. **Both sources** — same logical part landed once in each; result contains BOTH entries (no de-duplication); call sites that care about uniqueness must de-dupe themselves.
5. **Filtering** — non-`data-*` entries in `unstable_data` ignored; non-`{type:'data'}` entries in `content` ignored.
6. **Type narrowing** — TS infers `type` as a template literal `data-${string}`, not just `string`.

Use `@testing-library/react` `renderHook` per existing chat-v2 test conventions.
