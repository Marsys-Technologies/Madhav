## §1 — Project context (one-screen orientation)

**Project:** MARSYS-JIS — an LLM-operated Jyotish (Vedic astrology) instrument built for one native (Abhisek Mohanty, born 1984-02-05 10:43 IST Bhubaneswar) but designed to extend to a research instrument for the discipline. Quality bar: "acharya-grade". Governing artifact: `CLAUDE.md` at the project root. Macro plan: `00_ARCHITECTURE/MACRO_PLAN_v2_0.md` — currently in macro-phase M5.

**Architectural substrate (existing today):**

- L1 facts (FORENSIC v8.0) — chart_facts table, partially populated.
- L1.5 — panchang_daily + ephemeris_daily (full coverage 1900–2100).
- L2.5 synthesis layer — MSR v5.0 (514 signals), UCN v4.1, CDLM v1.3, CGM v9.0, RM v2.2.
- L4 discovery layer (lesser; M3 closed).
- LEL v1.6 — 36 verified life events + period summaries + chronic patterns.
- 09_MULTI_SCHOOL_TRIANGULATION corpus (Parashara primary; Jaimini, KP, Tajaka partial).
- 08_CLASSICAL_CROSS_REFERENCE corpus (BPHS + Jaimini Sutram + KP + Tajaka — partial coverage).
- RAG corpus (Vertex AI 768-dim embeddings over the above, in `rag_chunks` + `rag_embeddings`).
- A Next.js web app at `platform/` deployed as Cloud Run service `amjis-web` in asia-south1, serving a chat at `/consume` with a full server-side pipeline (planner → retrieval → synthesis).

**The MCP workstream** sat on top of all this. Per `MCP_BRIEF_v1_0.md` (`00_ARCHITECTURE/BRIEFS/MCP_BRIEF_v1_0.md`), it was authored as a concurrent workstream to expose MARSYS-JIS to external Claude sessions (Claude Chat custom integrations, Cowork remote MCPs). The brief framed Claude as *"a second seat at the instrument"* — explicit research-instrumentation intent.

**v1 of the MCP shipped 2026-05-21** with 19 tools and the architecture described in the brief: a Cloud Run sidecar `amjis-mcp` that authenticates Bearer keys, validates principals, and proxies tool calls back to platform endpoints under `/api/mcp/*`. The flagship tool `ask_madhav(query)` runs the full pipeline server-side (planner LLM → tools → synthesis LLM) and returns finished `answer_markdown`.

**This conversation is about why that doesn't work, and what should replace it.**

## §3 — Empirical findings (the diagnosis)

Full details in `MCP_DIAGNOSIS_2026-05-22.md`. Summary of what was found by reading the shipped code and empirically probing the live deployment via the MCP tools available in this Cowork session:

### §3.1 — The shipped architecture works at the transport layer

- API key auth, two-layer service-to-service handshake, principal-header passing, tool dispatch, trace logging, observability tools — all return clean 2xx responses.
- The MCP is registered at `https://amjis-mcp-qm256lasva-el.a.run.app`, served from Cloud Run with `min-instances: 1`.
- Probed 11 different tool calls; 10 returned 200 with reasonable data shape; 1 (`ask_madhav` for a non-trivial query) timed out at the platform's 120-s `maxDuration` ceiling.

### §3.2 — Five independent root causes for the four user-visible symptoms

| Symptom | Root cause | Evidence | Severity |
|---|---|---|---|

(correct answer was "Moon"). | **P0** |

### §3.3 — Performance budget breakdown for ask_madhav (the 60-second story)

```
Claude Chat → MCP server (amjis-mcp)
   network + key validation: ~50–250 ms
MCP server → platform /api/mcp/execute
   internal hop + service token: ~50 ms
Platform pipeline:
   resolve singleton chart: 5–20 ms
   rate-limit check: 5–20 ms
   planner (gemini-2.5-flash): 2–4 s
   budget arbitration + bundle hydration: ~50 ms
   parallel tool execution: 30 ms – several seconds
   synthesis (gemini-2.5-pro): 30–90 s ← DOMINANT (60.5s observed)
   citation extraction + envelope: <100 ms

Total observed: ~63 s for a 1-sentence answer.
Claude Chat tolerance: ~60 s.
```

The system was operating right at the timeout boundary on the easiest possible query. Anything non-trivial overshoots.

## §4 — Architectural evolution: v1 → v2 → v3 (the decision pivots)

The architecture went through three iterations during this conversation, each driven by a sharper insight from the native.

### §4.1 — v1 shipped (what existed)

Server-side everything. Pipeline planner picks tools. Pipeline executes tools. Pipeline synthesizes answer with Gemini 2.5 Pro. Returns finished `answer_markdown` to MCP server, which returns it to Claude (the host). Claude wraps the finished answer in its own reply.

Two LLM passes for every query. The 60-s timeout, the verbose `marsys_methodology_block` bloat, the inability of Claude to add value on top of an already-finished paragraph — all symptoms of the same architectural choice.

### §4.2 — Native's first pivot (synthesis off server)

> *"See the architecture is wrong. This is my concern. Synthesis should not happen at all by the synthesis LLM when we are deploying an MCP. The planner should build the context and pass it over to Claude from where we are triggering the messages and Claude should be able to use the payload along with its context to respond to the user. That's the right architecture."*

This produced v2 (`MCP_ARCH_v2_PROPOSAL_2026-05-22.md`, now `SUPERSEDED`): keep the planner, drop server-side synthesis, return a `context_bundle` to the host instead of `answer_markdown`. Claude synthesizes.

v2 was correct as far as it went — it removed one LLM pass, killed the timeout problem, raised quality. But it kept the planner as a server-side LLM.

### §4.3 — Native's second pivot (planner off server too)

> *"How about removing the planner LLM which is Gemini flash at this point in time and Claude the host model getting full visibility of the tools available and appropriately triggers those tools to get the information data from them which loads into the compose context bundle and everything follows the same track. This way two things happen. We have the host model which has got the best understanding of the query, the context of the query, dealing directly with the retrieval tools, triggers them correctly and has more control over the entire flow. We remove double LLM, we save time, save cost."*

Plus a second concurrent ask:

> *"For MCP implementation I would like to have a different and a simple performance measurement system which gives a very clear view of the performance of the retrieval tools and its associated data sources. This is the biggest, most important aspect I want to see."*

This pivot moves to pure MCP (no server-side LLM at all). It's the canonical MCP pattern: server exposes tools + resources, host model orchestrates. The discussion that followed concluded:

- B.11 enforcement (the project's whole-chart-read floor) moves from server pre-injection to a combination of `house-rules` instructions + post-hoc `validate_response()` audit.
- PPL discipline (prospective prediction logging) moves from server auto-logging to Claude-driven explicit `log_prediction()` calls.
- The planner's `query_class` classification is dropped (most of what it gated is being restructured anyway).
- A `holistic_bundle` "fat retrieval" tool is added — deterministic parallel fan-out, NO LLM — as a convenience for the host when it judges a query needs depth across many tools.

### §4.4 — Native's third pivot (substrate, not constraint)

> *"At the end of the day, the one thing that drives all decision preference is the quality of the output that the user will see. That is the sole objective and anything contradicting that can be done away with. So look at the entire system that is currently there not as a restriction but what you have available to you. I want you to fully leverage the data assets through the retrieval tools, and wherever you feel changes need to be made the entire MCP architecture can be different from what MARSYS-JIS internal architecture is. Retrieval tools, data assets, infrastructure — everything is open."*

This was the largest reframe. The MCP architecture is decoupled from MARSYS-JIS internals. Tools can be dropped, added, rewritten. Data assets can be modified, rebuilt, augmented. The web `/consume` chat (which still uses server-side synthesis) is left untouched as a separate surface.

A clarifying-questions tool call established the design rubric:

| Rubric | Native's decision |
|---|---|
| Primary user | Multi-tier: native + invited acharyas + external clients |
| Quality north star (multi-select) | Cross-domain depth + Calibrated epistemics + Classical grounding |
| **NOT** selected | Conversational warmth (intentional — output template leans formal/acharya, not guru-style) |
| Latency profile | Depth always — willing to wait 30s+ |

These three decisions are the spine of v3.

### §4.5 — Native's fourth pivot (lift the token-economy ceiling)

This came LAST in the conversation, after both design docs were authored. Quote:

> *"From a technical standpoint, one more thing that you must consider is currently these retrieval tools might have been configured in such a way that they are optimized for token usage. In the new MCP model, I don't want them to be limited by token usage but to be driven by accuracy and depth of information. Whatever can get the best output, that is the goal — always driven towards the objective."*

This directive arrived after v3 + perf brief were already written. It's been captured as addenda in both docs (§12 in each), and **is to be baked in throughout when Opus regenerates them.** Specifically:

- Server-side token-budget arbitration (`platform/src/lib/pipeline/budget_arbiter.ts`) is **removed entirely** from the v3 path. It existed to ration tool output against the synthesis prompt's context — there is no synthesis prompt anymore.
- Default primitive `limit` parameters are raised to "enough for depth", not "enough for token budget." Recommended new defaults are in v3 §12.
- `holistic_bundle` returns the deepest viable composition by default. The "standard vs exhaustive" tier dichotomy in the original v3 draft collapses to "exhaustive is the default; optional `subset` parameter narrows."
- No server-side bundle truncation. The host (Claude with 200k context) decides what to attend to.
- Perf-system implications: latency becomes informational (not a target to minimize); a new `avg_bundle_size_tokens` metric is added for honest reporting; tool ranking is by *useful signals delivered*, not by *tokens per useful signal*.

The frame shift: **the platform delivers the deepest accurate context possible. Pruning is the host's decision, not the server's.**

## §5 — Design rubric (the spine of v3)

For Opus's quick reference, the full design rubric the v3 architecture is optimized against:

1. **Primary user:** Multi-tier (super_admin / acharya / client). Tier model is load-bearing — drives retrieval filtering AND output template, not just access control.
2. **Quality dimensions** (in priority order, all selected):
   - Cross-domain depth — synthesize across MSR/UCN/CGM/CDLM/RM/multi-school/classical-text/LEL; surface linkages no single-domain look would catch.
   - Calibrated epistemics — every non-trivial claim carries confidence band + horizon (for predictions) + explicit falsifier. Visible in every reply, not buried in metadata.
   - Classical grounding — multi-school citations where convergent; honest disagreement-flagging where not. Source-of-rule traceable.
3. **Quality dimensions NOT in the rubric** (explicitly de-prioritized):
   - Conversational warmth (the formal acharya-style template is preferred over guru-style narration).
4. **Latency profile:** Depth always — no ceiling; willing to wait 30s+ for the right answer.
5. **Cost:** Not a stated constraint. The host pays Claude tokens; the platform pays cheap retrieval-only costs (no server-side LLM in v3).
6. **Data layer:** Open to rebuild. Anything sparse or missing can be backfilled. Tools can be rewritten.
7. **Token economy:** NOT a constraint. Optimize for accuracy and depth; bundles can be as fat as the host's context window can absorb.
8. **Trust model:** Operator (native) is trusted with everything. Acharya tier sees full data + acharya-grade rigor. Client tier sees calibrated outputs with appropriate disclosures.

## §7 — Decisions taken (the "settled" list)

For Opus's clarity — what's NOT up for re-litigation:

1. **No server-side LLM in v3.** Both synthesis and planner are removed. Pure MCP. (This is the core architectural commitment; everything else flows from it.)
2. **Multi-tier user model** (super_admin + acharya + client). All three are real audiences.
3. **Quality rubric: depth + epistemics + classical grounding.** No warmth. Formal acharya-style.
4. **Latency: depth always.** No sub-X-second target.
5. **Token economy: lifted as a constraint.** Optimize for depth.
6. **v3 stands alongside the web /consume chat,** which is untouched and continues to use server-side synthesis. Eventual web rebuild on top of v3 primitives is out of scope for this brief but flagged.
7. **No `ask_madhav` wrapper.** No entry-point tool. Conversation IS the entry point. Resources orient Claude; tools provide data on demand.
8. **`holistic_bundle` exists** as a deterministic parallel fan-out convenience. NOT a planner — no LLM judgment in it.
9. **Performance system is first-class agent context,** not just operator telemetry. Same data, three surfaces (MCP tools + resource snapshot + operator dashboard).
10. **Mandatory code-level fixes from diagnosis** (the `vector_search` placeholder query bug, the lying `chart_facts` enum doc, the `msr_sql` param smuggling, the cloudbuild `MCP_INTERNAL_TOKEN` gap) are inputs to v3.0.
