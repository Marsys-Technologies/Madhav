9. Accepted observations survive interruption/restart and cross-instance resumption. Supported pagination can reach a provable end, and incomplete pagination remains explicit.

## 4. Execution mechanism — how this is driven to completion

### 4.1 Ownership and sequencing

Use one accountable coordinator/integrator and at most two bounded implementation workers when their file ownership is disjoint. This parallel setup is part of the proposed execution plan; no agents are launched during planning. Workers are not alone in the repository and must preserve others' edits. | Evidence/knowledge worker | Availability contracts, semantic projection, coverage tests, targeted retrieval handlers | Regenerate shared artifacts concurrently or change global release infrastructure. |
| Inquiry/answer worker | Deep-planning policy, evidence-driven continuation, response accountability tests | Redesign producers, invent astrological facts, or silently alter coverage thresholds. |
| Release duty owner | Preflight, credential/configuration diagnosis, protected deployment | Run competing cutovers; weaken controls; access unrelated secrets. This may be the existing data-plane owner. |

The release duty can run alongside implementation; it need not occupy a separate permanent agent. Request independent read-only review at the integrated candidate boundary and for a material security/schema change, not after each tiny edit.

### 4.2 The closure loop

Every implementation slice follows this loop:

1. Select the highest-priority failing required scenario or prerequisite from the current completion matrix.
2. Reproduce at the actual boundary: discovery → availability → authorized retrieval → pagination → continuation → synthesis → response register → delivery.
3. Keep the minimal failing test/trace. Identify the first failing boundary, not the last symptom.
4. Implement the smallest reusable repair. Run the focused regression and affected mandatory scenarios.
5. Record the changed result and continue to the next failure. Update campaign state at a delivery milestone, not after each edit.

```text
while required completion outcomes remain:
    refresh only external state relevant to the next action
    choose a runnable blocker-removing work item
    if one exists:
        reproduce -> repair -> verify -> integrate -> record milestone
        continue
    classify the external dependency and attempt safe approved alternatives
    request one precise external action if genuinely necessary
    use the product's waiting mechanism only for a real awaited change
    never manufacture completion or rerun an unchanged failing operation
```

### 4.3 Anti-stall rules

- A failed full release is not retried until a material input changed or a justified transient condition is evidenced. Repeated unchanged attempts are forbidden.
- After two failures with the same signature, stop that attempt sequence; inspect its actual inputs and the next dependent checks together. Continue independent work.
- After roughly 60–90 minutes without a working increment, reduce the slice or switch from code reading to an executable reproduction. This is an intervention trigger, not a forced deadline or a reason to weaken tests.
- CI/merge waiting is used for acceptance instrumentation, test cases, defect triage, or read-only review of other owned work. No repeated narration of unchanged checks.
- An admin/configuration dependency does not block writing or testing the collector, capability contracts, reasoning policy, answer accountability, or disposable-database recovery.
- If all useful work is exhausted and a credential or approval is genuinely unavailable, report the exact owner/action, work already ready, and the command/check that will establish resolution. Do not promise autonomous access that does not exist.
- No repeated broad replanning. New findings enter the existing defect queue with the scenario they block. A true scope expansion goes to the Native; ordinary repairs within this plan do not.
- Maintain required protected CI. Run focused tests during development and the broad suite on cohesive integrated candidates; avoid repeated broad runs on unchanged source.
- Prefer 2–3 cohesive product PRs plus the necessary shared release repair. Do not make the count a rule that forces unsafe batching or delays a ready fix.

### 4.4 Progress reporting

At each meaningful milestone report: deployed SHA; required scenarios passed/total by channel; supported capability readiness by family; open material evidence defects; next executable action; and any external dependency owner. Do not turn 12/182 contracts, 7/13 old gates, test counts, or elapsed time into a completion percentage.
